## 1. 요구사항 분석
### 1.1 문제 정의
메신저의 **대화 단위(채널)** 가 필요하다. 1:1·그룹뿐 아니라 **부서·프로젝트·공지** 등
조직 구조와 연동된 채널 유형을 제공하고, 멤버·권한·생성·아카이브 라이프사이클을 통제해야 한다.
### 1.2 목표
- 채널 유형 5종: **DM(1:1)·GROUP·DEPARTMENT(F1-06)·PROJECT(F11)·ANNOUNCEMENT(공지)**
- 멤버십(owner/admin/member/guest) · 권한(F0-07 결합) · 공개/비공개 범위
- 생성·초대·탈퇴·아카이브·삭제 라이프사이클 · 테넌트 격리(F0-01)

## 3. 기능 설계
### 3.1 데이터 모델
- `channels(id, tenant_id, type=DM/GROUP/DEPARTMENT/PROJECT/ANNOUNCEMENT, name, description, icon, visibility=public/private, ref_type, ref_id, archived_at, created_by, created_at)`
  - `ref_type/ref_id`: DEPARTMENT→부서ID(F1-06), PROJECT→프로젝트ID(F11)
- `channel_members(channel_id, tenant_id, user_id, role=owner/admin/member/guest, muted, favorite, joined_at, last_read_at)`
  - DM은 유니크 키(정렬된 두 user_id 쌍)로 멱등 보장
- 모든 엔티티 `tenant_id` PostgreSQL **RLS**(F0-01) 적용
### 3.2 권한·동기화
- 권한: 채널 역할 × F0-07 RBAC 결합 → 작업별 유효권한(공지 write=admin 한정 등)
- 부서채널: F1-06 부서 멤버 변경 이벤트 구독 → 멤버 자동 가감(수동 초대 비허용)
- 프로젝트채널: F11 프로젝트 멤버 변경 시 동기화 · 프로젝트 아카이브 시 채널도 아카이브 제안
- 생성/멤버변경/아카이브 **감사 로그**(F0-08) 기록
### 3.3 API (대표)
- `POST /api/v1/channels` 생성 · `POST /api/v1/channels/dm` DM(멱등) · `GET /api/v1/channels` 내 채널
- `POST /api/v1/channels/{id}/members` 초대 · `PATCH …/members/{uid}` 역할 · `DELETE …/members/{uid}` 제거
- `POST /api/v1/channels/{id}/archive` · `POST …/restore`
