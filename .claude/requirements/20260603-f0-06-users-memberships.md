## 1. 요구사항 분석
### 1.1 문제 정의
테넌트 안에서 **사용자를 초대·가입·관리(활성/비활성/탈퇴)**하고, **테넌트-사용자 멤버십**을
관리해야 한다. (조직도·발령은 F1, 여기선 계정·멤버십 토대)

> **개정(2026-06-03)**: 인증·자격(비밀번호)은 **Keycloak**(F0-03)이 소유. 본 spec 의 사용자는
> **앱 측 프로필/멤버십 레코드**(Keycloak `sub` 매핑)이며, 초대→가입은 **Keycloak Admin API**로
> Keycloak 사용자 생성 + 앱 멤버십 생성으로 처리한다. (비밀번호/세션은 앱에 저장 안 함)

### 1.2 목표
- 관리자 **초대**(이메일) → 수락 → 멤버십 생성 + 역할 부여
- 사용자 프로필·상태(active/invited/suspended/left) 관리
- **시트 한도(F0-09)** 연동(초대 시 한도 체크)
- 멤버십은 **테넌트 범위**(한 사람이 여러 테넌트 소속 가능 — 멤버십 다중)

### 1.3 제약
- email 은 테넌트 내 unique(F0-03) · 모든 조작 권한 필요(F0-07) · 격리(F0-01)

## 2. 기능 정의
| ID | 기능 | 우선순위 |
|----|------|---------|
| F-001 | 사용자 프로필 CRUD + 상태 | Must |
| F-002 | 초대(토큰·만료) → 수락 → 멤버십 | Must |
| F-003 | 멤버십(테넌트-사용자, 역할 연결) | Must |
| F-004 | 비활성/정지/탈퇴 처리(자격·세션 무효화) | Must |
| F-005 | 시트 한도 체크(F0-09) | Should |

### 2.2 상세
- **F-002**: 초대 토큰(서명·만료) · 기존 사용자면 멤버십만 추가, 신규면 가입+멤버십
- **F-004**: suspend 시 토큰/세션 폐기(F0-03 refresh 무효화 연계)

## 3. 기능 설계
### 3.1 스택
Spring Boot · JPA · 메일 · PostgreSQL
### 3.2 데이터 모델
`users`(F0-03 공유) + `tenant_memberships(id, tenant_id, user_id, status, joined_at)` · `invitations(id, tenant_id, email, role_id, token_hash, expires_at, accepted_at)`
### 3.3 흐름
```
관리자 POST /members/invite → invitation + 메일
초대수락 POST /members/accept{token} → (신규 가입) + membership + user_roles
관리자 PATCH /members/{id} status=suspended → 세션/토큰 폐기
```
