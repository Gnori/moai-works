## 1. 요구사항 분석
### 1.1 문제 정의
새 결재유형(휴가·지출·품의…)을 추가할 때마다 화면·DB를 코딩하면 확장이 느리다.
**관리자가 폼 디자이너로 양식 1건을 정의**하면 곧 새 결재유형이 되도록 한다.
필드·레이아웃·유효성을 **데이터로 정의**하고, 제출 데이터는 jsonb 스키마로 저장한다.
### 1.2 목표
- 동적 폼 디자이너(필드·레이아웃·유효성 규칙) · 양식 **정의/버전/게시**
- 새 결재유형 = 양식 정의 1건 · 제출 데이터 jsonb 스키마 · 격리

## 3. 기능 설계
### 3.1 기술 스택
Spring Boot · PostgreSQL(jsonb) · Flyway · JSON Schema 검증 · JUnit5
### 3.2 데이터 모델
- `form_def(id, tenant_id, code, title, category, status, current_version, created_by)`
- `form_def_version(id, form_def_id, tenant_id, version, schema jsonb, published_at)`
  - `schema` = `{ fields:[{key,type,label,required,rules,options}], layout:[...] }`
- `form_submission(id, tenant_id, form_def_id, version, data jsonb, ...)` — F10-03 결재문서가 참조
- 인덱스: `(tenant_id, code)` · `(tenant_id, status)` · jsonb GIN(`data`)
- **모든 엔티티 tenant_id** — 교차 테넌트 정의/제출 접근 차단(F0-01)
### 3.3 흐름 / API
```
관리자 → 폼 디자이너에서 양식 정의/수정(draft) → 게시(version+1, published)
사용자 → 카탈로그에서 게시 양식 선택 → 제출 → 서버가 schema 기준 검증 → jsonb 저장
```
- `POST/PUT /forms` · `POST /forms/{id}/versions` · `POST /forms/{id}/publish` — `@RequiresPermission("approval:form-manage")`
- `GET /forms` (게시본 카탈로그) · `GET /forms/{id}` — `@RequiresPermission("approval:read")`
- `POST /forms/{id}/validate` (제출 전 검증) — 정의 schema 기준 서버측 검증
- user/dept 필드 옵션·표시는 **F1-06** 조회 결과 사용
- 정의/게시/보관 변경은 **F0-08 감사** 기록
