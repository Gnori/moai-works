# 트래커 · 워크플로 · 필드 요구사항 (FR-WFL)

트래커 · 상태 · 열거형(우선순위 · 작업 분류 · 문서 분류) · 워크플로(프로젝트 역할 × 트래커 × 상태 → 다음 상태, 작성자 · 담당자 전이, 복사) · 필드 권한(읽기전용 · 필수) · 사용자 정의 필드 · 카테고리 · 일감 추적 설정과, 워크스페이스를 처음 만들 때 넣는 시드의 요구사항이다. Redmine 의 "관리" 메뉴와 같은 일이고, 범위는 **워크스페이스**다(카테고리만 프로젝트). 설계는 [일감 추적 설계 §8 ~ §11](../design/05-issue-tracking.md#is-workflow)에 있다.

## 1. 트래커 · 상태 · 열거형

<a id="fr-wfl-001"></a>
### FR-WFL-001 트래커

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.1](../design/05-issue-tracking.md#is-config) |

**설명** — 트래커는 일감의 종류(버그 · 기능 · 지원)다. 트래커마다 기본 상태 · 쓰는 표준 필드 · 워크플로가 다르다(Redmine 과 같다).

**세부 요구사항**
1. 트래커는 이름(워크스페이스 안에서 겹치지 않음, 30자) · 설명 · 기본 상태 · 쓰는 표준 필드 · 로드맵에 보이기 · 순서를 가져야 한다.
2. 쓰는 표준 필드는 담당 · 카테고리 · 대상 버전 · 상위 · 시작 · 기한 · 예상 시간 · 진척률 · 설명 · 우선순위를 켜고 끌 수 있어야 한다. 끈 필드는 그 트래커의 일감에서 숨는다([FR-ISS-003](03-issue.md#fr-iss-003)).
3. 만들 때 다른 트래커의 워크플로를 복사해 오고, 쓸 프로젝트를 고를 수 있어야 한다.
4. 일감이 있는 트래커는 지울 수 없어야 한다. 지우면 프로젝트 연결 · 워크플로 줄을 함께 지운다.
5. 바꾸기는 `config.manage` 이고 감사 · `config.changed` 를 남겨야 한다.

**수용 기준**
- [ ] 멤버가 트래커를 만들면 403 이다
- [ ] 일감이 있는 트래커를 지우면 409 다
- [ ] 표준 필드를 끄면 새 일감 화면과 API 응답에서 그 필드가 사라진다
- [ ] 감사에 전 · 후 값이 남는다

<a id="fr-wfl-002"></a>
### FR-WFL-002 상태

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.2](../design/05-issue-tracking.md#is-config) |

**설명** — 상태는 일감이 어디까지 왔는지(신규 · 진행 · 해결 · 닫힘 …)다. 상태마다 "닫힘" 여부와 기본 진척률이 있다(Redmine 과 같다).

**세부 요구사항**
1. 상태는 이름(겹치지 않음, 30자) · 설명 · 닫힘 여부 · 기본 진척률(0 ~ 100 또는 없음) · 순서를 가져야 한다.
2. 일감이 닫힌 상태로 바뀌면 닫힌 때를 적어야 하고, 다시 열어도 지우지 않아야 한다.
3. 상태의 닫힘 여부를 바꿔도 이미 있는 일감의 닫힌 때는 그대로여야 한다.
4. 일감이 쓰는 상태와 어느 트래커의 기본 상태는 지울 수 없어야 한다.
5. "열림 · 닫힘" 필터와 보드의 닫힌 열 접기는 이 닫힘 여부를 따라야 한다.

**수용 기준**
- [ ] 닫힌 상태로 바꾸면 닫힌 때가 적히고, 다시 열어도 남는다
- [ ] 쓰는 상태 · 트래커 기본 상태를 지우면 409 다
- [ ] 상태의 닫힘 여부를 바꾸면 "열림" 필터 결과가 바로 바뀐다
- [ ] 멤버가 상태를 고치면 403 이다

<a id="fr-wfl-003"></a>
### FR-WFL-003 열거형 (우선순위 · 작업 분류 · 문서 분류)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.3](../design/05-issue-tracking.md#is-config) |

**설명** — 고르기 목록 세 가지를 워크스페이스가 정한다: 일감 우선순위, 시간 기록의 작업 분류, 문서의 문서 분류(Redmine 의 열거형). 작업 분류는 [시간 요구사항](07-time.md), 문서 분류는 [내용 요구사항](08-content.md)이 쓴다.

**세부 요구사항**
1. 열거형은 종류(`PRIORITY` · `TIME_ACTIVITY` · `DOCUMENT_CATEGORY`) · 이름(종류 안에서 겹치지 않음) · 순서 · 기본값(종류마다 하나) · 켜짐을 가져야 한다.
2. 우선순위는 순서가 높을수록 높아야 한다(정렬 · 롤업이 이것을 쓴다).
3. 끈 값은 새로 고를 수 없고, 이미 쓴 값은 그대로 보여야 한다.
4. 쓰는 값을 지우려면 옮길 값을 골라야 하고, 옮기기와 지우기를 한 번에 해야 한다.
5. 바꾸기는 `config.manage` 이고 감사에 남아야 한다.

**수용 기준**
- [ ] 한 종류에 기본값이 둘이 될 수 없다(새 기본값을 정하면 옛 것이 풀린다)
- [ ] 끈 우선순위로 새 일감을 만들면 422 이고, 이미 그 값인 일감은 그대로 보인다
- [ ] 쓰는 값을 지우면 옮길 값을 요구하고, 옮긴 뒤 지워진다
- [ ] 감사에 전 · 후가 남는다

## 2. 워크플로

<a id="fr-wfl-004"></a>
### FR-WFL-004 워크플로 상태 전이 표

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §8](../design/05-issue-tracking.md#is-workflow) |

**설명** — 프로젝트 역할 × 트래커마다 "지금 상태 → 바꿀 수 있는 다음 상태" 표를 정한다. Redmine 의 워크플로 화면(가로 · 세로 상태 체크 표)과 같다.

**세부 요구사항**
1. 화면은 트래커와 역할을 고르면 지금 상태 × 다음 상태 체크 표를 보여야 한다. 맨 위 줄은 "새 일감"(만들 때 고를 수 있는 첫 상태)이어야 한다.
2. "이 트래커가 쓰는 상태만 보기"를 고를 수 있어야 한다.
3. 저장은 고른 트래커 · 역할의 표를 한 번에 바꿔야 한다.
4. 바꾸기는 `config.manage` 이고, 감사에 더한 칸 · 뺀 칸을 남겨야 한다.
5. 저장하면 설정 판이 오르고 다음 요청부터 새 표로 판정해야 한다.

**수용 기준**
- [ ] 개발자 표에서 진행 → 닫힘을 빼면 개발자의 그 전이가 403 이다
- [ ] "새 일감" 줄에 없는 상태로 만들면 403 이다
- [ ] 저장하면 다른 api 인스턴스에서도 30초 안에 새 표로 판정한다
- [ ] 감사에 더한 칸 · 뺀 칸이 남는다

<a id="fr-wfl-005"></a>
### FR-WFL-005 워크플로 판정

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §8.2](../design/05-issue-tracking.md#is-workflow) · [§8.3 닫기 조건](../design/05-issue-tracking.md#is-closable) |

**설명** — 상태를 바꿀 때 그 사람의 프로젝트 역할들 × 트래커 × 지금 상태로 허용 다음 상태를 정한다. 워크플로를 정하는 사람(`config.manage`)은 우회한다. 열린 하위 · 막는 일감 · 닫힌 상위는 우회하는 사람도 막는다(Redmine 과 같다).

**세부 요구사항**
1. 워크플로 역할은 실효 프로젝트 역할 · 기본 역할(워크스페이스 공개 프로젝트의 비회원) · 워크스페이스 사용자 정의 역할의 대응(`issue.edit` → 개발자 표, `issue.create` → 보고자 표)이어야 한다.
2. 여러 역할의 전이는 합쳐야 한다.
3. 워크스페이스 층 `config.manage` 를 가진 사람은 그 트래커가 쓰는 모든 상태로 갈 수 있어야 한다.
4. 열린 하위가 있거나 막는 열린 일감이 있으면 닫힌 상태가, 상위가 닫혀 있으면 열린 상태가 허용 목록에서 빠져야 한다(우회하는 사람에게도). 이유를 함께 줘야 한다.
5. 트래커를 바꾸면 새 트래커 기준으로 판정하고, 지금 상태가 새 트래커에서 쓰이지 않으면 기본 상태로 가야 한다.
6. 허용 상태는 일감 응답 · MCP `list_issue_metadata` · 보드 카드에 같은 값으로 줘야 한다.
7. 허용되지 않은 전이는 403 `TRANSITION_NOT_ALLOWED` 와 허용 상태 목록을 돌려줘야 한다.

**수용 기준**
- [ ] 시드 상태에서 보고자는 자기 일감을 닫고, 남의 일감을 닫으면 403 이다
- [ ] 소유자는 모든 전이를 하지만, 열린 하위가 있는 일감을 닫으면 409 다
- [ ] 막힌 일감의 허용 목록에 닫힌 상태가 없고 이유 `BLOCKED` 가 온다
- [ ] 같은 일감의 허용 상태가 REST · MCP `list_issue_metadata` · 보드에서 같다
- [ ] 사용자 정의 역할(`issue.edit`)만 가진 사람은 개발자 표로 판정된다

<a id="fr-wfl-006"></a>
### FR-WFL-006 워크스페이스 시드

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.6](../design/05-issue-tracking.md#is-seed) |

**설명** — 워크스페이스를 처음 만들면 바로 일감을 쓸 수 있도록 Redmine 기본 데이터와 같은 트래커 · 상태 · 우선순위 · 작업 분류 · 기본 워크플로를 넣는다.

**세부 요구사항**
1. 상태: 신규 · 진행 · 해결 · 피드백 · 닫힘(닫힘) · 거절(닫힘)과 기본 진척률(0 · 50 · 90 · 50 · 100 · 100)을 넣어야 한다.
2. 트래커: 버그 · 기능 · 지원(기본 상태 신규, 표준 필드 모두 켬, 지원은 로드맵에 안 보임)을 넣어야 한다.
3. 우선순위: 낮음 · 보통(기본) · 높음 · 긴급 · 즉시, 작업 분류 · 문서 분류의 시드, 일감 추적 설정 기본값을 넣어야 한다.
4. 기본 워크플로: 관리자 = 모든 전이, 개발자 = {신규 · 진행 · 해결 · 피드백} → {진행 · 해결 · 피드백 · 닫힘}, 보고자 = {신규 · 진행 · 해결 · 피드백} → 닫힘 · 해결 → 피드백(작성자일 때만), 모든 역할 = 새 일감 → 신규.
5. 시드는 워크스페이스 만들기 단계 안에서 멱등이어야 하고(개인 워크스페이스 포함), 이미 있는 워크스페이스에는 한 번만 채워야 한다.

**수용 기준**
- [ ] 새 워크스페이스에 트래커 3 · 상태 6 · 우선순위 5(보통이 기본)가 있다
- [ ] 시드를 두 번 돌려도 겹치지 않는다
- [ ] 시드 표대로 개발자의 진행 → 해결은 되고, 신규 → 거절은 403 이다
- [ ] 보고자는 자기 일감의 해결 → 피드백을 할 수 있다

<a id="fr-wfl-007"></a>
### FR-WFL-007 작성자 · 담당자 추가 전이

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §8.2](../design/05-issue-tracking.md#is-workflow) |

**설명** — 일부 전이는 그 일감의 작성자나 담당자일 때만 연다(Redmine 의 "추가 전이: 작성자일 때 · 담당자일 때"). 예: 보고자는 자기가 올린 일감만 닫는다, 담당자만 "해결"로 바꾼다.

**세부 요구사항**
1. 전이 줄마다 범위(늘 · 작성자일 때 · 담당자일 때)를 가져야 하고, 워크플로 화면에 탭으로 나눠 보여야 한다.
2. 담당자 여부는 바꾸기 전 담당자로 판정해야 한다.
3. 범위가 다른 줄도 합쳐서 허용 상태를 내야 한다.
4. Agent 계정도 작성자 · 담당자로 판정해야 한다.

**수용 기준**
- [ ] 담당자 전용 전이를 담당자는 하고, 다른 개발자는 403 이다
- [ ] 담당을 바꾸면서 그 전이를 하면 옛 담당자 기준으로 판정한다
- [ ] Agent 계정이 담당자면 담당자 전용 전이를 MCP 로 할 수 있다

<a id="fr-wfl-008"></a>
### FR-WFL-008 워크플로 복사

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §8](../design/05-issue-tracking.md#is-workflow) · [§10.1 트래커](../design/05-issue-tracking.md#is-config) |

**설명** — 한 트래커 · 역할의 워크플로를 다른 트래커 · 역할들로 복사한다(Redmine 의 워크플로 복사).

**세부 요구사항**
1. 원본(트래커, 역할)과 대상(트래커 여럿 × 역할 여럿)을 골라야 한다.
2. 전이와 필드 권한을 함께 복사할지 골라야 한다.
3. 대상에 있던 줄은 덮어쓰고, 덮어쓰기 전에 확인을 받아야 한다.
4. 트래커를 만들 때도 같은 복사를 쓸 수 있어야 한다.
5. 감사 한 줄에 원본과 대상을 남겨야 한다.

**수용 기준**
- [ ] 버그/개발자 → 기능/보고자로 복사하면 두 표가 같다
- [ ] 대상에 있던 줄은 확인 뒤 덮어쓴다
- [ ] 감사에 원본 · 대상이 남는다

## 3. 필드 권한 · 진척률 · 설정 · 카테고리

<a id="fr-wfl-009"></a>
### FR-WFL-009 필드 권한 (읽기전용 · 필수)

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §9](../design/05-issue-tracking.md#is-field-rule) |

**설명** — 역할 × 트래커 × 상태마다 필드를 읽기전용이나 필수로 정한다(Redmine 의 필드 권한). 예: "해결"에서는 담당이 필수, "닫힘"에서는 모든 필드가 읽기전용.

**세부 요구사항**
1. 대상 필드는 프로젝트 · 트래커 · 제목 · 설명 · 우선순위 · 담당 · 카테고리 · 대상 버전 · 상위 · 시작 · 기한 · 예상 시간 · 진척률 · 비공개와 사용자 정의 필드여야 한다.
2. 여러 역할의 규칙은 Redmine 처럼 합쳐야 한다: 모든 역할이 규칙을 가질 때만 서고, 섞이면 필수다.
3. 규칙은 저장 뒤 상태를 기준으로 봐야 한다.
4. 워크플로를 우회하는 사람에게는 읽기전용이 없고 필수는 그대로여야 한다.
5. 하위에서 계산하는 상위 필드와 "상태로 정함"의 진척률은 규칙과 상관없이 읽기전용이어야 한다. 트래커에서 끈 필드는 필수로 만들 수 없어야 한다.
6. 읽기전용 필드의 값을 바꾸면 403 `FIELD_READONLY`(같은 값은 통과), 필수 필드가 비면 422 `FIELD_REQUIRED` 여야 한다.
7. 일감 응답 · MCP 는 바뀔 수 있는 상태마다 필드 규칙을 줘야 한다.

**수용 기준**
- [ ] "해결"에서 담당이 필수면 담당 없이 해결로 바꾸는 것이 422 다
- [ ] "진행"에서 기한이 읽기전용이면 기한을 바꾸는 것은 403, 같은 값을 보내는 것은 된다
- [ ] 두 역할의 규칙이 읽기전용 · 필수면 필수, 한 역할만 규칙이 있으면 규칙이 없다
- [ ] 같은 경우를 MCP `update_issue` 로 해도 결과가 같다

<a id="fr-wfl-010"></a>
### FR-WFL-010 진척률 계산 방식

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.5](../design/05-issue-tracking.md#is-settings) |

**설명** — 진척률을 사람이 적을지, 상태의 기본 진척률로 정할지 고른다(Redmine 의 "일감 진척률 계산").

**세부 요구사항**
1. 방식은 `FIELD`(진척률 필드, 기본) · `STATUS`(상태의 기본 진척률)여야 한다.
2. `STATUS` 면 진척률은 상태가 바뀔 때 그 상태의 기본 진척률로 정하고, 필드는 읽기전용이어야 한다.
3. `STATUS` 로 바꿀 때 "모든 일감의 진척률을 상태로 맞추기" 작업을 고를 수 있어야 한다.
4. 바꾸기는 `config.manage` 이고 감사에 남아야 한다.

**수용 기준**
- [ ] `STATUS` 에서 진척률을 고치면 403 이다
- [ ] `STATUS` 에서 상태를 진행으로 바꾸면 진척률이 50 이 된다(시드)
- [ ] 맞추기 작업 뒤 모든 일감의 진척률이 상태 값과 같다

<a id="fr-wfl-011"></a>
### FR-WFL-011 일감 추적 설정

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.5](../design/05-issue-tracking.md#is-settings) · [§6.2 롤업](../design/05-issue-tracking.md#is-rollup) |

**설명** — 하위 일감 롤업 · 프로젝트를 넘는 관계와 하위 일감 · 중복 자동 닫기 · 쉬는 요일 같은 워크스페이스 단위 규칙을 정한다(Redmine 의 "일감 추적" 설정).

**세부 요구사항**
1. 상위 일감의 시작 · 기한 · 우선순위 · 진척률 · 예상 시간마다 "하위에서 계산" · "따로"를 골라야 한다([FR-ISS-016](03-issue.md#fr-iss-016)).
2. 프로젝트를 넘는 관계 허용(기본 켬) · 하위 일감의 프로젝트 범위(기본 같은 맨 위 프로젝트 아래) · 중복 자동 닫기(기본 켬) · 하위 프로젝트 일감을 목록에 포함(기본 켬)을 정해야 한다.
3. 쉬는 요일(기본 토 · 일)과 주 시작(기본 월)을 정해야 한다.
4. 롤업 방식을 바꾸면 모든 상위를 다시 계산하는 작업을 돌려야 한다.
5. 바꾸기는 `config.manage` 이고 감사에 남아야 한다.

**수용 기준**
- [ ] 상위 날짜를 "따로"로 바꾸면 상위의 시작 · 기한을 직접 고칠 수 있다
- [ ] 프로젝트를 넘는 관계를 끄면 다른 프로젝트 일감과의 관계가 422 다
- [ ] 중복 자동 닫기를 끄면 원본을 닫아도 중복이 열려 있다
- [ ] 쉬는 요일을 바꾸면 일정 이동 계산이 새 요일을 쓴다

<a id="fr-wfl-012"></a>
### FR-WFL-012 카테고리

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.4](../design/05-issue-tracking.md#is-category) |

**설명** — 프로젝트 안에서 일감을 나누는 카테고리를 둔다. 카테고리마다 기본 담당을 두면 새 일감이 자동으로 그 사람(또는 Agent)에게 간다(Redmine 과 같다).

**세부 요구사항**
1. 카테고리는 프로젝트마다 있고 이름은 그 안에서 겹치지 않아야 한다(60자).
2. 기본 담당은 그 프로젝트의 담당 가능 주체(사람 · Agent 계정)여야 하고, 담당이 빈 새 일감에 넣어야 한다(만들 때만).
3. 쓰는 카테고리를 지우려면 다른 카테고리로 옮기거나 비우기를 골라야 하고, 일감마다 저널을 남겨야 한다.
4. 바꾸기는 `project.manage` 여야 하고, MCP 로는 바꾸지 못하며 `list_issue_metadata` 로는 보여야 한다.
5. 일감을 다른 프로젝트로 옮기면 같은 이름의 카테고리로 맞춰야 한다.

**수용 기준**
- [ ] 기본 담당이 Agent 인 카테고리로 일감을 만들면 담당이 그 Agent 다
- [ ] 쓰는 카테고리를 지우면 옮길 곳을 묻고, 옮긴 일감마다 저널이 남는다
- [ ] 개발자가 카테고리를 만들면 403 이다

## 4. 사용자 정의 필드

<a id="fr-wfl-013"></a>
### FR-WFL-013 사용자 정의 필드 정의

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §11.1](../design/05-issue-tracking.md#is-cf) |

**설명** — 워크스페이스는 일감 · 프로젝트 · 버전 · 시간 기록 · 사용자에 필드를 더한다(Redmine 의 사용자 정의 필드). 값은 엔티티의 JSONB 열에 둔다.

**세부 요구사항**
1. 정의는 대상 · 이름((워크스페이스, 대상) 안에서 겹치지 않음) · 설명 · 형식 · 필수 · 기본값 · 검증 · 여러 값 · 보이는 범위 · 찾기 · 필터 · 합계 · 연결 · 순서를 가져야 한다.
2. 형식은 만든 뒤 바꿀 수 없어야 한다.
3. 바꾸기는 `config.manage` 이고 감사에 남아야 한다.
4. 필드를 지우면 정의 · 연결 · 필드 권한 줄을 지우고, 모든 엔티티에서 그 값을 빼는 작업을 돌려야 한다. 저널의 옛 줄은 "(지운 필드)"로 남긴다.

**수용 기준**
- [ ] 형식을 바꾸려 하면 422 다
- [ ] 지운 필드의 값이 작업 뒤 모든 일감의 JSONB 에 없다
- [ ] 저널의 옛 줄은 "(지운 필드)"로 보인다
- [ ] 감사에 정의의 전 · 후가 남는다

<a id="fr-wfl-014"></a>
### FR-WFL-014 사용자 정의 필드 형식과 검증

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §11.2](../design/05-issue-tracking.md#is-cf-formats) |

**설명** — 형식은 문자 · 긴 글 · 정수 · 실수 · 날짜 · 예/아니요 · 목록 · 키-값 목록 · 사용자 · 버전 · 링크다. 모든 쓰기 길이 같은 검증을 거친다.

**세부 요구사항**
1. 형식마다 설계 §11.2 의 JSON 값과 검증(길이 · 정규식 · 범위 · 목록 안 · 그 프로젝트의 주체 · 공유된 버전 · `http`/`https` 링크)을 따라야 한다.
2. 여러 값은 목록 · 키-값 · 사용자 · 버전만 가질 수 있어야 한다.
3. 기본값은 새 엔티티에 채우고, 필수 필드가 비면 422 여야 한다.
4. REST · MCP · 일괄 · 복사 · 가져오기 · 메일 모든 쓰기 길이 같은 검증을 거쳐야 한다. 모르는 필드 · 연결되지 않은 필드의 값은 422 다.
5. 목록 값의 이름을 바꾸면 그 값을 쓰는 엔티티를 고치는 작업을 돌려야 한다. 키-값 목록은 이름만 바뀌고 값(id)은 그대로여야 한다.

**수용 기준**
- [ ] 형식마다 잘못된 값이 422 와 필드 id 를 돌려준다
- [ ] `javascript:` 링크 값은 422 다
- [ ] 목록 값 이름을 바꾸면 작업 뒤 일감의 값도 바뀌어 있다
- [ ] MCP `create_issue` 에도 같은 검증이 걸린다

<a id="fr-wfl-015"></a>
### FR-WFL-015 사용자 정의 필드 연결

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §11.1](../design/05-issue-tracking.md#is-cf) |

**설명** — 일감 필드는 트래커와 프로젝트에 연결해야 나온다(Redmine 과 같다). 다른 대상의 필드는 그 대상 전체에 나온다.

**세부 요구사항**
1. 일감 필드가 보이는 조건은 "그 일감의 트래커에 연결 ∧ (모든 프로젝트 ∨ 그 프로젝트가 고름) ∧ 보는 사람에게 보임"이어야 한다(프로젝트 고르기는 [FR-PRJ-011](02-project.md#fr-prj-011)).
2. 트래커 · 프로젝트가 바뀌어 연결이 끊긴 값은 지우지 않고 숨겨야 한다.
3. 프로젝트 · 버전 · 시간 기록 · 사용자 대상 필드는 연결 없이 그 대상 전체에 나와야 한다.

**수용 기준**
- [ ] 버그 트래커에만 연결한 필드는 기능 일감에 없다
- [ ] 트래커를 기능으로 바꾸면 값이 숨고, 다시 버그로 바꾸면 보인다
- [ ] "모든 프로젝트"를 끄고 프로젝트를 고르지 않으면 어느 일감에도 나오지 않는다

<a id="fr-wfl-016"></a>
### FR-WFL-016 사용자 정의 필드의 보이는 역할

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §11.4](../design/05-issue-tracking.md#is-cf-visibility) |

**설명** — 내부 비용 · 고객 등급처럼 일부 역할만 볼 필드가 있다(Redmine 의 "보이는 역할"). 못 보는 사람에게는 그 필드가 없는 것과 같다.

**세부 요구사항**
1. 필드는 "모두" 또는 "고른 프로젝트 역할만" 보이게 정할 수 있어야 한다. 워크플로를 우회하는 사람은 늘 본다.
2. 못 보는 사람에게는 응답 · MCP · 필터 · 열 · 정렬 · 묶기 · 합계 · 저널 · 내보내기 · 알림 어디에도 나오지 않아야 한다.
3. 못 보는 사람에게는 읽기전용이어야 한다(값을 보내면 422).
4. 검색 색인에는 모두에게 보이는 필드만 넣어야 한다.

**수용 기준**
- [ ] 관리자 역할만 보는 필드가 보고자의 응답 · 필터 · 저널 · CSV 에 없다
- [ ] 보고자가 그 필드 값을 보내면 422 다
- [ ] 그 필드 값으로 검색해도 보고자에게 결과가 없다

<a id="fr-wfl-017"></a>
### FR-WFL-017 사용자 정의 필드 찾기 · 필터

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §11.5](../design/05-issue-tracking.md#is-cf-query) · [§12.2 필터](../design/05-issue-tracking.md#is-filters) |

**설명** — 필드마다 질의 필터로 쓸지, 전문 검색에 넣을지, 목록 합계에 쓸지 정한다(Redmine 의 "필터로 사용" · "검색 가능" · "합계").

**세부 요구사항**

4. MCP `search_issues` 도 같은 키 `cf:<id>` 를 써야 한다.

**수용 기준**
- [ ] 필터 표시를 끈 필드로 거르면 400 이다
- [ ] 찾기를 켠 글 필드의 값으로 전문 검색하면 그 일감이 나온다
- [ ] 합계를 켠 정수 필드의 합계가 목록 아래에 나온다

### FR-WFL-018 트래커별 설명 틀

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.7](../design/05-issue-tracking.md#is-config) |

**설명** — 트래커마다 설명의 틀(Markdown)을 둔다. 사람의 새 일감 화면에 채워지고, Agent 는 `list_issue_metadata` 로 받아 같은 꼴로 쓴다. Redmine 에는 없다.

**세부 요구사항**
1. 트래커마다 설명 틀을 둘 수 있어야 한다(`config.manage`).
2. 웹의 새 일감 화면은 설명 칸을 틀로 채워야 한다.
3. MCP `list_issue_metadata` 는 틀을 돌려줘야 한다.
4. 틀을 바꿔도 이미 있는 일감은 그대로여야 한다.

**수용 기준**
- [ ] 버그 트래커로 새 일감을 열면 설명 칸에 틀이 있다
- [ ] MCP `list_issue_metadata` 응답에 틀이 있다
- [ ] 틀을 바꿔도 이미 있는 일감의 설명은 그대로다

<a id="fr-wfl-019"></a>
### FR-WFL-019 설정 묶음 내보내기 · 가져오기

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §10.8](../design/05-issue-tracking.md#is-config) |

**설명** — 한 워크스페이스에서 다듬은 트래커 · 상태 · 열거형 · 워크플로 · 필드 권한 · 사용자 정의 필드 정의를 다른 워크스페이스로 옮긴다.

**세부 요구사항**
1. 설정을 JSON 하나로 내보내야 하고, 일감 데이터는 들어가지 않아야 한다.
2. 가져오기 전에 이름으로 맞춰 차이(더함 · 바뀜 · 그대로)를 보여야 한다.
3. 양쪽 워크스페이스에서 `config.manage` 가 있어야 해야 한다.
4. 가져오기는 감사에 남아야 한다.

**수용 기준**
- [ ] 내보낸 JSON 에 일감 데이터가 없다
- [ ] 가져오기 전에 차이 미리보기가 나온다
- [ ] 가져온 뒤 워크플로 표가 원본과 같다
