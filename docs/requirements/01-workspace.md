# 워크스페이스 · 계정 요구사항 (FR-WSP)

회원가입, 개인 · 팀 워크스페이스, 가입 신청과 초대, 멤버십, 역할과 권한 코드, 감사, 시스템 관리자 기능의 요구사항이다. 모든 기능이 지켜야 하는 **보안 원칙**(인증 · 권한 판정 · 감사 · 전송 보안 · 비밀값)도 이 쪽 뒤쪽 번호([§6](#6-보안-원칙))에 둔다. 설계는 [워크스페이스 · 계정 · 권한 설계](../design/03-workspace-identity.md)에 있다.

> **진행을 읽는 법 (이 영역만의 예외).** 이 영역의 코드는 moai-wiki 에서 만들어 확인한 토대를 그대로 가져왔다(2026-11-21). 그래서 다른 영역처럼 모두 `할 일` 로 시작하지 않는다.
> - 수용 기준은 **moai-works 의 api 자동 테스트(66건, 2026-11-21 모두 통과)가 직접 확인하는 것만** 체크했다. 체크한 기준 끝 괄호에 그 테스트 클래스를 적었다.
> - 화면 · 실제 흐름 · Keycloak 실물로만 확인할 수 있는 기준은 실제로 확인한 것만 체크했다. 2026-11-22 렐름을 만들고 서비스를 띄워 로그인 흐름([FR-WSP-005](#fr-wsp-005))을 확인했다. 그 밖의 화면 흐름(가입 · 초대 · 가입 신청 · 역할 · 시스템 관리)은 아직이다.
> - 감사가 남는지는 아직 어떤 자동 테스트도 보지 않는다. 그래서 쓰기 요구사항은 모두 `일부` 다.

| 공통 | 내용 |
|---|---|
| 정본 | 계정 · 멤버십 · 워크스페이스 역할은 Keycloak(조직), 가입 정책 · 워크스페이스 설정 · 가입 신청 · 초대 · 감사는 api DB ([설계 §6](../design/03-workspace-identity.md#ws-sor)) |
| 권한 검사 | 모든 API 에서 api 가 한다. 화면 · web-backend 는 숨기기만 한다 ([FR-WSP-023](#fr-wsp-023)) |
| 거부 응답 | 읽기 거부(멤버 아님 · 존재를 숨김)는 404, 쓰기 거부(멤버지만 권한 없음)는 403 |
| 감사 | 모든 쓰기는 감사에 남긴다 ([FR-WSP-024](#fr-wsp-024)) |
| 프로젝트 층 | 프로젝트 공개 범위 · 독자 판정 · 프로젝트 역할 · 기본 프로젝트("내 프로젝트")는 [프로젝트 요구사항](02-project.md), 일감은 [일감 요구사항](03-issue.md) |
| MCP | MCP 입구 · MCP 키는 [MCP 요구사항](04-mcp.md). 키는 사용자의 것이고, 역할에 `mcp.key.issue.personal`("MCP 키로 이 워크스페이스에서 일하기")이 있는 워크스페이스만 키에게 보인다(2026-11-23 [ADR-029](../design/00-key-decisions.md#adr-029)). MCP 도구도 이 쪽의 인증 · 권한 판정 · 감사 원칙을 그대로 따른다 |

## 1. 계정과 가입

<a id="fr-wsp-001"></a>
### FR-WSP-001 회원가입

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — api 가 Keycloak 에 사용자를 만들고 사본을 저장, 비밀번호 정책 검사, 같은 이메일 거절, 저장 실패 때 Keycloak 사용자 삭제(보상), IP별 속도 제한, 감사). 남은 것: 가입 흐름의 자동 시험(정상 · 중간 실패 주입 · 정책 위반 비밀번호 · 속도 제한) · moai-works 렐름에서 가입 화면 → 계정 생성 흐름 확인. |
| 관련 설계 | [워크스페이스 설계 §7](../design/03-workspace-identity.md#ws-signup) |

**설명** — 사용자는 자체 가입 화면에서 이메일 · 비밀번호 · 표시 이름으로 가입한다. 계정은 Keycloak 에 만들고, api 는 판정에 쓸 사본(`user_profile`)을 둔다.

**세부 요구사항**
1. 가입 요청은 web-backend 를 거쳐 api(`POST /signup`, 공개 경로)가 받고, api 가 Keycloak 관리 API 로 사용자를 만들어야 한다. 활성 여부는 가입 정책([FR-WSP-002](#fr-wsp-002))이 정한다.
2. 비밀번호 규칙은 Keycloak 렐름 비밀번호 정책으로 검사해야 한다.
3. 같은 이메일(대소문자 무시)로 두 번 가입할 수 없어야 한다.
4. Keycloak 사용자는 만들었는데 api 저장이 실패하면 Keycloak 사용자를 지워야 한다(보상).
5. 가입 요청에 IP별 속도 제한을 걸어야 한다.
6. 가입을 감사(`account.signup`)에 남겨야 한다.

**수용 기준**
- [ ] 가입 후 Keycloak 에 사용자가 있고 `user_profile` 이 같은 id 로 생긴다
- [ ] 같은 이메일로 다시 가입하면 거부된다
- [ ] 중간 실패를 주입해도 Keycloak 과 api DB 에 반쪽 계정이 남지 않는다
- [ ] 정책 위반 비밀번호는 거부되고 이유가 보인다
- [ ] 같은 IP 에서 한도를 넘게 가입하면 거부된다
- [ ] 가입이 감사에 남는다

<a id="fr-wsp-002"></a>
### FR-WSP-002 가입 정책 설정 (시스템 관리자)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — 가입 받기 · 허용 도메인 · 이메일 인증 · 관리자 승인 · 속도 제한 · 팀 워크스페이스 기본 허용 수 설정, 시스템 관리자만 바꾸고 감사에 남김). 남은 것: 정책 API 의 자동 시험(권한 · 도메인 밖 가입 거부 · 세 스위치 8가지 조합) · moai-works 렐름에서 시스템 관리자 화면 확인. |
| 관련 설계 | [워크스페이스 설계 §7.1](../design/03-workspace-identity.md#ws-signup) |

**설명** — 시스템 관리자는 가입 정책을 정한다. 도메인 제한 · 이메일 인증 · 관리자 승인은 서로 독립된 스위치다.

**세부 요구사항**
1. 설정: 가입 받기, 허용 이메일 도메인 목록(비면 누구나), 이메일 인증 필수, 관리자 승인 필수, IP별 가입 속도 제한, 팀 워크스페이스 만들기를 허용할 때 넣는 기본 수. 계정별 허용 수는 계정 관리에서 정한다([FR-WSP-008](#fr-wsp-008)).
2. 시스템 관리자(렐름 역할 `system-admin`)만 바꿀 수 있어야 한다. 워크스페이스 소유자 · 관리자는 바꿀 수 없다.
3. 가입 화면이 쓰는 공개 부분(`GET /signup/policy`)은 로그인 없이 볼 수 있어야 한다.
4. 바꾼 값과 바꾼 사람을 감사(`platform.signup_policy.update`)에 남겨야 한다.

**수용 기준**
- [ ] 허용 도메인 밖 이메일의 가입이 거부된다
- [ ] 시스템 관리자가 아닌 사람(워크스페이스 소유자 포함)이 가입 정책 API 를 부르면 403 이다
- [ ] 세 스위치의 모든 조합(8가지)에서 계정 상태 전이가 설계와 같다
- [ ] 바꾼 값과 바꾼 사람이 감사에 남는다

<a id="fr-wsp-003"></a>
### FR-WSP-003 이메일 인증

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — 6자리 코드 · 10분 · 5회 · HMAC 만 저장 · 확인하면 Keycloak 인증 표시 · 재발송 속도 제한). 남은 것: 인증 대기 7일 뒤 계정 삭제(예약 작업이 없다) · 메일 실제 발송(지금은 로그 모드, SMTP 미정) · 자동 시험(만료 · 초과 코드 · 원문 미저장) · moai-works 렐름에서 흐름 확인. |
| 관련 설계 | [워크스페이스 설계 §7.3](../design/03-workspace-identity.md#ws-signup) |

**설명** — 인증이 켜져 있으면 메일로 받은 코드를 확인해야 계정이 다음 단계(승인 대기 또는 활성)로 간다.

**세부 요구사항**
1. 코드는 6자리, 유효 10분, 5회 틀리면 무효다. DB 에는 HMAC 만 저장해야 한다.
2. 확인하면 Keycloak 사용자를 `emailVerified=true` 로 바꿔야 한다.
3. 재발송에는 속도 제한을 건다. 인증 대기 7일이 지나면 계정을 지운다.

**수용 기준**
- [ ] 운영 메일 모드에서 코드 원문이 DB · 로그에 없다
- [ ] 만료되거나 5회 넘게 틀린 코드는 거부된다
- [ ] 확인하면 Keycloak 사용자가 이메일 인증 상태가 된다
- [ ] 인증 대기 7일이 지난 계정이 지워진다

### FR-WSP-004 가입 승인 (선택)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — 승인 대기 목록 · 승인 · 거절 API 와 화면, 승인 전 로그인 불가, 승인하면 개인 워크스페이스 생성, 감사). 남은 것: 결과를 메일로 알리기 · 승인 대기 30일 뒤 계정 삭제 · 자동 시험 · moai-works 렐름에서 흐름 확인. |
| 관련 설계 | [워크스페이스 설계 §7.2](../design/03-workspace-identity.md#ws-signup) |

**설명** — 승인이 켜져 있으면 시스템 관리자가 승인해야 계정이 활성화된다.

**세부 요구사항**
1. 승인 대기 목록, 승인 · 거절(사유) 기능을 시스템 관리자 화면에 둔다.
2. 승인 전에는 로그인할 수 없어야 한다(Keycloak `enabled=false`).
3. 결과를 가입자에게 메일로 알린다. 승인 대기 30일이 지나면 계정을 지운다.
4. 승인 · 거절을 감사(`account.approve` · `account.reject`)에 남긴다.

**수용 기준**
- [ ] 승인 대기 계정의 로그인이 거부된다
- [ ] 승인하면 개인 워크스페이스가 생긴다
- [ ] 승인 · 거절이 감사에 남는다

<a id="fr-wsp-005"></a>
### FR-WSP-005 로그인 · 로그아웃 · 세션

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 완료 (2026-11-22) — moai-wiki 에서 가져온 코드를 moai-works 렐름에서 실제로 확인했다: 세션 쿠키 `__Host-MOAI_WORKS_SESSION` 은 HttpOnly · Secure, 다시 로그인하면 세션 id 가 바뀐다, 수용 기준 다섯 개(아래 괄호에 확인 방법). 만료 때 갱신 흐름은 실제로 기다려 보지 않았고, web-backend 자동 시험은 없다(moai-wiki 와 같다). |
| 관련 설계 | [워크스페이스 설계 §8.1](../design/03-workspace-identity.md#ws-login) |

**설명** — 자체 로그인 화면에서 로그인한다. 토큰은 브라우저에 두지 않는다.

**세부 요구사항**
1. web-backend 가 Keycloak 패스워드 그랜트(클라이언트 `moai-works-web-backend`)로 토큰을 받아 서버 세션에 두고, 브라우저에는 HttpOnly · Secure 세션 쿠키(`__Host-MOAI_WORKS_SESSION`)만 줘야 한다.
2. 로그인하면 세션 id 를 바꾸고, 쓰기 요청은 CSRF 토큰을 확인해야 한다.
3. 액세스 토큰이 만료되면 갱신 토큰으로 갱신하고, 실패하면 로그아웃한다.
4. 로그아웃하면 Keycloak 세션도 끝내야 한다.
5. Keycloak 무차별 대입 방지(실패 횟수 잠금)를 켠다. web-backend 도 로그인 시도를 제한한다.
6. 로그인 직후 api(`POST /me/login`)가 계정 사본을 맞추고 로그인을 감사(`account.login`)에 남긴다.

**수용 기준**
- [x] 브라우저 저장소 · 응답 본문에 토큰이 없다 (2026-11-22 ego-browser — localStorage · sessionStorage · `/api/auth/session` · `/api/v1/me` 응답에 토큰 형태가 없고, 스크립트가 읽는 쿠키는 `XSRF-TOKEN` 뿐)
- [x] 정해진 횟수만큼 틀리면 계정이 잠긴다 (2026-11-22 — Keycloak 에서 10번 틀리면 맞는 비밀번호도 거절, 잠금을 풀면 다시 로그인된다. web-backend 는 같은 아이디의 11번째 시도를 429 로 막는다)
- [x] 로그아웃하면 Keycloak 세션이 끝나 이전 갱신 토큰을 쓸 수 없다 (2026-11-22 — 화면에서 로그아웃하자 Keycloak 관리 API 의 그 사용자 세션이 끝났고 `/api/auth/session` 은 401. 세션이 끝난 갱신 토큰은 쓸 수 없다)
- [x] CSRF 토큰 없는 쓰기 요청은 거부된다 (2026-11-22 — CSRF 헤더 없는 `POST /api/auth/sign-out` → 403, 세션은 그대로)
- [x] 로그인이 감사에 남는다 (2026-11-22 — 화면 로그인 두 번 모두 `audit_log` 에 `account.login`)

<a id="fr-wsp-006"></a>
### FR-WSP-006 비밀번호 재설정 · 변경

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: (2026-11-24, 일감 #28) 로그인한 사람의 변경(개인 설정 › 비밀번호 · 계정 메뉴 "비밀번호 변경" — 현재 비밀번호를 Keycloak 으로 확인, 틀리면 로그아웃되지 않는 400 · 15분에 5번 넘으면 잠시 막힘, 정책 오류의 까닭, "다른 기기의 로그인 끊기"(기본 켬 — 이 브라우저만 남김), 시스템 관리자 계정도) · 로그인 화면의 비밀번호 찾기(이메일 → 메일 코드 + 새 비밀번호 두 번, 있는 · 없는 이메일 같은 응답 · IP · 이메일 속도 제한, 받을 수 없는 계정(대기 · 정지 · 시스템 관리자)에는 보내지 않음, 성공하면 로그인 모두 끊기 · 잠금 풀기) · 감사 둘 · "비밀번호가 바뀌었습니다" 메일 · api 자동 시험 22건 · 화면 시험. **설명** — 잊은 비밀번호는 메일 코드로 재설정하고, 로그인한 사용자는 현재 비밀번호를 확인한 뒤 바꾼다.

**세부 요구사항**

2. 코드 규칙은 [FR-WSP-003](#fr-wsp-003)과 같다(`email_verification.purpose = PASSWORD_RESET`). 확인 뒤 Keycloak 비밀번호를 설정한다.

## 2. 워크스페이스와 멤버십

<a id="fr-wsp-007"></a>
### FR-WSP-007 개인 워크스페이스 자동 생성

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴, 기본 위키 단계는 뺌 — 계정이 활성화되거나 처음 로그인하면 단계별로 만든다, 멱등, 끊기면 다음 요청이 이어서 끝냄) · 자동 테스트(첫 로그인 뒤 생성 · 남의 개인 워크스페이스 404 · 나가기와 가입 신청 거부 확인). 남은 것: 단계마다 실패를 주입하는 자동 시험 · 주인이 모든 권한 코드를 갖는지 시험 · 감사 시험. |
| 관련 설계 | [워크스페이스 설계 §8.2](../design/03-workspace-identity.md#ws-login) |

**설명** — 계정이 활성화되면 개인 워크스페이스를 만들고 가입자를 소유자로 넣는다. Keycloak 에서 직접 만든 계정(개발 계정 · 관리자)은 처음 로그인할 때 만든다.

**세부 요구사항**
1. 워크스페이스 행 → Keycloak 조직 → 기본 역할 그룹 4개(`owner` · `admin` · `curator` · `member`)와 권한 코드 매핑 → 조직 멤버 추가 → `owner` 그룹 가입 → 기본 프로젝트 "내 프로젝트"(key `my`) 순으로 만들어야 한다. 기본 프로젝트 단계는 [FR-PRJ-009](02-project.md#fr-prj-009)가 정한다(2026-11-22 — moai-wiki 의 "내 위키"와 같게). 지금 코드는 기본 역할 3개까지이고 기본 프로젝트 단계가 없다.
2. 각 단계는 멱등해야 하고, 중간에 실패해도 다음 요청이 이어서 끝낼 수 있어야 한다.
3. 계정당 개인 워크스페이스는 정확히 1개다. 늘 프라이빗이고, 소유자는 바뀌지 않으며, 나갈 수 없고 따로 지울 수 없다.
4. 만들기를 감사(`workspace.create`)에 남긴다.
5. 시스템 관리자 계정에는 만들지 않는다([FR-WSP-019](#fr-wsp-019)).

**수용 기준**
- [x] 첫 로그인(`POST /me/login`) 뒤 개인 워크스페이스가 있다 (TeamWorkspaceRuleTest)
- [x] 남의 개인 워크스페이스는 404 다 (WorkspaceAccessTest)
- [x] 개인 워크스페이스는 나갈 수 없고, 가입 신청하면 없는 워크스페이스(404)로 답한다 (MembershipRulesTest · JoinRequestTest)
- [ ] 활성화 직후 주인이 개인 워크스페이스의 모든 권한 코드를 가진다
- [ ] 단계마다 실패를 주입하고 다시 실행해도 중복 조직 · 그룹이 생기지 않는다
- [ ] 만들기가 감사에 남는다

<a id="fr-wsp-008"></a>
### FR-WSP-008 팀 워크스페이스 만들기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴) · 자동 테스트(허용받지 않은 계정 거부 · 허용 수 한도 · 한도 올리기 · 0 으로 내려도 기존 유지 · 만든 사람 = 소유자 확인). 남은 것: 주소 고유 시험 · 감사 시험 · moai-works 렐름에서 화면 확인(만들 수 없는 계정에 만들기 입구가 없고 이유가 보이는지). |
| 관련 설계 | [워크스페이스 설계 §9](../design/03-workspace-identity.md#ws-workspace) |

**설명** — 시스템 관리자가 허용한 계정은 개인 워크스페이스 말고 팀 워크스페이스를 만들 수 있다(moai-wiki 2026-11-21 사용자 결정을 그대로 따른다).

**세부 요구사항**
1. 가입한 계정은 팀 워크스페이스를 만들 수 없다(0개). 시스템 관리자가 계정마다 만들 수 있는 수를 정한다(0~100, 허용할 때 기본 2개).
2. 만든 사람이 소유자다. 그 계정에 허용된 수(지운 것 제외)를 넘을 수 없다. 수를 줄여도 있는 워크스페이스는 그대로다.
3. 주소는 서버가 정한다(`workspace-` + 고유 id 12자). 플랫폼 전체에서 고유하고 만든 뒤 바꾸지 않는다. 사람은 이름만 정한다.
4. 만들 수 없는 계정에게는 만들기 입구를 보이지 않고, 화면에 이유를 알린다.
5. 만들기를 감사(`workspace.create`)에 남긴다.
6. 시스템 관리자 계정은 허용 수를 받아도 만들 수 없다 — 403 `SYSTEM_ADMIN_NOT_ALLOWED`([FR-WSP-019](#fr-wsp-019)).

**수용 기준**
- [x] 허용받지 않은 계정의 생성은 거부된다(403) (TeamWorkspaceRuleTest)
- [x] 허용된 수를 넘는 생성은 거부된다 (TeamWorkspaceRuleTest)
- [x] 시스템 관리자가 수를 올리면 더 만들 수 있고, 0 으로 내려도 있는 워크스페이스는 그대로다 (TeamWorkspaceRuleTest)
- [x] 만든 사람은 `owner` 역할이고 Keycloak 조직의 `owner` 그룹에 들어 있다 (MembershipRulesTest)
- [ ] 두 워크스페이스가 같은 주소를 가질 수 없다
- [ ] 만들 수 없는 계정에게는 만들기 입구가 보이지 않고 이유가 보인다
- [ ] 만들기가 감사에 남는다

### FR-WSP-009 워크스페이스 설정

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴) · 자동 테스트(프라이빗은 찾기 · 신청에서 숨김 · 프라이빗의 가입 방식 정리 · 권한 없는 멤버 403 · 멤버 아님 404 · 소유자 역할은 기본 역할 불가 확인). 남은 것: 설정 변경 감사 시험 · moai-works 렐름에서 설정 화면 확인. |
| 관련 설계 | [워크스페이스 설계 §9](../design/03-workspace-identity.md#ws-workspace) |

**설명** — 관리자는 이름 · 설명, 공개 범위(퍼블릭 `PUBLIC` · 프라이빗 `PRIVATE`), 퍼블릭의 가입 방식(관리자 승인 후 가입 `APPROVAL` · 자동 가입 `AUTO`), 가입 허용 도메인, 새 멤버 기본 역할, 재신청 대기 일수를 정한다. 프로젝트는 [프로젝트 요구사항](02-project.md)에 있다. 일감 유형 · 상태는 첫 출시에 고정이라 워크스페이스 설정이 없다([일감 요구사항](03-issue.md)).

**세부 요구사항**
1. `workspace.settings.manage` 권한이 필요하다.
2. `PRIVATE` 워크스페이스는 다른 사람에게 보이지 않아야 한다. 찾기에 나오지 않고, 신청하면 없는 워크스페이스처럼 답한다. 초대로만 들어온다.
3. 가입 방식은 퍼블릭에만 있다. 자동 가입이면 신청하는 즉시 멤버가 된다.
4. 소유자 역할은 새 멤버 기본 역할이 될 수 없다.
5. 바꾼 값을 감사(`workspace.settings.update`)에 남긴다.

**수용 기준**
- [x] `PRIVATE` 로 바꾸면 찾기 결과에서 사라지고 신청이 없는 워크스페이스(404)로 거부된다 (JoinRequestTest)
- [x] 프라이빗에는 가입 방식이 없다 — 저장된 값은 `APPROVAL` 로 맞춰지고, 없앤 `INVITE_ONLY` 는 거부된다 (JoinRequestTest)
- [x] `workspace.settings.manage` 가 없는 멤버가 설정을 바꾸면 403, 멤버가 아니면 404 다 (WorkspaceAccessTest)
- [x] 소유자 역할을 새 멤버 기본 역할로 정하면 거부된다 (RoleRulesTest)
- [ ] 바꾼 값과 바꾼 사람이 감사에 남는다

### FR-WSP-011 가입 신청 승인 · 거절

**수용 기준**
- [x] 승인 직후 다음 요청부터 신청자가 워크스페이스에 접근한다(토큰 갱신 불필요) (JoinRequestTest)

### FR-WSP-019 시스템 관리자 기능

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — 가입 정책 · 가입 승인 · 계정 정지 · 복구 · 팀 워크스페이스 허용 수, 시스템 관리자만; 2026-11-22 시스템 관리자는 워크스페이스가 없고 만들거나 들어갈 수 없음 · 로그인하면 시스템 관리 화면; 2026-11-23 팀 워크스페이스 사용 중지 · 다시 사용 · 사용 중지 뒤에만 삭제 · 워크스페이스 관리 화면(일감 #8, WBS 1.8)) · 자동 테스트(플랫폼 역할 없으면 403 · 멤버 아닌 워크스페이스 404 · 계정 정지 즉시 반영과 복구 · 자기 정지 금지 · 허용 수 범위 확인 · 사용 중지한 워크스페이스의 REST 403 · MCP 숨김과 다시 사용 · 사용 중지 안 한 것 지우기 409 · 확인 문구 · 개인 워크스페이스 409 · 지우기가 지우는 것과 남기는 것 · `admin.workspace.*` 감사 — WorkspaceSuspendTest). 남은 것: 소유자 재지정 · 계정 삭제 · 플랫폼 감사 화면 · 직무 분리 경고 · 계정 조치(`account.*`) 감사 시험 · moai-works 렐름에서 화면 확인(워크스페이스 관리 · 사용 중지 안내 포함). |
| 관련 설계 | [워크스페이스 설계 §3.1](../design/03-workspace-identity.md#ws-permissions) |

**설명** — 시스템 관리자는 **시스템만 관리한다**: 가입 정책, 가입 승인, 계정 정지 · 복구 · 삭제, 팀 워크스페이스 허용 수, 팀 워크스페이스 사용 중지 · 다시 사용 · 삭제, 소유자 재지정, 플랫폼 감사. 워크스페이스 영역과 나뉜다 — 워크스페이스가 없고, 만들거나 들어가지 않으며, 내용도 보지 않는다(2026-11-22 사용자 결정: "moai-works 에도 시스템 어드민 계정도 있어야 해" · "시스템 어드민 계정은 워크스페이스 생성할 수 없어" · "시스템 어드민은 시스템만 관리할 수 있어야 해서 그 영역도 구분해야 해" · "팀 워크스페이스는 시스템 어드민이 사용 못 하게 막을 수도 있어" · "다만 삭제는 사용 중지 후에만 가능해").

**세부 요구사항**
1. 렐름 역할 `system-admin` 만 쓸 수 있다(`@PlatformApi`).
2. 시스템 관리자도 멤버가 아닌 워크스페이스의 내용(설정 · 멤버 · 감사 · 프로젝트 · 일감)은 볼 수 없다.
3. 계정을 정지하면 토큰이 살아 있어도 다음 요청부터 막고 Keycloak 사용자도 끈다. 자기 계정은 정지할 수 없다.
4. 보안 담당(`security-officer`)과 직무를 나눈다. 같은 사람이 둘을 함께 가지면 경고한다.
5. 모든 조치를 감사(`account.*` · `platform.*` · `admin.*`)에 남긴다.
6. 처음 시스템 관리자 계정(`sysadmin`)은 렐름 설치 스크립트가 만든다(비밀번호는 `infra/keycloak/.env`).
7. 시스템 관리자 계정에는 개인 워크스페이스가 생기지 않는다. 팀 워크스페이스를 만들 수 없고(허용 수를 받아도), 가입 신청 · 초대 수락도 할 수 없다 — 403 `SYSTEM_ADMIN_NOT_ALLOWED`.
8. 화면: 시스템 관리자는 로그인하면 시스템 관리 화면으로 가고, 워크스페이스 전환 · 메뉴가 보이지 않는다.
9. 팀 워크스페이스를 **사용 중지**(정지)하고 다시 사용하게 한다. 사용 중지한 워크스페이스는 멤버의 화면 · REST · MCP 접근이 모두 막히고(키 포함), 소유자 · 멤버에게 사용 중지 안내가 보인다. 이유를 받고 감사(`admin.workspace.suspend` · `admin.workspace.resume`)에 남긴다. 2026-11-23 만든 모양: Keycloak 조직을 먼저 끄고(`enabled=false`) 사본을 `SUSPENDED` 로 바꾼다. 멤버의 REST 는 403 `WORKSPACE_SUSPENDED`(멤버가 아니면 없는 것과 같은 404), MCP 키에게는 보이지 않는다(목록에서 빠지고 이름을 줘도 404 `WORKSPACE_NOT_FOUND`), 그 워크스페이스의 알림은 알림함에서 숨긴다. 이유는 시스템 관리 화면과 감사에만 보인다. 다시 사용하면 지운 것 없이 그대로 돌아온다.
10. 워크스페이스 **삭제는 사용 중지한 워크스페이스에만** 한다(위험 작업 확인 — [FR-WSP-028](#fr-wsp-028)). 감사 `admin.workspace.delete`. 지우는 것 · 남기는 것은 [FR-WSP-020](#fr-wsp-020) 세부 3.
10-1. **개인 워크스페이스는 사용 중지 · 삭제하지 않는다**(409 `PERSONAL_WORKSPACE`, 2026-11-23 moai-wiki 설계를 따름 — 개인 워크스페이스는 계정에 묶여 따로 지우지 않는다). 한 사람을 막으려면 계정을 정지한다. 목록에는 종류와 함께 보인다.
11. 시스템 관리자가 보는 워크스페이스 목록은 이름 · 주소 · 종류 · 소유자 · 멤버 수 · 상태 · 만든 날까지다(내용은 보지 않는다).
12. 판정은 접근 판정 한 곳에서 한다(moai-wiki 와 같은 모양, 2026-11-22): 사람 계정 입구(`@UserApi`)는 시스템 관리자를 **기본으로 막고**(403 `SYSTEM_ADMIN_NOT_ALLOWED`) 내 정보 · 로그인 기록 · 이름 바꾸기만 연다. 워크스페이스 · 프로젝트 입구는 시스템 관리자를 멤버로 보지 않는다(멤버가 아닌 사람과 같은 404 `WORKSPACE_NOT_FOUND`). 시스템 관리자 계정에 팀 워크스페이스 허용 수를 주면 409 `SYSTEM_ADMIN_ACCOUNT`. 시스템 관리자 계정은 MCP 키도 발급할 수 없다(403 `SYSTEM_ADMIN_NOT_ALLOWED`).
13. 워크스페이스를 쓰던 계정에 시스템 관리자 역할을 주면(역할은 Keycloak 에서 주므로 api 가 막지 못한다) 남아 있는 멤버십도 열지 않는다(404). 자료는 지우지 않고, 역할을 거두면 다음 요청부터 다시 열린다. 계정 관리 목록이 "워크스페이스 N곳에 남아 있음"으로 알린다. 시스템 관리는 전용 계정으로 한다.
14. 화면은 돌아갈 주소(returnTo)가 워크스페이스 쪽이면 무시하고 시스템 관리 화면으로 가며, 워크스페이스 쪽 주소를 열면 안내를 보인다. 메뉴 이름은 "시스템 관리"다.

**수용 기준**
- [x] 플랫폼 역할이 없으면 시스템 관리자 API(계정 목록 · 팀 워크스페이스 허용 수)가 403 이다 (WorkspaceAccessTest · TeamWorkspaceRuleTest)

| 관련 설계 | [Agent 스킬 설계](../design/08-skill.md) · [MCP 설계 §8.23](../design/06-mcp.md#mc-t-skills) |

**설명** — 바깥 AI Agent(Claude Code 등)가 지침으로 읽는 스킬(`SKILL.md`)을 moai-works 가 정본으로 가진다. 시스템 관리자가 등록 · 수정 · 삭제하고, 바꿀 때마다 리비전이 쌓인다(일감 리비전과 같은 모양). Agent 는 MCP 로 받는다. 저장소의 스킬 파일은 내보낸 사본이 된다(2026-11-24 사용자: "moai-works 스킬은 시스템 관리자가 등록, 수정 삭제 할 수 있게 하고 역시 리비전 관리 해줘" · "스킬은 mcp로 내려받을 수 있게 해줘").

**세부 요구사항**
1. 스킬은 시스템 전체의 것이다(워크스페이스에 묶이지 않는다). 이름(`name` — 영문 소문자 · 숫자 · 하이픈, 64자, 같은 이름 하나, 만든 뒤 바꾸지 않음) · 설명(1024자, 필수 — Agent 가 언제 쓸지 고르는 글) · 본문(Markdown, 10만 자, 필수). 설명 · 본문에 줄바꿈 · 탭 말고 제어 문자는 받지 않는다(moai-wiki 와 같은 규칙).
2. **쓰기는 시스템 관리자만**(`@PlatformApi(system-admin)`): 만들기 · 수정(읽은 리비전 `baseRevisionNo` — 낡았으면 409 `SKILL_CHANGED`, 내용이 그대로면 리비전 없이 200) · 삭제 · 되살리기 · 리비전으로 되돌리기 · SKILL.md 가져오기. **읽기는 로그인한 사람 누구나**(시스템 관리자 포함)와 MCP 키 누구나 — 목록 · 하나 · 리비전 · 차이 · SKILL.md 내려받기. 지운 스킬은 시스템 관리자에게만 보인다.
3. **리비전**: 만들기 · 수정 · 가져오기 · 되돌리기마다 그때의 전체(이름 · 설명 · 본문)와 리비전 번호 · 누가 · 길(WEB · MCP · API) · 밀리초까지의 때 · **바뀐 점 요약**을 남긴다. 요약은 Agent 에게 보이는 글로 수정 · 되돌리기 · 가져오기에는 5~500자로 꼭 받고(없으면 400 `CHANGE_NOTE_REQUIRED`), 만들기는 비우면 "처음 만듦"이다. 요약을 받기 전의 리비전은 그대로 둔다(2026-11-24 일감 #183 — 사용자: "버전 정보만 보고 업데이트하는 건 안 맞잖아? 간략한 설명도?"). 리비전은 추가만 한다(DB 트리거). 옛 리비전으로 되돌리면 그 내용으로 새 리비전을 만든다.
4. **삭제는 지움 표시**다 — 목록 · MCP 에서 숨고, 리비전은 남고, 되살릴 수 있다. 지운 스킬의 이름으로 새로 만들지 않는다(되살린다).
5. **SKILL.md**: 내려받기는 frontmatter(name · description) + 본문을 조립한 파일(`text/markdown`)이고, 출처 표시 줄(리비전 · 지문)이 붙는다. 가져오기는 올린 파일 · 붙여 넣은 글의 frontmatter 를 읽어 새로 만들거나 그 스킬을 고친다(있던 스킬이면 한 번 묻는다).
6. **감사**: `admin.skill.create` · `update` · `restore`(옛 리비전으로 되돌림) · `delete` · `undelete`(되살림) — moai-wiki 와 같은 이름, 시스템 기록(워크스페이스 없음).
7. **MCP**(일감 입구, 읽기만): `list_skills` — name · description · revisionNo · updatedAt · `latestChange`(지금 리비전의 바뀐 점). `get_skill(name, revision?, sinceRevision?)` — name · description · revisionNo · updatedAt · `files: [{path, content}]`(SKILL.md), `sinceRevision`(사본의 리비전)을 주면 `changes`(그 뒤 리비전마다 때 · 누가 · 한 일 · 요약, 옛 것부터). 결과는 시스템 관리자가 관리하는 지침이라는 안내를 싣는다. 접근 기록에 스킬 이름이 남는다. 도구 설명은 사본의 출처 표시 줄 리비전을 견주고 `get_skill(sinceRevision)` 으로 바뀐 점을 읽고 다시 읽으라고 알린다.
8. **받기 도구**(`tools/sync_skills.py`): MCP 로 받아 `<대상>/<name>/` 에 쓰고 리비전과 **바뀐 점 요약**으로 무엇이 바뀌었는지 알린다(훅 한 줄 — 요약마다 200자 · 5개까지, 새로 받으면 지금 요약만, 옛 서버면 번호만). 그 자리에서 고친 사본은 `--force` 없이 덮어쓰지 않는다. 키를 찍지 않는다.
9. **화면**(시스템 관리 › 스킬): 목록(삭제한 스킬도 보기) · 새 스킬 · 수정(일감과 같은 Markdown 편집기) · 보기(내용 · 리비전 탭 — 일감과 같은 타임라인 · 차이 · 전체, 되돌리기 확인) · 삭제(확인) · 되살리기 · 가져오기 · 내려받기. 반응형 · 다크 · 두 언어.
10. 스킬은 Agent 에게 들어가는 지시라 프롬프트 주입 통로다 — 쓰는 사람을 시스템 관리자로 좁히고, 모든 변경을 리비전 · 감사로 남기고, MCP 에 쓰기 도구를 두지 않는다([SECURITY.md](../../SECURITY.md) §8.3).
11. **MCP 연결 안내**(initialize 의 `instructions`, 두 입구): 이 서버가 무엇인지 · 스킬마다 이름 · 지금 리비전 · 마지막 바뀐 점 · 사본을 새로 받는 방법을 1,500자 안으로, 연결마다 지금 DB 로 만든다 — 훅이 없는 Agent 도 붙는 순간 안다. serverInfo 의 판은 이 api 의 실제 판(Maven 판 + 짧은 커밋)이다(2026-11-24 일감 #183 — 사용자: "스킬 업데이트되면 에이전트들은 어떻게 알고 업데이트해?" · "이걸 기능적으로 되게 만들어").

**수용 기준**
- [x] 일반 사용자의 쓰기(만들기 · 수정 · 삭제 · 되살리기 · 되돌리기 · 가져오기)는 403 이고, 읽기(목록 · 하나 · 리비전 · 차이 · SKILL.md)는 사용자 · 시스템 관리자 모두 된다. 토큰이 없으면 401 (SkillTest)
- [x] 이름 규칙에 어긋나면 400 `SKILL_NAME_INVALID`, 같은 이름은 409, 수정 요청의 이름은 듣지 않고 DB 도 이름 바꾸기 · 행 지우기를 막는다 (SkillTest · SkillFileTest)
- [x] 낡은 리비전(`baseRevisionNo`)의 수정 · 되돌리기는 409 `SKILL_CHANGED` 이고, 내용이 그대로면(되돌리기 포함) 리비전이 늘지 않는다 (SkillTest)
- [x] 만들기 · 수정 · 되돌리기마다 리비전이 쌓이고(누가 · 길 · 한 일 · 바뀐 것 · 바꾼 까닭 · 되돌린 리비전), 차이 · 전체를 읽는다 (SkillTest)
- [x] 설명 · 본문의 제어 문자(줄바꿈 · 탭 말고)와 10만 자를 넘는 본문은 400 이고, SKILL.md 의 설명은 늘 큰따옴표 한 줄이다 (SkillTest · SkillFileTest)
- [x] 리비전은 고치기 · 지우기 · 비우기가 막힌다 (SkillTest)
- [x] 삭제하면 사용자 목록 · 직접 열기 · MCP 에서 숨고(시스템 관리자는 지운 것까지 본다), 고칠 수 없고, 되살리면 내용 · 리비전 그대로 돌아온다 (SkillTest)
- [x] SKILL.md 를 내보내고 가져오면 같은 스킬이고(YAML 에서 조심할 글 · CRLF · BOM · 블록 값), 읽을 수 없는 파일 · 받지 않는 frontmatter 항목은 400 이다. 저장소의 지금 스킬 파일은 출처 표시 줄만 더해져 그대로 나온다 (SkillTest · SkillFileTest)
- [x] 쓰기마다 시스템 감사 `admin.skill.*` 가 남고 본문은 남지 않는다 (SkillTest)
- [x] MCP `list_skills` · `get_skill`(리비전 고르기 포함)이 REST 내려받기와 같은 SKILL.md 를 주고, 접근 기록에 `skill:<이름>` 이 남으며, 프로젝트 관리 입구에는 없다 (SkillTest)
- [x] 화면: 목록 · 삭제 확인 · 되살리기 · 가져오기(있던 스킬이면 묻고 그 리비전으로) · 새 스킬 이름 규칙 · 수정 겹침 · 리비전 탭(타임라인 · 차이) · 되돌리기 확인 (skills-screens.test)
- [x] 받기 도구가 새로 받기 · 같음 · 새 리비전 · 그 자리에서 고친 사본 건너뛰기 · `--force` · 경로 규칙(moai-wiki 제안)에 어긋나거나 폴더 밖인 경로 거절을 하고 키를 찍지 않는다 (test_sync_skills.py)
- [x] 수정 · 되돌리기 · 가져오기에 바뀐 점 요약(5~500자)이 없거나 짧으면 400 `CHANGE_NOTE_REQUIRED`, 길면 `SKILL_NOTE_TOO_LONG`, 제어 문자면 `CHANGE_NOTE_INVALID` 이고 리비전이 늘지 않는다. 만들기는 비우면 "처음 만듦" (SkillTest)
- [x] REST `?sinceRevision=` · MCP `get_skill(sinceRevision)` 이 그 사이 바뀐 점(때 · 누가 · 한 일 · 되돌린 리비전 · 요약)을 옛 것부터 주고(50개까지, 나머지는 수), 요약 없는 옛 리비전은 null, 목록 · `list_skills` 에 `latestChange` (SkillTest)
- [x] MCP 연결 안내가 두 입구 모두 스킬의 지금 리비전 · 바뀐 점 · 갱신 방법을 1,500자 안으로 싣고, 고치면 다음 연결에 바로 보이며, 요약은 한 줄로 펴고 숨은 서식 문자를 걷는다. serverInfo 판은 빌드 판(`0.1.0` 고정이 아님) · `/actuator/info` 의 `app.version` (SkillTest · McpInstructionsTest · AppVersionTest)
- [x] 화면: 바뀐 점 요약 칸(Agent 에게 보임)이 수정 · 가져오기 · 되돌리기에서 필수이고 5자 미만이면 보내지 않는다. 새 스킬은 비워도 된다 (skills-screens.test)
- [x] 받기 도구가 사본의 리비전부터 바뀐 점 요약을 찍고(200자 · 5개 · 외 앞선 N개, 새로 받으면 지금 요약만, 제어 문자 걷기), `sinceRevision` 을 모르는 옛 서버면 번호만 찍는다 (test_sync_skills.py)
- [ ] 실제 화면에서 데스크톱 · 390px · 다크 · 영어로 목록 · 수정 · 리비전 탭 · 되돌리기를 확인한다 (ego-browser)

- [ ] 실제 Claude Code 로 붙어 연결 안내(스킬 리비전 · 바뀐 점)와 serverInfo 판을 보고, 스킬을 고친 뒤 훅 줄에 바뀐 점이 찍히는 것을 확인한다

## 5. 삭제와 한도

<a id="fr-wsp-020"></a>
### FR-WSP-020 워크스페이스 삭제

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 일부 — 한 것: 시스템 관리자의 삭제(2026-11-23, WBS 1.8 — 사용 중지한 팀 워크스페이스만 · 409 `WORKSPACE_NOT_SUSPENDED` · 영향 미리보기와 확인 문구 · Keycloak 조직 · 사본 · 첨부 파일을 지우고 행 · 이력 · 감사는 남김 · 감사 `admin.workspace.delete` · 지운 뒤 MCP 키에 보이지 않음 — WorkspaceSuspendTest). 남은 것: 소유자의 삭제 요청 · 7일 유예 · 취소 · 유예 중 읽기 전용 · 요청 · 취소 감사, 보존 기간 뒤 프로젝트 · 일감 영구 삭제. |
| 관련 설계 | [워크스페이스 설계 §9](../design/03-workspace-identity.md#ws-workspace) |

**설명** — 팀 워크스페이스의 소유자는 삭제를 요청한다. 7일 유예 뒤 지운다. 시스템 관리자가 지우는 것은 사용 중지한 워크스페이스에만 한다([FR-WSP-019](#fr-wsp-019) — "다만 삭제는 사용 중지 후에만 가능해").

**세부 요구사항**
1. 소유자만 요청한다(`workspace.delete`, 소유자 전용). 개인 워크스페이스는 따로 지울 수 없다(계정을 지울 때 함께 처리).
2. 유예 중에는 소유자가 취소할 수 있고, 워크스페이스는 읽기 전용이다.
2-1. 시스템 관리자의 삭제는 사용 중지(`SUSPENDED`)한 워크스페이스에만 한다. 아니면 409 `WORKSPACE_NOT_SUSPENDED` 다.
3. 삭제하면 Keycloak 조직(프로젝트 역할 그룹 포함)을 지우고, 데이터(프로젝트 · 일감 · 이력)는 보존 규칙대로 지운다. 모든 MCP 엔드포인트와 키가 무효가 된다. 2026-11-23 만든 모양(moai-wiki 설계 "DELETED — Keycloak 조직 삭제, 데이터는 보존 규칙대로"와 같다): 지우는 것 — Keycloak 조직, 객체 저장소의 첨부 파일(`ws/<워크스페이스 id>/` 아래 전부), 멤버십 · 역할 · 역할 권한 · 프로젝트 역할 사본 · 가입 신청 · 초대 · 일감 템플릿 · 그 워크스페이스의 알림 · 첨부 티켓. 남기는 것 — 워크스페이스 행(`DELETED`, 주소를 다시 쓰지 않는다) · 프로젝트(`DELETED`) · 일감 · 이력 · 리비전 · 작업 시간 · 첨부 기록(지움 표시) · 감사 — 추가 전용이라 지우지 않고 아무에게도 보이지 않으며, 영구 삭제는 나중의 보존 작업이 한다. MCP 키는 사용자의 것이라 그대로이고(ADR-029) 이 워크스페이스만 보이지 않는다.
4. 위험 작업 확인([FR-WSP-028](#fr-wsp-028))을 거친다. 요청 · 취소 · 삭제를 감사에 남긴다.

**수용 기준**
- [ ] 유예 기간 안에 취소하면 모든 것이 그대로다
- [ ] 소유자가 아니면(관리자 포함) 403 이다
- [x] 삭제가 끝나면 그 워크스페이스의 MCP 키 호출이 모두 거부된다 (WorkspaceSuspendTest — 시스템 관리자의 삭제)
- [ ] 요청 · 취소 · 삭제가 감사에 남는다

## 6. 보안 원칙

moai-wiki 의 보안 요구사항(FR-SEC) 가운데 moai-works 에도 해당하는 것을 옮겼다. 위키 · 보안등급 · 문서 적격성 · 원천 ACL · 외부 LLM 처럼 위키에만 있는 것은 뺐다. MCP 응답의 프롬프트 주입 대비(본문을 "사용자 데이터"로 표시)는 [MCP 요구사항](04-mcp.md#fr-mcp-004)에 있다.

<a id="fr-wsp-022"></a>
### FR-WSP-022 인증 — 모든 입구는 인증을 거친다

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — REST 는 Keycloak JWT 를 JWKS 로 api 가 직접 검증, 공개 경로는 가입뿐, 서비스 계정 토큰은 사람용 API 를 못 씀) · 자동 테스트(토큰 없음 · 만료 · 다른 audience · 다른 발급자 · 다른 키 서명 401, 서비스 계정 403, 가입 정책은 토큰 없이 확인). 남은 것: moai-works 렐름이 발급한 실제 토큰으로 확인. |
| 관련 설계 | [워크스페이스 설계 §12](../design/03-workspace-identity.md#ws-security) |

**설명** — 사람은 Keycloak 계정으로, 바깥 AI Agent 는 MCP 키로 들어온다. 그 밖의 길은 없다.

**세부 요구사항**
1. REST(`/moai-works-api/**`)는 Keycloak 이 발급한 토큰이 있어야 한다. api 는 JWKS 로 서명을 확인하고 만료 · 발급자 · audience(`moai-works-api`)를 확인해야 한다. 요청마다 Keycloak 에 묻지 않는다.
2. 로그인 없이 부를 수 있는 경로는 가입 · 인증 코드(`/moai-works-api/v1/signup/**`)와 상태 확인(`/actuator/health`)뿐이어야 한다.
3. 사람용 API 는 사람 토큰만 받는다. 서비스 계정 토큰은 403 이다.
4. MCP 입구(`/mcp/**`)는 MCP 키로만 인증한다([MCP 요구사항](04-mcp.md#fr-mcp-001)).
5. 브라우저는 토큰을 갖지 않는다. 웹 화면은 web-backend 세션으로만 api 를 부른다([FR-WSP-005](#fr-wsp-005)).

**수용 기준**
- [x] 토큰 없이 사람용 API 를 부르면 401 이다 (TokenAuthenticationTest)
- [x] 만료된 토큰 · 다른 발급자 · audience 에 `moai-works-api` 가 없는 토큰 · 다른 키로 서명한 토큰은 모두 401 이다 (TokenAuthenticationTest)
- [x] 서비스 계정 토큰으로 사람용 API 를 부르면 403 이다 (TokenAuthenticationTest)
- [x] 공개 경로(가입 정책 보기)는 토큰 없이 부를 수 있다 (TokenAuthenticationTest)
- [ ] moai-works 렐름에서 web-backend 로 로그인해 받은 실제 토큰으로 api 를 부르면 통과한다

<a id="fr-wsp-023"></a>
### FR-WSP-023 권한 판정은 api 한 곳에서

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — REST 핸들러마다 접근 어노테이션 정확히 하나, 없으면 기동 실패, 워크스페이스 판정은 한 서비스에서 DB 사본으로) · 자동 테스트(모든 워크스페이스 경로의 404 · 403, 없는 것과 남의 것 구별 불가, 역할 변경이 다음 요청부터, 모든 테스트가 기동 검사를 지남). 남은 것: 어노테이션이 빠졌을 때 기동이 멈추는지 부정 시험 · 프로젝트 · 일감 경로 판정(프로젝트 영역) · MCP 도구가 같은 판정을 쓰는지(MCP 영역). |
| 관련 설계 | [워크스페이스 설계 §3.4](../design/03-workspace-identity.md#ws-rules) · [§12](../design/03-workspace-identity.md#ws-security) |

**설명** — 사람이 화면으로 하든, 바깥 Agent 가 MCP 로 하든, 스크립트가 REST 로 하든 같은 서비스 · 같은 판정을 거친다. 판정하는 곳은 api 한 곳이다.

**세부 요구사항**
1. 모든 권한 판정은 api 가 해야 한다. web-backend 와 화면은 판정하지 않고 숨기기만 한다. 화면을 거치지 않고 API 를 직접 불러도 결과가 같아야 한다.
2. REST 핸들러마다 접근 어노테이션(`@PublicApi` · `@AuthenticatedApi` · `@UserApi` · `@ServiceApi` · `@PlatformApi` · `@WorkspaceApi(권한)`, 계획 `@ProjectApi(권한)` — 일감 경로도 프로젝트 아래라 `@ProjectApi` 를 쓴다)이 정확히 하나 있어야 하고, 없거나 둘이면 기동하지 않아야 한다.
3. 판정은 토큰에 실린 역할이 아니라 매 요청 api DB 사본으로 해야 한다. 역할 · 정지 변경이 다음 요청부터 반영된다.
4. 읽기 거부(멤버 아님 · 독자 아님)는 404 로 존재를 숨기고, 쓰기 거부(멤버지만 권한 없음)는 403 이어야 한다. 없는 대상과 남의 대상의 응답이 같아야 한다.
5. 관리 역할(시스템 관리자 포함)이 있어도 멤버가 아니면 워크스페이스 내용을 볼 수 없다.
6. MCP 도구도 같은 서비스 · 같은 판정을 거친다. 모델이 넘긴 프로젝트 · 일감도 다시 판정한다([MCP 요구사항](04-mcp.md#fr-mcp-003)).

**수용 기준**
- [x] 지금의 모든 REST 핸들러가 접근 어노테이션을 정확히 하나 가진다 — api 를 띄울 때 도는 기동 검사를 지난다 (8개 테스트 클래스 모두)
- [ ] 어노테이션이 없는 핸들러를 넣으면 기동이 멈춘다
- [x] 멤버가 아니면 워크스페이스 안 모든 경로가 404 이고, 없는 워크스페이스와 응답이 같다 (WorkspaceAccessTest)
- [x] 멤버지만 권한이 없으면 관리 경로가 403 이다 (WorkspaceAccessTest)
- [x] 역할을 바꾸면 토큰을 다시 받지 않아도 다음 요청부터 바뀐 권한으로 판정한다 (WorkspaceAccessTest)
- [ ] 프로젝트 · 일감 경로도 같은 규칙(독자 아님 404 · 권한 없음 403)을 따른다

### FR-WSP-024 감사 기록

| 항목 | 내용 |

**세부 요구사항**
1. 다음 행동을 기록해야 한다.

   | 분류 | `action` |
   |---|---|

   | 플랫폼 | `platform.signup_policy.update` |
   | 워크스페이스 | `workspace.create` `workspace.settings.update` (계획: `workspace.ownership.transfer` `workspace.delete.*`) |
   | 멤버 · 신청 · 초대 | `member.add` `member.roles.update` `member.remove` `member.leave` `join_request.*` `invitation.*` |
   | 역할 | `role.create` `role.update` `role.delete` |
   | MCP (계획) | `mcp.endpoint.create` `mcp.endpoint.update` `mcp.endpoint.delete` `mcp.key.issue` `mcp.key.expire` `mcp.access_log.export` — [MCP 요구사항](04-mcp.md). MCP 키로 들어온 모든 요청(읽기 포함)은 따로 [MCP 접근 기록](04-mcp.md#fr-mcp-006)에 남는다 |
   | 프로젝트 (계획) | `project.create` `project.update` `project.archive` `project.restore` `project.delete` `project.roles.update` — [FR-PRJ-011](02-project.md#fr-prj-011) |
   | 일감 (계획) | `issue.create` `issue.update` `issue.comment` `issue.link.add` `issue.link.remove` `issue.delete` — [FR-ISS-010](03-issue.md#fr-iss-010) |

2. 기록마다 언제 · 누가(주체 종류: 사람 `USER`(MCP 로 한 일은 키 주인) · 서비스 `SERVICE`(Keycloak 서비스 계정 — MCP 는 쓰지 않는다) · 시스템 `SYSTEM`) · 어느 길로(경로: 웹 · REST · MCP — MCP 면 엔드포인트 id · 키 id) · 어느 워크스페이스 · 무엇을(대상 종류 · id · 바뀐 값) · IP · trace_id 를 남겨야 한다.
3. 추가만 할 수 있어야 한다(DB 가 UPDATE · DELETE 를 막는다).
4. 쓰기 행동은 감사 기록이 실패하면 업무도 실패해야 한다(같은 트랜잭션).
5. 비밀번호 · 토큰 · 인증 코드 · MCP 키 원문은 기록하지 않는다.
6. 기본 보존 기간은 3년이다. 변조 감지(하루 단위 해시 체인 또는 WORM 보관)는 운영 배치에서 한다.
7. 감사 화면에서 잘 거를 수 있어야 한다(2026-11-22 사용자 결정 "필터 기능도 잘 만들고"): 기간 · 행동 · 주체 종류 · 주체 · 경로(웹 · MCP) · 대상 종류 · 대상 · MCP 키 · 클라이언트. 여러 조건을 함께 걸고, 조건은 주소에 남는다. MCP 키로 들어온 읽기까지의 모든 접근은 [MCP 접근 기록](04-mcp.md#fr-mcp-010)에서 같은 방식으로 본다.

**수용 기준**
- [ ] 표의 모든 쓰기 행동이 시험 시나리오에서 감사에 남는다
- [ ] 애플리케이션 DB 계정으로 `audit_log` 를 고치거나 지우면 거부된다
- [ ] MCP 로 한 쓰기에는 주체(키 주인) · 경로 MCP · 엔드포인트 · 키 id 가 남는다
- [ ] 감사 저장이 실패하면 그 쓰기도 되돌려진다
- [ ] 감사 기록에 비밀값 원문이 없다
- [ ] 감사 화면에서 기간 · 행동 · 주체 · 경로 · 대상으로 거를 수 있고, 거른 주소를 새로 고쳐도 같다

### FR-WSP-025 관리 기능 접근 통제 (MFA · 접속 위치)

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [워크스페이스 설계 §12](../design/03-workspace-identity.md#ws-security) |

**설명** — 플랫폼 관리 기능은 영향이 크므로 일반 기능보다 강하게 보호한다.

**세부 요구사항**
1. `system-admin` · `security-officer` 의 행위는 다중 인증(MFA)을 거친 세션에서만 할 수 있어야 한다. 패스워드 그랜트에서 MFA(OTP)를 받을 수 있는지 먼저 확인한다.

3. 관리 기능 세션은 유휴 15분에 만료한다.
4. 관리 계정의 반복 로그인 실패, 처음 보는 접속 위치를 보안 담당에게 알린다.

**수용 기준**
- [ ] MFA 를 거치지 않은 세션으로 시스템 관리자 API 를 쓰면 거부된다
- [ ] 허용 대역 밖 IP 에서 관리 기능에 접근하면 거부된다

<a id="fr-wsp-026"></a>
### FR-WSP-026 전송 · 저장 암호화

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — api · web-backend 는 기본으로 HTTPS 로만 연다, localhost 가 아닌 호스트에만 HSTS, 세션 쿠키 `__Host-` · Secure · HttpOnly). 남은 것: moai-works 서비스를 띄워 평문 HTTP 거부 확인 · HSTS 규칙 시험 · 운영 저장소 암호화 점검(PostgreSQL · MinIO · OpenSearch · 백업). |
| 관련 설계 | [워크스페이스 설계 §12](../design/03-workspace-identity.md#ws-security) |

**설명** — 통신 구간과 저장소 모두에서 데이터를 암호화한다.

**세부 요구사항**
1. 바깥 · 안쪽 통신은 모두 TLS 1.2 이상이어야 한다. 인증서 확인을 끄는 설정을 두지 않는다.
2. localhost 가 아닌 호스트에는 HSTS 를 보낸다. localhost 에는 보내지 않는다(같은 PC 의 다른 서비스가 막히지 않게).
3. 서비스의 TLS 는 앞단(프록시 · 인그레스)이 TLS 를 끝내는 배치에서만 끈다.
4. PostgreSQL · 객체 저장소 · OpenSearch · 백업의 저장 데이터는 운영에서 암호화해야 한다.
5. 객체 저장소 버킷(첨부는 [나중 후보](00-overview.md#7-나중-후보))은 api 만 읽고 쓴다. 내려받기도 api 를 거친다(권한 판정).

**수용 기준**
- [ ] 평문 HTTP 로 api · web-backend 에 접근할 수 없다
- [ ] localhost 가 아닌 호스트의 HTTPS 응답에 HSTS 가 있고, localhost 응답에는 없다
- [ ] 운영 저장소의 저장 암호화가 켜져 있다(점검 스크립트)

<a id="fr-wsp-027"></a>
### FR-WSP-027 비밀값 · 자격 증명 관리

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 코드(moai-wiki 에서 가져옴 — 비밀값은 git 에서 뺀 `.env` 와 환경 변수로만 넣고 설정 파일에는 키 이름만, DB 에는 해시만(MCP 키 · 초대 토큰 SHA-256, 인증 코드 HMAC), 감사에 비밀값을 넣지 않음, 코드 HMAC 비밀값이 없거나 짧으면 기동하지 않음). 남은 것: 로그 · DB 전수 검사 · CI 비밀 검사 · 교체 주기 알림 · 운영 비밀 저장소. |
| 관련 설계 | [워크스페이스 설계 §12](../design/03-workspace-identity.md#ws-security) |

**설명** — DB 비밀번호 · Keycloak 클라이언트 비밀값 · 객체 저장소 열쇠 · MCP 키가 새면 바로 데이터 유출로 이어진다.

**세부 요구사항**
1. 비밀값은 git 에서 뺀 `.env` 또는 운영 비밀 저장소에만 둔다. 문서 · 커밋 · 로그 · 대화에는 키 이름만 적는다.
2. DB 에는 비밀값 원문을 두지 않는다. MCP 키 · 초대 링크 토큰은 SHA-256, 인증 코드는 HMAC 만 저장하고, MCP 키 원문은 발급 응답에 한 번만 보여 준다.
3. 오류 메시지 · 로그 · 감사에 비밀값이 나오지 않는다. 메일 로그 모드(인증 코드를 로그에 씀)는 로컬 개발에서만 쓴다.
4. 각 비밀값은 그것을 쓰는 서비스만 읽는다.
5. 교체 주기는 90일을 권하고 만료 30일 전에 알린다. CI 에서 비밀 검사를 돌려 발견되면 병합을 막는다.

**수용 기준**
- [ ] 로그 · DB · 감사 전수 검사에서 비밀값 원문이 0건이다
- [ ] 비밀값이 든 커밋은 CI 에서 병합이 막힌다
- [ ] 코드 HMAC 비밀값이 없거나 32자보다 짧으면 api 가 기동하지 않는다

### FR-WSP-028 위험 작업 이중 확인

**세부 요구사항**
1. 대상: 워크스페이스 삭제, 소유권 이전, 프로젝트 삭제 · 보관, 역할 일괄 변경, 멤버 대량 제거. (일감 일괄 삭제는 첫 출시에 없다.)
2. 모든 대상 작업은 영향 미리보기(지워질 프로젝트 · 일감 수 등)와 확인 문구 입력을 거쳐야 한다. 확인 문구는 api 가 다시 검사한다.
3. MCP 로는 하지 않는다(사람만 웹에서 — [MCP 요구사항](04-mcp.md)).
4. 요청 · 실행을 감사에 남긴다.

**수용 기준**
- [x] 워크스페이스 삭제는 영향 미리보기와 확인 문구 없이 실행되지 않는다 (WorkspaceSuspendTest · workspaces-screens.test — 화면은 미리보기를 받은 뒤에만 입력 칸이 열린다)
- [x] 확인 문구가 틀리면 api 가 거부한다(화면만 막지 않는다) (WorkspaceSuspendTest)

<a id="fr-wsp-029"></a>
### FR-WSP-029 계정 탈퇴와 개인정보

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [워크스페이스 설계 §7.2](../design/03-workspace-identity.md#ws-signup) |

**설명** — 사용자는 스스로 탈퇴할 수 있고, 시스템 관리자는 개인정보 열람 · 삭제 요청을 처리한다. 다른 사람이 쓰는 기록(일감 · 이력)은 지우지 않는다.

**세부 요구사항**
1. 본인이 탈퇴할 수 있어야 한다. 팀 워크스페이스의 마지막 소유자면 먼저 소유권을 넘겨야 한다.
2. 탈퇴하면 Keycloak 사용자를 끄고 지우며, 모든 멤버십을 거두고 그 사람의 MCP 키를 모두 만료시킨다. 개인 워크스페이스는 [워크스페이스 삭제](#fr-wsp-020) 규칙으로 지운다.
3. 그 사람이 쓴 일감 · 이력 · 댓글은 남기고 작성자는 "탈퇴한 사용자"로 보인다. 감사의 주체 id 는 보존 기간 동안 남긴다.
4. 시스템 관리자는 정보주체의 열람 · 삭제 요청을 처리할 수 있어야 한다(계정 정보 내보내기 · 삭제).
5. 개인정보는 가입에 필요한 것(이메일 · 표시 이름)만 받는다.

**수용 기준**
- [ ] 탈퇴한 계정으로 로그인할 수 없고 모든 워크스페이스에서 빠진다
- [ ] 마지막 소유자는 소유권을 넘기기 전에 탈퇴할 수 없다
- [ ] 탈퇴한 사람이 쓴 일감 · 이력은 남고 작성자는 "탈퇴한 사용자"로 보인다
- [ ] 탈퇴가 감사에 남는다
