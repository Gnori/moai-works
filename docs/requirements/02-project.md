# 프로젝트 요구사항 (FR-PRJ)

프로젝트 만들기 · 식별자 · 공개 범위 · 상태(닫힘 · 보관 · 삭제) · 하위 프로젝트와 멤버 이어받기 · 모듈 · 멤버(사람 · Agent 계정)와 프로젝트 역할 4종 · 목록과 개요 쪽의 요구사항이다. Redmine 의 프로젝트 동작을 기준으로, 권한 경계를 프로젝트로 두는 moai-works 결정을 따른다. 설계는 [프로젝트와 권한 설계](../design/04-project-permissions.md)에 있다.

| MCP 동등성 | MCP 도구(`list_projects` · `get_project`)는 REST 와 같은 서비스 · 같은 판정을 부르고 같은 결과를 낸다. 프로젝트 만들기 · 설정 · 멤버 · 지우기는 MCP 에 없다(사람만 웹에서) |
| 정본 | 사람의 프로젝트 역할은 Keycloak 조직 그룹 `/projects/<project id>/<role key>`, Agent 계정의 역할과 프로젝트 자체는 api DB |
| 화면 | ko/en, 390px 와 데스크톱, 다크 모드 |

## 1. 만들기 · 정보

<a id="fr-prj-001"></a>
### FR-PRJ-001 프로젝트 만들기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §14](../design/04-project-permissions.md#pp-lifecycle) · [§3 권한 코드](../design/04-project-permissions.md#pp-codes) |

**설명** — 워크스페이스 안에서 프로젝트를 만든다. 맨 위 프로젝트는 워크스페이스 층 `project.create`, 하위 프로젝트는 상위의 `project.manage` 가 있어야 만든다. 만든 사람이 워크스페이스 전체를 관리하는 사람이 아니면 그 프로젝트의 관리자가 된다(Redmine 의 "프로젝트를 만든 비관리자에게 주는 역할"과 같다).

**세부 요구사항**
1. 시스템은 이름(필수, 100자) · 식별자([FR-PRJ-002](#fr-prj-002)) · 설명(Markdown) · 홈페이지 · 공개 범위 · 상위 프로젝트 · 이어받기 · 모듈 · 트래커를 받아야 한다. 비운 값은 새 프로젝트 기본값([FR-PRJ-020](#fr-prj-020))으로 채운다.
2. 맨 위 프로젝트는 워크스페이스 층 `project.create` 가 있어야 만들 수 있어야 한다. 하위 프로젝트는 [FR-PRJ-014](#fr-prj-014)를 따른다.
3. 만든 사람이 워크스페이스 층 `project.manage` 를 갖고 있지 않으면 그 사람에게 `project-manager` 역할을 줘야 한다(Keycloak 그룹에 먼저 쓰고 사본을 고친다).
4. 역할 부여가 중간에 실패해도 프로젝트는 남기고, Keycloak 쓰기 기록으로 이어서 끝내야 한다.
5. 만들기는 감사 `project.created` 와 이벤트 `project.created` 를 남겨야 한다.
6. MCP 로는 프로젝트를 만들 수 없어야 한다.

**수용 기준**
- [ ] `project.create` 가 없는 멤버가 맨 위 프로젝트를 만들면 403 이다
- [ ] 사용자 정의 역할로 `project.create` 만 가진 사람이 만들면 그 사람이 프로젝트 관리자로 멤버 목록에 나온다. 워크스페이스 관리자가 만들면 역할이 생기지 않는다
- [ ] 만든 직후 감사에 `project.created` 와 입력 값이 남는다
- [ ] Keycloak 역할 부여 실패를 주입해도 프로젝트는 남고, 재시도 뒤 바인딩이 생긴다
- [ ] MCP `tools/list` 에 프로젝트 만들기 도구가 없다

<a id="fr-prj-002"></a>
### FR-PRJ-002 프로젝트 식별자

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §14.1](../design/04-project-permissions.md#pp-lifecycle) |

**설명** — 식별자는 REST 경로(`/workspaces/{workspace}/projects/{project}`)와 MCP 리소스(`moai-works://{ws}/projects/{식별자}`)에 들어가는 주소 이름이다. 워크스페이스 안에서 하나이고, 만든 뒤 바꾸지 않는다(Redmine 과 같다).

**세부 요구사항**
1. 식별자는 영문 소문자로 시작하고 소문자 · 숫자 · 하이픈만 쓰며 2 ~ 50자여야 한다. 하이픈으로 끝나거나 하이픈을 두 번 이을 수 없어야 한다.
2. 식별자는 워크스페이스 안에서 하나여야 한다. 다른 워크스페이스와는 겹쳐도 된다.
3. 만든 뒤에는 바꿀 수 없어야 한다. 이름은 바꿀 수 있다.
4. 화면 경로와 겹치는 말(`new` · `settings` · `archived` · `templates`)은 쓸 수 없어야 한다.
5. 지운 프로젝트의 식별자는 정리 작업([FR-PRJ-019](#fr-prj-019))이 끝난 뒤에만 다시 쓸 수 있어야 한다.
6. 화면은 이름으로 식별자를 제안해야 한다.

**수용 기준**
- [ ] `My-Proj` · `a` · `abc-` · `a--b` · `new` 는 422 로 거부된다
- [ ] 같은 워크스페이스에서 같은 식별자는 409, 다른 워크스페이스에서는 만들어진다
- [ ] PATCH 로 식별자를 바꾸려 하면 거부되고 값이 그대로다
- [ ] 정리 중인 지운 프로젝트의 식별자는 409, 정리가 끝나면 쓸 수 있다

<a id="fr-prj-003"></a>
### FR-PRJ-003 프로젝트 정보 고치기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §15 API](../design/04-project-permissions.md#pp-api) · [§17 테이블](../design/04-project-permissions.md#pp-ddl) |

**설명** — 프로젝트 관리자는 이름 · 설명 · 홈페이지 · 프로젝트 사용자 정의 필드 값을 고친다. 설명은 Markdown 이고 텍스트 링크(`#123`)를 쓴다. 동시에 고쳐도 잃지 않게 낙관적 잠금을 쓴다.

**세부 요구사항**
1. 고치기는 그 프로젝트의 `project.manage` 가 있어야 해야 한다.
2. 요청에 `lock_version` 이 있어야 하고, 지금 판과 다르면 409 여야 한다.
3. 설명은 Markdown(GFM)으로 저장하고 미리보기와 텍스트 링크([FR-ISS-012](03-issue.md#fr-iss-012))를 지원해야 한다.
4. 홈페이지는 `http` · `https` 주소만 받아야 한다.
5. 대상이 "프로젝트"인 사용자 정의 필드가 있으면 그 값을 같은 검증으로 받아야 한다([FR-WFL-014](04-workflow.md#fr-wfl-014)).
6. 바꾼 필드의 전 · 후를 감사에 남기고 `project.updated` 를 내야 한다(설명 본문은 길이만).

**수용 기준**
- [ ] 개발자가 PATCH 하면 403, 비독자는 404 다
- [ ] 오래된 `lock_version` 으로 고치면 409 이고 값이 바뀌지 않는다
- [ ] `javascript:` 홈페이지는 422 다
- [ ] 고친 뒤 감사에 바뀐 필드의 전 · 후가 남는다

## 2. 공개 범위 · 역할 · 멤버

<a id="fr-prj-004"></a>
### FR-PRJ-004 공개 범위

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §5](../design/04-project-permissions.md#pp-visibility) · [§7 판정 규칙](../design/04-project-permissions.md#pp-rule) |

**설명** — 프로젝트는 워크스페이스 공개(`WORKSPACE`)와 지정 멤버(`RESTRICTED`) 중 하나다. 독자가 아니면 프로젝트가 있는지도 알 수 없다. 이것이 moai-works 의 권한 경계다.

**세부 요구사항**
1. 공개 범위는 `WORKSPACE` · `RESTRICTED` 둘이어야 하고, 기본값은 워크스페이스 설정을 따라야 한다.
2. `WORKSPACE` 프로젝트의 독자는 워크스페이스의 활성 멤버(사람) 전원과 그 프로젝트의 역할을 받은 Agent 계정이어야 한다.
3. `RESTRICTED` 프로젝트의 독자는 그 프로젝트(또는 이어받은 상위)의 역할을 받은 사람 · Agent 와, 워크스페이스 층 `project.manage` 를 가진 사람(기본: 소유자 · 관리자)이어야 한다.
4. 독자가 아니면 목록 · 트리 · 찾기 · 검색 · 텍스트 링크 · MCP 어디에도 그 프로젝트가 나오지 않아야 하고, 직접 요청하면 없는 프로젝트와 똑같은 404 여야 한다.
5. 공개 범위를 바꿀 때 화면은 독자 증감을 미리 보여야 하고, 바꾸면 감사 · `project.access.changed` 를 남기고 다음 요청부터(다른 인스턴스는 30초 안에) 반영해야 한다.
6. 하위 프로젝트의 공개 범위는 상위와 따로 정할 수 있어야 한다.

**수용 기준**
- [ ] `RESTRICTED` 비독자에게 프로젝트 · 일감 · 목록 · 보드 · 검색 · MCP `get_project` 가 모두 404 이거나 나오지 않고, 404 본문이 없는 식별자의 것과 같다
- [ ] 워크스페이스 관리자는 역할 없이도 `RESTRICTED` 프로젝트를 본다
- [ ] `WORKSPACE` → `RESTRICTED` 로 바꾸면 역할 없는 멤버가 다음 요청부터 404 다(다른 인스턴스는 30초 안)
- [ ] 바꾸기가 감사와 `project.access.changed` 를 남긴다
- [ ] 같은 경우를 MCP 도구로 해도 결과가 같다

<a id="fr-prj-005"></a>
### FR-PRJ-005 워크스페이스 공개 프로젝트의 기본 역할

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §5.1](../design/04-project-permissions.md#pp-visibility) |

**설명** — 워크스페이스의 기본 역할 `member` 에는 일감 읽기 코드가 없다. 그래서 `WORKSPACE` 프로젝트에서 역할이 없는 사람이 받을 역할을 프로젝트마다 정한다. Redmine 의 내장 "비회원" 역할 자리다. 사내 IT 지원처럼 누구나 일감을 올리는 프로젝트는 보고자로 둔다.

**세부 요구사항**
1. 프로젝트는 기본 역할 `project-viewer`(기본) 또는 `project-reporter` 를 가져야 한다.
2. 기본 역할은 `WORKSPACE` 프로젝트에서 실효 역할(직접 · 이어받음)이 없는 사람에게만 적용해야 한다.
3. 기본 역할은 하위 프로젝트로 이어받지 않아야 하고, 기본 역할만 가진 사람은 담당자가 될 수 없어야 한다.
4. Agent 계정에는 기본 역할을 적용하지 않아야 한다.
5. 바꾸기는 `project.manage` 이고 감사에 남아야 한다.

**수용 기준**
- [ ] 기본 역할이 독자면 역할 없는 멤버가 일감을 보고, 만들기는 403 이다
- [ ] 기본 역할을 보고자로 바꾸면 역할 없는 멤버가 일감을 만들 수 있고, 담당자 목록에는 나오지 않는다
- [ ] 역할 없는 Agent 계정은 `WORKSPACE` 프로젝트에서도 404 다
- [ ] `RESTRICTED` 프로젝트에서는 기본 역할이 아무 효과가 없다

<a id="fr-prj-006"></a>
### FR-PRJ-006 프로젝트 역할 4종

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §4](../design/04-project-permissions.md#pp-roles) · [§3.2 역할별 표](../design/04-project-permissions.md#pp-role-matrix) |

**설명** — 프로젝트 안에서 할 수 있는 일은 프로젝트 역할이 정한다. 관리자 · 개발자 · 보고자 · 독자 네 가지로 고정하고(moai-wiki 의 위키 역할과 같은 구조), 독자 ⊂ 보고자 ⊂ 개발자 ⊂ 관리자의 포함 관계다. 사용자 정의 프로젝트 역할은 나중(C)이다.

**세부 요구사항**
1. 역할 키는 `project-manager` · `project-developer` · `project-reporter` · `project-viewer` 여야 한다.
2. 역할마다 받는 권한 코드는 설계 §3.2 의 확정안과 같아야 한다.
3. 한 주체는 한 프로젝트에서 직접 역할을 하나만 가져야 한다.
4. 실효 역할은 직접 역할과 이어받은 역할([FR-PRJ-016](#fr-prj-016)) 가운데 가장 높은 것이어야 한다.
5. 판정은 "워크스페이스 역할의 코드 ∪ 실효 역할의 코드(없으면 기본 역할의 코드)"로 해야 한다.
6. 프로젝트 응답에 화면용 `myAccess`(실효 역할 · 코드 · 켜진 모듈)를 넣어야 한다.

**수용 기준**
- [ ] 역할별 표의 모든 칸을 자동 테스트로 확인한다(포함 관계 포함)
- [ ] 보고자는 자기가 만든 일감의 제목을 고칠 수 있고, 남의 일감은 403 이다
- [ ] 독자가 메모를 쓰면 403, 개발자가 프로젝트 설정을 바꾸면 403, 관리자는 일감을 지울 수 있다
- [ ] 같은 경우를 MCP 도구로 해도 결과가 같다

<a id="fr-prj-007"></a>
### FR-PRJ-007 멤버 관리 (사람)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §4.1](../design/04-project-permissions.md#pp-roles) · [§6 Keycloak](../design/04-project-permissions.md#pp-keycloak) |

**설명** — 프로젝트 관리자는 워크스페이스 멤버에게 프로젝트 역할을 주고, 바꾸고, 뺀다. 사람의 역할은 Keycloak 조직 그룹이 정본이고 api DB 는 판정용 사본이다.

**세부 요구사항**
1. 멤버 관리는 그 프로젝트의 `project.manage` 가 있어야 해야 한다.
2. 대상은 같은 워크스페이스의 활성 멤버여야 하고, 여러 사람에게 한 역할을 한 번에 줄 수 있어야 한다.
3. 역할을 주면 Keycloak 그룹 `/projects/<project id>/<role key>` 에 먼저 넣고 사본(`project_role_binding`)을 고쳐야 한다. 바꾸면 그 프로젝트의 다른 역할 그룹에서 빼야 한다.
4. 마지막 프로젝트 관리자를 빼거나 낮추면 경고하고, 자기 역할을 낮추면 확인을 받아야 한다.
5. 워크스페이스에서 나간 멤버는 모든 프로젝트 그룹과 바인딩에서 빠져야 하고, 정지된 멤버의 바인딩은 판정에서 빠져야 한다.
6. 15분 대사로 Keycloak 과 사본의 차이를 찾아 Keycloak 기준으로 고치고 감사에 남겨야 한다.
7. 넣기 · 바꾸기 · 빼기는 감사 `project.member.*` 를 남겨야 한다.

**수용 기준**
- [ ] 개발자가 멤버를 넣으면 403 이다
- [ ] 넣은 뒤 Keycloak 그룹에 들어가 있고 사본이 생기며, 다음 요청부터 그 사람이 `RESTRICTED` 프로젝트의 독자다
- [ ] 워크스페이스에서 내보낸 사람의 바인딩이 남지 않는다
- [ ] Keycloak 콘솔에서 그룹에 넣은 사람은 대사 뒤 사본에 반영되고 `security.drift.detected` 감사가 남는다
- [ ] 감사에 주체 · 전 역할 · 후 역할이 남는다

<a id="fr-prj-008"></a>
### FR-PRJ-008 Agent 계정 멤버

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §6](../design/04-project-permissions.md#pp-keycloak) · [§4.2 담당자](../design/04-project-permissions.md#pp-assignable) |

**설명** — Agent 계정도 프로젝트 역할을 받아 사람과 같은 판정으로 일한다. Agent 계정은 Keycloak 에 없으므로 api DB 의 바인딩이 정본이다. Agent 계정 자체(만들기 · 키)는 [MCP 요구사항](12-mcp.md)에 있다.

**세부 요구사항**
1. 대상은 같은 워크스페이스의 활성 Agent 계정이어야 하고, 사람과 같은 멤버 화면에서 넣어야 한다.
2. Agent 의 바인딩은 주체 종류 `AGENT` 로 저장하고 Keycloak 을 쓰지 않아야 한다.
3. Agent 의 판정은 사람과 같은 함수를 써야 한다. Agent 의 워크스페이스 권한은 없으므로 `WORKSPACE` 프로젝트라도 역할이 있어야 독자여야 한다.
4. 보고자 이상의 역할을 받은 Agent 는 담당자 목록에 나와야 하고, 화면은 "Agent" 표시를 해야 한다.
5. Agent 계정을 끄면 바인딩은 남기고 판정에서 빼야 하며, 지우면 바인딩도 지워야 한다.
6. Agent 는 MCP 로 멤버 · 역할을 바꿀 수 없어야 한다.

**수용 기준**
- [ ] 역할 없는 Agent 의 MCP `get_project` 는 `WORKSPACE` 프로젝트라도 404 다
- [ ] 개발자 역할 Agent 는 `update_issue` 를 할 수 있고, 담당자 목록에 "Agent" 표시로 나온다
- [ ] Agent 계정을 끄면 다음 호출부터 404 다
- [ ] Agent 역할을 줄 때 Keycloak 쓰기 호출이 없고, 감사는 사람과 같이 남는다

<a id="fr-prj-009"></a>
### FR-PRJ-009 모듈 켜고 끄기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §9](../design/04-project-permissions.md#pp-modules) |

**설명** — 프로젝트마다 기능 묶음을 켜고 끈다: 일감 · 시간 · 뉴스 · 문서 · 파일 · 위키 · 저장소 · 포럼 · 캘린더 · 간트 · 보드. 꺼진 모듈은 그 프로젝트에 없는 것과 같다(Redmine 과 같고, 보드는 추가).

**세부 요구사항**
1. 모듈 키는 `issue_tracking` · `time_tracking` · `news` · `documents` · `files` · `wiki` · `repository` · `forums` · `calendar` · `gantt` · `kanban` 이어야 한다.
2. 켜고 끄기는 `project.manage` 가 있어야 해야 한다.
3. 꺼진 모듈은 화면 메뉴에서 빠지고, REST 는 404, 그 프로젝트를 대상으로 한 MCP 도구는 404 여야 하며, 검색 결과에서 빠져야 한다.
4. 끄더라도 데이터는 지우지 않아야 하고, 다시 켜면 그대로 보여야 한다.
5. `calendar` · `gantt` · `kanban` 은 `issue_tracking` 없이 켤 수 없어야 하고, `issue_tracking` 을 끄면 함께 꺼져야 한다(확인을 받는다).
6. 꺼진 모듈의 대상을 가리키는 텍스트 링크는 글자로만 보여야 한다.
7. 바꾸기는 감사와 `project.module.changed` · `project.access.changed` 를 남겨야 한다.

**수용 기준**
- [ ] `time_tracking` 을 끄면 시간 기록 REST 와 MCP `log_time` 이 404 이고 일감 쪽의 소요 시간 칸이 없다
- [ ] 다시 켜면 이전 시간 기록이 그대로 보인다
- [ ] `issue_tracking` 을 끄면 보드 · 간트 · 캘린더도 꺼진다
- [ ] 감사에 켠 모듈 · 끈 모듈이 남는다

<a id="fr-prj-010"></a>
### FR-PRJ-010 일감 추적 설정 (트래커 · 기본 담당 · 기본 버전)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §17 테이블](../design/04-project-permissions.md#pp-ddl) · [일감 설계 §10](../design/05-issue-tracking.md#is-config) · [§10.4 카테고리](../design/05-issue-tracking.md#is-category) |

**설명** — 프로젝트에서 쓸 트래커와 새 일감의 기본 담당 · 기본 대상 버전을 정한다. Redmine 프로젝트 설정의 "일감 추적" 탭과 같다. 트래커 자체는 워크스페이스 설정이다([FR-WFL-001](04-workflow.md#fr-wfl-001)).

**세부 요구사항**
1. 워크스페이스 트래커 가운데 이 프로젝트에서 쓸 것을 하나 이상 골라야 한다.
2. 그 트래커의 일감이 있는 동안에는 그 트래커를 뺄 수 없어야 한다(일감 수를 보인다).
3. 기본 담당은 그 프로젝트의 담당 가능 주체(사람 · Agent 계정) 가운데서 골라야 하고, 담당이 빈 새 일감에 카테고리 기본 담당이 없을 때 넣어야 한다.
4. 기본 대상 버전은 그 프로젝트에 공유된 열린 버전이어야 한다([버전 요구사항](06-planning.md)).
5. 바꾸기는 `project.manage` 이고 감사에 남아야 한다.

**수용 기준**
- [ ] 고르지 않은 트래커는 새 일감 화면에 없고, REST · MCP 로 보내면 422 다
- [ ] 일감이 있는 트래커를 빼면 422 와 일감 수가 나온다
- [ ] 카테고리 기본 담당이 없을 때 새 일감의 담당이 프로젝트 기본 담당이 된다
- [ ] 담당 가능하지 않은 주체를 기본 담당으로 정하면 422 다

### FR-PRJ-011 사용자 정의 필드 고르기

| 항목 | 내용 |

| 우선순위 | S |
| 진행 | 할 일 |

**설명** — "모든 프로젝트"가 아닌 일감 사용자 정의 필드 가운데 이 프로젝트에서 쓸 것을 고른다(Redmine 과 같다). 필드 정의는 [FR-WFL-013](04-workflow.md#fr-wfl-013)에 있다.

**세부 요구사항**
1. 고를 수 있는 필드는 대상이 일감이고 `is_for_all` 이 꺼진 필드여야 한다.
2. 고른 필드는 그 필드에 연결된 트래커의 일감 화면 · API · 필터에 나와야 한다.

**수용 기준**
- [ ] 고르지 않은 필드는 일감 응답 · 필터 · MCP 에 나오지 않는다
- [ ] 뺐다가 다시 고르면 옛 값이 보인다
- [ ] 개발자가 바꾸면 403 이다

## 3. 목록 · 개요

<a id="fr-prj-012"></a>
### FR-PRJ-012 프로젝트 목록 · 트리 · 찾기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §15 API](../design/04-project-permissions.md#pp-api) · [§8.1 트리](../design/04-project-permissions.md#pp-tree) |

**설명** — 사람은 읽을 수 있는 프로젝트를 목록이나 트리로 보고, 이름으로 찾고, 내가 멤버인 프로젝트만 거른다. Agent 는 MCP `list_projects` 로 같은 결과를 받는다.

**세부 요구사항**
1. 목록 · 트리에는 독자인 프로젝트만 나와야 한다.
2. 트리에서 상위를 읽을 수 없으면 읽을 수 있는 가장 가까운 조상 아래(없으면 맨 위)에 붙여야 하고, 숨긴 상위의 이름은 응답 어디에도 없어야 한다.
3. 거르기: 상태(기본 활성, 닫힘 포함 고르기) · 내 프로젝트(직접 · 이어받은 역할) · 이름 · 식별자 · 설명 찾기 · 공개 범위 · 프로젝트 사용자 정의 필드.
4. 보관한 프로젝트는 `project.archive` 를 가진 사람의 "보관함"에만 나와야 한다.
5. 목록은 이름순이고 쪽을 나눠야 한다.
6. MCP `list_projects` 는 같은 서비스로 같은 결과를 내야 한다.

**수용 기준**
- [ ] `RESTRICTED` 비독자에게 그 프로젝트가 목록 · 트리 · 찾기에 없다. 그 아래의 `WORKSPACE` 하위는 맨 위에 붙어 보이고, 숨긴 상위 이름이 응답에 없다
- [ ] 닫힌 프로젝트는 기본으로 숨고, "닫힘 포함"으로 보인다
- [ ] 보관한 프로젝트는 관리자의 보관함에만 나온다
- [ ] 같은 사람의 MCP `list_projects` 와 REST 목록이 같다

<a id="fr-prj-013"></a>
### FR-PRJ-013 프로젝트 개요 쪽

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §15 API](../design/04-project-permissions.md#pp-api) |

**설명** — 프로젝트의 첫 화면이다. Redmine 의 "개요"처럼 설명 · 홈페이지 · 트래커별 일감 수 · 멤버 · 하위 프로젝트 · 최근 뉴스 · 시간 합계를 한곳에 보인다.

**세부 요구사항**
1. 개요는 그 프로젝트의 독자 누구나 볼 수 있어야 한다.
2. 설명(Markdown) · 홈페이지 · 프로젝트 사용자 정의 필드 값을 보여야 한다.
3. 트래커별 일감 수(열림 · 닫힘 · 전체)는 **보는 사람의 보기 범위로** 세야 한다(못 보는 비공개 일감은 세지 않는다).
4. 멤버는 역할별로 보여야 한다(관리자 · 개발자 · 보고자는 이름, 독자는 수). Agent 계정은 "Agent" 표시를 한다.
5. 하위 프로젝트는 읽을 수 있는 것만 보여야 한다.
6. 뉴스 · 시간 칸은 그 모듈이 켜져 있고 코드가 있을 때만 보여야 한다([내용 요구사항](08-content.md) · [시간 요구사항](07-time.md)).
7. MCP `get_project` 는 같은 요약을 줘야 한다.

**수용 기준**
- [ ] 같은 프로젝트에서 보고자와 개발자의 일감 수가 비공개 일감만큼 다르다
- [ ] `time_tracking` 을 끄면 시간 칸이 없다
- [ ] 읽을 수 없는 하위 프로젝트는 개요에 없다
- [ ] 비독자는 404 다

## 4. 하위 프로젝트

<a id="fr-prj-014"></a>
### FR-PRJ-014 하위 프로젝트

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §8](../design/04-project-permissions.md#pp-subprojects) · [§8.1 트리](../design/04-project-permissions.md#pp-tree) |

**설명** — 프로젝트 아래에 프로젝트를 둔다(Redmine 의 하위 프로젝트). 상위의 관리자가 하위를 만들고, 하위는 기본으로 상위의 멤버를 이어받는다.

**세부 요구사항**
1. 상위는 같은 워크스페이스의 프로젝트여야 하고, 깊이는 1 ~ 10 이어야 한다.
2. 하위 만들기는 상위에서 `project.manage` 가 있어야 하고 상위가 활성이어야 한다. 워크스페이스 층 `project.create` 만으로는 하위를 만들 수 없어야 한다.
3. 새 하위의 기본값은 공개 범위 = 상위와 같음, 이어받기 = 켬, 모듈 · 트래커 = 상위와 같음이어야 한다.
4. 상위의 일감 목록은 설정에 따라 하위 프로젝트의 일감을 포함해야 한다([FR-QRY-007](05-query.md#fr-qry-007)).
5. 하위의 공개 범위는 상위와 따로 정할 수 있어야 한다.

**수용 기준**
- [ ] 상위의 개발자가 하위를 만들면 403, 관리자는 만들고 이어받기가 켜져 있다
- [ ] 깊이 11 이 되는 하위는 422 다
- [ ] 하위의 일감이 상위 목록에 나오고, "하위 포함"을 끄면 빠진다

<a id="fr-prj-015"></a>
### FR-PRJ-015 상위 프로젝트 바꾸기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §8.4](../design/04-project-permissions.md#pp-subprojects) |

**설명** — 프로젝트를 다른 상위 아래로(또는 맨 위로) 옮긴다. 이어받는 멤버 · 공유 버전 · 하위 일감 범위가 함께 바뀌므로 미리 보여 주고 검사한다.

**세부 요구사항**
1. 옮길 프로젝트의 `project.manage` 와, 새 상위의 `project.manage`(맨 위로 옮기면 워크스페이스 층 `project.create`)가 있어야 해야 한다.
2. 자기 · 자기 하위 아래로 옮길 수 없어야 하고, 옮긴 뒤 깊이가 10 을 넘지 않아야 한다.
3. 옮길 프로젝트와 새 상위가 활성이어야 한다.
4. 동시에 옮기기가 겹쳐 고리가 생기지 않게 워크스페이스마다 한 번에 하나만 처리해야 한다.
5. 화면은 저장 전에 이어받은 독자의 증감을 보여야 한다.
6. 더는 공유되지 않는 버전을 대상으로 한 일감의 대상 버전을 비워야 한다([버전 요구사항](06-planning.md)).
7. 하위 일감 범위 설정을 어기는 상위-하위 일감 쌍이 생기면 옮기기를 막고 목록을 보여야 한다.
8. 감사 `project.moved` 와 `project.updated` · `project.access.changed` 를 남겨야 한다.

**수용 기준**
- [ ] 자기 하위 아래로 옮기면 422 다
- [ ] 새 상위에서 권한이 없으면 403 이다
- [ ] 옮긴 직후 새 상위의 멤버가 이어받아 독자가 된다
- [ ] 하위 일감 범위를 어기면 거부되고 걸린 일감 번호가 나온다

<a id="fr-prj-016"></a>
### FR-PRJ-016 멤버 이어받기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §8.3](../design/04-project-permissions.md#pp-subprojects) · [§7 판정 규칙](../design/04-project-permissions.md#pp-rule) |

**설명** — 하위 프로젝트는 상위의 멤버와 역할을 이어받을 수 있다(`inherit_members`, Redmine 과 같다). 큰 팀을 상위에 한 번만 넣으면 하위마다 넣지 않아도 된다.

**세부 요구사항**
1. 이어받기를 켜면 상위의 실효 역할(상위가 이어받은 것 포함, 재귀)을 그대로 이어받아야 한다.
2. 직접 역할과 이어받은 역할이 겹치면 높은 것이어야 한다.
3. 이어받은 멤버는 하위에서 뺄 수 없어야 하고, 화면은 "상위에서 이어받음"을 보여야 한다.
4. 기본 역할([FR-PRJ-005](#fr-prj-005))은 이어받지 않아야 한다.
5. 이어받은 역할은 Keycloak 에 펼쳐 쓰지 않고 api 가 계산해야 한다.
6. 켜고 끌 때 독자 증감을 미리 보이고 감사 · `project.access.changed` 를 남겨야 한다.

**수용 기준**
- [ ] 상위의 보고자는 이어받기를 켠 하위에서 보고자이고, 끈 `RESTRICTED` 하위에서는 404 다
- [ ] 하위에 직접 개발자 + 상위 보고자면 하위에서 개발자다
- [ ] 하위에서 이어받은 멤버를 빼면 400 이다
- [ ] 상위에서 멤버를 빼면 하위에서도 다음 요청부터 빠진다(3단 트리에서도)

## 5. 상태 · 지우기 · 기본값 · 복사

<a id="fr-prj-017"></a>
### FR-PRJ-017 프로젝트 닫기 · 다시 열기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §10](../design/04-project-permissions.md#pp-status) |

**설명** — 끝난 프로젝트를 닫으면 읽기 전용이 된다(Redmine 의 "닫힌 프로젝트"). 기록은 그대로 보이고 새로 쓰지는 못한다.

**세부 요구사항**
1. 닫기 · 다시 열기는 `project.manage` 가 있어야 해야 한다.
2. 닫힌 프로젝트의 쓰기는 409 `PROJECT_READ_ONLY` 여야 한다. 다시 열기와 개인 일(나를 관찰자로 · 개인 질의 저장 · 내보내기)만 된다.
3. 닫으면 하위 프로젝트도 모두 닫고, 다시 열면 하위도 함께 열어야 한다. 상위가 닫혀 있으면 다시 열 수 없어야 한다.
4. 닫힌 프로젝트는 목록의 기본 거르기에서 빠져야 한다.
5. MCP 쓰기 도구도 같은 409 를 내야 한다.
6. 감사 `project.closed` · `project.reopened` 를 남겨야 한다.

**수용 기준**
- [ ] 닫힌 프로젝트의 일감 고치기는 REST · MCP 모두 409 이고, 보기는 된다
- [ ] 닫으면 하위도 닫힌다
- [ ] 상위가 닫힌 하위를 다시 열면 409 다
- [ ] 감사에 함께 바뀐 하위가 남는다

<a id="fr-prj-018"></a>
### FR-PRJ-018 프로젝트 보관 · 보관 풀기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §10](../design/04-project-permissions.md#pp-status) |

**설명** — 더는 쓰지 않는 프로젝트를 보관하면 관리자 외에는 보이지 않는다(Redmine 의 보관). 지우기 전 단계이기도 하다.

**세부 요구사항**
1. 보관 · 보관 풀기는 워크스페이스 층 `project.archive` 가 있어야 해야 한다(프로젝트 관리자는 할 수 없다).
2. 보관하면 하위 프로젝트도 모두 보관해야 한다.
3. 보관한 프로젝트는 `project.archive` 를 가진 사람만 보관함에서 읽기 전용으로 보고, 나머지에게는 404(MCP 포함)여야 한다. 검색에서 숨기고 텍스트 링크는 글자로만 보여야 한다.
4. 상위가 보관 상태면 보관을 풀 수 없어야 하고, 풀 때 하위도 함께 풀지 고를 수 있어야 한다.
5. 감사 `project.archived` · `project.unarchived` 를 남겨야 한다.

**수용 기준**
- [ ] 프로젝트 관리자가 보관하면 403 이다
- [ ] 보관한 뒤 그 프로젝트의 개발자에게 404 다
- [ ] 워크스페이스 관리자는 보관함에서 보고, 고치기는 409 다
- [ ] 상위가 보관된 하위의 보관을 풀면 409 다

<a id="fr-prj-019"></a>
### FR-PRJ-019 프로젝트 지우기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §10](../design/04-project-permissions.md#pp-status) |

**설명** — 보관한 프로젝트를 지운다. 되돌릴 수 없으므로 보관을 먼저 거치고 식별자를 다시 입력하게 한다. 데이터는 뒷일 작업이 차례로 지운다.

**세부 요구사항**
1. 지우기는 워크스페이스 층 `project.delete` 가 있어야 하고, 보관 상태에서만 해야 한다.
2. 하위 프로젝트 전체를 함께 지워야 하고, 사유와 식별자를 다시 입력받아야 한다(이중 확인).
3. 지우면 바로 모두에게 404 가 되고, 작업 큐가 일감 · 첨부(MinIO 객체) · 시간 기록 · 버전 · 위키 · 질의 · 바인딩 · Keycloak 그룹 · 검색 색인을 지운 뒤 프로젝트 행을 지워야 한다.
4. 지운 일감의 번호는 다시 쓰지 않아야 한다.
5. 감사 `project.deleted`(사유 · 지운 수)와 정리가 끝나면 `project.purged` 를 남겨야 한다.
6. MCP 로는 지울 수 없어야 한다.

**수용 기준**
- [ ] 보관하지 않은 프로젝트를 지우면 409 다
- [ ] 식별자를 틀리게 입력하면 400 이다
- [ ] 지운 직후 프로젝트 · 일감이 모두 404 다
- [ ] 정리가 끝나면 그 프로젝트의 MinIO 객체 · 검색 문서가 없고 감사 `project.purged` 가 남는다

<a id="fr-prj-020"></a>
### FR-PRJ-020 새 프로젝트 기본값

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §14](../design/04-project-permissions.md#pp-lifecycle) · [일감 설계 §10.5](../design/05-issue-tracking.md#is-settings) |

**설명** — 워크스페이스는 새 프로젝트의 기본 공개 범위 · 기본 모듈 · 기본 트래커를 정한다(Redmine 의 "새 프로젝트 기본값" 설정).

**세부 요구사항**
1. 설정은 기본 공개 범위 · 기본 모듈 · 기본 트래커(비면 모두)를 가져야 한다.
2. 바꾸기는 `config.manage` 가 있어야 해야 한다.
3. 만들기 화면은 이 값으로 미리 채워야 한다.
4. 바꿔도 이미 있는 프로젝트는 그대로여야 한다.
5. 바꾸기는 감사에 남아야 한다.

**수용 기준**
- [ ] 기본 모듈을 바꾸면 그 뒤 만든 프로젝트에 반영되고, 있던 프로젝트는 그대로다
- [ ] 멤버가 설정을 바꾸면 403 이다
- [ ] 감사에 전 · 후 값이 남는다

<a id="fr-prj-021"></a>
### FR-PRJ-021 프로젝트 복사 · 틀

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §14.3](../design/04-project-permissions.md#pp-copy) |

**설명** — 있는 프로젝트를 복사해 새 프로젝트를 만든다(Redmine 의 프로젝트 복사). 자주 쓰는 모양은 "틀"로 표시해 두고 거기서 만든다.

**세부 요구사항**
1. 원본을 읽을 수 있고 새 프로젝트를 만들 권한([FR-PRJ-001](#fr-prj-001))이 있어야 해야 한다.
2. 늘 복사하는 것(설정 · 모듈 · 트래커 · 사용자 정의 필드)과 고르는 것(멤버 · 버전 · 카테고리 · 일감 · 공개 질의 · 위키)을 나눠야 한다.
3. 일감은 복사하는 사람에게 보이는 것만 복사하고, 새 번호를 주며, 대상 버전 · 카테고리를 복사본으로 맞춰야 한다. 저널 · 시간 기록은 복사하지 않는다.
4. 큰 복사는 작업 큐로 돌리고 끝나면 알려야 한다. 중간에 실패하면 새 프로젝트를 보관 상태로 두고 빠진 것을 보여야 한다.
5. `is_template` 을 켠 프로젝트는 "틀에서 만들기"에 나와야 하고, 읽을 수 있는 틀만 보여야 한다.

**수용 기준**
- [ ] 비공개 일감을 못 보는 사람의 복사본에는 그 일감이 없다
- [ ] 복사본 일감의 대상 버전이 복사된 버전을 가리킨다
- [ ] 원본의 저널 · 시간 기록은 복사본에 없다
- [ ] 틀 고르기에 읽을 수 있는 틀만 나온다
