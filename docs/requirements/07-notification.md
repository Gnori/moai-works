# 알림 요구사항 (FR-NOTI)

사람에게 알려야 할 일을 그 사람의 **알림함**에 쌓고 화면에 보이는 요구사항이다. 사용자 지시(2026-11-22): "알림 시스템도 만들어야 해. 알림해야 할 게 뭔지 도출해 보고 만들어". 알림함의 모양 · 규칙은 moai-wiki 와 같다(같은 날 moai-wiki 가 먼저 만들었다). 알릴 일은 moai-works 의 기능(일감 · 작업 시간 · 프로젝트 역할 · MCP 키)에서 도출했다. 설계는 [알림 설계](../design/07-notification.md)에 있다.

| 우선순위 | 개수 | 요구사항 |
|---|---|---|
| M | 4 | [001](#fr-noti-001) · [002](#fr-noti-002) · [003](#fr-noti-003) · [005](#fr-noti-005) |
| S | 1 | [004](#fr-noti-004) |
| C | 1 | [006](#fr-noti-006) |
| 합계 | 6 | |

| 공통 | 내용 |
|---|---|
| 내 것만 | 알림은 받는 사람 한 사람의 것이다. 남의 알림은 어떤 값으로도 닿지 않는다(남의 알림 id 는 404) |
| 본문 없음 | 알림에는 제목 · 이름 · 번호 · 수 같은 값만 넣는다. 일감 설명 · 댓글 본문은 넣지 않는다. 눌러서 들어간 화면이 지금 권한으로 다시 판정한다 |
| 자기 일은 빼기 | 자기가 한 일은 자기에게 알리지 않는다 |
| 같은 트랜잭션 | 알림은 그 일을 하는 트랜잭션 안에서 쌓는다 — 일이 되돌려지면 알림도 없다 |
| 시스템 관리자 | 시스템 관리자 계정에는 알림함이 없다(워크스페이스가 없다 — `@UserApi` 기본 403) |
| 경로 | MCP 로 한 일도 웹으로 한 일과 같이 알린다. 알림의 값에 경로(`via`)가 있어 화면이 "(MCP)"를 붙인다 |

<a id="fr-noti-001"></a>
### FR-NOTI-001 알림함

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-22: api(V6 · 알림함 · 읽지 않은 수 · 읽음 · 모두 읽음 · 묶기 · 시각 + id 커서) · 화면(왼쪽 아래 종 · 수, 알림함 /notifications) · 자동 테스트 · ego-browser(데스크톱). 남은 것: 390px · 다크 · 영어 확인 |
| 관련 설계 | [알림 설계 §1 · §4](../design/07-notification.md#nt-inbox) |

**설명** — 사람마다 알림함 하나가 있다. 새 것부터 보이고, 읽지 않은 수를 화면이 늘 보인다. 같은 일감을 여러 번 고쳐도 읽지 않은 동안에는 알림 한 줄로 묶인다.

**세부 요구사항**
1. `GET /v1/me/notifications?unread=&before=&limit=` 는 내 알림을 새 것부터 한 쪽(최대 30)씩 준다. 다음 쪽 커서(`next`)는 마지막 줄의 시각과 id 로 만들어 같은 밀리초의 줄을 건너뛰지 않아야 한다.
2. `GET /v1/me/notifications/unread-count` 는 읽지 않은 수를 준다. 화면은 이것을 주기적으로 읽는다.
3. `POST /v1/me/notifications/{id}/read` 는 하나를, `POST /v1/me/notifications/read-all` 은 모두를 읽음으로 한다. 남의 알림 id 는 404 `NOTIFICATION_NOT_FOUND` 다.
4. 같은 사람 · 같은 종류 · 같은 대상의 읽지 않은 알림이 있으면 새로 만들지 않고 그 알림에 묶어(`count` + 1) 마지막 값 · 시각으로 바꾼다.
5. 알림 한 줄은 종류 · 대상 · 값 · 한 사람 이름 · 묶인 수 · 워크스페이스(주소 · 이름) · 처음 · 마지막 시각 · 읽은 시각을 준다.

**수용 기준**
- [x] 같은 일감을 세 번 고치면 읽지 않은 알림은 한 줄이고 `count` 가 3 이다 (자동 테스트 2026-11-22)
- [x] 남의 알림을 읽음으로 하면 404 다
- [x] 같은 밀리초에 쌓인 알림이 여럿이어도 더 보기로 모두 한 번씩 나온다
- [x] 시스템 관리자 계정의 알림함 요청은 403 이다
- [x] 화면의 읽지 않은 수가 새 알림이 생긴 뒤 1분 안에 바뀐다 (60초마다 다시 읽기 · 화면 테스트)

<a id="fr-noti-002"></a>
### FR-NOTI-002 무엇을 누구에게 알리는가

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-22: 종류 21개(워크스페이스 5 · 프로젝트 1 · 일감 11 · 작업 시간 2 · MCP 키 2 — 이 가운데 셋은 아침 알림 — FR-NOTI-003), 각 기능의 트랜잭션에 연결, 자동 테스트. 2026-11-25(일감 #272): 관리자 확인 셋 더해 24개(일감 14) — 확인 요청 · 확인 · 되돌림, 화면 문장 · 메일 글 두 언어, 자동 테스트. 2026-11-26(일감 #302): 긴급 하나 더해 25개(일감 15) — `issue.priority_urgent`, 화면 문장 · 메일 글 두 언어, 자동 테스트. 남은 것: 화면 문장 · 링크 |
| 관련 설계 | [알림 설계 §2](../design/07-notification.md#nt-kinds) |

**설명** — 알릴 일을 기능마다 도출했다(2026-11-22). 기준은 "그 사람이 다음에 무엇을 해야 하거나, 그 사람의 일 · 권한이 바뀌었는가"다. 받는 사람은 그 일의 관리자 · 담당자처럼 일에 묶인 사람과, 처리할 권한이 있는 사람이다.

**세부 요구사항**
1. 워크스페이스(moai-wiki 와 같다): 가입 신청 → 처리할 수 있는 사람(`member.request.review`), 승인 · 거절 → 신청한 사람, 역할 바뀜 → 그 멤버, 내보내짐 → 그 사람(스스로 나간 것은 알리지 않는다).
2. 프로젝트: 프로젝트 역할을 받거나 빠짐 → 그 멤버.
3. 일감:
   - 담당자로 정함 → 새 담당자, 담당자에서 빠짐 → 옛 담당자, 관리자로 정함 → 새 관리자(만들 때도).
   - 상태 바뀜 · 내용(제목 · 설명 · 날짜 · 유형 · 상위 · 예상 공수 · 우선순위) 바뀜 → 관리자 · 담당자. 같은 변경으로 담당 · 관리 알림을 받은 사람에게는 겹쳐 보내지 않는다.
   - 댓글 → 관리자 · 담당자 · 앞서 댓글을 단 사람.
   - 하위 일감이 생김(만들거나 옮겨 옴) → 상위의 관리자 · 담당자.
   - 연결됨 → 양쪽 일감의 관리자 · 담당자(상대 일감과 함께).
   - 지워짐 → 관리자 · 담당자.
   - 관리자 확인(2026-11-25, 일감 #272 — [FR-ISS-005](03-issue.md#fr-iss-005)): 확인요청으로 옮김 → 관리자(`issue.review_requested`), 확인완료로 옮김 → 담당자(`issue.review_confirmed`), 확인요청을 되돌림(반려 · 거둠) → 관리자 · 담당자(`issue.review_returned`). 이 알림을 받은 사람에게는 같은 옮김의 상태 바뀜을 겹쳐 보내지 않는다.
   - 긴급이 됨(2026-11-26, 일감 #302 — [FR-ISS-028](03-issue.md#fr-iss-028)): 긴급으로 만들거나 다른 우선순위에서 긴급으로 올림 → 관리자 · 담당자(`issue.priority_urgent`, 같은 사람이면 한 번). 이미 긴급이면 다시 보내지 않고, 우선순위 때문의 내용 바뀜은 겹쳐 보내지 않는다. 다른 우선순위 바뀜(보통 → 높음 등)은 내용 바뀜(`issue.updated`)이다.
4. 작업 시간: 다른 사람이 작업 시간을 적음 → 관리자. 쓴 시간이 예상 공수를 넘는 순간 한 번 → 관리자 · 담당자.
5. MCP 키: 다른 사람(관리자)이 내 키를 만료시킴 → 키 주인(이유와 함께). (2026-11-23 부터 키는 주인만 만료시키므로 이 알림은 더 생기지 않는다 — 종류는 옛 알림 · 설정 표시용으로 남긴다, [ADR-029](../design/00-key-decisions.md#adr-029))

**수용 기준**
- [x] 다른 사람이 나를 담당자로 정하면 `issue.assigned` 가 오고, 내가 만든 일감의 관리자인 나에게는 오지 않는다 (자동 테스트 2026-11-22)
- [x] 담당자를 바꾸면 새 담당자에게 `issue.assigned`, 옛 담당자에게 `issue.unassigned` 가 온다
- [x] 댓글은 관리자 · 담당자 · 앞서 댓글을 단 사람에게 가고, 쓴 사람에게는 가지 않는다
- [x] 예상 공수 4시간 일감에 3 · 2 · 1 시간을 적으면 `issue.over_estimate` 는 한 번만 온다
- [x] 확인요청은 관리자에게 `issue.review_requested`, 확인완료는 담당자에게 `issue.review_confirmed`, 반려는 `issue.review_returned` 로 오고, 그 사람에게 상태 바뀜은 겹쳐 오지 않는다 (`NotificationTest` 2026-11-25, 일감 #272)
- [x] 긴급이 되면 관리자 · 담당자에게 `issue.priority_urgent` 가 한 번 오고, 보통 → 높음이나 이미 긴급인 일감을 고치면 오지 않는다 (`NotificationTest` 2026-11-26, 일감 #302)
- [x] 가입 승인 · 역할 바뀜 · 프로젝트 역할 바뀜 · 내보내짐이 그 사람에게 오고, 스스로 나가면 오지 않는다
- [x] 관리자가 내 MCP 키를 만료시키면 이유와 함께 `mcp_key.expired` 가 온다 (2026-11-22. 2026-11-23 부터 관리자는 남의 키를 만료시킬 수 없어 이 알림은 생기지 않고, 스스로 만료시키면 알리지 않는다 — `NotificationTest.MCP_키는_주인만_만료시키고_스스로_한_일은_알리지_않는다`)
- [ ] MCP 로 고친 일감의 알림에 경로 `MCP` 가 보인다(MCP 쓰기 도구가 생기면)

<a id="fr-noti-003"></a>
### FR-NOTI-003 아침 알림 (기한 · 키 만료)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-22: `NotificationReminders`(매일 09:00 Asia/Seoul, DB 권고 잠금, 같은 값으로 두 번 보내지 않음), 자동 테스트. 남은 것: 운영에서 하루 지켜보기 |
| 관련 설계 | [알림 설계 §3](../design/07-notification.md#nt-reminders) |

**설명** — 시간이 지나서 생기는 일은 아무도 "하지" 않으므로 매일 아침 한 번 살핀다.

**세부 요구사항**
1. 완료 기한이 내일인 열린 일감(신규 · 진행) → 담당자 · 관리자(`issue.due_soon`).
2. 완료 기한이 지난 열린 일감(지난 7일 안) → 담당자 · 관리자(`issue.overdue`). 기한 날짜마다 한 번.
3. 7일 안에 만료되는 MCP 키(일찍 만료시키지 않은 것) → 키 주인(`mcp_key.expiring`). 키마다 한 번. 키는 사용자의 것이라 워크스페이스 없는 알림이다(2026-11-23).
4. 같은 대상 · 같은 값(기한 날짜 · 만료 시각)으로는 두 번 보내지 않는다. 여러 인스턴스가 함께 돌아도 한 곳만 돈다.
5. 사용 중지된 워크스페이스 · 보관한 프로젝트 · 지운 일감 · 완료 · 종료 일감은 건너뛴다.

**수용 기준**
- [x] 기한이 내일 · 그저께인 열린 일감과 3일 뒤 만료되는 키가 있을 때 한 번 돌리면 각각 한 번씩 오고, 두 번 돌려도 늘지 않는다 (자동 테스트 2026-11-22)
- [x] 완료한 일감은 기한이 지나도 오지 않는다

### FR-NOTI-004 알림 받기 설정

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 일부 — 2026-11-22: api · 화면(계정 메뉴 › 개인 설정 › 알림 설정 — 묶음별 켬 · 끔, 끌 수 없는 것은 잠금) · 자동 테스트 · ego-browser. 2026-11-23: 메일 열(FR-NOTI-006 — `PUT …/preferences/{kind}` `{enabled?, email?}`, 화면에 알림함 · 메일 두 열). 남은 것: 영어 확인, 메일 열의 브라우저 확인 |
| 관련 설계 | [알림 설계 §5](../design/07-notification.md#nt-preferences) |

**설명** — 사람마다 종류별로 알림을 끌 수 있다. 개인 설정(왼쪽 메뉴)의 "알림 설정"에서 고른다. 보안 · 접근이 사라지는 일은 끌 수 없다.

**세부 요구사항**
1. 기본은 모두 받는다. 끈 종류만 남긴다.
2. 꼭 받아야 하는 종류(`member.removed` · `mcp_key.expired` · `mcp_key.expiring`)를 끄면 400 `NOTIFICATION_MANDATORY` 다. 모르는 종류는 400 `UNKNOWN_NOTIFICATION_KIND` 다.
3. 끈 종류는 쌓지 않는다(나중에 켜도 그동안의 것은 없다).
4. 종류마다 메일 받기도 고른다(2026-11-23, [FR-NOTI-006](#fr-noti-006)). 알림함 · 메일 가운데 준 쪽만 바뀌고, 둘 다 없으면 400 `INVALID_PREFERENCE` 다. 메일은 꼭 받아야 하는 종류도 끌 수 있다.

**수용 기준**
- [x] `issue.assigned` 를 끄면 담당자로 정해져도 알림이 없고, 다시 켜면 온다 (자동 테스트 2026-11-22)
- [x] `mcp_key.expired` 를 끄면 400 이다
- [x] 개인 설정의 알림 설정 화면에서 묶음별로 켜고 끈다 (ego-browser 2026-11-22)

<a id="fr-noti-005"></a>
### FR-NOTI-005 알림 화면

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-22: 화면(종 · 읽지 않은 수 1분마다 · 창으로 돌아올 때, 알림함 탭 · 모두 읽음 · 더 보기, 누르면 읽음 + 그 화면, 종류 21 문장 · 링크, MCP 키 알림은 개인 설정 대화 상자로) · 화면 테스트 · ego-browser(데스크톱 — 알림을 눌러 프로젝트로 감). 남은 것: 390px · 다크 · 영어 |
| 관련 설계 | [알림 설계 §6](../design/07-notification.md#nt-screen) |

**설명** — 화면 어디서나 읽지 않은 알림 수가 보이고, 알림 하나를 누르면 그 일감 · 화면으로 간다.

**세부 요구사항**
1. 왼쪽 메뉴(계정 영역 근처)에 종 모양과 읽지 않은 수를 보인다. 1분마다, 그리고 창으로 돌아올 때 수를 다시 읽는다.
2. 알림함 화면(`/notifications`)은 전체 · 읽지 않음, 모두 읽음, 더 보기를 준다. 한 줄은 문장(누가 · 무엇을 · 「제목」) · 워크스페이스 · 묶인 수 · 시각(밀리초)이다.
3. 누르면 읽음으로 하고 그 일감(또는 가입 신청 · 워크스페이스 · 내 MCP 키 화면)으로 간다. 갈 곳이 없으면(내보내진 워크스페이스 · 지운 일감) 읽음으로만 한다.
4. 모르는 종류(화면보다 서버가 새 것)는 일반 문장으로 보인다.
5. 반응형(390px) · 다크 · 영어.

**수용 기준**
- [x] 다른 사람이 나를 담당자로 정하면 1분 안에 종 모양의 수가 오르고, 누르면 그 일감이 열리고 수가 내려간다 (프로젝트 역할 알림으로 ego-browser 2026-11-22 — 누르면 그 프로젝트로 가고 수가 5 → 4)
- [ ] 390px 에서 가로 넘침이 없다

<a id="fr-noti-006"></a>
### FR-NOTI-006 메일 알림

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 일부 — 2026-11-23(일감 #10): api(V18 — 설정의 메일 열 · 보낼 통 `notification_mail`, `NotificationMailSender` 30초마다 · 한 줄씩 잠금 · 보낼 때 다시 판정 · 다시 보내기 다섯 번 · 로그 모드 한 줄, `Mailer` smtp 모드) · 화면(알림 설정에 메일 열, 한국어 · 영어) · 자동 테스트. 남은 것: 화면 브라우저 확인(데스크톱 · 390px · 다크 · 영어), 실제 api 에서 로그 한 줄 확인, SMTP 서버 · 보내는 주소(WBS 결정 D-06) |
| 관련 설계 | [알림 설계 §8](../design/07-notification.md#nt-mail) · [§5 받기 설정](../design/07-notification.md#nt-preferences) |

**설명** — 알림함의 알림을 메일로도 보낸다. SMTP 가 정해질 때까지는 로그 모드다(WBS 결정 D-06). smtp 모드는 만들어 두었지만 아직 어디서도 켜지 않았다.

**세부 요구사항**
1. 사람마다 종류별로 메일 받기를 고른다(알림 받기 설정에 메일 열). 기본은 아침 알림(기한 임박 · 기한 지남 · MCP 키 만료 예정)만 켜고 나머지는 끈다. 알림함을 끈 종류는 메일도 가지 않는다.
2. 보낼 때 받는 사람의 권한을 다시 판정한다 — 지금도 활성 계정 · 활성 멤버이고 그 대상을 볼 수 있어야 한다(알림함 · 화면과 같은 판정). 아니면 보내지 않고 까닭을 남긴다.
3. 메일은 알림이 새로 생길 때 한 번이다 — 알림을 쌓는 트랜잭션 안에서 보낼 통에 넣고, 정해진 주기의 보내기가 한 줄씩 잠그고 보낸다. 죽어도 잃지 않고, 여럿이 돌아도 겹쳐 보내지 않는다. 보내지 못하면 늦춰 가며 다시 보내고, 다섯 번째에도 못 하면 실패로 둔다.
4. 본문은 글자만 — 무슨 일인지 · 그 화면 링크 · 받는 까닭. 일감 설명 · 댓글 본문은 싣지 않는다. 언어는 받는 사람의 언어 설정이 있으면 그것, 없으면 한국어.
5. 로그 모드는 보내지 않고 가린 받는 사람 · 종류 · 제목 한 줄만 남긴다(본문 · 주소 없음). smtp 모드의 서버 · 계정은 env 로만 넣고, 평문 SMTP 는 쓰지 않는다.

**수용 기준**
- [x] 메일을 켠 종류의 알림이 생기면 메일(로그 모드에서는 로그)이 한 번 나간다 (자동 테스트 2026-11-23 — `NotificationMailTest`)
- [x] 기본은 아침 알림만 메일이 가고, 켠 종류만 가며, 알림함을 끈 종류는 메일 설정이 켜져 있어도 가지 않는다 (`메일을_켠_종류만_한_통씩_가고_기본은_아침_알림만_켜져_있다`)
- [x] 보내기 전에 내보내지거나 · 메일을 끄거나 · 일감이 지워지면 보내지 않고 `SKIPPED` 와 까닭이 남는다 (`보낼_때_다시_판정해서_볼_수_없게_된_사람에게는_보내지_않는다`)
- [x] 같은 일감을 여러 번 고쳐도 메일은 한 통이고, 두 곳이 함께 보내도 한 줄은 한 번만 나간다 (`알림_하나에_메일은_한_번만_가고_여럿이_함께_보내도_겹치지_않는다` — 잠금을 빼면 6통이 나가 실패하는 것을 확인)
- [x] 로그 모드는 가린 주소 · 종류 · 제목 한 줄만 남기고, 메일 본문에 댓글이 없다. 언어가 영어면 영어로 간다 (`로그_모드는_가린_주소와_종류와_제목_한_줄만_남기고_본문에는_댓글을_싣지_않는다`)
- [x] 보내지 못하면 1분 뒤에 다시 보내고, 다섯 번째에도 못 하면 `FAILED` 로 두고 더 집지 않는다 (`보내지_못하면_나중에_다시_보내고_다_쓰면_실패로_둔다`)
- [ ] 개인 설정 › 알림 설정에서 종류마다 메일을 켜고 끈다 — 데스크톱 · 390px · 다크 · 영어 (화면 테스트만 — 브라우저 확인 전)
- [ ] 실제 api(로그 모드)에서 메일을 켠 종류의 알림이 생기면 30초 안에 로그 한 줄이 남는다
