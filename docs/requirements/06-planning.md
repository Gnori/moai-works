# 버전 · 로드맵 · 간트 · 캘린더 요구사항 (FR-PLN)

일감을 버전(릴리스)으로 묶고, 로드맵 · 간트 · 캘린더로 일정과 진척을 보는 기능의 요구사항이다. Redmine 의 버전 상태 · 공유 범위 · 로드맵 진척 계산 · 간트 막대 규칙을 따른다. 설계는 [계획 · 시간 설계](../design/06-planning-time.md)에 있다.

| 공통 | 내용 |
|---|---|
| 권한 검사 | api 가 요청마다 판정한다(`@ProjectApi`). 프로젝트 독자가 아니거나 모듈이 꺼져 있으면 404, 권한 코드가 없으면 403. 화면은 숨기기만 한다([프로젝트 요구사항](02-project.md)). 닫힌 프로젝트의 쓰기는 409 `PROJECT_READ_ONLY` |
| 권한 코드 | 보기 `issue.read`(모듈 `issue_tracking` · `gantt` · `calendar`), 버전 관리 `version.manage` |
| 보는 사람 기준 | 진척 · 일감 수 · 간트 · 캘린더는 보는 사람이 읽을 수 있는 일감만 센다(비공개 일감 규칙은 [일감 요구사항](03-issue.md)) |

| MCP 동등성 | `list_versions` · `get_roadmap` 은 REST 와 같은 서비스 · 같은 판정을 부른다([MCP 요구사항](12-mcp.md)) |
| 질의 | 간트 · 캘린더의 거르기는 일감 질의와 같다([질의 요구사항](05-query.md)) |

<a id="fr-pln-001"></a>
### FR-PLN-001 버전 만들기 · 고치기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §3](../design/06-planning-time.md#pt-version) · [§11.2 SQL](../design/06-planning-time.md#pt-ddl) |

**설명** — 버전은 일감을 내보낼 묶음(릴리스 · 스프린트)이다. 이름 · 설명 · 기한 · 위키 쪽 · 사용자 정의 필드를 가진다. 프로젝트 설정의 "버전" 탭과 로드맵에서 만든다.

**세부 요구사항**
1. 시스템은 `version.manage` 를 가진 사람이 버전을 만들고 고칠 수 있게 해야 한다.
2. 이름은 프로젝트 안에서 대소문자를 무시하고 겹치지 않아야 하고 60자를 넘지 않아야 한다.
3. 필드는 이름 · 설명(1000자) · 기한(날짜, 선택) · 상태 · 공유 범위 · 위키 쪽 이름(선택) · 버전 대상 사용자 정의 필드여야 한다.
4. 위키 쪽 이름은 같은 프로젝트 위키의 쪽을 가리키고, 그 쪽이 아직 없어도 저장되어야 한다.
5. 고치기는 낙관적 잠금(`row_version`)을 지켜야 한다.

**수용 기준**
- [ ] 같은 프로젝트에 대소문자만 다른 이름으로 만들면 409 다
- [ ] `version.manage` 없이 만들면 403, 독자가 아닌 프로젝트에 만들면 404 다
- [ ] 만들기 · 고치기가 감사에 행위자 · 경로와 함께 남는다
- [ ] 다른 사람이 먼저 고친 버전을 옛 `row_version` 으로 저장하면 409 다

<a id="fr-pln-002"></a>
### FR-PLN-002 버전 상태 (열림 · 잠김 · 닫힘)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §3.2](../design/06-planning-time.md#pt-version-status) |

**설명** — Redmine 과 같이 버전은 열림 · 잠김 · 닫힘 세 상태를 가진다. 잠김과 닫힘은 새 일감을 받지 않는다. 닫힌 버전은 로드맵에서 기본으로 숨긴다.

**세부 요구사항**
1. 열림 버전에만 새 일감을 넣을 수 있어야 한다.
2. 잠김 · 닫힘 버전에 일감을 새로 넣으려 하면 일감 저장이 422(필드 오류)여야 한다. 이미 그 버전인 일감의 다른 필드 고치기는 막지 않아야 한다.
3. 대상 버전 고르기 목록에는 열림 버전과 그 일감의 지금 값만 나와야 한다.
4. 열린 일감이 남은 버전을 닫을 때는 막지 않고 남은 수를 경고하고, 다음 버전으로 옮기기(일괄 수정)로 안내해야 한다.
5. 늦음(기한 지남 ∧ 열린 일감 있음) · 일정보다 늦음 · 완료됨을 계산해 보여야 한다.

**수용 기준**
- [ ] 잠김 버전에 새 일감을 넣으면 422, 이미 묶인 일감의 제목 고치기는 된다
- [ ] 닫힘 버전은 다른 일감의 고르기 목록에 나오지 않는다
- [ ] 열린 일감 3개가 남은 버전을 닫으면 경고에 3이 보이고, 닫기는 된다
- [ ] 상태 바꾸기가 감사와 이벤트 `version.updated` 에 남는다

<a id="fr-pln-003"></a>
### FR-PLN-003 버전 공유 범위

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §4](../design/06-planning-time.md#pt-sharing) |

**설명** — 하위 프로젝트가 있는 팀은 한 버전을 여러 프로젝트가 함께 쓴다. Redmine 의 공유 범위 다섯 가지(없음 · 하위 프로젝트 · 계층 · 트리 · 시스템)를 두되, 시스템은 워크스페이스로 바꾼다.

**세부 요구사항**
1. 공유 범위는 `NONE` · `DESCENDANTS` · `HIERARCHY` · `TREE` · `WORKSPACE` 여야 하고, 각각 쓸 수 있는 프로젝트가 설계와 같아야 한다.
2. `HIERARCHY` · `TREE` 로 바꾸려면 루트 프로젝트에서 `version.manage`, `WORKSPACE` 로 바꾸려면 워크스페이스 역할로 `version.manage` 가 있어야 한다.
3. 공유받은 프로젝트의 독자에게 버전 이름 · 기한 · 상태가 보여야 하고, 원래 프로젝트를 읽을 수 없으면 그 이름 대신 "다른 프로젝트"로 보여야 한다.
4. 공유 범위를 좁히거나 프로젝트 트리가 바뀌어 더는 쓸 수 없게 된 일감의 대상 버전은 비우고, 일감마다 이력을 남겨야 한다.
5. 저장 전에 비워질 일감 수를 미리 보여 주고 확인을 받아야 한다.

**수용 기준**
- [ ] 다섯 값마다 하위 · 상위 · 형제 프로젝트의 고르기 목록이 설계 표와 같다
- [ ] 루트 권한 없이 `TREE` 로 바꾸면 403, 프로젝트 관리자만으로 `WORKSPACE` 로 바꾸면 403 이다
- [ ] `TREE` → `NONE` 으로 바꾸면 다른 프로젝트 일감의 대상 버전이 비고, 그 일감 이력에 바꾼 사람이 남는다
- [ ] 원래 프로젝트를 못 읽는 사람의 응답에 그 프로젝트 이름 · 식별자가 없다

<a id="fr-pln-004"></a>
### FR-PLN-004 대상 버전 고르기 규칙

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §4.3](../design/06-planning-time.md#pt-assignable) |

**설명** — 일감의 대상 버전으로 무엇을 고를 수 있는지를 정한다. 화면 목록과 저장 검사가 같은 규칙을 써야 한다. 일감 필드 자체는 [일감 요구사항](03-issue.md)에 있다.

**세부 요구사항**
1. 고를 수 있는 버전은 그 일감의 프로젝트에 공유된 열림 버전 + 그 일감의 지금 값이어야 한다.
2. 일감 저장(웹 · REST · MCP · 메일 · 일괄 수정 · 가져오기) 때 서비스가 이 규칙을 다시 검사해야 한다.
3. 보관한 프로젝트의 버전은 고를 수 없어야 한다.
4. 일감을 다른 프로젝트로 옮길 때 새 프로젝트에서 쓸 수 없는 버전이면 대상 버전을 비우고 이력에 남겨야 한다.

**수용 기준**
- [ ] 공유되지 않은 다른 프로젝트 버전 id 를 REST 로 넣으면 422 다
- [ ] MCP `update_issue` 로 넣어도 같은 422 다
- [ ] 일감을 옮기면 쓸 수 없게 된 대상 버전이 비고 이력에 남는다

<a id="fr-pln-005"></a>
### FR-PLN-005 기본 버전

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §3.1](../design/06-planning-time.md#pt-version) |

**설명** — 프로젝트마다 기본 버전을 정해 두면, 새 일감에 대상 버전을 주지 않을 때 그 버전이 들어간다(Redmine 과 같다).

**세부 요구사항**
1. `project.manage` 를 가진 사람이 프로젝트 설정에서 기본 버전을 고를 수 있어야 한다. 고를 수 있는 것은 그 프로젝트에 공유된 열림 버전이다.
2. 새 일감에 대상 버전이 없고 기본 버전이 열림이면 기본 버전을 넣어야 한다. 잠김 · 닫힘이면 넣지 않아야 한다.
3. 기본 버전을 지우면 기본 버전 설정이 비어야 한다.

**수용 기준**
- [ ] 기본 버전이 있는 프로젝트에서 대상 버전 없이 만든 일감에 기본 버전이 들어간다(MCP `create_issue` 도 같다)
- [ ] 기본 버전을 닫으면 새 일감에 들어가지 않는다
- [ ] 설정 바꾸기가 감사에 남는다

<a id="fr-pln-006"></a>
### FR-PLN-006 버전 지우기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §3.3](../design/06-planning-time.md#pt-version-delete) |

**설명** — 잘못 만든 버전은 지운다. 일감이나 파일이 묶여 있으면 지울 수 없다(Redmine 과 같다). 대신 닫기를 권한다.

**세부 요구사항**
1. `version.manage` 를 가진 사람만 지울 수 있어야 한다.
2. 일감(공유받은 다른 프로젝트 일감 포함)이 하나라도 묶여 있으면 409 와 묶인 수를 돌려줘야 한다. 보는 사람이 그 일감을 못 읽어도 수는 센다.
3. 내려받기 파일이 묶여 있어도 지울 수 없어야 한다.
4. 지운 버전의 이름 · 기한 · 상태를 감사에 남겨야 한다.

**수용 기준**
- [ ] 일감이 묶인 버전을 지우면 409 이고 버전이 그대로 있다
- [ ] 묶인 것이 없는 버전은 지워지고 감사에 남는다
- [ ] `version.manage` 없이 지우면 403 이다

<a id="fr-pln-007"></a>
### FR-PLN-007 로드맵 화면

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §5.1](../design/06-planning-time.md#pt-roadmap) |

**설명** — 로드맵은 프로젝트의 버전들을 기한순으로 늘어놓고 버전마다 진척과 일감 목록을 보인다. 완료된 버전은 기본으로 숨긴다.

**세부 요구사항**
1. 프로젝트에 공유된 모든 버전(자기 것 + 공유받은 것)을 보여야 하고, "하위 프로젝트 포함"을 켜면 하위 프로젝트 버전도 보여야 한다.
2. 완료된 버전(닫힘이거나, 기한이 지났고 열린 일감이 없음)은 기본으로 숨기고 "완료 버전 보기"로 보여야 한다.
3. 정렬은 기한 오름차순, 기한 없는 버전은 뒤, 같으면 이름순이어야 한다.
4. 트래커 거르기의 기본은 "로드맵에 보이기"가 켜진 트래커여야 하고, 고른 트래커가 진척 계산에도 쓰여야 한다.
5. 버전마다 이름 · 기한(남은 날 · 늦음) · 설명 · 진척 막대 · 일감 수(닫힘 · 열림) · 고른 트래커의 일감 목록 · 위키 쪽 링크를 보여야 한다.
6. 390px 화면에서도 버전 카드가 한 줄로 읽혀야 한다.

**수용 기준**
- [ ] 닫힌 버전이 기본으로 안 보이고 "완료 버전 보기"를 켜면 보인다
- [ ] 기한 없는 버전이 기한 있는 버전 뒤에 나온다
- [ ] 트래커 하나를 끄면 그 트래커 일감이 목록 · 진척에서 빠진다
- [ ] 독자가 아닌 프로젝트의 로드맵은 404, `issue_tracking` 모듈이 꺼져 있으면 404 다

<a id="fr-pln-008"></a>
### FR-PLN-008 로드맵 진척 계산

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §5.2](../design/06-planning-time.md#pt-progress) · [§5.5 Redmine 과 다른 점](../design/06-planning-time.md#pt-redmine-diff) |

**설명** — 진척은 예상 시간으로 가중한 완료율과 닫힌 일감 비율 두 가지다. Redmine 의 `completed_percent` · `closed_percent` 와 같은 식을 쓰되, 상위 일감은 빼서 두 번 세지 않는다.

**세부 요구사항**
1. 대상은 보는 사람이 읽을 수 있고, 고른 트래커이고, 하위 일감이 없는 일감이어야 한다.
2. 가중은 예상 시간이 있으면 그 값, 없으면 예상이 있는 일감들의 평균(그런 일감이 없으면 1)이어야 한다.
3. 닫힘 비율 = 닫힌 일감 가중 합 × 100 / 가중 합, 완료율 = Σ(가중 × 진척) / 가중 합이어야 한다. 닫힌 일감의 진척은 100 이다.
4. 일감이 없으면 둘 다 0, 열린 일감이 없으면 완료율 100 이어야 한다.
5. 진척률은 일감 설정(필드 또는 상태로 정함)이 정한 값을 써야 한다.
6. 계산은 버전 수와 상관없이 일정한 질의 수로 해야 한다.

**수용 기준**
- [ ] 설계의 보기(예상 8 · 4 · 없음 · 없음)에서 닫힘 비율 58.3%, 완료율 66.7% 다
- [ ] 예상이 하나도 없으면 일감 수 기준 비율과 같다
- [ ] 상위 일감과 그 하위가 같은 버전에 있어도 가중에 상위가 들어가지 않는다
- [ ] 비공개 일감이 있는 버전에서 볼 수 있는 사람과 없는 사람의 일감 수가 다르게 나온다

<a id="fr-pln-009"></a>
### FR-PLN-009 버전 쪽

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §5.4](../design/06-planning-time.md#pt-version-page) |

**설명** — 버전 하나의 상세 쪽이다. 진척 · 예상 대 소요 시간 · 묶음별 수 · 일감 목록 · 연결한 위키 쪽 본문을 한곳에서 본다.

**세부 요구사항**
1. 머리에 이름 · 상태 · 기한(늦음 · 일정보다 늦음) · 공유 범위 · 원래 프로젝트를 보여야 한다.
2. 예상 합계(잎 일감의 예상 합)와 소요 합계(묶인 일감의 시간 기록 합)를 보여야 한다. 소요는 `time.read` 가 있고 `time_tracking` 모듈이 켜진 프로젝트 것만 센다.
3. 상태 · 트래커 · 우선순위 · 카테고리 · 담당자 중 하나로 묶은 일감 수를 막대로 보이고, 누르면 그 조건의 일감 목록으로 가야 한다.
4. 연결한 위키 쪽은 보는 사람이 그 쪽을 읽을 수 있을 때만 본문을 보여야 한다.
5. 버전을 쓸 수 있는 프로젝트 중 하나라도 읽을 수 있으면 열리고, 아니면 404 여야 한다.

**수용 기준**
- [ ] 묶음 막대를 누르면 같은 수의 일감 목록이 나온다
- [ ] `time.read` 가 없는 사람에게 소요 합계가 보이지 않는다
- [ ] 위키 모듈이 꺼진 프로젝트의 버전 쪽에는 위키 본문이 없다
- [ ] 어느 쪽도 읽을 수 없는 사람이 버전 id 로 열면 404 다

<a id="fr-pln-010"></a>
### FR-PLN-010 간트 차트

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §6](../design/06-planning-time.md#pt-gantt) |

**설명** — 일감 · 버전 · 프로젝트를 기간 막대로 보인다. Redmine 간트처럼 왼쪽에 줄 목록과 고른 열, 오른쪽에 막대와 진척을 그린다.

**세부 요구사항**
1. 줄은 프로젝트 → 버전 → 일감(하위 일감은 들여쓰기) 트리여야 한다.
2. 막대 규칙: 일감은 시작일 ~ 기한(없으면 대상 버전 기한), 상위 일감은 하위의 처음 ~ 끝, 버전은 시작일 ~ 기한, 프로젝트는 안의 처음 ~ 끝이어야 한다. 한쪽만 있으면 하루 막대, 둘 다 없으면 막대 없이 목록에만 나와야 한다.
3. 진척은 완료 칸(초록) · 늦음 칸(빨강, 오늘까지 못 한 몫) · 나머지로 칠해야 한다. 닫힌 일감은 100 이다.
4. 거르기는 일감 질의와 같아야 하고 저장한 질의를 간트로 열 수 있어야 한다.
5. 기간은 시작 월 + 개월 수(1~24), 확대는 월 · 주 · 일 단계, 오늘 선을 그려야 한다.
6. 줄은 500개(설정)까지만 주고, 넘으면 거르기를 좁히라고 알려야 한다.
7. 고른 열(제목 · 상태 · 우선순위 · 담당자 · 진척률 · 시작 · 기한 · 예상)을 왼쪽에 보일 수 있어야 한다.

**수용 기준**
- [ ] 시작 · 기한이 비어 있는 네 경우의 막대가 설계와 같다
- [ ] 진척 30% 인 일감의 늦음 칸이 설계 식대로 그려진다
- [ ] 줄이 500개를 넘으면 500개와 "더 있다" 표시가 나온다
- [ ] 비공개 일감은 볼 수 없는 사람의 간트에 없다. `gantt` 모듈이 꺼지면 404 다

<a id="fr-pln-011"></a>
### FR-PLN-011 간트 관계 화살표 · 진척선

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §6.2 · §6.3](../design/06-planning-time.md#pt-gantt) |

**설명** — 일감 관계(선행 · 막음)를 막대 사이 화살표로, 일정 대비 진척을 진척선으로 보여 늦어지는 줄을 바로 알게 한다.

**세부 요구사항**
1. 선행/후행은 앞 막대 끝 → 뒤 막대 시작 파란 화살표, 막음/막힘은 빨간 화살표로 그려야 한다. 관련 · 중복 · 복사는 그리지 않는다.
2. 양쪽 일감이 모두 지금 줄 목록에 있을 때만 그려야 한다.
3. 진척선(일감마다 완료점을 이은 선)을 켜고 끌 수 있어야 한다(기본 끔).
4. 관계 화살표 그리기를 켜고 끌 수 있어야 한다(기본 켬).

**수용 기준**
- [ ] 선행 관계 일감 둘이 보이면 화살표가 하나 그려진다
- [ ] 한쪽이 거르기로 빠지거나 볼 수 없으면 화살표가 없다
- [ ] 진척선을 켜면 늦은 일감의 점이 오늘 선 왼쪽에 놓인다

### FR-PLN-013 캘린더 (월 · 주)

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §7](../design/06-planning-time.md#pt-calendar) |

**설명** — 일감의 시작일 · 기한과 버전 기한을 달력에 표시한다. Redmine 의 월 캘린더에 주 보기를 더한다.

**세부 요구사항**
1. 월 보기(기본)와 주 보기, 이전 · 다음 · 오늘 이동이 있어야 한다.
2. 일감 시작일(시작 표시) · 기한(기한 표시) · 같은 날(둘 다 표시) · 버전 기한(깃발)을 보여야 한다.
3. 거르기는 일감 질의와 같고 저장한 질의를 캘린더로 열 수 있어야 한다.
4. 주 시작 요일은 사용자 설정 → 워크스페이스 설정(기본 월요일)을 따라야 한다.
5. 한 날짜에 10개가 넘으면 "+N 더 보기"로 접어야 한다.

**수용 기준**
- [ ] 시작과 기한이 같은 일감이 한 번만 "둘 다" 표시로 나온다
- [ ] 버전 기한이 그 날짜에 깃발로 나온다
- [ ] 주 시작을 일요일로 바꾸면 달력 첫 칸이 일요일이다
- [ ] `calendar` 모듈이 꺼지면 404, 볼 수 없는 일감은 나오지 않는다

### FR-PLN-014 MCP 로 버전 · 로드맵 보기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [계획 설계 §13](../design/06-planning-time.md#pt-mcp) |

**설명** — 바깥 Agent 가 "다음 릴리스에 무엇이 남았나"를 물을 수 있게 버전 목록과 로드맵을 MCP 도구로 연다.

**세부 요구사항**
1. `list_versions` 는 프로젝트 · 상태 · 공유받은 것 포함 여부 · 커서 · 개수를 받아 버전마다 상태 · 공유 범위 · 기한 · 닫힘 비율 · 완료율 · 일감 수를 돌려줘야 한다.
2. `get_roadmap` 은 트래커 · 완료 버전 포함 · 하위 프로젝트 포함 · 버전당 일감 수(최대 100)를 받아 화면 로드맵과 같은 순서 · 같은 숫자를 돌려줘야 한다.
3. 진척과 일감 목록은 키 주체(사람 또는 Agent 계정)가 읽을 수 있는 일감만으로 계산하고, 엔드포인트 대상 프로젝트로 한 번 더 좁혀야 한다.
4. 결과는 Markdown `content` 와 `structuredContent` 둘 다여야 한다.

**수용 기준**
- [ ] 같은 사람의 개인 키로 부른 `get_roadmap` 의 진척이 화면 로드맵과 같다
- [ ] 엔드포인트 대상이 아닌 프로젝트를 넘기면 화면의 404 와 같은 오류다
- [ ] Agent 계정이 역할이 없는 RESTRICTED 프로젝트 버전을 볼 수 없다
