# 비기능 요구사항 (NFR)

성능 · 규모 · 보안 · 가용성 · 관측 · 품질 · 운영 · 언어 · 사용성 요구사항이다. 숫자는 첫 출시 목표이고, 운영 배치가 정해지면([정해야 할 것](../wbs/08-decisions.md)) 다시 본다. 2026-11-22 재정리 때 `13-non-functional.md` 에서 옮겼다 — ID 와 진행은 그대로이고, [나중 후보](00-overview.md#7-나중-후보) 기능(첨부 · 활동 · 알림 · 검색 · 작업 큐 · 간트 · 보드)과 폐기한 Agent 계정에 걸린 문장만 뺐다. 이 영역에서 통째로 뺀 요구사항은 없다(12개 모두 첫 출시 범위에 걸린다).

| 공통 | 내용 |
|---|---|
| 측정 | 로컬 같이 쓰는 컨테이너가 아니라 운영과 같은 구성에서 잰다(6단계 규모 시험, [테스트 전략 §5](../plan/02-test-strategy.md#ts-data)) |
| 분류 | `PERF` 성능 · `SCL` 규모 · `SEC` 보안 · `AVL` 가용성 · `OBS` 관측 · `QLT` 품질 · `MNT` 유지보수 · `DEP` 배포 · `I18N` 언어 · `USA` 사용성 |

<a id="nfr-perf-001"></a>
### NFR-PERF-001 화면 · REST 응답 시간

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [아키텍처](../design/01-architecture.md) |

**설명** — 사람이 쓰는 화면이 기다림 없이 움직여야 한다.

**세부 요구사항**
1. 일감 보기 · 고치기 · 댓글 달기 REST 는 p95 300ms 이내여야 한다.
2. 일감 목록(필터 3개 · 50건 · 일감 10만 건 프로젝트)은 p95 800ms 이내여야 한다.
3. 화면 첫 로드(캐시 없음)의 스크립트는 경로 단위로 나눠 첫 번들을 1MB 이하로 유지해야 한다.

**수용 기준**
- [ ] 규모 시험 데이터에서 위 p95 를 잰 결과가 기준 안이다
- [ ] 빌드 결과의 첫 번들 크기가 기준 안이다

<a id="nfr-perf-002"></a>
### NFR-PERF-002 MCP 도구 응답 시간

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [MCP 설계](../design/06-mcp.md) |

**설명** — Agent 는 도구를 여러 번 연달아 부른다. 도구 하나가 느리면 Agent 작업 전체가 느려진다.

**세부 요구사항**
1. 읽기 도구(`get_issue` · `search_issues` 50건)는 p95 500ms, 쓰기 도구는 p95 600ms 이내여야 한다.
2. 한 응답의 크기는 기본 상한(본문 64KB, [FR-MCP-007](04-mcp.md#fr-mcp-007))을 넘지 않고, 넘으면 잘라서 이어 받기 커서를 줘야 한다.

**수용 기준**
- [ ] 규모 시험 데이터에서 도구별 p95 가 기준 안이다
- [ ] 큰 일감(댓글 500개)을 읽으면 잘린 응답과 이어 받기 커서가 온다

**수용 기준**
- [ ] 규모 시험 보고서가 있고 병목과 대응이 적혀 있다

<a id="nfr-sec-001"></a>
### NFR-SEC-001 경계 누출 0

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 설계](../design/04-project.md) · [SECURITY.md](../../SECURITY.md) |

**설명** — 워크스페이스 · 프로젝트의 경계를 넘는 읽기가 하나도 없어야 한다.

**세부 요구사항**
1. 모든 읽기 경로(프로젝트 목록 · 일감 목록 · 보기 · 하위 · 연결 · 이력 · 감사 · MCP)는 같은 판정 함수([FR-PRJ-006](02-project.md#fr-prj-006))를 거쳐야 한다.
2. 경계 회귀 테스트가 `./mvnw package` 에서 돌아야 한다.

**수용 기준**
- [ ] 읽기 경로마다 "다른 워크스페이스 · 독자 아님" 경계 테스트가 있다
- [ ] 일감의 하위 · 연결 목록과 MCP 결과에서도 같은 경계가 지켜진다

<a id="nfr-sec-002"></a>
### NFR-SEC-002 Agent 의 한계

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [MCP 설계](../design/06-mcp.md) |

**설명** — Agent 는 실수하거나 본문 속 지시(프롬프트 주입)에 속을 수 있다. 피해 범위를 작게 둔다.

**세부 요구사항**
1. MCP 로는 삭제 · 일괄 수정 · 멤버/권한/설정 변경을 할 수 없어야 한다.
2. 키 · 엔드포인트별 속도 제한이 있어야 한다.
3. Agent 가 한 모든 변경은 사람이 화면에서 찾아 되돌릴 수 있어야 한다(이력에 주체 · 경로가 있다).

**수용 기준**
- [ ] 삭제 · 일괄 · 설정 도구가 `tools/list` 에 없다
- [ ] 한도를 넘으면 429 와 다시 시도할 시간이 온다
- [ ] 이력에서 경로 = MCP 인 줄을 거를 수 있다

<a id="nfr-avl-001"></a>
### NFR-AVL-001 가용성

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [아키텍처 §7](../design/01-architecture.md#ar-deploy) |

**설명** — api · web-backend 는 여러 인스턴스로 돌 수 있어야 하고, Keycloak 이 잠깐 멈춰도 이미 로그인한 사람은 계속 일할 수 있어야 한다.

**세부 요구사항**
1. api 는 무상태여야 한다(세션 없음, MCP 무상태). 판정은 DB 사본으로 해서 Keycloak 장애가 읽기 장애가 되지 않아야 한다.
2. web-backend 세션은 Redis 에 두어 인스턴스가 바뀌어도 이어져야 한다.
3. 월 가용성 목표 99.5%(운영 배치가 정해지면 다시 본다).

**수용 기준**
- [ ] api 두 인스턴스 사이를 오가는 요청이 모두 성공한다
- [ ] Keycloak 을 멈춘 동안 이미 받은 토큰으로 일감을 읽고 고칠 수 있다

### NFR-OBS-001 관측

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [아키텍처](../design/01-architecture.md) |

**설명** — 무엇이 느리고 무엇이 실패했는지 알 수 있어야 한다.

**세부 요구사항**
1. 모든 요청 로그에 요청 id · 워크스페이스 · 주체 종류(사람 · 서비스) · 경로(웹 · REST · MCP)가 있어야 한다. 비밀값 · 토큰 · 키 원문은 없어야 한다.
2. MCP 도구별 호출 수 · 오류율 · 지연을 볼 수 있어야 한다.

**수용 기준**
- [ ] 로그에서 한 요청을 끝까지 따라갈 수 있다
- [ ] MCP 지표를 조회할 수 있다

### NFR-QLT-001 시험

| 항목 | 내용 |
|---|---|
| 우선순위 | M |

| 관련 설계 | [테스트 전략](../plan/02-test-strategy.md) |

**설명** — 권한 · 상태와 날짜 규칙 · MCP 동등성은 사람이 매번 손으로 확인할 수 없다.

**세부 요구사항**
1. 새 엔드포인트 · 권한 규칙 · MCP 도구는 같은 작업에서 자동 테스트를 더해야 한다([테스트 전략 §2](../plan/02-test-strategy.md#ts-must)).
2. 검사 명령(`./mvnw -q package` · `npm run lint && npm run typecheck && npm test && npm run build` · 문서 검사)이 통과해야 끝난 것으로 본다.

**수용 기준**
- [x] 토대의 접근 · 멤버십 · 역할 · 초대 · 가입 신청 테스트가 `./mvnw -q package` 에서 돈다
- [ ] 프로젝트 · 일감 · MCP 의 경계 · 동등성 테스트가 돈다

<a id="nfr-mnt-001"></a>
### NFR-MNT-001 형제 저장소와 맞추기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [ADR-002](../design/00-key-decisions.md#adr-002) |

**설명** — 토대가 moai-wiki 와 같으므로, 한쪽에서 고친 보안 · 버그가 다른 쪽에 빠지지 않아야 한다.

**세부 요구사항**
1. 토대 코드(account · workspace · security · keycloak · audit · BFF)를 고칠 때 moai-wiki 에 같은 고침이 필요한지 확인하고 HANDOFF 에 적어야 한다.
2. 의존성 판을 올릴 때 두 저장소를 함께 올릴지 정해야 한다.

**수용 기준**
- [ ] 토대 변경 커밋마다 "moai-wiki 에도 필요/불필요"가 HANDOFF 작업 기록에 있다

<a id="nfr-dep-001"></a>
### NFR-DEP-001 배포와 설정

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [DEVELOPE.md](../../DEVELOPE.md) |

**설명** — 같은 빌드를 설정만 바꿔 어디든 띄울 수 있어야 한다.

**세부 요구사항**
1. 모든 설정은 `MOAI_WORKS_*` 환경 변수로 바꿀 수 있어야 하고, 비밀값은 기본값이 없어야 한다.
2. 스키마는 Flyway 로만 바뀌어야 한다(적용된 파일은 고치지 않는다).
3. 모든 서비스는 HTTPS 로 열려야 한다(앞단 프록시가 끝내는 배치만 예외).

**수용 기준**
- [ ] 빈 DB 에서 api 를 띄우면 Flyway 가 스키마를 만들고 기동한다
- [ ] 비밀값이 없으면 어떤 값이 없는지 알려 주고 멈춘다(또는 그 기능만 막는다)

### NFR-USA-001 반응형 · 접근성

| 항목 | 내용 |
|---|---|
