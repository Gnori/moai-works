# 위키 · 뉴스 · 문서 · 파일 · 포럼 요구사항 (FR-CNT)

프로젝트 안에서 일감 말고 함께 쓰는 내용 — 위키(판 · 차이 · 되돌리기 · 이름 바꾸기 · 보호), 뉴스(+댓글), 문서(분류 + 첨부), 파일(버전에 묶은 내려받기), 포럼(게시판 · 글 · 답글) — 의 요구사항이다. Redmine 의 동작을 따르고 본문은 Markdown 하나다. 설계는 [공동 작업 설계](../design/08-collaboration.md)에 있다.

| 공통 | 내용 |
|---|---|
| 권한 검사 | api 가 요청마다 판정한다. 프로젝트 독자가 아니거나 그 모듈(`wiki` · `news` · `documents` · `files` · `forums`)이 꺼져 있으면 404, 권한 코드가 없으면 403([프로젝트 요구사항](02-project.md)). 닫힌 프로젝트의 쓰기는 409 `PROJECT_READ_ONLY` |
| 권한 코드 | `wiki.read` · `wiki.edit` · `wiki.manage` · `news.manage` · `document.read` · `document.manage` · `file.read` · `file.manage` · `forum.post` · `forum.manage`. 뉴스 · 게시판 읽기는 프로젝트 독자면 된다 |
| 본문 | Markdown(GFM) 하나. 링크 표기 `#123` · `[[쪽]]` · `@사용자` 는 일감과 같다 |
| 감사 · 이력 | 모든 쓰기는 감사에 행위자(사람 · Agent 계정) · 경로(웹 · REST · MCP + 키 id)를 남긴다. 위키는 저장마다 판을 쌓는다 |
| 이벤트 | 쓰기는 이벤트를 내고 알림 · 활동 · 검색 색인이 따른다([알림 요구사항](09-notification.md) · [활동 · 검색 요구사항](10-activity-search.md)) |
| MCP 동등성 | 위키 도구(`list_wiki_pages` · `get_wiki_page` · `create_wiki_page` · `update_wiki_page`)는 REST 와 같은 서비스 · 같은 판정을 부른다([MCP 요구사항](12-mcp.md)) |
| 첨부 | 첨부 저장 · 내려받기 판정은 일감 첨부와 같다([일감 요구사항](03-issue.md)) |

<a id="fr-cnt-001"></a>
### FR-CNT-001 프로젝트 위키 · 시작 쪽 · 링크

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.1](../design/08-collaboration.md#co-wiki) · [§3.2](../design/08-collaboration.md#co-wiki-names) |

**설명** — 프로젝트마다 위키가 하나 있고, 시작 쪽이 위키의 첫 화면이다. 쪽은 `[[쪽 이름]]` 으로 서로 잇는다(Redmine 과 같다).

**세부 요구사항**
1. `wiki` 모듈을 처음 켜면 위키를 만들고, 시작 쪽 이름(기본 `Wiki`)을 `wiki.manage` 가 바꿀 수 있어야 한다.
2. 쪽 제목은 위키 안에서 대소문자 · 공백 차이를 무시하고 겹치지 않아야 하고, `/ \ ? # [ ] | : < > "` 를 쓸 수 없어야 한다.
3. `[[쪽]]` · `[[쪽#제목]]` · `[[쪽|보이는 글]]` · `[[프로젝트:쪽]]` · `[[프로젝트:]]` 링크를 풀어야 한다.
4. 없는 쪽 링크는 빨간 링크로 보이고, `wiki.edit` 가 있으면 누르면 그 이름으로 새 쪽 만들기가 열려야 한다.
5. 보는 사람이 읽을 수 없는 다른 프로젝트 위키 링크는 링크가 아닌 글자로 보여야 한다.

**수용 기준**
- [ ] `설치 안내` 와 `설치  안내`(공백 둘), `Install Guide` 와 `install guide` 는 각각 같은 쪽이다
- [ ] 금지 글자가 든 제목은 422 다
- [ ] 못 읽는 프로젝트의 `[[frontend:쪽]]` 링크는 응답 `references` 에서 "보이지 않음"이고 주소가 없다
- [ ] 위키 모듈이 꺼진 프로젝트의 위키 주소는 404 다

<a id="fr-cnt-002"></a>
### FR-CNT-002 위키 쪽 만들기 · 고치기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.3](../design/08-collaboration.md#co-wiki-revision) |

**설명** — Markdown 편집기(CodeMirror + 미리보기)로 쪽을 만들고 고친다. 저장마다 새 판이 생기고, 남이 먼저 고쳤으면 덮어쓰지 않는다.

**세부 요구사항**
1. `wiki.edit` 를 가진 사람이 쪽을 만들고 고칠 수 있어야 한다. 저장할 때 변경 요약(1024자, 선택)을 적을 수 있어야 한다.
2. 저장 요청에 보던 판 번호를 넣고, 지금 판과 다르면 409 와 지금 본문을 돌려줘 합치게 해야 한다.
3. 본문이 바뀌지 않은 저장은 판을 만들지 않아야 한다.
4. 쪽에 파일을 첨부하고 본문에서 그림으로 넣을 수 있어야 한다(`![](그림.png)` 는 그 쪽의 첨부로 풀린다).
5. 판마다 작성자(사람 · Agent 계정 · "사람 (MCP 로)")와 경로를 남겨야 한다.

**수용 기준**
- [ ] 두 사람이 같은 판에서 고쳐 저장하면 뒤 사람은 409 를 받고 먼저 저장한 판이 지워지지 않는다
- [ ] 같은 본문으로 저장하면 판 수가 늘지 않는다
- [ ] `wiki.edit` 없이 저장하면 403, 위키를 못 읽으면 404 다
- [ ] 판과 감사에 작성자 · 경로가 남는다

<a id="fr-cnt-003"></a>
### FR-CNT-003 쪽 계층 · 색인

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.4](../design/08-collaboration.md#co-wiki-tree) |

**설명** — 쪽에 상위 쪽을 정해 트리로 묶는다. 위키 전체는 제목순(트리) · 날짜순 색인으로 본다(Redmine 과 같다).

**세부 요구사항**
1. 상위 쪽은 같은 위키의 쪽이어야 하고, 자기 자신 · 자기 하위 아래로 옮길 수 없어야 한다.
2. 동시에 옮겨도 순환이 생기지 않아야 한다.
3. 쪽 머리에 상위 쪽 길, 아래에 하위 쪽 목록을 보여야 한다.
4. 색인은 제목순(트리)과 날짜순(최근 고친 순, 날짜별 묶음) 두 가지여야 한다.

**수용 기준**
- [ ] A 를 A 의 하위 아래로 옮기면 422 다
- [ ] A→B 아래, B→A 아래를 동시에 요청해도 하나만 성공한다
- [ ] 날짜순 색인이 마지막 판 시각 순서다

<a id="fr-cnt-004"></a>
### FR-CNT-004 판 · 차이 · 되돌리기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.3](../design/08-collaboration.md#co-wiki-revision) |

**설명** — 쪽의 모든 판을 보고, 두 판의 차이를 보고, 옛 판으로 되돌린다. 판은 지우지 않는다(이력은 쌓기만).

**세부 요구사항**
1. 판 목록(번호 · 시각 · 작성자 · 변경 요약 · 크기)과 옛 판 보기를 `wiki.read` 로 열어야 한다.
2. 두 판을 골라 줄 단위 차이와 줄 안 낱말 강조를 보여야 한다.
3. 되돌리기는 옛 판 본문으로 새 판을 만들고 변경 요약에 "판 N 으로 되돌림"을 남겨야 한다(`wiki.edit`, 보호된 쪽은 `wiki.manage`).
4. 판을 지우는 기능은 두지 않아야 한다.

**수용 기준**
- [ ] 판 3 으로 되돌리면 판 N+1 이 생기고 본문이 판 3 과 같다
- [ ] 차이 화면에 더한 줄 · 뺀 줄이 표시된다
- [ ] 판 지우기 API 가 없다

<a id="fr-cnt-005"></a>
### FR-CNT-005 이름 바꾸기 · 옛 이름 넘기기 · 옮기기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.5](../design/08-collaboration.md#co-wiki-rename) |

**설명** — 쪽 이름을 바꿔도 옛 이름 링크가 깨지지 않게 옛 이름으로 오면 새 쪽으로 넘긴다. 다른 프로젝트 위키로 옮길 수도 있다(Redmine 과 같다).

**세부 요구사항**
1. `wiki.manage` 를 가진 사람이 이름을 바꿀 수 있어야 하고, "옛 이름으로 오면 넘기기"(기본 켬)를 고를 수 있어야 한다.
2. 이름을 여러 번 바꿔도 처음 이름으로 오면 지금 쪽으로 가야 한다.
3. 옛 이름으로 새 쪽을 만들면 그 이름의 넘기기는 없어져야 한다.
4. 다른 프로젝트 위키로 옮기려면 대상 프로젝트에서도 `wiki.manage` 가 있어야 하고, 하위 쪽 · 판 · 첨부가 함께 가야 한다.
5. 이름 바꾸기 · 옮기기는 판을 만들지 않고 감사에 옛 이름 · 새 이름을 남겨야 한다.

**수용 기준**
- [ ] A → B → C 로 바꾼 뒤 A 주소로 오면 C 가 열린다
- [ ] 대상 위키에 같은 이름이 있으면 409 다
- [ ] 대상 프로젝트에 `wiki.manage` 가 없으면 403 이다

<a id="fr-cnt-006"></a>
### FR-CNT-006 쪽 보호 · 지우기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.6](../design/08-collaboration.md#co-wiki-protect) · [§3.4](../design/08-collaboration.md#co-wiki-tree) |

**설명** — 중요한 쪽은 보호해 관리자만 고치게 한다. 지울 때 하위 쪽을 어떻게 할지 고른다(Redmine 과 같다).

**세부 요구사항**
1. `wiki.manage` 를 가진 사람이 쪽을 보호하고 풀 수 있어야 한다. 보호된 쪽은 `wiki.manage` 만 고치기 · 되돌리기 · 첨부 · 이름 바꾸기 · 지우기를 해야 한다.
2. 지우기는 `wiki.manage` 이고, 하위가 있으면 "하위를 위로 올리기"(기본) · "하위도 지우기" · "다른 쪽 아래로" 중 고르게 해야 한다.
3. 시작 쪽은 다른 쪽을 시작 쪽으로 정하기 전에는 지울 수 없어야 한다.
4. 지운 쪽의 제목 · 판 수 · 마지막 판 해시를 감사에 남겨야 한다.

**수용 기준**
- [ ] 보호된 쪽을 `wiki.edit` 만 가진 사람이 고치면 403 이다(MCP `update_wiki_page` 도 같다)
- [ ] "하위를 위로 올리기"로 지우면 하위 쪽의 상위가 지운 쪽의 상위가 된다
- [ ] 시작 쪽 지우기는 409 다

<a id="fr-cnt-007"></a>
### FR-CNT-007 위키 관찰

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §8](../design/08-collaboration.md#co-watch) |

**설명** — 쪽 하나나 위키 전체를 관찰하면 고칠 때마다 알림을 받는다(Redmine 과 같다).

**세부 요구사항**
1. 위키를 읽을 수 있는 사람은 쪽 하나 · 위키 전체를 스스로 관찰하고 그만둘 수 있어야 한다.
2. 관찰자는 그 쪽(또는 위키의 모든 쪽)이 만들어지거나 고쳐지면 알림을 받아야 한다(알림 설정을 따른다).
3. 관찰자가 읽기 권한을 잃으면 알림이 가지 않아야 한다.

**수용 기준**
- [ ] 쪽을 관찰한 사람에게 그 쪽 새 판 알림이 간다
- [ ] 프로젝트에서 빠진 관찰자에게는 알림이 가지 않는다

<a id="fr-cnt-008"></a>
### FR-CNT-008 위키 내보내기

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.7](../design/08-collaboration.md#co-wiki-export) |

**설명** — 쪽 하나나 위키 전체를 파일로 내려받는다(Redmine 의 쪽 · 위키 내보내기).

**세부 요구사항**
1. 쪽 하나를 Markdown 원문 · HTML 로 내려받을 수 있어야 한다. PDF 는 인쇄용 화면으로 만든다.
2. 위키 전체를 ZIP(쪽마다 `.md` + 첨부 + 색인)으로 만들어야 하고, 작업 큐에서 만든 뒤 24시간 쓸 수 있는 링크를 알려야 한다.
3. ZIP 안의 `[[…]]` 링크는 상대 경로로 바꿔야 한다.

**수용 기준**
- [ ] ZIP 을 풀면 쪽 수만큼 `.md` 가 있고 링크가 서로 이어진다
- [ ] `wiki.read` 가 없으면 내보내기가 404 다

<a id="fr-cnt-009"></a>
### FR-CNT-009 MCP 로 위키 읽고 쓰기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §16](../design/08-collaboration.md#co-mcp) |

**설명** — 바깥 Agent 가 설계 문서를 읽거나 회의록 · 릴리스 노트를 쓸 수 있게 위키 도구와 리소스를 연다.

**세부 요구사항**
1. `list_wiki_pages` · `get_wiki_page` · `create_wiki_page` · `update_wiki_page` 를 두어야 하고, 판정은 REST 와 같아야 한다.
2. `update_wiki_page` 는 읽은 판 번호(`base_revision`)가 필수이고, 어긋나면 충돌 오류(`CONCURRENT_UPDATE`)와 지금 판 번호를 돌려줘야 한다. `create_wiki_page` 는 같은 이름이 있으면 `ALREADY_EXISTS` 다.
3. `create_wiki_page` 는 `idempotency_key` 가 필수이고 같은 키는 24시간 같은 결과를 돌려줘야 한다.
4. `get_wiki_page` 의 본문은 "사용자 데이터"로 표시해야 한다.
5. 리소스 `moai-works://{ws}/projects/{식별자}/wiki/{페이지}` 로도 읽을 수 있어야 한다.
6. MCP 로 만든 판에 경로 MCP · 키 id 가 남아야 한다.

**수용 기준**
- [ ] `update_wiki_page` 를 옛 판 번호로 부르면 충돌 오류이고 본문이 바뀌지 않는다
- [ ] 판 목록에 "김가 (MCP 로)" 또는 "Agent X" 가 보인다
- [ ] 엔드포인트 대상이 아닌 프로젝트 위키는 읽을 수 없다
- [ ] 같은 멱등 키로 `create_wiki_page` 를 두 번 불러도 쪽이 하나다

<a id="fr-cnt-010"></a>
### FR-CNT-010 뉴스 · 댓글

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §4](../design/08-collaboration.md#co-news) |

**설명** — 릴리스 · 공지를 프로젝트 뉴스로 알리고 댓글을 받는다. 워크스페이스 뉴스는 읽을 수 있는 모든 프로젝트 뉴스를 모은다(Redmine 과 같다).

**세부 요구사항**
1. `news.manage` 를 가진 사람(Agent 계정 포함)이 제목(60자) · 요약(255자) · 본문 · 첨부로 뉴스를 쓰고 고치고 지울 수 있어야 한다.
2. 프로젝트 독자는 뉴스와 댓글을 읽을 수 있어야 한다.
3. `forum.post` 를 가진 사람이 댓글을 달고 자기 댓글을 고치고 지울 수 있어야 한다. 남의 댓글은 `news.manage` 가 지운다.
4. 작성자 · 댓글 단 사람은 그 뉴스를 자동 관찰해야 한다.
5. 프로젝트 개요에 최근 뉴스 5개, 워크스페이스 뉴스 목록을 두어야 한다.

**수용 기준**
- [ ] 독자가 아닌 RESTRICTED 프로젝트 뉴스가 워크스페이스 뉴스에 나오지 않는다
- [ ] `forum.post` 없이 댓글을 달면 403 이다
- [ ] 뉴스 · 댓글 쓰기가 감사에 남고 새 뉴스 알림이 간다

<a id="fr-cnt-011"></a>
### FR-CNT-011 문서

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §5](../design/08-collaboration.md#co-document) |

**설명** — 사용 설명서 · 계약서처럼 분류로 묶는 문서를 첨부와 함께 둔다(Redmine 문서 모듈). 분류는 워크스페이스 열거형이다([워크플로 요구사항](04-workflow.md)).

**세부 요구사항**
1. `document.manage` 를 가진 사람이 분류 · 제목(255자) · 설명 · 첨부 여러 개로 문서를 만들고 고치고 지울 수 있어야 한다.
2. `document.read` 를 가진 사람이 목록 · 문서 · 첨부를 볼 수 있어야 한다.
3. 목록은 분류(기본) · 날짜 · 제목 · 작성자로 묶고, "마지막 갱신"은 문서 고친 시각과 마지막 첨부 시각 중 늦은 것이어야 한다.

**수용 기준**
- [ ] 문서에 첨부를 더하면 목록의 마지막 갱신이 바뀐다
- [ ] `document.read` 없이 첨부를 내려받으면 404 다
- [ ] 문서를 지우면 첨부도 지워지고 감사에 남는다

<a id="fr-cnt-012"></a>
### FR-CNT-012 파일 (내려받기)

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §6](../design/08-collaboration.md#co-file) |

**설명** — 설치본 · 배포 묶음을 버전에 묶어 내려받게 한다. 내려받은 수와 체크섬(SHA-256)을 보인다(Redmine 파일 모듈).

**세부 요구사항**
1. `file.manage` 를 가진 사람이 파일을 올리고 버전(선택) · 설명을 정하고 지울 수 있어야 한다.
2. 올릴 때 SHA-256 을 계산해 저장하고 목록에 보여야 한다.
3. 목록은 버전별 묶음이고, 칸은 파일 이름 · 날짜 · 크기 · 내려받은 수 · SHA-256 · 설명이어야 한다.
4. 내려받기는 api 를 거쳐 `file.read` 를 판정하고 내려받은 수를 하나 올려야 한다.
5. 파일이 묶인 버전은 지울 수 없어야 한다.

**수용 기준**
- [ ] 목록의 SHA-256 이 내려받은 파일의 SHA-256 과 같다
- [ ] 두 번 내려받으면 수가 2 오른다
- [ ] `file.read` 가 없으면 내려받기가 404 다

<a id="fr-cnt-013"></a>
### FR-CNT-013 포럼 — 게시판 · 글 · 답글

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §7](../design/08-collaboration.md#co-forum) |

**설명** — 프로젝트에 게시판을 두고 글과 답글로 이야기한다(Redmine 포럼).

**세부 요구사항**
1. 프로젝트 독자는 게시판 · 글 · 답글을 읽을 수 있어야 한다.
2. `forum.post` 를 가진 사람이 글 · 답글을 쓰고, 자기 글을 고치고, 자기 답글과 답글 없는 자기 주제 글을 지울 수 있어야 한다.
3. 답글은 주제 글 아래 한 줄로 쌓이고, 인용 단추로 원문을 인용할 수 있어야 한다.
4. 글 목록은 고정 글 먼저, 그다음 마지막 활동 최근순이어야 한다.

**수용 기준**
- [ ] 답글이 달린 자기 주제 글을 지우면 409 다
- [ ] `forum.post` 없이 글을 쓰면 403, `forums` 모듈이 꺼지면 404 다
- [ ] 글 쓰기가 감사에 남는다

<a id="fr-cnt-014"></a>
### FR-CNT-014 포럼 관리 — 잠금 · 고정 · 관찰

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §7](../design/08-collaboration.md#co-forum) · [§8](../design/08-collaboration.md#co-watch) |

**설명** — 게시판을 만들고 순서를 정하고, 글을 잠그거나 위에 고정한다. 게시판 · 글을 관찰해 새 글 · 답글 알림을 받는다.

**세부 요구사항**
1. `forum.manage` 를 가진 사람이 게시판 만들기 · 고치기 · 순서 · 지우기(글이 있으면 옮기거나 함께 지우기)를 할 수 있어야 한다. 상위 게시판은 한 단계까지다.
2. `forum.manage` 가 글을 잠그고(답글 금지) 고정하고, 같은 프로젝트의 다른 게시판으로 옮기고, 남의 글을 고치고 지울 수 있어야 한다.
3. 잠긴 글에는 누구도 답글을 달 수 없어야 한다.
4. 게시판 · 글을 스스로 관찰할 수 있어야 하고, 주제 작성자와 답글 작성자는 그 글을 자동 관찰해야 한다.

**수용 기준**
- [ ] 잠긴 글에 답글을 달면 403 이다
- [ ] 고정한 글이 목록 맨 위에 있다
- [ ] 게시판 관찰자에게 새 글 알림이 간다

<a id="fr-cnt-015"></a>
### FR-CNT-015 위키 절 고치기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.3](../design/08-collaboration.md#co-wiki-revision) |

**설명** — 긴 쪽에서 제목으로 나뉜 절 하나만 연다. 다른 사람이 다른 절을 고쳐도 부딪치지 않는다(Redmine 의 절 고치기).

**세부 요구사항**
1. `#`~`###` 제목마다 "이 절 고치기"를 두어야 한다.
2. 저장할 때 그 절의 내용 해시를 보내고, 그 절이 그사이 바뀌었으면 409, 다른 절만 바뀌었으면 합쳐서 새 판으로 저장해야 한다.

**수용 기준**
- [ ] 두 사람이 서로 다른 절을 고쳐 저장하면 둘 다 저장되고 판이 2개 는다
- [ ] 같은 절을 고치면 뒤 사람은 409 다

<a id="fr-cnt-016"></a>
### FR-CNT-016 위키 매크로 · 사이드바

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §3.2](../design/08-collaboration.md#co-wiki-names) |

**설명** — Redmine 위키의 자주 쓰는 매크로(목차 · 하위 쪽 목록 · 다른 쪽 넣기)와 사이드바 쪽을 둔다.

**세부 요구사항**
1. `{{toc}}` · `{{child_pages}}` · `{{include(쪽)}}` 를 풀어야 한다.
2. `{{include}}` 는 보는 사람이 그 쪽을 읽을 수 있을 때만 내용을 넣어야 한다.
3. `Sidebar` 라는 이름의 쪽이 있으면 위키 옆에 보여야 한다.

**수용 기준**
- [ ] 못 읽는 프로젝트 쪽을 `{{include}}` 하면 내용이 들어가지 않는다
- [ ] `{{child_pages}}` 가 지금 하위 쪽 목록과 같다
