# 일감 요구사항 (FR-ISS)

프로젝트 안의 일감 — 만들기 · 보기 · 고치기, 일감 유형 · 상태, 관리자와 담당자, 날짜 다섯 개, 상위 · 하위 일감, 연결 일감, 이력과 댓글, 목록 · 필터 · 정렬, 지우기, 화면의 요구사항이다. **일감은 moai-wiki 의 페이지 자리다** — 프로젝트 안에 여러 개 있고, 페이지 유형처럼 일감 유형이 있고, 페이지 트리처럼 상위 · 하위가 있고, 페이지 소유자처럼 관리자가 있다. 여기에 사람이 직접 든 것(담당자 · 날짜 · 연결 일감)을 더했다. 설계는 [일감 설계](../design/05-issue.md)에 있다.

| 공통 | 내용 |
|---|---|
| moai-wiki 대응 | 페이지 → 일감, 페이지 유형 → 일감 유형, 페이지 트리 → 상위 · 하위 일감, 페이지 소유자(`page.owner.assign`) → 일감 관리자(`issue.manager.assign`), 페이지 링크 → 연결 일감, 리비전 → 이력, 피드백 → 댓글. 담당자와 날짜는 moai-wiki 에 없는 것이다 |
| 판정 | 모든 REST 는 `/moai-works-api/v1/workspaces/{workspace}/projects/{project}` 아래의 `@ProjectApi(권한)` 이다 — 판정 규칙은 [FR-PRJ-006](02-project.md#fr-prj-006). 프로젝트 독자가 아니면 404 `PROJECT_NOT_FOUND`, 일감이 없거나 지웠으면 404 `ISSUE_NOT_FOUND`, 권한 코드가 없으면 403 `PERMISSION_REQUIRED`, 보관한 프로젝트에 쓰면 409 `PROJECT_NOT_WRITABLE` |
| 일감 번호 | 프로젝트 안 순번(1, 2, 3 …). 주소는 `…/issues/{number}` 다. 다른 프로젝트의 같은 번호와 섞이지 않는다 |
| 같은 서비스 | MCP 도구는 REST 와 같은 서비스 · 같은 판정 · 같은 검증 · 같은 오류 코드를 쓴다 ([MCP 요구사항](04-mcp.md)) |
| 이력 · 감사 | 일감의 모든 쓰기는 이력(`issue_journal`)에 한 줄씩 남고 감사(`audit_log`)에도 남는다. 둘 다 주체(사람 — MCP 로 한 일은 키 주인)와 경로(웹 · MCP)를 남긴다 ([FR-ISS-010](#fr-iss-010)) |
| 첫 출시 밖 | 사용자 정의 워크플로 · 필드, 프로젝트별 일감 유형, 첨부, 관찰자, 알림, 시간 기록, 다른 프로젝트와의 연결은 [나중 후보](00-overview.md#7-나중-후보)다 |

## 1. 만들기 · 보기 · 고치기

<a id="fr-iss-001"></a>
### FR-ISS-001 일감 만들기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(프로젝트 행을 잠가 순번, 관리자 기본 = 만든 사람, 이력 첫 줄 · 감사 `issue.create`) · 자동 테스트. 남은 것: 동시 20개 번호 · 지운 번호 재사용 안 함 · 다른 관리자 지정 403 · 길이 상한 시험 · 화면. |
| 관련 설계 | [일감 설계](../design/05-issue.md) · [데이터 모델](../design/02-data-model.md) |

**설명** — 프로젝트에 일감을 만든다. 일감 번호는 프로젝트 안 순번이라 사람과 Agent 가 "PROJ 의 12번"처럼 같은 이름으로 부른다.

**세부 요구사항**
1. `POST /projects/{project}/issues` 는 `@ProjectApi(issue.create)` 여야 한다. 기본 역할로는 소유자 · 관리자 · 큐레이터, 프로젝트 역할로는 `project-editor` 이상이 만든다.
2. 입력은 일감 유형(필수, [FR-ISS-004](#fr-iss-004)) · 제목(필수, 앞뒤 공백을 뺀 1~200자) · 설명(Markdown, 30000자 이하) · 상태(기본 `NEW`, [FR-ISS-005](#fr-iss-005)) · 관리자(기본 = 만든 사람) · 담당자(선택, [FR-ISS-006](#fr-iss-006)) · 상위 일감 번호(선택, [FR-ISS-008](#fr-iss-008)) · 날짜(완료 기한 · 시작일 · 완료 예정일 · 완료일 · 종료일, [FR-ISS-007](#fr-iss-007))다.
3. 번호는 `project` 행을 잠그고(`SELECT … FOR UPDATE`) `issue_seq` 를 1 올린 값이어야 한다. `(project_id, number)` 는 고유하다. 동시에 만들어도 번호가 겹치거나 빠지지 않는다.
4. 번호는 다시 쓰지 않는다. 지운 일감의 번호도 쓴 번호다.
5. 제목이 비거나 200자를 넘으면 400 `INVALID_ISSUE_TITLE`, 설명이 30000자를 넘으면 400 `ISSUE_DESCRIPTION_TOO_LONG` 이다.
6. 관리자를 만든 사람이 아닌 사람으로 정하려면 `issue.manager.assign` 도 있어야 한다. 없으면 403 `PERMISSION_REQUIRED` 다.
7. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
8. 만들기도 이력의 첫 줄로 남긴다 — `changes` 에 처음 값(유형 · 제목 · 상태 · 관리자 · 담당자 · 상위 · 날짜)을 전 값 없이 담는다. 그래서 웹으로 만들었는지 MCP 로 만들었는지 이력에서 보인다.
9. 응답은 201 과 일감 상세(번호 · `rowVersion` 포함)다.
10. 만들기를 감사(`issue.create` — 프로젝트 · 번호 · 유형)에 남긴다.

**수용 기준**
- [x] 새 프로젝트에 일감 세 개를 만들면 번호가 1 · 2 · 3 이다 (IssueTest)
- [ ] 같은 프로젝트에 20개를 동시에 만들어도 번호가 1~20 으로 겹치거나 빠지지 않는다
- [ ] 일감을 지운 뒤 새로 만들면 지운 번호를 다시 쓰지 않는다
- [ ] 관리자를 비우면 만든 사람이 관리자다. `issue.manager.assign` 없이 다른 사람을 관리자로 정하면 403 이다
- [x] 기본 역할 멤버가 만들면 403, 독자가 아니면 404 `PROJECT_NOT_FOUND` 다 (IssueTest)
- [ ] 제목 201자 · 설명 30001자 · 없는 유형은 각각 400 이다
- [x] 보관한 프로젝트에서 만들면 409 `PROJECT_NOT_WRITABLE` 이다 (IssueTest)
- [x] 만든 뒤 이력의 첫 줄과 감사에 만든 사람 · 경로가 있다 (IssueTest)

<a id="fr-iss-002"></a>
### FR-ISS-002 일감 보기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(하위 · 연결(양쪽) · 이력을 함께) · 자동 테스트. 남은 것: 이력 100줄 넘을 때 커서 · 화면의 HTML 막기. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감 하나를 열면 필드 · 하위 일감 · 연결 일감 · 이력이 한 번에 온다. 사람 화면과 MCP `get_issue` 가 같은 응답을 쓴다.

**세부 요구사항**
1. `GET /projects/{project}/issues/{number}` 는 `@ProjectApi(issue.read)` 여야 한다. 기본 역할은 모두 `issue.read` 를 가지므로 `WORKSPACE` 프로젝트의 일감은 모든 활성 멤버가 본다.
2. 응답은 번호 · 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자(사람 id · 표시 이름 · 떠난 멤버 표시) · 상위 일감(번호 · 제목) · 날짜 다섯 개 · 만든 사람 · 만든 때 · 고친 때 · `rowVersion` 과 다음을 담아야 한다.
   - 하위 일감: 번호 · 유형 · 제목 · 상태 · 담당자(번호순)
   - 연결 일감: 연결 id · 연결 종류 · 이 일감에서 본 방향 · 상대 일감의 번호 · 제목 · 상태(양쪽 어느 일감에서 걸었든 보인다)
   - 이력: 오래된 것부터 100줄, 더 있으면 이어 받기 커서
   - `myActions`: 이 사람이 지금 할 수 있는 일(고치기 · 댓글 · 관리자 바꾸기 · 지우기)
3. 없거나 지운 일감은 404 `ISSUE_NOT_FOUND` 다. 번호는 경로의 프로젝트 안에서만 찾는다.
4. 설명 · 댓글의 Markdown 은 화면에서 안전하게 그려야 한다(원시 HTML · 스크립트를 실행하지 않는다, moai-wiki 와 같은 렌더러).

**수용 기준**
- [x] 응답에 하위 일감 · 연결 일감(양쪽 방향) · 이력이 있다 (IssueTest)
- [x] 지운 일감은 404 `ISSUE_NOT_FOUND`, 다른 프로젝트에만 있는 번호도 404 `ISSUE_NOT_FOUND` 다 (IssueTest)
- [x] 독자가 아닌 `RESTRICTED` 프로젝트의 일감을 열면 404 `PROJECT_NOT_FOUND` 이고, 없는 프로젝트와 응답이 같다 (IssueTest)
- [ ] 이력이 100줄을 넘는 일감은 커서로 나머지를 받는다
- [ ] 설명에 넣은 `<script>` 가 화면에서 실행되지 않는다

<a id="fr-iss-003"></a>
### FR-ISS-003 일감 고치기 (동시 수정 포함)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(넣은 필드만 · rowVersion 필수 · 409 `CONCURRENT_UPDATE` · 이력 한 줄 · 감사 `issue.update`) · 자동 테스트. 남은 것: 동시 요청 시험 · 바뀐 값 없음 시험 · 403 때 다른 필드 그대로 시험 · 다른 프로젝트 편집자 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감의 필드를 고친다. 사람과 Agent 가 같은 일감을 동시에 고칠 수 있으므로, 남이 먼저 고친 것을 모르고 덮어쓰지 않게 `rowVersion` 으로 막는다.

**세부 요구사항**
1. `PATCH /projects/{project}/issues/{number}` 는 `@ProjectApi(issue.edit)` 여야 한다. 상태 · 날짜 · 담당자 · 상위 일감도 이 요청으로 고친다.
2. 요청에는 `rowVersion`(필수)과 바꿀 필드만 담는다. 고칠 수 있는 것: 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자 · 상위 일감 · 날짜 다섯 개. 검증은 만들기와 같다.
3. 관리자를 바꾸면 서비스가 `issue.manager.assign` 도 확인해야 한다. 없으면 403 `PERMISSION_REQUIRED` 이고 아무것도 바뀌지 않는다.
4. `rowVersion` 이 지금 값과 다르면 409 `CONCURRENT_UPDATE` 이고 아무것도 바뀌지 않아야 한다. 응답에 지금 `rowVersion` 을 담는다.
5. 바뀐 필드는 모두 이력 한 줄에 전 · 후로 남긴다. 상태에 따라 자동으로 채운 날짜도 같은 줄이다([FR-ISS-005](#fr-iss-005)).
6. 고치면서 댓글(`notes`)을 함께 남길 수 있다 — 같은 이력 줄에 든다.
7. 실제로 바뀐 값이 없으면 이력을 남기지 않고 `rowVersion` 도 그대로 두고 200 으로 답한다.
8. 저장하면 `updated_at` 을 고치고 `rowVersion` 을 1 올린다.
9. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
10. 고치기를 감사(`issue.update` — 바뀐 필드 이름)에 남긴다.

**수용 기준**
- [x] 옛 `rowVersion` 으로 고치면 409 `CONCURRENT_UPDATE` 이고 일감이 그대로다 (IssueTest)
- [ ] 같은 `rowVersion` 으로 동시에 보낸 두 요청 가운데 하나만 성공하고 다른 하나는 409 다
- [x] 제목 · 상태 · 담당자를 한 번에 고치면 이력 한 줄에 세 필드의 전 · 후가 있다 (IssueTest)
- [ ] 바뀐 값이 없는 요청은 이력을 남기지 않는다
- [ ] `issue.manager.assign` 없이 관리자를 바꾸면 403 이고, 같은 요청의 다른 필드도 바뀌지 않는다
- [ ] 다른 프로젝트에서만 편집자인 사람이 고치면 403 이다
- [x] 고치기가 감사에 남는다 (IssueTest)

## 2. 유형 · 상태 · 사람 · 날짜

<a id="fr-iss-004"></a>
### FR-ISS-004 일감 유형

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(쓰는 유형 넷 · 옛 유형 둘은 더 쓰지 않음 · 순서 · 없는 유형 400 · 옛 유형 400 `ISSUE_TYPE_RETIRED`) · 화면(새 일감 · 고치기에서 쓰는 유형만) · 자동 테스트 · ego-browser. 남은 것: 유형 바꾸기 이력 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감에는 유형이 있다. moai-wiki 의 페이지 유형처럼 모든 워크스페이스가 같이 쓰는 시드 표로 시작한다. 프로젝트마다 유형을 바꾸는 것은 나중 후보다. 2026-11-22 사용자: "유형 : 새기능, 버그, 테스트, 기술조사" — 처음 넣은 요구사항 · 작업은 더 쓰지 않는다(V8).

**세부 요구사항**
1. 표 `issue_type`(key · 이름 · 설명 · 순서 · 쓰는지)은 Flyway 시드로 다음을 가져야 한다. 새 일감에서 고를 수 있는 것은 쓰는 유형 넷뿐이다.

   | key | 이름 | 순서 | 쓰는지 |
   |---|---|---|---|
   | `feature` | 새기능 | 1 | 씀 |
   | `bug` | 버그 | 2 | 씀 |
   | `test` | 테스트 | 3 | 씀 |
   | `research` | 기술조사 | 4 | 씀 |
   | `requirement` | 요구사항 | 91 | 더 쓰지 않음 — 그 유형의 일감 · 판이 남아 있어 지우지 않는다 |
   | `task` | 작업 | 92 | 더 쓰지 않음 |

2. `GET /projects/{project}/issue-types` 는 `@ProjectApi(issue.read)` 로 순서대로 준다.
3. 일감을 만들거나 고칠 때 없는 유형 key 는 400 `UNKNOWN_ISSUE_TYPE`, 더 쓰지 않는 유형으로 만들거나 바꾸면 400 `ISSUE_TYPE_RETIRED` 다. 이미 옛 유형인 일감은 유형을 그대로 둔 채 다른 것을 고칠 수 있다. 목록 응답의 `active` 로 화면이 고를 수 있는 유형만 보인다.
4. 유형을 바꾸는 것은 `issue.edit` 이고 이력에 남는다.
5. 유형을 더하거나 고치는 API 는 첫 출시에 없다. 화면은 유형 key 로 다국어 이름을 보인다.

**수용 기준**
- [x] 유형 목록이 쓰는 넷(새기능 · 버그 · 테스트 · 기술조사)을 순서대로, 옛 둘을 `active: false` 로 준다 (IssueTest 2026-11-22)
- [x] 쓰는 유형으로 일감을 만들 수 있고, 없는 유형은 400 `UNKNOWN_ISSUE_TYPE`, 옛 유형은 400 `ISSUE_TYPE_RETIRED` 다 (IssueTest)
- [x] 새 일감 화면의 유형 고르기에 쓰는 넷만 나온다 (ego-browser 2026-11-22)
- [ ] 유형을 바꾸면 이력에 전 · 후가 남는다
- [x] 화면에서 유형 이름이 한국어 · 영어로 나온다 (ego-browser 2026-11-22)

### FR-ISS-005 상태

| 항목 | 내용 |

**설명** — 일감의 상태는 고정 5개이고 아무 상태로나 옮길 수 있다. 완료 · 종료로 옮기면 완료일 · 종료일을 자동으로 채운다. 워크플로를 사용자가 정하는 것은 나중 후보다. 2026-11-22 사용자: "상태 : 등록, 진행, 테스트, 완료, 종료" — `NEW` 의 이름을 신규 → 등록으로 바꾸고 `TESTING`(테스트)을 진행과 완료 사이에 더했다(V7).

**세부 요구사항**
1. 상태는 `NEW`(등록) · `IN_PROGRESS`(진행) · `TESTING`(테스트) · `DONE`(완료) · `CLOSED`(종료) 5개여야 한다. 그 밖의 값은 400 `INVALID_ISSUE_STATUS` 다.
2. 어느 상태에서 어느 상태로나 옮길 수 있다(`issue.edit`). `NEW` · `IN_PROGRESS` · `TESTING` 을 "열린 일감", `DONE` · `CLOSED` 를 "닫힌 일감"으로 묶어 목록 필터 · 기한 지남 · 아침 알림에 쓴다.

   | → `DONE` | 비어 있으면 오늘 | 그대로 |
   | → `CLOSED` | 그대로 | 비어 있으면 오늘 |
   | → `NEW` · `IN_PROGRESS` · `TESTING` | 비운다 | 비운다 |

4. "오늘"은 api 의 기준 시간대(지금은 Asia/Seoul 고정, 워크스페이스 시간대 설정은 나중)의 날짜다.
5. 같은 요청에서 상태와 함께 완료일 · 종료일을 직접 주면 준 값을 쓴다(자동 채움은 빈 경우만).
6. 자동으로 채우거나 비운 날짜도 그 고치기의 이력 줄에 전 · 후로 남는다.

4. 관리자를 바꾸려면 `issue.manager.assign`, 담당자를 바꾸려면 `issue.edit` 가 있어야 한다.
5. 관리자 · 담당자가 워크스페이스를 떠나거나 · 제거되거나 · 정지되거나 · 그 프로젝트의 독자가 아니게 되면, 일감의 값은 그대로 두고 화면 · 응답에 "떠난 멤버"로 표시해야 한다. 그 사람을 새로 지정할 수는 없다. 목록에서 그 사람으로 걸러 찾아 바꾼다.
6. 화면은 후보를 그 프로젝트의 독자인 활성 멤버에서 고르게 한다(api 가 후보 목록을 준다).
7. 바꾸기는 이력에 전 · 후로 남는다.

8. 상위 바꾸기는 하위 일감의 이력에 전 · 후로 남는다.

2. 만들기 · 고치기 · 상위 바꾸기 · 연결 걸기 · 풀기 · 댓글마다 한 줄을 남겨야 한다. 한 요청은 한 줄이다. 댓글은 `notes` 만 있는 줄이다.
3. 남기는 필드는 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자 · 상위 · 날짜 다섯 개 · 연결이다. 설명은 전 · 후 전문을 남기고 화면은 차이를 보여 준다.
4. MCP 로 한 일은 키 주인(`USER`) · 경로 `MCP` 이고 어느 키인지(키 id)를 남긴다. 사람 권한을 넘어 워크스페이스 이름으로 쓰는 주체(서비스 키)는 없다(2026-11-22 — [FR-MCP-001](04-mcp.md#fr-mcp-001)).
5. 이력은 업무와 같은 트랜잭션에 저장해야 한다. 이력 저장이 실패하면 변경도 되돌린다.
6. 이력 줄을 고치거나 지우는 API 는 없어야 한다. 댓글 고치기 · 지우기도 첫 출시에 없다.
7. 일감의 쓰기는 감사에도 남긴다: `issue.create` · `issue.update` · `issue.comment` · `issue.link.add` · `issue.link.remove` · `issue.delete`. MCP 로 한 쓰기는 엔드포인트 id · 키 id · 도구 이름을 함께 남긴다([FR-MCP-006](04-mcp.md#fr-mcp-006)).
8. 화면은 이력을 전체 · 댓글만 · 변경만으로 거르고, 경로가 MCP 인 줄에 표시를 단다.

**설명** — 프로젝트의 일감을 거르고 정렬해 쪽으로 나눠 본다. 화면 목록과 MCP `search_issues` 가 같은 질의 서비스를 쓴다.

**세부 요구사항**

2. 필터는 다음과 같아야 한다. 서로 다른 필터는 모두 만족(AND), 한 필터의 여러 값은 하나라도(OR)다.

   | 필터 | 값 |
   |---|---|
   | `status` | 상태 여러 개, 또는 `open`(등록 · 진행 · 테스트) · `closed`(완료 · 종료) |

4. 쪽 나누기: 쪽 크기 기본 50, 최대 100(넘게 달라고 하면 100). 전체 개수를 함께 준다.
5. 각 줄은 번호 · 유형 · 제목 · 상태 · 관리자 · 담당자 · 완료 기한 · 완료 예정일 · 상위 번호 · 하위 수 · 고친 때 · 기한 지남 여부를 준다.
6. 지운 일감은 나오지 않는다. 경로의 프로젝트 일감만 나온다.
7. 모르는 필터 값(없는 상태 · 유형, 숫자가 아닌 상위)은 400 `INVALID_FILTER` 다.
8. 성능은 [NFR-PERF-001](05-non-functional.md#nfr-perf-001)(일감 10만 건 프로젝트에서 p95 800ms)을 지킨다.

**세부 요구사항**

2. 댓글 · 연결 · 작업 시간 기록은 판을 만들지 않는다(이력에는 남는다). 필드를 바꾼 이력 줄에는 그 판 번호가 붙는다.
3. 판은 덮어쓰지 않는다 — 고치거나 지우는 길이 없고, DB 가 막는다.
4. `GET …/issues/{n}/revisions?before=&limit=` — 새 판부터, 판마다 누가 · 어느 길로 · 언제 · 바뀐 필드 이름 · 지금 판 표시. 쪽 넘김(최대 50).
5. `GET …/issues/{n}/revisions/{no}` — 그 판의 일감 전체.
6. `GET …/issues/{n}/revisions/{no}/diff?from=` — 두 판의 차이. `from` 이 비면 바로 앞 판과, 1판은 "없음"과 견준다. 필드는 전 · 후, 설명은 줄 단위(git 처럼 넣은 줄 · 지운 줄 · 줄 번호, 넣은 · 지운 줄 수). 같은 판끼리는 400 `SAME_REVISION`, 없는 판은 404 `REVISION_NOT_FOUND`.
7. 화면: 일감의 "리비전 · 차이" 화면 — 판 타임라인(누가 · 언제 · MCP 표시 · 바뀐 필드), 판을 고르면 바로 앞 판과의 차이, 아무 두 판 견주기, 한 판 전체 보기. 차이는 지운 줄 빨강 · 넣은 줄 초록에 `−` · `+` 를 함께 적는다(색만으로 전하지 않는다). 고른 판은 주소에 남는다.
8. 판 보기는 `issue.read` 다(독자면 누구나).

1. 자기 댓글만 고친다(고친 표시 · 고친 이력). 지우기는 자기 것 또는 `project.manage`, 지움 표시만("지운 댓글").
2. MCP: 댓글 목록(쪽 나누기) · 고치기 · 지우기.

**수용 기준**
- [ ] 남의 댓글을 고치면 403 이다
- [ ] 지운 댓글은 "지운 댓글"로 남는다

### FR-ISS-020 유형별 일감 템플릿 (워크스페이스 기본 · 프로젝트 덮어쓰기 · MCP)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-23: V12 · REST(워크스페이스 기본 · 프로젝트 덮어쓰기 · 되돌리기, 권한 · 감사 · 409) · 빠진 항목 알림 · MCP(일감 입구 `get_issue_template` · 결과의 `templateCheck`, 프로젝트 관리 입구 `list_issue_templates` · `set_issue_template` · `reset_issue_template`) · 자동 테스트 7건. 남은 것: 화면(워크스페이스 설정 · 프로젝트 설정의 템플릿 관리, 새 일감에서 템플릿 채우기, 빠진 항목 경고) |
| 관련 설계 | [일감 설계 — 템플릿](../design/05-issue.md#is-templates) · [MCP 설계 — 템플릿 도구](../design/06-mcp.md#mc-t-templates) |

**설명** — 사용자(2026-11-23): "이슈의 유형별로 작성 템플릿 넣어 주고 그걸 관리할 수 있게 해 줘. 또한 mcp 제공해서 그에 맞게 이슈 작성 및 수정할 수 있게". 결정: 워크스페이스 + 프로젝트(워크스페이스가 기본, 프로젝트가 덮어씀) · MCP 관리 도구도 · 빠진 항목은 알려만 줌.

**세부 요구사항**
1. 지금 쓰는 유형(새기능 · 버그 · 테스트 · 기술조사)마다 템플릿(Markdown, 30000자까지)이 하나 쓰인다. 고르는 순서는 프로젝트 덮어쓰기 → 워크스페이스 기본 → 처음 템플릿이다. 옛 유형에는 템플릿이 없다(`ISSUE_TYPE_RETIRED`).
2. 워크스페이스 기본은 `workspace.settings.manage`, 프로젝트 덮어쓰기는 `project.manage` 가 고친다. 지우면(되돌리기) 한 단계 위로 돌아간다. 읽기는 `workspace.read` · `issue.read`.
3. 고치기 · 되돌리기는 감사에 남는다(범위 · 유형 · 프로젝트 · 경로 WEB/MCP). 이미 정한 것을 고칠 때 낡은 `rowVersion` 이면 409 `CONCURRENT_UPDATE`.
4. 템플릿의 제목(#)이 항목이다. 제목 끝이 "(선택)" 이면 비워도 되는 항목이다. 일감 설명에 빠진 필수 항목은 저장을 막지 않고 알려만 준다(코드 블록 안의 제목은 세지 않고, 제목 수준 · 대소문자 · 공백은 따지지 않는다).
5. MCP 일감 입구는 템플릿을 주고(`get_issue_template`), `create_issue` · `update_issue` 결과에 `templateCheck`(출처 · 빠진 항목)를 붙인다. 프로젝트 관리 입구는 같은 권한으로 템플릿을 보고 · 정하고 · 되돌린다.
6. 화면: 워크스페이스 설정과 프로젝트 설정에 템플릿 관리(유형마다 Markdown 편집 · 출처 표시 · 되돌리기), 새 일감에서 유형을 고르면 설명이 비어 있을 때 템플릿을 채우고, 빠진 항목을 경고한다.

**수용 기준**
- [x] 처음에는 유형마다 처음 템플릿이 쓰이고 옛 유형은 목록에 없다
- [x] 워크스페이스 기본을 정하면 프로젝트가 물려받고, 프로젝트가 덮어쓰고, 되돌리면 한 단계 위로 돌아간다
- [x] 큐레이터 · 멤버는 템플릿을 고칠 수 없다(403 · MCP `PERMISSION_REQUIRED`)
- [x] 낡은 `rowVersion` 으로 고치면 409 다
- [x] MCP `create_issue` 결과가 빠진 필수 항목을 알려 주고, 다 채우면 빈 목록이다
- [x] 템플릿 고치기 · 되돌리기가 감사에 남는다(MCP 면 경로 MCP)
- [ ] 워크스페이스 설정 · 프로젝트 설정에서 템플릿을 고치고 되돌린다
- [ ] 새 일감에서 유형을 고르면 템플릿이 채워지고, 빠진 항목이 경고로 보인다

### FR-ISS-021 Markdown 편집기 (쓰면서 바로 그려지는 편집 · 도구 막대 · 목차 · 원문)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-23: Milkdown(Crepe) 편집기 · 위 고정 도구 막대 · 목차 · Markdown 원문 보기, 일감 설명 · 댓글 모두, 원문 보존(moai-wiki 와 같은 source-blocks — 실제 글 55건 열자마자 저장 = 원문), 첨부 그림 보이기 · 붙여 넣기 · 끌어 놓기 · 단추로 올리기, CSP 확인, 화면 자동 테스트 · ego-browser. 2026-11-23 보안: 편집기 schema 의 그림 toDOM 은 `attachment:` 만 `<img>`(글자로 붙여 넣기 · insert · 끌어 놓기에서 바깥 `<img>` 0회 확인). 남은 것: 영어 화면에서 편집기 둘러보기 · 표 칸 단위 고치기 보존(덩어리 단위의 한계) |
| 관련 설계 | [일감 설계 — 편집기](../design/05-issue.md#is-editor) · [WEB-DESIGN.md](../../WEB-DESIGN.md) · [SECURITY.md §9](../../SECURITY.md#9-화면web-frontend의-보안-규칙) |

**설명** — 사용자(2026-11-23): "이렇게 md 편집기를 만들고 이슈의 본문이나 덧글은 모두 md 로 작성할 수 있게 해 줘"(VS Code Markdown Editor 화면 — 위 도구 막대 · 왼쪽 목차 · 쓰면서 바로 그려짐). 저장 형식은 그대로 Markdown 이다.

**세부 요구사항**
1. 일감 설명(새 일감 · 고치기)과 댓글은 쓰면서 바로 그려지는 Markdown 편집기로 쓴다. 저장하는 값은 늘 Markdown 이다.
2. 위 고정 도구 막대: 목차 · 제목/문단 · 굵게 · 기울임 · 취소선 · 링크 | 글머리 · 번호 · 할 일 목록 · 표 | 인용 · 코드 블록 · 줄 안 코드 · 가로줄 | 되돌리기 · 다시 | 이미지 · 파일 넣기 · Markdown 원문. 도구 설명(단축키 함께)과 aria-label 이 있고, 좁은 화면에서는 막대 안에서만 가로로 밀린다.
3. 목차는 설명 편집기에서 편집 칸이 넓으면(900px 이상) 처음부터 열고, 제목을 누르면 그 자리로 간다. 댓글에는 목차가 없다.
4. "Markdown 원문"으로 원문을 그대로 고칠 수 있다(CodeMirror). 돌아오면 그 원문으로 편집기를 다시 만든다.
5. 손대지 않은 덩어리는 원문 그대로 저장한다 — 열자마자 저장하면 원문과 한 글자도 다르지 않다. 고친 덩어리만 편집기 모양이 된다(긴 목록 · 표의 한 칸을 고치면 그 덩어리 전체).
6. 첨부: 그림 · 파일을 붙여 넣거나 끌어 놓거나 단추로 고르면 그 일감에 올리고 그 자리에 `![이름](attachment:<id>)` 를 넣는다(올리는 동안 자리 표시 · 저장 단추 잠금, 새 일감은 만든 뒤부터). `attachment:` 그림은 편집 중에도 그 일감의 첨부로 보이고, 바깥 주소 그림은 받지 않는다.
7. 남이 쓴 글의 HTML 은 편집 중에도 실행하지 않는다(글자로 보인다). 편집 중에는 링크를 열지 않는다. 링크 넣기는 http · https · mailto · 이 화면 안의 경로 · 첨부 표시만 받는다.
8. 화면 보안 정책(CSP `script-src 'self'`)에서 바깥 스크립트 없이 돈다. 바깥 서비스(AI)를 부르는 편집기 기능은 끈다.
9. 다크 · 라이트를 따르고, 390px 에서도 쓸 수 있다.

**수용 기준**
- [x] 실제 일감 설명 · 댓글(moai-works · moai-wiki 39건)과 어려운 경우 16건을 편집기에 열자마자 꺼내 저장하면 원문과 한 글자도 다르지 않다(자동 시험) — 실제 앱에서도 #2 · #5 · #11 · #12 를 열고 원문 보기로 바꿔 저장된 글과 같음을 확인
- [x] 마지막 덩어리 하나를 고치면 그 덩어리만 바뀐다(자동 시험)
- [x] 붙여 넣기 · 단추로 그림을 올리면 그 자리에 표시가 들어가고 편집 중에도 그림이 보인다(ego-browser 2026-11-23)
- [x] 링크 넣기에서 javascript: 는 거절한다(자동 시험 · ego-browser)
- [x] CSP 위반 없이 편집기가 돈다 — 고치기 · 댓글 · 원문 보기 · 올리기(ego-browser, web-backend 11002)
- [x] 다크 · 390px 에서 쓸 수 있고 페이지가 가로로 밀리지 않는다(ego-browser 2026-11-23)
- [ ] 영어 화면에서 도구 막대 · 목차 · 링크 대화 상자를 확인했다
