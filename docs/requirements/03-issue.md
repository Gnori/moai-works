# 일감 요구사항 (FR-ISS)

일감 번호 · 필드 · 만들기 · 보기 · 고치기 · 지우기, 이력과 메모(비공개 메모 · 메모 고친 이력 · 사람/Agent 행위자 표시), 하위 일감과 롤업, 관계와 일정 이동, 관찰자 · 멘션, 첨부, 비공개 일감과 보기 범위, 일괄 편집 · 복사 · 옮기기, 텍스트 링크의 요구사항이다. Redmine 의 일감 동작을 기준으로 한다. 설계는 [일감 추적 설계](../design/05-issue-tracking.md)와 [프로젝트와 권한 설계](../design/04-project-permissions.md)에 있다.

## 1. 일감

<a id="fr-iss-001"></a>
### FR-ISS-001 일감 번호

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §3](../design/05-issue-tracking.md#is-number) |

**설명** — 일감은 워크스페이스 안 하나의 순번 `#123` 으로 부른다(Redmine 의 일감 id 와 같은 뜻, 범위는 워크스페이스). 프로젝트를 옮겨도 번호는 그대로이고, 글 속 `#123` · 커밋 `refs #123` 이 이 번호를 쓴다.

**세부 요구사항**
1. 번호는 프로젝트와 상관없이 워크스페이스마다 하나의 순번이어야 한다.
2. 번호는 일감을 만드는 트랜잭션 안에서 카운터 행으로 받아야 한다. 동시에 만들어도 겹치지 않고, 되돌린 만들기는 번호를 쓰지 않아야 한다.
3. 지운 일감의 번호는 다시 쓰지 않아야 한다.
4. 다른 프로젝트로 옮겨도 번호는 그대로여야 한다.
5. REST 경로는 `/workspaces/{workspace}/issues/{number}`, MCP 리소스는 `moai-works://{ws}/issues/{번호}` 여야 한다.
6. 없는 번호와 볼 수 없는 번호는 같은 404 여야 한다.

**수용 기준**
- [ ] 같은 워크스페이스에서 100개를 동시에 만들어도 번호가 겹치거나 비지 않는다
- [ ] 실패해 되돌린 만들기의 번호는 다음 일감이 쓴다
- [ ] 옮긴 일감의 번호가 같다
- [ ] 볼 수 없는 번호와 없는 번호의 응답(상태 · 본문)이 같다

<a id="fr-iss-002"></a>
### FR-ISS-002 일감 만들기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §4.1](../design/05-issue-tracking.md#is-lock) · [§2 모델](../design/05-issue-tracking.md#is-model) |

**설명** — 프로젝트에서 일감을 만든다. 사람은 웹으로, Agent 는 MCP `create_issue` 로 만들고 같은 규칙을 거친다. 담당을 비우면 카테고리 · 프로젝트의 기본 담당이 들어간다(Redmine 과 같다).

**세부 요구사항**
1. 만들기는 그 프로젝트의 `issue.create` 와 켜진 `issue_tracking` 모듈, 활성 프로젝트가 있어야 해야 한다.
2. 기본값: 트래커(프로젝트의 첫 트래커) · 상태(트래커 기본 상태) · 우선순위(기본 우선순위) · 사용자 정의 필드 기본값.
3. 필드마다 권한을 봐야 한다: 담당 `issue.assign` · 비공개 `issue.private.read` · 관찰자 `issue.watcher.manage` · 상위 일감 `issue.edit`.
4. 첫 상태는 워크플로의 "새 일감" 전이가 허용하는 상태여야 한다([FR-WFL-004](04-workflow.md#fr-wfl-004)).
5. 담당이 비었으면 카테고리의 기본 담당, 없으면 프로젝트의 기본 담당을 넣어야 한다(만들 때만).
6. 첨부 · 관찰자 · 멘션을 함께 받을 수 있어야 한다.
7. 작성자 · 만든 경로(`created_via`), MCP 면 엔드포인트 · 키를 남기고 이벤트 `issue.created` 를 내야 한다.
8. MCP `create_issue` 는 멱등 키를 받아 같은 키면 24시간 같은 일감을 돌려줘야 한다.

**수용 기준**
- [ ] 독자가 만들면 403, 비독자는 404 다
- [ ] 보고자가 담당을 정하면 403 이고, 담당 없이 만들면 카테고리 기본 담당이 들어간다
- [ ] 만든 일감에 작성자 · 경로가 남고 `issue.created` 가 나간다
- [ ] MCP `create_issue` 로 만든 결과가 REST 와 같고, 같은 멱등 키로 두 번 부르면 일감은 하나다

<a id="fr-iss-003"></a>
### FR-ISS-003 일감 필드와 검증

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §2](../design/05-issue-tracking.md#is-model) · [§2.2 검증](../design/05-issue-tracking.md#is-validation) |

**설명** — 일감은 Redmine 의 표준 필드(트래커 · 제목 · 설명 · 상태 · 우선순위 · 담당 · 카테고리 · 대상 버전 · 상위 · 시작 · 기한 · 예상 시간 · 진척률 · 비공개)와 사용자 정의 필드를 가진다. 트래커마다 일부 필드를 끌 수 있다.

**세부 요구사항**
1. 필드와 규칙은 설계 §2.1 과 같아야 한다(제목 1 ~ 255자 필수, 기한 ≥ 시작, 예상 시간 0 이상, 진척률 0 ~ 100).
2. 트래커에서 끈 표준 필드는 화면 · 응답에 나오지 않아야 하고, 값을 보내면 422 `FIELD_DISABLED` 여야 한다.
3. 담당은 담당 가능 주체, 카테고리는 그 프로젝트 것, 대상 버전은 그 프로젝트에 공유된 열린 버전이어야 한다(바꿀 때만 검사).
4. 오류는 RFC 9457 꼴이고, 필드 오류는 `errors: [{field, code, message}]` 로 한 번에 모두 돌려줘야 한다.
5. 번호 · 작성자 · 만든 때 · 고친 때 · 닫힌 때 · 총 예상 시간 · 만든 경로는 시스템이 정해야 한다.

**수용 기준**
- [ ] 기한이 시작보다 앞이면 422 다
- [ ] 끈 필드에 값을 보내면 422 `FIELD_DISABLED` 다
- [ ] 그 프로젝트에 공유되지 않은 버전을 고르면 422 다
- [ ] 오류가 여럿이면 한 응답에 모두 나온다

<a id="fr-iss-004"></a>
### FR-ISS-004 일감 보기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §4.6](../design/05-issue-tracking.md#is-lock) · [§19 API](../design/05-issue-tracking.md#is-api) |

**설명** — 일감 쪽은 필드 · 설명 · 이력 · 하위 일감 · 관계 · 첨부 · 관찰자를 보인다. 화면과 Agent 가 "지금 무엇을 할 수 있나"를 미리 알도록 할 수 있는 일과 허용 상태를 함께 준다.

**세부 요구사항**
1. 보이는 일감만 보여야 한다([FR-ISS-021](#fr-iss-021)).
2. `include` 로 이력 · 관계 · 하위 · 첨부 · 관찰자를 고를 수 있어야 한다.
3. 볼 수 없는 하위 · 관계 상대는 빼고, 볼 수 없는 상위는 "비공개 일감"으로만 보여야 한다.
4. 응답에 `myActions`(고칠 수 있는 필드 · 담당 · 지우기 · 메모 · 관계 · 관찰 등) · `allowedStatuses` · `fieldRules` 를 넣어야 한다.
5. 설명 · 메모의 텍스트 링크는 `references` 로 풀어 줘야 한다([FR-ISS-012](#fr-iss-012)).
6. MCP `get_issue` 는 같은 서비스로 같은 내용을 줘야 하고, 설명 · 메모를 "사용자 데이터"로 표시해야 한다([MCP 요구사항](12-mcp.md)).

**수용 기준**
- [ ] 보고자의 일감 쪽 하위 목록에 남의 비공개 하위가 없다
- [ ] `myActions` 가 "된다"고 한 일은 실제로 되고, "안 된다"고 한 일은 실제로 403 이다
- [ ] 같은 사람의 MCP `get_issue` 와 REST 응답의 필드 · 거름이 같다
- [ ] 비독자는 404 다

<a id="fr-iss-005"></a>
### FR-ISS-005 일감 고치기와 낙관적 잠금

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §4.2](../design/05-issue-tracking.md#is-lock) · [§4.3 필드별 권한](../design/05-issue-tracking.md#is-change-policy) |

**설명** — 일감을 고칠 때 필드마다 필요한 권한이 다르다(필드는 편집 권한, 담당은 담당 권한, 상태는 워크플로). 남이 먼저 고쳤으면 덮어쓰지 않도록 `lock_version` 을 확인한다.

**세부 요구사항**
1. 고치기 요청(REST · MCP `update_issue`)에는 `lock_version` 이 있어야 하고, 다르면 409 와 그 사이의 저널을 돌려줘야 한다.
2. 필드별 권한은 설계 §4.3 의 표를 따라야 한다: 필드 = `issue.edit` 또는 (`issue.edit.own` ∧ 작성자), 담당 = `issue.assign`, 상태 = 워크플로, 비공개 = `issue.private.read`.
3. 트래커 → 상태를 먼저 적용하고, 필드 권한은 저장 뒤 상태로 봐야 한다.
4. 같은 값만 보내면 저널 · 이벤트 없이 끝나야 한다.
5. 저장하면 상위 롤업 · 후행 일정 이동 · 중복 닫기를 같은 트랜잭션에서 해야 한다.
6. 화면은 충돌 때 덮어쓰기 · 메모만 남기기 · 취소를 고르게 해야 한다.
7. 저장마다 저널 하나와 이벤트 `issue.updated` 를 남겨야 한다.

**수용 기준**
- [ ] 오래된 `lock_version` 으로 고치면 409 와 `currentLockVersion` 이 오고 값이 바뀌지 않는다
- [ ] 보고자는 자기 일감의 제목을 고치고, 남의 일감은 403 이다
- [ ] 개발자는 담당을 바꾸고, 보고자는 403 이다
- [ ] 같은 고치기를 MCP `update_issue` 로 해도 결과 · 저널이 같다

<a id="fr-iss-006"></a>
### FR-ISS-006 일감 지우기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §17.4](../design/05-issue-tracking.md#is-delete) |

**설명** — 잘못 만든 일감을 지운다(Redmine 과 같이 행을 지운다). 되돌릴 수 없으므로 하위 일감과 시간 기록 처리를 확인받고, 감사에 요약을 남긴다.

**세부 요구사항**
1. 지우기는 `issue.delete` 가 있어야 해야 하고, MCP 에는 없어야 한다.
2. 하위 일감 전체를 함께 지워야 한다(목록을 보이고 확인).
3. 시간 기록은 지우기 · 프로젝트에 남기기(기본) · 다른 일감으로 옮기기 중에 골라야 한다([시간 요구사항](07-time.md)).
4. 저널 · 관계 · 관찰자는 함께 지우고, 첨부 객체는 작업 큐가 지워야 한다.
5. 감사 `issue.deleted` 에 번호 · 프로젝트 · 트래커 · 상태 · 제목 · 작성자 · 함께 지운 하위 번호를 남기고, 이벤트 `issue.deleted` 를 내야 한다.
6. 지운 번호는 다시 쓰지 않고, 그 번호의 텍스트 링크는 글자로만 보여야 한다.

**수용 기준**
- [ ] 개발자가 지우면 403 이다
- [ ] 하위 3개가 함께 지워지고 감사에 그 번호들이 남는다
- [ ] 지운 뒤 `#123` 은 글자로만 보인다
- [ ] MCP `tools/list` 에 지우기 도구가 없다

## 2. 이력 · 메모

<a id="fr-iss-007"></a>
### FR-ISS-007 변경 이력 (저널)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §5](../design/05-issue-tracking.md#is-journal) |

**설명** — 저장한 번마다 저널 하나가 쌓인다. 저널은 누가 · 언제 · 어디로 · 무엇을 바꿨는지(필드마다 전 · 후)와 메모를 담는다. Redmine 의 이력과 같다.

**세부 요구사항**
1. 저장마다 저널 하나를 만들고, 바뀐 필드마다 상세 줄(`ATTR` · `CF` · `ATTACHMENT` · `RELATION`)을 남겨야 한다.
2. 값은 id 로 저장하고 이름은 읽을 때 찾아야 한다(지운 값은 "(지운 값)").
3. 설명 같은 긴 글의 변경은 차이로 보여야 한다.
4. 저널은 메모 고치기 열 말고는 바꿀 수 없어야 한다(DB 가 막는다).
5. 비공개 메모 · 못 보는 사용자 정의 필드 · 안 보이는 관계 상대의 줄은 그것을 볼 수 없는 사람에게 빼야 한다.
6. 상위 일감의 계산 값은 저널을 남기지 않고, 일정 이동 · 중복 닫기 · 버전 비우기는 원인과 함께 남겨야 한다.

**수용 기준**
- [ ] 필드 5개를 한 번에 바꾸면 저널 하나에 상세 5줄이다
- [ ] DB 에서 저널의 메모 밖 열을 고치려 하면 거부된다
- [ ] 못 보는 사용자 정의 필드의 상세 줄이 응답에 없다
- [ ] 일정 이동 저널에 원인 일감 번호가 있다

<a id="fr-iss-008"></a>
### FR-ISS-008 메모

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §5](../design/05-issue-tracking.md#is-journal) · [§4.5 메모만 쓰기](../design/05-issue-tracking.md#is-lock) |

**설명** — 일감에 메모를 단다. 사람과 Agent 가 일감 위에서 대화하는 곳이다. 메모는 쌓기만 하므로 동시에 써도 잃지 않는다.

**세부 요구사항**
1. 메모 쓰기는 `issue.note` 가 있어야 해야 한다.
2. 메모는 Markdown 이고 텍스트 링크 · 멘션 · 첨부를 함께 쓸 수 있어야 한다.
3. 메모만 쓸 때는 `lock_version` 이 필요 없어야 하고, 일감의 `lock_version` 을 올리지 않아야 한다.
4. 필드 변경과 함께 쓰면 한 저널이어야 한다.
5. MCP `add_issue_note` 는 같은 서비스를 불러야 한다.
6. `#123#note-4` 처럼 메모로 가는 링크가 있어야 한다.

**수용 기준**
- [ ] 독자가 메모를 쓰면 403 이다
- [ ] 두 사람이 동시에 메모를 써도 둘 다 남는다
- [ ] 메모가 달린 뒤에도 그 전에 읽은 `lock_version` 으로 필드를 고칠 수 있다
- [ ] MCP `add_issue_note` 의 저널에 Agent 행위자와 MCP 경로가 남는다

<a id="fr-iss-009"></a>
### FR-ISS-009 행위자와 경로 표시

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §5.1](../design/05-issue-tracking.md#is-actor) |

**설명** — 사람과 Agent 가 같은 일감을 다루므로 누가 · 어떤 길로 했는지가 분명해야 한다. 이력에 "Agent 빌드봇" 또는 "김지원 (MCP 로)" 처럼 보인다.

**세부 요구사항**
1. 작성자 · 담당 · 저널 행위자 · 관찰자는 주체 열(`*_type` = `USER` · `AGENT` · `SYSTEM` + `*_id`)로 저장해야 한다.
2. 경로 `via`(`WEB` · `REST` · `MCP` · `EMAIL` · `SCM` · `IMPORT` · `SYSTEM`)와, MCP 면 엔드포인트 · 키 id 를 남겨야 한다.
3. 화면은 설계 §5.1 의 표대로 보여야 한다: 서비스 키 = "Agent 이름 + Agent 표 + 책임자", 개인 키 = "이름 (MCP 로 · 엔드포인트)", 시스템 = "시스템 (원인)".
4. 일감을 만든 경로도 일감 쪽 머리에 보여야 한다.
5. 지운 Agent · 사람은 남긴 표시 이름으로 보여야 한다.

**수용 기준**
- [ ] 서비스 키로 쓴 메모는 "빌드봇 Agent" 로 보인다
- [ ] 개인 키로 쓴 메모는 "이름 (MCP 로 · 엔드포인트 이름)" 으로 보인다
- [ ] 웹에서 쓴 메모는 이름만 보인다
- [ ] 일감 행과 저널에 MCP 키 id 가 남고, 감사의 행위자와 저널의 행위자가 같다

## 3. 첨부 · 텍스트 링크

<a id="fr-iss-010"></a>
### FR-ISS-010 첨부 올리기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §14](../design/05-issue-tracking.md#is-attachment) |

**설명** — 일감 · 메모에 파일을 붙인다. 파일은 MinIO 버킷 `moai-works-attachments` 에 두고, 키는 api 가 정한다. 먼저 올려서 받은 id 를 일감 저장 때 붙이는 두 단계다(Redmine 의 업로드 토큰과 같다).

**세부 요구사항**
1. `POST /workspaces/{ws}/uploads` 로 올리면 api 가 크기 · 확장자를 확인하고 MinIO 에 흘려 저장하며 SHA-256 과 내용 형식을 구해 `PENDING` id 를 돌려줘야 한다.
2. 키는 `{workspace_id}/{yyyy}/{mm}/{attachment_id}` 여야 한다(파일 이름 · 프로젝트를 넣지 않는다).
3. 크기 한도(기본 20 MB) · 허용 확장자 · 막는 확장자(기본 실행 파일)는 워크스페이스 설정을 따라야 한다.
4. 붙이기는 올린 사람만 자기 `PENDING` 에 할 수 있어야 하고, 일감을 고칠 권한 또는 메모 권한이 있어야 한다.
5. 붙이면 저널에 `ATTACHMENT` 줄을 남겨야 한다.
6. 붙이지 않은 올림은 24시간 뒤 객체와 함께 지워야 한다.
7. 본문의 `![설명](attachment:파일이름.png)` 은 그 일감의 첨부로 풀어야 한다.

**수용 기준**
- [ ] 한도를 넘는 파일은 413, 막는 확장자는 422 다
- [ ] 남이 올린 id 를 붙이면 404 다
- [ ] 24시간 지난 `PENDING` 은 행과 객체가 모두 지워진다
- [ ] 붙이면 저널에 파일 이름이 남는다

<a id="fr-iss-011"></a>
### FR-ISS-011 첨부 내려받기와 권한

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §14](../design/05-issue-tracking.md#is-attachment) |

**설명** — 첨부는 api 를 거쳐 내려받는다. 첨부가 붙은 일감을 볼 수 있는 사람만 받는다. 올린 파일이 브라우저에서 실행되지 않게 응답 머리를 둔다.

**세부 요구사항**
1. 내려받기는 api 를 거쳐 흘려 보내야 하고, MinIO 주소를 주지 않아야 한다.
2. 첨부가 붙은 곳을 볼 수 없으면 404 여야 한다(일감은 보기 범위까지).
3. 응답은 `Content-Disposition: attachment` · `X-Content-Type-Options: nosniff` · `Content-Security-Policy: sandbox` 를 가져야 하고, 그림(png · jpeg · gif · webp)만 바로 보기를 허용해야 한다.
4. 범위 요청(`Range`)을 지원해야 한다.
5. 지우기는 그 일감을 고칠 수 있는 주체만 할 수 있어야 하고, 저널 줄을 남기고 객체는 작업 큐가 지워야 한다.

**수용 기준**
- [ ] 비공개 일감을 못 보는 사람이 그 첨부를 받으면 404 다
- [ ] 응답 머리가 위와 같다
- [ ] HTML 파일을 받아도 브라우저가 실행하지 않는다
- [ ] 보고자가 남의 일감 첨부를 지우면 403 이다

<a id="fr-iss-012"></a>
### FR-ISS-012 텍스트 링크

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §15](../design/05-issue-tracking.md#is-links) |

**설명** — 글 속의 `#123` 은 그 일감으로 링크된다(Redmine 과 같다). 링크가 볼 수 없는 일감의 제목을 흘리지 않아야 한다.

**세부 요구사항**
1. `#123` · `##123`(제목과 함께) · `#123#note-4` · `#note-4` · `!#123`(풀지 않음) · `project:식별자` · `attachment:파일이름` 을 풀어야 한다.
2. 코드 칸 · 코드 묶음 안에서는 풀지 않아야 한다.
3. 응답에 `references` 를 줘야 하고, 볼 수 없는 대상과 없는 대상은 똑같이 `visible: false`(글자 그대로)여야 한다.
4. 닫힌 일감은 줄을 긋도록 `closed` 를 줘야 한다.
5. `version:` · `[[쪽]]` · `commit:` 같은 다른 표기는 그 모듈이 같은 틀로 더해야 한다.
6. 편집기 미리보기용 API 가 있어야 하고, MCP 는 원문과 `references` 를 함께 줘야 한다.

**수용 기준**
- [ ] 볼 수 없는 `#123` 과 없는 `#999999` 의 `references` 가 같다(제목 없음)
- [ ] 코드 칸 안의 `#123` 은 링크가 아니다
- [ ] 닫힌 일감의 링크에 `closed: true` 가 온다
- [ ] `!#123` 은 글자로 남는다

## 4. 비공개 메모 · 메모 고치기

<a id="fr-iss-013"></a>
### FR-ISS-013 비공개 메모

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §5.3](../design/05-issue-tracking.md#is-private-notes) · [프로젝트 권한 §11](../design/04-project-permissions.md#pp-private) |

**설명** — 고객 · 다른 팀이 보는 일감에 내부 사람만 보는 메모를 단다(Redmine 의 비공개 메모).

**세부 요구사항**
1. 메모마다 비공개 표시가 있어야 하고, 쓰기 · 보기 · 바꾸기는 `issue.note.private` 가 있어야 해야 한다.
2. 볼 수 없는 사람에게는 메모를 빼고, 같은 저널에 필드 변경이 있으면 변경만 보여야 한다. 변경도 없으면 저널 줄을 빼야 한다.
3. 알림 · 웹훅 · 검색 · 내보내기 · MCP 모두 같은 규칙을 따라야 한다.
4. 이벤트에 `privateNote` 표시를 실어야 한다.

**수용 기준**
- [ ] 보고자에게 비공개 메모가 화면 · REST · MCP · CSV 어디에도 없다
- [ ] 필드 변경과 비공개 메모가 함께인 저널은 보고자에게 변경만 보인다
- [ ] 보고자가 비공개 메모를 쓰면 403 이다
- [ ] 비공개 메모 알림이 보고자에게 가지 않는다([알림 요구사항](09-notification.md)과 함께 확인)

<a id="fr-iss-014"></a>
### FR-ISS-014 메모 고치기와 고친 이력

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §5.4](../design/05-issue-tracking.md#is-note-edit) |

**설명** — 쓴 사람은 자기 메모를 고칠 수 있고, 고쳐도 옛 글이 남는다(Redmine 은 남기지 않지만 여기서는 남긴다). 프로젝트 관리자는 부적절한 메모를 숨긴다.

**세부 요구사항**
1. 메모 고치기 · 비공개로 바꾸기 · 비우기는 쓴 사람만, `issue.note`(비공개면 `issue.note.private`)가 있을 때 해야 한다.
2. 고칠 때마다 옛 글을 이력에 쌓고 저널에 "고침" 표시를 해야 한다.
3. 남의 메모 숨기기 · 다시 보이기는 `project.manage` 가 있어야 하고, 숨긴 메모의 원문은 그 사람만 봐야 한다.
4. 고친 이력은 `issue.read` 로 보되, 비공개 메모의 이력은 `issue.note.private` 로만 봐야 한다.
5. 이벤트 `issue.note.edited` 를 내야 한다.

**수용 기준**
- [ ] 남의 메모를 고치면 403 이다
- [ ] 고친 뒤 이력에 옛 글이 있다
- [ ] 숨긴 메모는 프로젝트 관리자만 원문을 본다
- [ ] 비공개 메모의 이력은 보고자에게 보이지 않는다

## 5. 하위 일감 · 관계

<a id="fr-iss-015"></a>
### FR-ISS-015 하위 일감

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §6](../design/05-issue-tracking.md#is-tree) |

**설명** — 큰 일감을 하위 일감으로 나눈다(Redmine 의 하위 일감). Agent 가 기능을 할 일로 쪼갤 때도 쓴다.

**세부 요구사항**
1. 상위를 정하거나 바꾸려면 그 일감에서 `issue.edit` 이 있고 새 상위를 볼 수 있어야 해야 한다.
2. 상위 · 하위의 프로젝트 관계는 워크스페이스 설정(기본: 같은 맨 위 프로젝트 아래)을 따라야 한다.
3. 자기 · 자기 하위를 상위로 정할 수 없고, 깊이는 10 까지여야 한다.
4. 상위 · 하위 사이에 관계를 걸 수 없고, 선행 · 차단으로 이어진 일감을 상위로 정할 수 없어야 한다.
5. 열린 하위가 있으면 상위를 닫을 수 없고, 상위가 닫혀 있으면 하위를 다시 열 수 없어야 한다([FR-WFL-005](04-workflow.md#fr-wfl-005)).
6. 상위를 지우거나 옮기면 하위(같은 프로젝트에 있던 것)가 따라가야 한다.
7. MCP `create_issue` · `update_issue` 의 상위 필드도 같은 규칙이어야 한다.

**수용 기준**
- [ ] 자기 하위를 상위로 정하면 422 다
- [ ] 다른 맨 위 프로젝트의 일감을 상위로 정하면(기본 설정) 422 다
- [ ] 열린 하위가 있는 상위는 허용 상태에 닫힌 상태가 없고, 억지로 보내면 409 다
- [ ] 같은 경우를 MCP 로 해도 결과가 같다

<a id="fr-iss-016"></a>
### FR-ISS-016 상위 일감 값 계산 (롤업)

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §6.2](../design/05-issue-tracking.md#is-rollup) |

**설명** — 상위 일감의 시작 · 기한 · 우선순위 · 진척률 · 예상 시간을 하위에서 계산한다. 필드마다 계산할지 따로 둘지는 워크스페이스 설정([FR-WFL-011](04-workflow.md#fr-wfl-011))이다. 식은 Redmine 과 같다.

**세부 요구사항**
1. 시작 = 하위 시작의 최솟값, 기한 = 하위 기한의 최댓값이어야 한다.
2. 우선순위 = 열린 하위 가운데 가장 높은 우선순위, 열린 하위가 없으면 기본 우선순위여야 한다.
3. 총 예상 = 자기 예상 + 하위 총 예상의 합이어야 하고, 설정이 "하위에서 계산"이면 자기 예상도 하위 합(읽기전용)이어야 한다.
4. 진척률 = 하위의 총 예상으로 가중한 평균(예상 없는 하위는 평균 예상, 닫힌 하위는 100)이어야 한다. "상태로 정함"이고 상태에 기본 진척률이 있으면 그것이어야 한다.
5. 계산하는 필드는 상위에서 읽기전용이어야 한다.
6. 하위를 만들고 · 고치고 · 지우고 · 옮길 때 그 상위부터 맨 위까지 같은 트랜잭션에서 다시 계산해야 한다. 계산 값의 변화는 저널을 남기지 않는다.

**수용 기준**
- [ ] 하위 A(예상 10, 진척 50%) · B(예상 30, 닫힘)의 상위 진척률이 87% 다
- [ ] 하위 기간 11-01 ~ 11-05 · 11-10 ~ 11-20 의 상위가 11-01 ~ 11-20 이다
- [ ] 열린 하위가 높음 · 긴급이면 상위가 긴급이다
- [ ] 계산하는 필드를 상위에서 고치면 403, 설정을 "따로"로 바꾸면 고칠 수 있다

<a id="fr-iss-017"></a>
### FR-ISS-017 일감 관계

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §7](../design/05-issue-tracking.md#is-relation) |

**설명** — 일감 사이에 관련 · 중복 · 차단 · 선행/후행(지연 일수) · 복사 관계를 건다(Redmine 과 같다). 차단은 닫기를 막고, 선행은 일정을 움직이고, 중복은 원본과 함께 닫힌다.

**세부 요구사항**
1. 종류는 `RELATES` · `DUPLICATES` · `BLOCKS` · `PRECEDES`(지연 0 ~ 999일) · `COPIED_TO` 여야 하고, 반대 이름(`duplicated_by` · `blocked_by` · `follows` · `copied_from`)도 받아야 한다.
2. 관계를 걸고 빼려면 보고 있는 일감의 프로젝트에서 `issue.relation.manage` 가 있고 상대 일감을 볼 수 있어야 해야 한다.
3. 두 일감 사이에는 관계 하나, 자기 자신 · 상위 · 하위와는 안 되고, 프로젝트를 넘는 관계는 설정을 따라야 한다.
4. 선행 · 차단 관계에 고리가 생기지 않아야 한다.
5. 걸고 빼면 양쪽 일감에 저널을 남겨야 한다.
6. 상대를 볼 수 없는 관계는 보이지 않아야 한다.
7. MCP `add_issue_relation` · `remove_issue_relation` 은 같은 규칙이어야 한다.

**수용 기준**
- [ ] 같은 쌍에 두 번째 관계는 409 다
- [ ] A 선행 B 가 있을 때 B 선행 A 는 422 `CIRCULAR_DEPENDENCY` 다
- [ ] 상대를 볼 수 없으면 없는 번호와 같은 404 다
- [ ] 양쪽 일감에 저널이 남고, 보고자가 걸면 403 이다

<a id="fr-iss-018"></a>
### FR-ISS-018 선행 · 후행 일정 자동 이동

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §7.3](../design/05-issue-tracking.md#is-schedule) |

**설명** — 선행 일감의 기한이 바뀌면 후행 일감의 날짜가 따라 움직인다(Redmine 3.3 이후와 같다). 기간은 작업일로 지킨다.

**세부 요구사항**
1. 후행의 가장 이른 시작 = 선행의 기한 + 지연 + 1 작업일(선행이 여럿이면 가장 늦은 것)이어야 한다. 쉬는 요일은 워크스페이스 설정(기본 토 · 일)이다.
2. 후행의 시작을 가장 이른 시작보다 앞으로 놓으면 422 여야 한다.
3. 선행의 시작 · 기한이 바뀌면 후행을 가장 이른 시작으로 맞춰야 한다(늦어지면 밀고, 당겨지면 당긴다). 기간은 작업일 수로 지킨다.
4. 사슬(A → B → C)과 날짜를 하위에서 계산하는 상위(그 잎들)까지 이어서 움직여야 한다.
5. 움직인 일감마다 저널(원인 = 선행 번호, 행위자 = 선행을 바꾼 사람)을 남겨야 한다.
6. 한 번에 500개를 넘게 움직여야 하면 저장을 거부해야 한다.

**수용 기준**
- [ ] A 기한 금 11-20, 지연 0 이면 이틀짜리 B 가 월 11-23 ~ 화 11-24 다
- [ ] A 기한을 2 작업일 늦추면 B 도 2 작업일 밀리고, 당기면 당겨진다
- [ ] B 의 시작을 가장 이른 시작보다 앞으로 놓으면 422 다
- [ ] A → B → C 사슬이 함께 움직이고, B · C 저널에 원인 `#A` 가 있다

## 6. 관찰자 · 멘션 · 비공개

<a id="fr-iss-019"></a>
### FR-ISS-019 관찰자

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §16](../design/05-issue-tracking.md#is-watcher) |

**설명** — 일감의 변경 알림을 받을 사람(또는 Agent 계정)을 관찰자로 넣는다(Redmine 과 같다). 알림을 실제로 보내는 규칙은 [알림 요구사항](09-notification.md)에 있다.

**세부 요구사항**
1. 관찰자는 그 일감을 볼 수 있는 사람 · Agent 계정이어야 한다.
2. 나를 넣고 빼기는 `issue.read` 로, 남을 넣고 빼기는 `issue.watcher.manage` 로 해야 한다. 만들 때 함께 고를 수 있어야 한다.
3. 관찰자 목록은 `issue.read` 로 봐야 한다.
4. 관찰자가 일감을 볼 수 없게 되면 행은 남기고 알림 · 목록에서 빼야 한다.
5. 저널은 남기지 않고 이벤트 `issue.watcher.added` · `removed` 를 내야 한다.

**수용 기준**
- [ ] 독자는 자기를 관찰자로 넣고, 남을 넣으면 403 이다
- [ ] 그 비공개 일감을 볼 수 없는 사람을 넣으면 422 다
- [ ] Agent 계정을 관찰자로 넣을 수 있다
- [ ] 넣으면 `issue.watcher.added` 가 나간다

<a id="fr-iss-020"></a>
### FR-ISS-020 멘션

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §15.3](../design/05-issue-tracking.md#is-mention) |

**설명** — 설명 · 메모에서 `@사람` 으로 부르면 그 사람이 관찰자가 되고 알림을 받는다. Agent 계정도 부를 수 있다.

**세부 요구사항**
1. 멘션은 `@[이름](mention:user/<id>)` · `@[이름](mention:agent/<id>)` 꼴로 저장하고, `@이메일` 도 받아 이 꼴로 바꿔야 한다.
2. 저장할 때 멘션된 주체 가운데 그 일감을 볼 수 있는 주체만(비공개 메모면 `issue.note.private` 도) 관찰자로 넣고 `issue.mentioned` 를 내야 한다.
3. 볼 수 없는 주체는 조용히 건너뛰어야 한다(존재를 알리지 않는다).
4. 편집기 자동 완성은 그 일감을 볼 수 있는 프로젝트 주체만 보여야 한다.
5. 글 하나에 50명까지여야 한다.

**수용 기준**
- [ ] 멘션된 개발자가 관찰자가 되고 `issue.mentioned` 의 대상이 된다
- [ ] 볼 수 없는 사람을 멘션하면 관찰자가 되지 않고, 응답에서 그 사실이 드러나지 않는다
- [ ] `@이메일` 이 표준 꼴로 저장된다
- [ ] 자동 완성 목록에 `RESTRICTED` 프로젝트의 비독자가 없다

<a id="fr-iss-021"></a>
### FR-ISS-021 비공개 일감과 보기 범위

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §11](../design/04-project-permissions.md#pp-private) · [일감 설계 §12.3](../design/05-issue-tracking.md#is-query-acl) |

**설명** — 일감을 비공개로 하면 권한이 있는 사람과 작성자 · 담당자만 본다(Redmine 의 비공개 일감과 "일감 보기 범위"). 같은 판정을 모든 읽기 길에 쓴다.

**세부 요구사항**
1. 보기 범위는 `ALL`(`issue.private.read` 가 있으면 — 비공개 포함 전체) · `DEFAULT`(비공개가 아닌 것 + 내가 만들었거나 맡은 비공개 일감)여야 한다.
2. 관찰자라서 보이지는 않아야 한다.
3. 비공개로 정하고 풀기는 `issue.private.read` 가 있어야 해야 한다.
4. 목록 · 보드 · 검색 · 간트 · 캘린더 · 로드맵 · 관계 · 하위 · 텍스트 링크 · 알림 · 활동 · 웹훅 · 내보내기 · MCP 가 같은 판정을 써야 한다.
5. 담당에서 빠지면 다음 요청부터 그 비공개 일감을 볼 수 없어야 한다(다른 조건이 없으면).

**수용 기준**
- [ ] 보고자에게 남의 비공개 일감이 404 이고 목록 · 검색에 없다
- [ ] 보고자는 자기가 만들었거나 맡은 비공개 일감을 본다
- [ ] 담당에서 빠진 뒤 다음 요청부터 404 다
- [ ] 보고자가 비공개로 정하면 403 이고, 같은 경우를 MCP `search_issues` · `get_issue` 로 해도 결과가 같다

## 7. 일괄 · 복사 · 옮기기

<a id="fr-iss-022"></a>
### FR-ISS-022 일괄 편집

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §17.1](../design/05-issue-tracking.md#is-bulk) |

**설명** — 목록에서 여러 일감을 골라 상태 · 담당 · 버전 등을 한 번에 바꾼다(Redmine 의 일괄 편집). 사람만 웹에서 한다.

**세부 요구사항**
1. 한 번에 200개까지, 여러 프로젝트에 걸쳐 고를 수 있어야 한다.
2. 고를 수 있는 값은 고른 일감 모두에 쓸 수 있는 값(상태는 허용 상태의 교집합 등)이어야 하고, "비우기"가 있어야 한다.
3. 일감마다 따로 트랜잭션으로 고치기의 모든 판정(권한 · 워크플로 · 필드 권한 · 검증)을 거쳐야 한다.
4. 모두에 같은 메모(비공개 선택)를 달 수 있어야 한다.
5. 결과는 일감마다 성공 · 실패와 이유를 보여야 한다.
6. 일감마다 저널(원인 `BULK`)과 감사 `issue.bulk_updated` 를 남겨야 한다.
7. 일괄 지우기 · 복사 · 옮기기도 같은 방식이어야 하고, MCP 에는 없어야 한다.

**수용 기준**
- [ ] 권한 없는 일감이 섞이면 그것만 실패하고 이유가 나오며, 나머지는 저장된다
- [ ] 교집합 밖의 상태는 고를 수 없고, API 로 보내면 그 일감만 실패한다
- [ ] 일감마다 저널의 원인이 `BULK` 다
- [ ] MCP `tools/list` 에 일괄 도구가 없다

<a id="fr-iss-023"></a>
### FR-ISS-023 일감 복사

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §17.2](../design/05-issue-tracking.md#is-copy) |

**설명** — 일감을 같은 프로젝트나 다른 프로젝트로 복사한다(Redmine 과 같다). 하위 · 첨부 · 관찰자를 함께 복사하고 원본과 이을 수 있다.

**세부 요구사항**
1. 원본을 볼 수 있고 대상 프로젝트에서 `issue.create` 가 있어야 해야 한다.
2. 대상 프로젝트 · 트래커 · 상태와 첨부 · 하위 · 관찰자 복사 · 원본과 잇기를 골라야 한다.
3. 번호 · 작성자(복사한 사람) · 때 · 저널 · 시간 기록은 새로 해야 한다.
4. 대상에서 쓸 수 없는 값(담당 · 카테고리 · 버전 · 사용자 정의 필드 · 상태)은 비우거나 기본값으로 맞춰야 한다.
5. 하위는 보이는 것만 복사하고, 첨부는 서버 쪽 복사로 새 키를 줘야 한다.
6. 원본과 이으면 `COPIED_TO` 관계를 만들어야 한다.

**수용 기준**
- [ ] 대상에서 `issue.create` 가 없으면 403 이다
- [ ] 복사한 첨부는 원본 첨부를 지워도 남는다
- [ ] 볼 수 없는 하위는 복사되지 않는다
- [ ] 이은 경우 양쪽에서 복사 관계가 보인다

<a id="fr-iss-024"></a>
### FR-ISS-024 일감 옮기기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §17.3](../design/05-issue-tracking.md#is-move) |

**설명** — 일감을 다른 프로젝트로 옮긴다. 번호는 그대로이고, 새 프로젝트에서 쓸 수 없는 값은 맞춘다(Redmine 과 같다).

**세부 요구사항**
1. 원래 쪽의 편집 권한(`issue.edit`, 또는 `issue.edit.own` ∧ 작성자)과 대상의 `issue.create` 가 있어야 해야 한다.
2. 번호는 그대로여야 한다.
3. 대상이 그 트래커를 쓰지 않으면 같은 요청에서 트래커를 골라야 하고, 상태 · 담당 · 카테고리(같은 이름) · 버전은 대상에서 쓸 수 있으면 두고 아니면 비워야 한다.
4. 하위 일감 범위를 어기면 거부하고, 같은 프로젝트에 있던 하위는 함께 옮겨야 한다.
5. 프로젝트를 넘는 관계가 꺼져 있으면 다른 프로젝트와의 관계를 지워야 한다(양쪽 저널).
6. 시간 기록의 프로젝트를 같은 트랜잭션에서 옮겨야 한다.
7. 저널(원인 `MOVE`)과 `issue.updated`(옛 프로젝트 포함)를 남겨야 하며, MCP `update_issue` 의 프로젝트 필드도 같은 규칙이어야 한다.

**수용 기준**
- [ ] 대상이 쓰지 않는 트래커인데 트래커를 고르지 않으면 422 다
- [ ] 옮긴 뒤 번호가 같고 시간 기록의 프로젝트도 바뀌어 있다
- [ ] 대상에서 담당 자격이 없으면 담당이 비고 저널에 남는다
- [ ] `RESTRICTED` 프로젝트로 옮기면 옛 프로젝트만 읽던 사람의 검색 · 목록에서 사라진다

<a id="fr-iss-025"></a>
### FR-ISS-025 "내가 만들거나 맡은 것만" 보기 범위

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [프로젝트 권한 §11.1](../design/04-project-permissions.md#pp-private) |

**설명** — 고객 지원처럼 보고자끼리 서로의 일감을 보면 안 되는 프로젝트가 있다. 프로젝트 설정으로 `issue.private.read` 가 없는 주체에게 자기가 만들었거나 맡은 일감만 보이게 한다(Redmine 역할 설정의 "일감 보기 범위: 내가 만들거나 맡은 일감").

**세부 요구사항**
1. 프로젝트 설정 `issue_visibility` 는 `DEFAULT`(기본) · `OWN` 이어야 한다.
2. `OWN` 이면 `issue.private.read` 가 없는 주체(보고자 · 독자 · 기본 역할)는 자기가 만들었거나 맡은 일감만 봐야 한다.
3. 개발자 이상은 영향이 없어야 한다.
4. 모든 읽기 길(목록 · 개요의 일감 수 · 검색 · 보드 · MCP)이 같은 조건을 써야 한다.
5. 바꾸기는 `project.manage` 이고 감사에 남아야 한다.

**수용 기준**
- [ ] `OWN` 프로젝트의 보고자에게 남의 공개 일감이 404 이고 목록에 없다
- [ ] 같은 프로젝트의 개발자는 모든 일감을 본다
- [ ] 개요 쪽의 일감 수도 보고자에게는 자기 일감만 센다
