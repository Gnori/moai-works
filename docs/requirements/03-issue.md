# 일감 요구사항 (FR-ISS)

프로젝트 안의 일감 — 만들기 · 보기 · 고치기, 일감 유형 · 상태, 관리자와 담당자, 날짜 다섯 개, 상위 · 하위 일감, 연결 일감, 이력과 댓글, 목록 · 필터 · 정렬, 지우기, 화면의 요구사항이다. **일감은 moai-wiki 의 페이지 자리다** — 프로젝트 안에 여러 개 있고, 페이지 유형처럼 일감 유형이 있고, 페이지 트리처럼 상위 · 하위가 있고, 페이지 소유자처럼 관리자가 있다. 여기에 사람이 직접 든 것(담당자 · 날짜 · 연결 일감)을 더했다. 설계는 [일감 설계](../design/05-issue.md)에 있다.

| 우선순위 | 개수 | 요구사항 |
|---|---|---|
| M | 14 | [001](#fr-iss-001) ~ [014](#fr-iss-014) |
| 합계 | 14 | |

| 공통 | 내용 |
|---|---|
| moai-wiki 대응 | 페이지 → 일감, 페이지 유형 → 일감 유형, 페이지 트리 → 상위 · 하위 일감, 페이지 소유자(`page.owner.assign`) → 일감 관리자(`issue.manager.assign`), 페이지 링크 → 연결 일감, 리비전 → 이력, 피드백 → 댓글. 담당자와 날짜는 moai-wiki 에 없는 것이다 |
| 판정 | 모든 REST 는 `/moai-works-api/v1/workspaces/{workspace}/projects/{project}` 아래의 `@ProjectApi(권한)` 이다 — 판정 규칙은 [FR-PRJ-006](02-project.md#fr-prj-006). 프로젝트 독자가 아니면 404 `PROJECT_NOT_FOUND`, 일감이 없거나 지웠으면 404 `ISSUE_NOT_FOUND`, 권한 코드가 없으면 403 `PERMISSION_REQUIRED`, 보관한 프로젝트에 쓰면 409 `PROJECT_NOT_WRITABLE` |
| 일감 번호 | 프로젝트 안 순번(1, 2, 3 …). 주소는 `…/issues/{number}` 다. 다른 프로젝트의 같은 번호와 섞이지 않는다 |
| 같은 서비스 | MCP 도구는 REST 와 같은 서비스 · 같은 판정 · 같은 검증 · 같은 오류 코드를 쓴다 ([MCP 요구사항](04-mcp.md)) |
| 이력 · 감사 | 일감의 모든 쓰기는 이력(`issue_journal`)에 한 줄씩 남고 감사(`audit_log`)에도 남는다. 둘 다 주체(사람 · 서비스)와 경로(웹 · MCP)를 남긴다 ([FR-ISS-010](#fr-iss-010)) |
| 첫 출시 밖 | 사용자 정의 워크플로 · 필드, 프로젝트별 일감 유형, 첨부, 관찰자, 알림, 시간 기록, 다른 프로젝트와의 연결은 [나중 후보](00-overview.md#7-나중-후보)다 |

## 1. 만들기 · 보기 · 고치기

<a id="fr-iss-001"></a>
### FR-ISS-001 일감 만들기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(프로젝트 행을 잠가 순번, 관리자 기본 = 만든 사람, 이력 첫 줄 · 감사 `issue.create`) · 자동 테스트. 남은 것: 동시 20개 번호 · 지운 번호 재사용 안 함 · 다른 관리자 지정 403 · 길이 상한 시험 · 화면. |
| 관련 설계 | [일감 설계](../design/05-issue.md) · [데이터 모델](../design/02-data-model.md) |

**설명** — 프로젝트에 일감을 만든다. 일감 번호는 프로젝트 안 순번이라 사람과 Agent 가 "PROJ 의 12번"처럼 같은 이름으로 부른다.

**세부 요구사항**
1. `POST /projects/{project}/issues` 는 `@ProjectApi(issue.create)` 여야 한다. 기본 역할로는 소유자 · 관리자 · 큐레이터, 프로젝트 역할로는 `project-editor` 이상이 만든다.
2. 입력은 일감 유형(필수, [FR-ISS-004](#fr-iss-004)) · 제목(필수, 앞뒤 공백을 뺀 1~200자) · 설명(Markdown, 30000자 이하) · 상태(기본 `NEW`, [FR-ISS-005](#fr-iss-005)) · 관리자(기본 = 만든 사람) · 담당자(선택, [FR-ISS-006](#fr-iss-006)) · 상위 일감 번호(선택, [FR-ISS-008](#fr-iss-008)) · 날짜(완료 기한 · 시작일 · 완료 예정일 · 완료일 · 종료일, [FR-ISS-007](#fr-iss-007))다.
3. 번호는 `project` 행을 잠그고(`SELECT … FOR UPDATE`) `issue_seq` 를 1 올린 값이어야 한다. `(project_id, number)` 는 고유하다. 동시에 만들어도 번호가 겹치거나 빠지지 않는다.
4. 번호는 다시 쓰지 않는다. 지운 일감의 번호도 쓴 번호다.
5. 제목이 비거나 200자를 넘으면 400 `INVALID_ISSUE_TITLE`, 설명이 30000자를 넘으면 400 `ISSUE_DESCRIPTION_TOO_LONG` 이다.
6. 관리자를 만든 사람이 아닌 사람으로 정하려면 `issue.manager.assign` 도 있어야 한다. 없으면 403 `PERMISSION_REQUIRED` 다.
7. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
8. 만들기도 이력의 첫 줄로 남긴다 — `changes` 에 처음 값(유형 · 제목 · 상태 · 관리자 · 담당자 · 상위 · 날짜)을 전 값 없이 담는다. 그래서 웹으로 만들었는지 MCP 로 만들었는지 이력에서 보인다.
9. 응답은 201 과 일감 상세(번호 · `rowVersion` 포함)다.
10. 만들기를 감사(`issue.create` — 프로젝트 · 번호 · 유형)에 남긴다.

**수용 기준**
- [x] 새 프로젝트에 일감 세 개를 만들면 번호가 1 · 2 · 3 이다 (IssueTest)
- [ ] 같은 프로젝트에 20개를 동시에 만들어도 번호가 1~20 으로 겹치거나 빠지지 않는다
- [ ] 일감을 지운 뒤 새로 만들면 지운 번호를 다시 쓰지 않는다
- [ ] 관리자를 비우면 만든 사람이 관리자다. `issue.manager.assign` 없이 다른 사람을 관리자로 정하면 403 이다
- [x] 기본 역할 멤버가 만들면 403, 독자가 아니면 404 `PROJECT_NOT_FOUND` 다 (IssueTest)
- [ ] 제목 201자 · 설명 30001자 · 없는 유형은 각각 400 이다
- [x] 보관한 프로젝트에서 만들면 409 `PROJECT_NOT_WRITABLE` 이다 (IssueTest)
- [x] 만든 뒤 이력의 첫 줄과 감사에 만든 사람 · 경로가 있다 (IssueTest)

<a id="fr-iss-002"></a>
### FR-ISS-002 일감 보기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(하위 · 연결(양쪽) · 이력을 함께) · 자동 테스트. 남은 것: 이력 100줄 넘을 때 커서 · 화면의 HTML 막기. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감 하나를 열면 필드 · 하위 일감 · 연결 일감 · 이력이 한 번에 온다. 사람 화면과 MCP `get_issue` 가 같은 응답을 쓴다.

**세부 요구사항**
1. `GET /projects/{project}/issues/{number}` 는 `@ProjectApi(issue.read)` 여야 한다. 기본 역할은 모두 `issue.read` 를 가지므로 `WORKSPACE` 프로젝트의 일감은 모든 활성 멤버가 본다.
2. 응답은 번호 · 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자(사람 id · 표시 이름 · 떠난 멤버 표시) · 상위 일감(번호 · 제목) · 날짜 다섯 개 · 만든 사람 · 만든 때 · 고친 때 · `rowVersion` 과 다음을 담아야 한다.
   - 하위 일감: 번호 · 유형 · 제목 · 상태 · 담당자(번호순)
   - 연결 일감: 연결 id · 연결 종류 · 이 일감에서 본 방향 · 상대 일감의 번호 · 제목 · 상태(양쪽 어느 일감에서 걸었든 보인다)
   - 이력: 오래된 것부터 100줄, 더 있으면 이어 받기 커서
   - `myActions`: 이 사람이 지금 할 수 있는 일(고치기 · 댓글 · 관리자 바꾸기 · 지우기)
3. 없거나 지운 일감은 404 `ISSUE_NOT_FOUND` 다. 번호는 경로의 프로젝트 안에서만 찾는다.
4. 설명 · 댓글의 Markdown 은 화면에서 안전하게 그려야 한다(원시 HTML · 스크립트를 실행하지 않는다, moai-wiki 와 같은 렌더러).

**수용 기준**
- [x] 응답에 하위 일감 · 연결 일감(양쪽 방향) · 이력이 있다 (IssueTest)
- [x] 지운 일감은 404 `ISSUE_NOT_FOUND`, 다른 프로젝트에만 있는 번호도 404 `ISSUE_NOT_FOUND` 다 (IssueTest)
- [x] 독자가 아닌 `RESTRICTED` 프로젝트의 일감을 열면 404 `PROJECT_NOT_FOUND` 이고, 없는 프로젝트와 응답이 같다 (IssueTest)
- [ ] 이력이 100줄을 넘는 일감은 커서로 나머지를 받는다
- [ ] 설명에 넣은 `<script>` 가 화면에서 실행되지 않는다

<a id="fr-iss-003"></a>
### FR-ISS-003 일감 고치기 (동시 수정 포함)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(넣은 필드만 · rowVersion 필수 · 409 `CONCURRENT_UPDATE` · 이력 한 줄 · 감사 `issue.update`) · 자동 테스트. 남은 것: 동시 요청 시험 · 바뀐 값 없음 시험 · 403 때 다른 필드 그대로 시험 · 다른 프로젝트 편집자 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감의 필드를 고친다. 사람과 Agent 가 같은 일감을 동시에 고칠 수 있으므로, 남이 먼저 고친 것을 모르고 덮어쓰지 않게 `rowVersion` 으로 막는다.

**세부 요구사항**
1. `PATCH /projects/{project}/issues/{number}` 는 `@ProjectApi(issue.edit)` 여야 한다. 상태 · 날짜 · 담당자 · 상위 일감도 이 요청으로 고친다.
2. 요청에는 `rowVersion`(필수)과 바꿀 필드만 담는다. 고칠 수 있는 것: 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자 · 상위 일감 · 날짜 다섯 개. 검증은 만들기와 같다.
3. 관리자를 바꾸면 서비스가 `issue.manager.assign` 도 확인해야 한다. 없으면 403 `PERMISSION_REQUIRED` 이고 아무것도 바뀌지 않는다.
4. `rowVersion` 이 지금 값과 다르면 409 `CONCURRENT_UPDATE` 이고 아무것도 바뀌지 않아야 한다. 응답에 지금 `rowVersion` 을 담는다.
5. 바뀐 필드는 모두 이력 한 줄에 전 · 후로 남긴다. 상태에 따라 자동으로 채운 날짜도 같은 줄이다([FR-ISS-005](#fr-iss-005)).
6. 고치면서 댓글(`notes`)을 함께 남길 수 있다 — 같은 이력 줄에 든다.
7. 실제로 바뀐 값이 없으면 이력을 남기지 않고 `rowVersion` 도 그대로 두고 200 으로 답한다.
8. 저장하면 `updated_at` 을 고치고 `rowVersion` 을 1 올린다.
9. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
10. 고치기를 감사(`issue.update` — 바뀐 필드 이름)에 남긴다.

**수용 기준**
- [x] 옛 `rowVersion` 으로 고치면 409 `CONCURRENT_UPDATE` 이고 일감이 그대로다 (IssueTest)
- [ ] 같은 `rowVersion` 으로 동시에 보낸 두 요청 가운데 하나만 성공하고 다른 하나는 409 다
- [x] 제목 · 상태 · 담당자를 한 번에 고치면 이력 한 줄에 세 필드의 전 · 후가 있다 (IssueTest)
- [ ] 바뀐 값이 없는 요청은 이력을 남기지 않는다
- [ ] `issue.manager.assign` 없이 관리자를 바꾸면 403 이고, 같은 요청의 다른 필드도 바뀌지 않는다
- [ ] 다른 프로젝트에서만 편집자인 사람이 고치면 403 이다
- [x] 고치기가 감사에 남는다 (IssueTest)

## 2. 유형 · 상태 · 사람 · 날짜

<a id="fr-iss-004"></a>
### FR-ISS-004 일감 유형

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(공통 시드 넷 · 순서 · 없는 유형 400 `UNKNOWN_ISSUE_TYPE`) · 자동 테스트. 남은 것: 유형 바꾸기 이력 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감에는 유형이 있다(예: 요구사항). moai-wiki 의 페이지 유형처럼 모든 워크스페이스가 같이 쓰는 시드 표로 시작한다. 프로젝트마다 유형을 바꾸는 것은 나중 후보다.

**세부 요구사항**
1. 표 `issue_type`(key · 이름 · 설명 · 순서)은 Flyway 시드로 다음 4개를 가져야 한다.

   | key | 이름 | 순서 |
   |---|---|---|
   | `requirement` | 요구사항 | 1 |
   | `feature` | 기능 | 2 |
   | `bug` | 버그 | 3 |
   | `task` | 작업 | 4 |

2. `GET /projects/{project}/issue-types` 는 `@ProjectApi(issue.read)` 로 순서대로 준다.
3. 일감을 만들거나 고칠 때 없는 유형 key 는 400 `UNKNOWN_ISSUE_TYPE` 이다.
4. 유형을 바꾸는 것은 `issue.edit` 이고 이력에 남는다.
5. 유형을 더하거나 고치는 API 는 첫 출시에 없다. 화면은 유형 key 로 다국어 이름을 보인다.

**수용 기준**
- [x] 유형 목록이 4개를 순서대로 준다 (IssueTest)
- [x] 네 유형으로 각각 일감을 만들 수 있고, 없는 유형은 400 `UNKNOWN_ISSUE_TYPE` 이다 (IssueTest)
- [ ] 유형을 바꾸면 이력에 전 · 후가 남는다
- [x] 화면에서 유형 이름이 한국어 · 영어로 나온다 (ego-browser 2026-11-22)

<a id="fr-iss-005"></a>
### FR-ISS-005 상태

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(고정 넷, 완료일 · 종료일 자동 채움과 비움, 직접 넣은 날짜는 그대로) · 자동 테스트. 남은 것: NEW → CLOSED 시험 · 자동 날짜의 이력 시험 · 없는 상태 400 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) · [핵심 설계 결정](../design/00-key-decisions.md) |

**설명** — 일감의 상태는 고정 4개이고 아무 상태로나 옮길 수 있다. 완료 · 종료로 옮기면 완료일 · 종료일을 자동으로 채운다. 워크플로를 사용자가 정하는 것은 나중 후보다.

**세부 요구사항**
1. 상태는 `NEW`(신규) · `IN_PROGRESS`(진행) · `DONE`(완료) · `CLOSED`(종료) 4개여야 한다. 그 밖의 값은 400 `INVALID_ISSUE_STATUS` 다.
2. 어느 상태에서 어느 상태로나 옮길 수 있다(`issue.edit`). `NEW` · `IN_PROGRESS` 를 "열린 일감", `DONE` · `CLOSED` 를 "닫힌 일감"으로 묶어 목록 필터에 쓴다.
3. 날짜 자동 채움은 요청의 값을 먼저 적용한 뒤 다음과 같아야 한다.

   | 옮긴 상태 | 완료일 `completed_on` | 종료일 `closed_on` |
   |---|---|---|
   | → `DONE` | 비어 있으면 오늘 | 그대로 |
   | → `CLOSED` | 그대로 | 비어 있으면 오늘 |
   | → `NEW` · `IN_PROGRESS` | 비운다 | 비운다 |

4. "오늘"은 api 의 기준 시간대(지금은 Asia/Seoul 고정, 워크스페이스 시간대 설정은 나중)의 날짜다.
5. 같은 요청에서 상태와 함께 완료일 · 종료일을 직접 주면 준 값을 쓴다(자동 채움은 빈 경우만).
6. 자동으로 채우거나 비운 날짜도 그 고치기의 이력 줄에 전 · 후로 남는다.

**수용 기준**

- [x] `DONE` → `CLOSED` 면 종료일이 오늘이 되고 완료일은 그대로다 (IssueTest)
- [ ] `NEW` → `CLOSED` 면 종료일만 오늘이고 완료일은 비어 있다

5. 사람 없이 서비스 키로 만들 때는 관리자를 꼭 넘겨야 한다. 없으면 400 `ISSUE_MANAGER_REQUIRED` 다([FR-MCP-005](04-mcp.md#fr-mcp-005)).

7. 화면은 후보를 그 프로젝트의 독자인 활성 멤버에서 고르게 한다(api 가 후보 목록을 준다).
8. 바꾸기는 이력에 전 · 후로 남는다.

7. 하위 일감 목록은 보기([FR-ISS-002](#fr-iss-002))에 오고, 목록에서 상위로 거를 수 있다([FR-ISS-012](#fr-iss-012)).
8. 상위 바꾸기는 하위 일감의 이력에 전 · 후로 남는다.
9. 상위 일감의 상태 · 날짜를 하위에서 계산하지 않는다(첫 출시). 하위가 있는 일감은 지울 수 없다([FR-ISS-013](#fr-iss-013)).

## 4. 이력과 댓글

<a id="fr-iss-010"></a>
### FR-ISS-010 이력

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(`issue_journal` — 고칠 때마다 한 줄, 주체 · 경로, 고치는 경로 없음, 쓰기 여섯 가지 감사) · 자동 테스트. 남은 것: MCP 경로 표시(4단계) · 저장 실패 되돌림 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감에 일어난 모든 변경과 댓글을 시간순으로 남긴다(moai-wiki 의 리비전 자리). 사람과 Agent 가 같은 일감을 다루므로 "누가 · 어느 길로" 바꿨는지가 늘 보여야 한다.

**세부 요구사항**
1. 표 `issue_journal` 은 id · 일감 · 주체 id · 주체 종류(`USER` · `SERVICE`) · 경로(`WEB` · `MCP`) · 만든 때 · 댓글(`notes`, Markdown, 없어도 됨) · 변경(`changes` jsonb `[{field, before, after}]`)을 가져야 한다.
2. 만들기 · 고치기 · 상위 바꾸기 · 연결 걸기 · 풀기 · 댓글마다 한 줄을 남겨야 한다. 한 요청은 한 줄이다. 댓글은 `notes` 만 있는 줄이다.
3. 남기는 필드는 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자 · 상위 · 날짜 다섯 개 · 연결이다. 설명은 전 · 후 전문을 남기고 화면은 차이를 보여 준다.
4. 서비스 키로 한 일은 주체 종류 `SERVICE` 이고 어느 키인지(키 id)를 남긴다. 개인 키로 한 일은 키 주인(`USER`) · 경로 `MCP` 다.
5. 이력은 업무와 같은 트랜잭션에 저장해야 한다. 이력 저장이 실패하면 변경도 되돌린다.
6. 이력 줄을 고치거나 지우는 API 는 없어야 한다. 댓글 고치기 · 지우기도 첫 출시에 없다.
7. 일감의 쓰기는 감사에도 남긴다: `issue.create` · `issue.update` · `issue.comment` · `issue.link.add` · `issue.link.remove` · `issue.delete`. MCP 로 한 쓰기는 엔드포인트 id · 키 id · 도구 이름을 함께 남긴다([FR-MCP-006](04-mcp.md#fr-mcp-006)).
8. 화면은 이력을 전체 · 댓글만 · 변경만으로 거르고, 경로가 MCP 인 줄에 표시를 단다.

**수용 기준**
- [x] 고치기 한 번에 이력 한 줄이 생기고, 바뀐 필드마다 전 · 후가 맞다 (IssueTest)
- [ ] MCP 로 고친 줄은 경로 `MCP` 와 주체(키 주인 또는 서비스)가 보인다
- [ ] 이력 저장을 실패시키면 일감 변경도 되돌려진다
- [x] 이력 줄을 고치거나 지우는 REST · MCP 경로가 없다 (IssueTest)
- [x] 일감의 쓰기 여섯 가지가 감사에 남는다 (IssueTest)

<a id="fr-iss-011"></a>
### FR-ISS-011 댓글

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(`issue.comment`, notes 만 있는 이력 줄, 감사) · 자동 테스트. 남은 것: 30001자 · issue.read 만 있는 역할 403 · 닫힌 일감 댓글 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감에 댓글을 단다(moai-wiki 의 피드백 자리). 기본 역할 멤버도 읽을 수 있는 프로젝트의 일감에는 댓글을 달 수 있다.

**세부 요구사항**
1. `POST /projects/{project}/issues/{number}/comments` `{notes}` 는 `@ProjectApi(issue.comment)` 여야 한다. 기본 역할은 모두 `issue.comment` 를 가진다.
2. 댓글은 Markdown, 앞뒤 공백을 뺀 1~30000자여야 한다. 비면 400 `INVALID_COMMENT`, 넘으면 400 `COMMENT_TOO_LONG` 이다.
3. 댓글은 `notes` 만 있는 이력 줄로 저장한다([FR-ISS-010](#fr-iss-010)). 상태와 상관없이(닫힌 일감에도) 달 수 있다.
4. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
5. 멘션 · 알림은 첫 출시에 없다([나중 후보](00-overview.md#7-나중-후보)).
6. 댓글을 감사(`issue.comment`)에 남긴다.

**수용 기준**
- [x] 기본 역할 멤버가 `WORKSPACE` 프로젝트의 일감에 댓글을 달면 이력에 `notes` 만 있는 줄이 생긴다 (IssueTest)
- [ ] 빈 댓글은 400, 30001자는 400 이다
- [ ] `issue.read` 만 넣은 사용자 정의 역할로는 403 이다
- [ ] 닫힌 일감에도 댓글을 단다
- [x] 댓글이 감사에 남는다 (IssueTest)

## 5. 목록 · 지우기 · 화면

<a id="fr-iss-012"></a>
### FR-ISS-012 일감 목록 · 필터 · 정렬

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(상태(open · closed 별칭) · 유형 · 관리자 · 담당자(me · none) · 상위(top · none) · 검색어 · 정렬 · 쪽) · 자동 테스트. 남은 것: 쪽 크기 상한 · 지운 일감 제외 시험 · MCP 와 같은 결과(4단계). |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 프로젝트의 일감을 거르고 정렬해 쪽으로 나눠 본다. 화면 목록과 MCP `search_issues` 가 같은 질의 서비스를 쓴다.

**세부 요구사항**
1. `GET /projects/{project}/issues` 는 `@ProjectApi(issue.read)` 여야 한다.
2. 필터는 다음과 같아야 한다. 서로 다른 필터는 모두 만족(AND), 한 필터의 여러 값은 하나라도(OR)다.

   | 필터 | 값 |
   |---|---|
   | `status` | 상태 여러 개, 또는 `open`(신규 · 진행) · `closed`(완료 · 종료) |
   | `type` | 유형 key 여러 개 |
   | `manager` | 사람 id 또는 `me` |
   | `assignee` | 사람 id · `me` · `none`(담당자 없음) |
   | `parent` | 상위 번호(바로 아래 하위만) 또는 `none`(최상위만) |
   | `q` | 제목에 든 글자(대소문자 무시). 숫자만이면 그 번호도 찾는다 |

3. 정렬은 번호 · 고친 때 · 만든 때 · 완료 기한 · 완료 예정일 · 상태 · 제목, 오름 · 내림이다. 빈 날짜는 늘 뒤에 둔다. 같으면 번호로 정한다. 기본은 번호 내림차순이다.
4. 쪽 나누기: 쪽 크기 기본 50, 최대 100(넘게 달라고 하면 100). 전체 개수를 함께 준다.
5. 각 줄은 번호 · 유형 · 제목 · 상태 · 관리자 · 담당자 · 완료 기한 · 완료 예정일 · 상위 번호 · 하위 수 · 고친 때 · 기한 지남 여부를 준다.
6. 지운 일감은 나오지 않는다. 경로의 프로젝트 일감만 나온다.
7. 모르는 필터 값(없는 상태 · 유형, 숫자가 아닌 상위)은 400 `INVALID_FILTER` 다.
8. 성능은 [NFR-PERF-001](05-non-functional.md#nfr-perf-001)(일감 10만 건 프로젝트에서 p95 800ms)을 지킨다.

**수용 기준**
- [x] `status=open&assignee=me` 가 내가 맡은 열린 일감만 준다 (IssueTest)
- [x] `assignee=none` · `parent=none` 이 각각 담당자 없는 일감 · 최상위 일감만 준다 (IssueTest)
- [x] `q` 가 제목을 대소문자 없이 찾고, 숫자만 넣으면 그 번호의 일감도 나온다 (IssueTest)
- [x] 완료 기한으로 정렬하면 빈 값이 뒤에 온다 (IssueTest)
- [ ] 쪽 크기 500 을 달라고 하면 100 개가 오고 전체 개수가 맞다
- [ ] 지운 일감과 다른 프로젝트의 일감은 나오지 않는다
- [x] 없는 상태로 거르면 400 `INVALID_FILTER` 다 (IssueTest)
- [ ] 같은 필터로 REST 와 MCP `search_issues` 를 부르면 같은 일감이 같은 순서로 나온다

<a id="fr-iss-013"></a>
### FR-ISS-013 일감 지우기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(소프트 삭제 · 하위가 있으면 409 · 연결 함께 지우고 상대 이력에 남김 · 감사) · 자동 테스트. 남은 것: 상대 이력 시험 · 프로젝트 역할별 지우기 시험 · MCP 에 지우기 도구 없음(4단계). |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 잘못 만든 일감을 지운다. 지우기는 사람만 웹에서 하고(MCP 로 열지 않는다), 기록을 남기려고 소프트 삭제한다.

**세부 요구사항**
1. `DELETE /projects/{project}/issues/{number}` 는 `@ProjectApi(issue.delete)` 여야 한다. 기본 역할로는 소유자 · 관리자, 프로젝트 역할로는 `project-admin` 만 지운다(큐레이터는 못 한다).
2. 소프트 삭제다 — `deleted_at` 을 채운다. 지운 일감은 보기 · 목록 · 연결 · 하위 · MCP 어디에도 나오지 않고 404 `ISSUE_NOT_FOUND` 다.
3. 지우지 않은 하위 일감이 있으면 409 `ISSUE_HAS_CHILDREN` 이다. 먼저 하위를 옮기거나 지운다.
4. 그 일감의 연결은 함께 지운다. 상대 일감의 이력에 연결이 빠졌다고 남긴다.
5. 번호는 다시 쓰지 않는다. 되살리기는 첫 출시에 없다(데이터는 남는다).
6. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
7. 화면은 번호 · 제목을 보이고 확인을 받는다.
8. 지우기를 감사(`issue.delete` — 번호 · 제목)에 남긴다.

**수용 기준**
- [x] 지운 일감은 404 `ISSUE_NOT_FOUND` 이고 목록에 없다 (IssueTest)
- [x] 하위 일감이 있으면 409 `ISSUE_HAS_CHILDREN` 이다 (IssueTest)
- [ ] 지운 일감에 걸려 있던 연결이 상대 일감의 보기에서 사라지고 상대 이력에 남는다
- [ ] 워크스페이스 큐레이터 · `project-curator` 가 지우면 403, `project-admin` 은 지운다
- [x] 지우기가 감사에 남는다 (IssueTest)
- [ ] 어떤 MCP 엔드포인트의 `tools/list` 에도 지우기 도구가 없다

<a id="fr-iss-014"></a>
### FR-ISS-014 일감 화면

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: 화면(목록 — 데스크톱 표 · 390px 카드, 필터를 주소에 둠 · 새 일감 · 보기 · 고치기 · 상태 바꾸기 · 하위 · 연결 · 이력 · 댓글 · 지우기 대화 상자) · 화면 자동 테스트(필터 ↔ 주소 · 바뀐 필드만 보내기 · 이력 읽기) · 브라우저 확인. 남은 것: 새로 고침 뒤 같은 목록 · 두 창 충돌 알림을 브라우저로 확인 · MCP 표시(4단계). |
| 관련 설계 | [일감 설계](../design/05-issue.md) · [WEB-DESIGN.md](../../WEB-DESIGN.md) |

**설명** — 일감 화면은 moai-wiki 의 페이지 화면 구조(`p/:pageSlug` · `new` · `edit` · `history`)를 그대로 쓴다. 모두 `ProjectLayout` 안에 있다.

**세부 요구사항**
1. 경로와 구성은 다음과 같아야 한다(`/w/:slug/projects/:projectKey` 아래).

   | 경로 | 화면 |
   |---|---|
   | `''`(프로젝트 홈) | 일감 목록 — 표(번호 · 유형 · 제목 · 상태 · 관리자 · 담당자 · 완료 예정일 · 완료 기한 · 고친 때), 필터 줄(상태 열림 · 닫힘 · 전체, 유형, 관리자, 담당자(나 · 없음 포함), 상위, 찾기), 열 머리로 정렬, 쪽 나누기, "새 일감" 버튼 |
   | `issues/new` | 만들기 — 유형 · 제목 · 설명(Markdown 편집 · 미리보기) · 상태 · 관리자 · 담당자 · 상위 일감(번호 · 제목으로 찾기) · 날짜 다섯 개. 하위 일감 만들기로 오면 상위가 채워져 있다 |
   | `issues/:number` | 보기 — 머리(#번호 · 제목 · 유형 · 상태, 상태 바로 바꾸기), 속성(관리자 · 담당자 · 날짜 · 상위), 설명, 하위 일감(하위 만들기), 연결 일감(걸기 · 풀기), 이력 · 댓글(MCP 표시, 거르기), 댓글 입력 |
   | `issues/:number/edit` | 고치기 — 만들기와 같은 양식, `rowVersion` 을 함께 보낸다 |

2. 필터 · 정렬 · 쪽은 주소의 질의 문자열에 둬서 새로 고침 · 공유해도 같은 목록이 나와야 한다. 화면 기본은 열린 일감, 고친 때 내림차순이다.
3. 409 `CONCURRENT_UPDATE` 를 받으면 "다른 사람이 먼저 고쳤습니다"를 알리고, 입력한 값을 지우지 않은 채 최신 값을 다시 불러 비교하게 해야 한다.
4. api 의 검증 오류(`code`)는 해당 입력 칸에 알린다.
5. 버튼(새 일감 · 고치기 · 관리자 바꾸기 · 지우기 · 댓글)은 상세의 `myPermissions` · `myActions` 로 숨긴다. 판정은 api 가 한다.
6. 없거나 지운 일감은 "일감을 찾을 수 없습니다" 화면이다.
7. 390px 에서는 목록을 카드로 바꿔 가로 스크롤이 없게 한다. ko/en, 다크 모드, 키보드만으로 목록 · 보기 · 고치기를 할 수 있다.

**수용 기준**
- [x] 화면에서 일감을 만들면 새 일감의 보기로 간다 (ego-browser 2026-11-22)
- [ ] 필터를 바꾼 목록 주소를 새로 고쳐도 같은 목록이 나온다
- [ ] 두 창에서 같은 일감을 고치면 나중 창에 충돌 알림이 뜨고 입력이 남아 있다
- [x] 기본 역할 멤버에게는 새 일감 · 고치기 · 지우기 버튼이 없고 댓글 입력은 있다 (ego-browser 2026-11-22 — 멤버는 댓글 입력만)
