# 일감 요구사항 (FR-ISS)

워크스페이스 아래의 일감 — 만들기 · 보기 · 고치기 · 다른 프로젝트로 옮기기, 일감 유형 · 상태 · 우선순위, 관리자와 담당자, 날짜 다섯 개, 상위 · 하위 일감, 연결 일감, 이력과 댓글, 목록 · 필터 · 정렬(프로젝트 목록 · 워크스페이스 전체 목록), 지우기, 화면의 요구사항이다. **일감은 moai-wiki 의 페이지 자리다** — 프로젝트 안에 여러 개 있고, 페이지 유형처럼 일감 유형이 있고, 페이지 트리처럼 상위 · 하위가 있고, 페이지 소유자처럼 관리자가 있다. 여기에 사람이 직접 든 것(담당자 · 날짜 · 연결 일감)을 더했다. 2026-11-24 부터 **일감은 워크스페이스 아래에 있고 프로젝트는 일감의 속성이다**(Redmine 과 같다 — [ADR-030](../design/00-key-decisions.md#adr-030), moai-works 일감 #29): 번호는 워크스페이스 안에서 하나이고, 프로젝트는 옮길 수 있다. 권한 경계는 그대로 그 일감의 지금 프로젝트다. 설계는 [일감 설계](../design/05-issue.md)에 있다.

| 공통 | 내용 |
|---|---|
| moai-wiki 대응 | 페이지 → 일감, 페이지 유형 → 일감 유형, 페이지 트리 → 상위 · 하위 일감, 페이지 소유자(`page.owner.assign`) → 일감 관리자(`issue.manager.assign`), 페이지 링크 → 연결 일감, 리비전 → 이력, 피드백 → 댓글. 담당자와 날짜는 moai-wiki 에 없는 것이다 |
| 판정 | 프로젝트의 목록 · 만들기 · 유형 · 쓰인 세션은 `/moai-works-api/v1/workspaces/{workspace}/projects/{project}` 아래의 `@ProjectApi(권한)`, 일감 하나(번호)를 다루는 일은 정식 주소 `/moai-works-api/v1/workspaces/{workspace}/issues/{number}` 아래의 `@IssueApi(권한)` 이다 — 둘 다 판정 규칙은 [FR-PRJ-006](02-project.md#fr-prj-006) 이고, `@IssueApi` 는 **그 일감의 지금 프로젝트**로 판정한다. 프로젝트 독자가 아니면 404(프로젝트 주소 `PROJECT_NOT_FOUND`, 일감 주소 `ISSUE_NOT_FOUND` — 일감이 있는지 · 어느 프로젝트인지 숨긴다), 일감이 없거나 지웠으면 404 `ISSUE_NOT_FOUND`, 권한 코드가 없으면 403 `PERMISSION_REQUIRED`, 보관한 프로젝트에 쓰면 409 `PROJECT_NOT_WRITABLE`. 워크스페이스 전체 목록은 `@WorkspaceApi(workspace.read)` 이고 읽을 수 있는 프로젝트만 모은다([FR-ISS-025](#fr-iss-025)) |
| 일감 번호 | **워크스페이스 안 순번**(1, 2, 3 …, 2026-11-24 — [ADR-030](../design/00-key-decisions.md#adr-030)). 어느 프로젝트에 만들든 워크스페이스에서 다음 번호를 받고, 옮겨도 그대로다. 정식 주소는 `/w/{ws}/issues/{number}`, 글에서는 `#12` 가 그 워크스페이스의 12번이다. 다른 워크스페이스의 같은 번호와는 따로다. 옛 프로젝트 안 번호는 V23 이 다시 매겼다([FR-ISS-026](#fr-iss-026)) |
| 같은 서비스 | MCP 도구는 REST 와 같은 서비스 · 같은 판정 · 같은 검증 · 같은 오류 코드를 쓴다 ([MCP 요구사항](04-mcp.md)) |
| 이력 · 감사 | 일감의 모든 쓰기는 이력(`issue_journal`)에 한 줄씩 남고 감사(`audit_log`)에도 남는다. 둘 다 주체(사람 — MCP 로 한 일은 키 주인)와 경로(웹 · MCP)를 남긴다 ([FR-ISS-010](#fr-iss-010)). MCP 로 쓴 이력 줄 · 작업 시간 기록 · 첨부에는 에이전트 세션 이름도 남는다([FR-ISS-029](#fr-iss-029)) |
| 첫 출시 밖 | 사용자 정의 워크플로 · 필드, 프로젝트별 일감 유형, 관찰자는 [나중 후보](00-overview.md#7-나중-후보)다. 다른 프로젝트와의 연결은 2026-11-24 부터 된다(같은 워크스페이스 안, [FR-ISS-009](#fr-iss-009)) |

## 1. 만들기 · 보기 · 고치기

<a id="fr-iss-001"></a>
### FR-ISS-001 일감 만들기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(관리자 기본 = 만든 사람, 이력 첫 줄 · 감사 `issue.create`) · 2026-11-24 번호를 워크스페이스 순번으로(워크스페이스 행을 잠가 올림 — 동시 만들기 · 지운 번호 시험, WorkspaceIssueTest) · 자동 테스트. 남은 것: 다른 관리자 지정 403 · 길이 상한 시험 · 화면. |
| 관련 설계 | [일감 설계](../design/05-issue.md) · [데이터 모델](../design/02-data-model.md) |

**설명** — 프로젝트에 일감을 만든다. 일감 번호는 워크스페이스 안 순번이라 사람과 Agent 가 "12번"처럼 프로젝트 없이 같은 이름으로 부른다(2026-11-24 사용자: "워크스페이스 단위로 유니크한 번호여야해").

**세부 요구사항**
1. `POST /projects/{project}/issues` 는 `@ProjectApi(issue.create)` 여야 한다. 기본 역할로는 소유자 · 관리자 · 큐레이터, 프로젝트 역할로는 `project-editor` 이상이 만든다.
2. 입력은 일감 유형(필수, [FR-ISS-004](#fr-iss-004)) · 제목(필수, 앞뒤 공백을 뺀 1~200자) · 설명(Markdown, 30000자 이하) · 상태(기본 `NEW`, 보류 · 취소 · 확인요청은 안 되고 확인완료는 관리자가 웹에서만 — [FR-ISS-005](#fr-iss-005)) · 관리자(기본 = 만든 사람) · 담당자(선택, [FR-ISS-006](#fr-iss-006)) · 상위 일감 번호(선택, [FR-ISS-008](#fr-iss-008)) · 날짜(완료 기한 · 시작일 · 완료 예정일 · 완료일 · 종료일, [FR-ISS-007](#fr-iss-007))다.
3. 번호는 만드는 트랜잭션 안에서 `workspace` 행의 `issue_seq` 를 1 올린 값이어야 한다(`UPDATE workspace SET issue_seq = issue_seq + 1 … RETURNING` — 행을 잠그고, 워크스페이스의 `row_version` 은 건드리지 않는다). `(workspace_id, number)` 는 고유하다(DB 제약). 같은 워크스페이스의 만들기는 어느 프로젝트든 줄을 서서, 동시에 만들어도 번호가 겹치거나 빠지지 않는다. 만들기가 되돌려지면 번호도 되돌려진다.
4. 번호는 다시 쓰지 않는다. 지운 일감의 번호도 쓴 번호다. 일감을 다른 프로젝트로 옮겨도 번호는 그대로다([FR-ISS-024](#fr-iss-024)).
5. 제목이 비거나 200자를 넘으면 400 `INVALID_ISSUE_TITLE`, 설명이 30000자를 넘으면 400 `ISSUE_DESCRIPTION_TOO_LONG` 이다.
6. 관리자를 만든 사람이 아닌 사람으로 정하려면 `issue.manager.assign` 도 있어야 한다. 없으면 403 `PERMISSION_REQUIRED` 다.
7. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
8. 만들기도 이력의 첫 줄로 남긴다 — `changes` 에 처음 값(유형 · 제목 · 상태 · 관리자 · 담당자 · 상위 · 날짜)을 전 값 없이 담는다. 그래서 웹으로 만들었는지 MCP 로 만들었는지 이력에서 보인다.
9. 응답은 201 과 일감 상세(번호 · `rowVersion` 포함)다.
10. 만들기를 감사(`issue.create` — 프로젝트 · 번호 · 유형)에 남긴다.

**수용 기준**
- [x] 한 워크스페이스의 두 프로젝트에 번갈아 만들면 번호가 워크스페이스에서 이어지고(1 · 2 · 3), 다른 워크스페이스는 따로 1 부터다 (WorkspaceIssueTest · IssueTest 2026-11-24)
- [x] 두 프로젝트에 동시에 여러 개(시험은 8개)를 만들어도 번호가 겹치거나 빠지지 않는다 (WorkspaceIssueTest 2026-11-24)
- [x] 일감을 지운 뒤 새로 만들면 지운 번호를 다시 쓰지 않는다 (WorkspaceIssueTest 2026-11-24)
- [ ] 관리자를 비우면 만든 사람이 관리자다. `issue.manager.assign` 없이 다른 사람을 관리자로 정하면 403 이다
- [x] 기본 역할 멤버가 만들면 403, 독자가 아니면 404 `PROJECT_NOT_FOUND` 다 (IssueTest)
- [ ] 제목 201자 · 설명 30001자 · 없는 유형은 각각 400 이다
- [x] 보관한 프로젝트에서 만들면 409 `PROJECT_NOT_WRITABLE` 이다 (IssueTest)
- [x] 만든 뒤 이력의 첫 줄과 감사에 만든 사람 · 경로가 있다 (IssueTest)

### FR-ISS-002 일감 보기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(하위 · 연결(양쪽) · 이력을 함께) · 2026-11-24 정식 주소 `/workspaces/{ws}/issues/{number}` · `@IssueApi`(그 일감의 지금 프로젝트로 판정) · 응답의 `project {key, name}` · 읽을 수 없는 연결 숨김 · 자동 테스트. 남은 것: 이력 100줄 넘을 때 커서 · 화면의 HTML 막기. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감 하나를 열면 필드 · 하위 일감 · 연결 일감 · 이력이 한 번에 온다. 사람 화면과 MCP `get_issue` 가 같은 응답을 쓴다.

**세부 요구사항**
1. `GET /workspaces/{workspace}/issues/{number}` 는 `@IssueApi(issue.read)` 여야 한다 — 그 일감의 지금 프로젝트로 판정한다. 기본 역할은 모두 `issue.read` 를 가지므로 `WORKSPACE` 프로젝트의 일감은 모든 활성 멤버가 본다.
2. 응답은 번호 · 프로젝트(`project {key, name}` — 일감의 속성) · 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자(사람 id · 표시 이름 · 떠난 멤버 표시) · 상위 일감(번호 · 제목) · 날짜 다섯 개 · 만든 사람 · 만든 때 · 고친 때 · `rowVersion` 과 다음을 담아야 한다.
   - 하위 일감: 번호 · 유형 · 제목 · 상태 · 담당자(번호순)
   - 연결 일감: 연결 id · 연결 종류 · 이 일감에서 본 방향 · 상대 일감의 번호 · 프로젝트 · 제목 · 상태(양쪽 어느 일감에서 걸었든 보인다). 보는 사람이 읽을 수 없는 프로젝트의 상대는 빼고 준다([FR-ISS-009](#fr-iss-009))
   - 이력: 오래된 것부터 100줄, 더 있으면 이어 받기 커서
   - `myActions`: 이 사람이 지금 할 수 있는 일(고치기 · 댓글 · 관리자 바꾸기 · 지우기)
3. 없거나 지운 일감, 그 일감의 프로젝트를 읽을 수 없으면 모두 같은 404 `ISSUE_NOT_FOUND` 다(어느 프로젝트에 있는지도 숨긴다). 번호는 경로의 워크스페이스 안에서 찾는다.
4. 설명 · 댓글의 Markdown 은 화면에서 안전하게 그려야 한다(원시 HTML · 스크립트를 실행하지 않는다, moai-wiki 와 같은 렌더러).

**수용 기준**
- [x] 응답에 하위 일감 · 연결 일감(양쪽 방향) · 이력이 있다 (IssueTest)
- [x] 지운 일감 · 없는 번호는 404 `ISSUE_NOT_FOUND` 다 (IssueTest · WorkspaceIssueTest)
- [x] 독자가 아닌 `RESTRICTED` 프로젝트의 일감을 정식 주소로 열면 404 `ISSUE_NOT_FOUND` 이고, 없는 번호와 응답이 같다 (IssueTest · WorkspaceIssueTest 2026-11-24)
- [ ] 이력이 100줄을 넘는 일감은 커서로 나머지를 받는다
- [ ] 설명에 넣은 `<script>` 가 화면에서 실행되지 않는다

<a id="fr-iss-003"></a>
### FR-ISS-003 일감 고치기 (동시 수정 포함)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(넣은 필드만 · rowVersion 필수 · 409 `CONCURRENT_UPDATE` · 이력 한 줄 · 감사 `issue.update`) · 자동 테스트. 남은 것: 동시 요청 시험 · 바뀐 값 없음 시험 · 403 때 다른 필드 그대로 시험 · 다른 프로젝트 편집자 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감의 필드를 고친다. 사람과 Agent 가 같은 일감을 동시에 고칠 수 있으므로, 남이 먼저 고친 것을 모르고 덮어쓰지 않게 `rowVersion` 으로 막는다.

**세부 요구사항**
1. `PATCH /workspaces/{workspace}/issues/{number}` 는 `@IssueApi(issue.edit)` 여야 한다. 상태 · 날짜 · 담당자 · 상위 일감도 이 요청으로 고친다. `project` 에 다른 프로젝트를 넣으면 옮긴다([FR-ISS-024](#fr-iss-024)).
2. 요청에는 `rowVersion`(필수)과 바꿀 필드만 담는다. 고칠 수 있는 것: 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자 · 상위 일감 · 날짜 다섯 개. 검증은 만들기와 같다.
3. 관리자를 바꾸면 서비스가 `issue.manager.assign` 도 확인해야 한다. 없으면 403 `PERMISSION_REQUIRED` 이고 아무것도 바뀌지 않는다.
4. `rowVersion` 이 지금 값과 다르면 409 `CONCURRENT_UPDATE` 이고 아무것도 바뀌지 않아야 한다. 응답에 지금 `rowVersion` 을 담는다.
5. 바뀐 필드는 모두 이력 한 줄에 전 · 후로 남긴다. 상태에 따라 자동으로 채운 날짜도 같은 줄이다([FR-ISS-005](#fr-iss-005)).
6. 고치면서 댓글(`notes`)을 함께 남길 수 있다 — 같은 이력 줄에 든다.
7. 실제로 바뀐 값이 없으면 이력을 남기지 않고 `rowVersion` 도 그대로 두고 200 으로 답한다.
8. 저장하면 `updated_at` 을 고치고 `rowVersion` 을 1 올린다.
9. 보관한 프로젝트에서는 409 `PROJECT_NOT_WRITABLE` 이다.
10. 고치기를 감사(`issue.update` — 바뀐 필드 이름)에 남긴다.

**수용 기준**
- [x] 옛 `rowVersion` 으로 고치면 409 `CONCURRENT_UPDATE` 이고 일감이 그대로다 (IssueTest)
- [ ] 같은 `rowVersion` 으로 동시에 보낸 두 요청 가운데 하나만 성공하고 다른 하나는 409 다
- [x] 제목 · 상태 · 담당자를 한 번에 고치면 이력 한 줄에 세 필드의 전 · 후가 있다 (IssueTest)
- [ ] 바뀐 값이 없는 요청은 이력을 남기지 않는다

**설명** — 일감의 상태는 고정 11개이고 아무 상태로나 옮길 수 있다(확인완료 둘은 관리자만 웹에서). 완료 · 종료 · 취소로 옮기면 완료일 · 종료일을 자동으로 채우거나 비운다. 워크플로를 사용자가 정하는 것은 나중 후보다. 2026-11-22 사용자: "상태 : 등록, 진행, 테스트, 완료, 종료" — `NEW` 의 이름을 신규 → 등록으로 바꾸고 `TESTING`(테스트)을 진행과 완료 사이에 더했다(V7). 2026-11-24 사용자: "이슈 상태에 취소, 보류도 만들어"(moai-works 일감 #152) — `ON_HOLD`(보류)와 `CANCELLED`(취소)를 더했다(V26). 보류는 사람의 결정이나 다른 일을 기다리며 멈춘 일이고, 취소는 하지 않기로 한 일 · 중복이다. 종료는 이제 "완료한 일을 사람이 확인해 닫음"만 뜻한다. 2026-11-25 사용자: "이슈 상태에 확인요청, 확인완료 상태 추가하자 — 확인요청은 요구사항 관리자에게 확인해 달라고 요청하는 것이고, 확인완료는 요구사항 관리자가 확인 완료했으니 완료 처리해라" · "요구사항 확인요청, 요구사항 확인완료 2가지 건도 더 추가해"(moai-works 일감 #272) — 관리자 확인 넷을 더했다(V28). 요구사항 확인요청(`REQUIREMENT_REVIEW`)은 일을 시작하기 전에 Agent · 담당자가 이해한 요구사항을 적고 관리자에게 맞는지 확인해 달라는 것, 요구사항 확인완료(`REQUIREMENT_CONFIRMED`)는 관리자가 확인했으니 진행으로 시작하라는 것, 확인요청(`REVIEW`)은 일을 마친 뒤 결과를 확인해 달라는 것, 확인완료(`CONFIRMED`)는 관리자가 확인했으니 완료하라는 것이다. "관리자"는 그 일감의 관리자(`manager_id`)다. Agent 가 스스로 확인할 수 없게 확인완료는 웹에서만 한다.

**세부 요구사항**
1. 상태는 `NEW`(등록) · `REQUIREMENT_REVIEW`(요구사항 확인요청) · `REQUIREMENT_CONFIRMED`(요구사항 확인완료) · `IN_PROGRESS`(진행) · `TESTING`(테스트) · `REVIEW`(확인요청) · `CONFIRMED`(확인완료) · `ON_HOLD`(보류) · `DONE`(완료) · `CLOSED`(종료) · `CANCELLED`(취소) 11개이고, 상태를 늘어놓는 곳(목록 · 메뉴 · 거르기 · `sort=status`)은 모두 이 차례여야 한다. 그 밖의 값은 400 `INVALID_ISSUE_STATUS` 다.
2. 어느 상태에서 어느 상태로나 옮길 수 있다(`issue.edit` — 확인완료 둘은 11번). `NEW` · 관리자 확인 넷 · `IN_PROGRESS` · `TESTING` · `ON_HOLD` 를 "열린 일감", `DONE` · `CLOSED` · `CANCELLED` 를 "닫힌 일감"으로 묶어 목록 필터(`open` · `closed`) · 기한 지남 · 아침 알림에 쓴다 — 보류 · 확인을 기다리는 중이어도 완료 기한은 뜻이 있다.
3. 날짜 자동 채움은 요청의 값을 먼저 적용한 뒤 다음과 같아야 한다.

   | 옮긴 상태 | 완료일 `completed_on` | 종료일 `closed_on` |
   |---|---|---|
   | → `DONE` | 비어 있으면 오늘 | 그대로(`CANCELLED` 에서 오면 비운다) |
   | → `CLOSED` | 그대로 | 비어 있으면 오늘 |
   | → `CANCELLED` | 비운다(취소는 끝낸 것이 아니다) | 비어 있으면 오늘 |
   | → 열린 상태(`NEW` · 관리자 확인 넷 · `IN_PROGRESS` · `TESTING` · `ON_HOLD`) | 비운다 | 비운다 |

4. "오늘"은 api 의 기준 시간대(지금은 Asia/Seoul 고정, 워크스페이스 시간대 설정은 나중)의 날짜다.
5. 같은 요청에서 상태와 함께 완료일 · 종료일을 직접 주면 준 값을 쓴다(자동 채움은 빈 경우만).
6. 자동으로 채우거나 비운 날짜도 그 고치기의 이력 줄에 전 · 후로 남는다.
7. 다른 상태에서 `ON_HOLD` · `CANCELLED` · `REQUIREMENT_REVIEW` · `REVIEW` 로 옮길 때는 까닭이 있어야 한다 — 확인요청이면 관리자가 무엇을 확인할지(요구사항: 이해한 요구사항 · 범위 · 수용 기준 · 물을 것, 결과: 한 것 · 확인 방법 · 결과 · 남은 것)다. 같은 요청의 댓글(REST `notes` · MCP `reason` · `comment`)이고, 상태 변경과 같은 이력 줄에 남는다. 확인요청에서 그 짝인 확인완료(요구사항 확인요청 → 요구사항 확인완료, 확인요청 → 확인완료)가 아닌 곳으로 옮길 때(관리자의 **반려** · 요청한 쪽의 **거둠**)도 까닭이 있어야 한다. 없거나 빈칸뿐이면 400 `STATUS_REASON_REQUIRED`(REST · MCP 같은 code)이고 일감은 그대로다. 그 밖의 옮김(보류 · 취소에서 나가는 것, 확인완료에서 이어 가는 것 포함)은 까닭이 없어도 된다.
8. `ON_HOLD` · `CANCELLED` · `REQUIREMENT_REVIEW` · `REVIEW` 로는 일감을 만들 수 없다(만들기에는 댓글이 없다) — 400 `STATUS_REASON_REQUIRED`. 만든 뒤 까닭과 함께 옮긴다. 확인완료로 만드는 것은 11번 규칙을 따른다(웹에서 관리자가 자기를 관리자로 두고 만들 때만).
9. 종료(`CLOSED`)는 완료한 일을 사람이 확인해 닫을 때 쓰고, 하지 않을 일 · 중복은 취소(`CANCELLED`)를 쓴다. 화면 · MCP 도구 설명이 이 뜻을 알린다. 이미 종료로 닫힌 일감은 옮기지 않는다.
10. 관리자 확인은 **고를 수 있는 단계**다 — 흔한 흐름은 `NEW` → (`REQUIREMENT_REVIEW` → `REQUIREMENT_CONFIRMED`) → `IN_PROGRESS` → `TESTING` → (`REVIEW` → `CONFIRMED`) → `DONE` 이고, `NEW` → `IN_PROGRESS`, `TESTING` → `DONE` 도 그대로 된다. 반려는 요구사항 확인요청 → `NEW`(또는 `IN_PROGRESS`), 확인요청 → `IN_PROGRESS` 다.
11. `REQUIREMENT_CONFIRMED` · `CONFIRMED` 로는 그 일감의 관리자(바꾸기 전의 관리자 — 같은 요청에서 나를 관리자로 바꾸고 확인할 수 없다) 또는 그 프로젝트의 `project.manage` 가 있는 사람만, **웹(REST)으로만** 옮긴다. 다른 사람이 REST 로 옮기면 403 `CONFIRM_BY_MANAGER_ONLY`, MCP 로는 키 주인이 관리자여도 늘 403 `CONFIRM_BY_MANAGER_ONLY`(관리자에게 웹에서 확인해 달라고 하라는 글)이고 일감은 그대로다 — Agent 가 스스로 확인할 수 없게.
12. 알림 — 확인요청으로 옮기면 관리자에게 `issue.review_requested`, 확인완료로 옮기면 담당자에게 `issue.review_confirmed`, 확인요청을 되돌리면(반려 · 거둠) 관리자 · 담당자에게 `issue.review_returned`. 받는 사람에게 그 옮김의 `issue.status_changed` 는 따로 보내지 않는다(읽지 않은 상태 바뀜에 묶여 묻히지 않게). 자기가 한 일은 자기에게 알리지 않고, 까닭 댓글의 `issue.commented` 는 따로 간다. 메일은 다른 종류처럼 사람이 켠 종류만([FR-NOTI-006](07-notification.md#fr-noti-006)).
13. 화면은 확인요청에 있는 일감의 보기 머리 아래에 띠를 보인다 — 관리자 · `project.manage` 에게는 요청한 사람 · 무엇을 확인할지와 "확인 완료"(짝인 확인완료로) · "반려"(까닭을 받아 되돌림) 단추, 그 밖의 사람에게는 누구의 확인을 기다리는지. 관리자가 아니면 상태 바꾸기 메뉴 · 고치기의 확인완료 둘을 꺼 두고 누가 고를 수 있는지 적는다. MCP 결과의 `next` 는 확인요청이면 "관리자 확인을 기다린다 — 시간을 적지 말고 다른 일감을 잡는다", 요구사항 확인완료면 진행으로 시작, 확인완료면 완료(처리 결과)를 알린다.

### FR-ISS-006 관리자와 담당자

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(관리자 필수 · 바꾸기는 issue.manager.assign · 관리자 · 담당자는 프로젝트 독자만 `USER_NOT_PROJECT_READER` · 담당자 비우기) · 자동 테스트. 남은 것: 지정 멤버 프로젝트의 비독자 멤버 시험 · 관리자 비우기 400 시험 · 떠난 멤버 표시(화면). |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감마다 책임지는 관리자(예: 요구사항 관리자)와 일을 하는 담당자(예: 요구사항 담당자)가 있다. 관리자는 moai-wiki 의 페이지 소유자 자리이고, 담당자는 새로 더한 것이다. 각각 한 명이다.

**세부 요구사항**
1. 관리자(`manager_id`)는 필수여야 한다. 기본은 만든 사람이다(MCP 로 만들면 키 주인 — [FR-MCP-005](04-mcp.md#fr-mcp-005)). 비우려 하면 400 `ISSUE_MANAGER_REQUIRED` 다.
2. 담당자(`assignee_id`)는 없어도 된다. 비울 수 있다.
3. 관리자 · 담당자는 그 프로젝트의 독자인 활성 멤버여야 한다([FR-PRJ-006](02-project.md#fr-prj-006)). 아니면 400 `USER_NOT_PROJECT_READER` 다(워크스페이스 멤버가 아닌 사람도 같은 답이다).
4. 관리자를 바꾸려면 `issue.manager.assign`, 담당자를 바꾸려면 `issue.edit` 가 있어야 한다.
5. 관리자 · 담당자가 워크스페이스를 떠나거나 · 제거되거나 · 정지되거나 · 그 프로젝트의 독자가 아니게 되면, 일감의 값은 그대로 두고 화면 · 응답에 "떠난 멤버"로 표시해야 한다. 그 사람을 새로 지정할 수는 없다. 목록에서 그 사람으로 걸러 찾아 바꾼다.
6. 화면은 후보를 그 프로젝트의 독자인 활성 멤버에서 고르게 한다(api 가 후보 목록을 준다).
7. 바꾸기는 이력에 전 · 후로 남는다.

**수용 기준**
- [x] 관리자를 정하지 않고 만들면 만든 사람이 관리자다 (IssueTest)
- [x] `issue.manager.assign` 이 없으면 관리자를 바꿀 수 없고(403), 있으면 바뀌고 이력에 남는다 (IssueTest)
- [ ] `RESTRICTED` 프로젝트의 독자가 아닌 멤버를 담당자로 정하면 400 `USER_NOT_PROJECT_READER` 다
- [ ] 담당자를 비울 수 있고, 관리자를 비우면 400 `ISSUE_MANAGER_REQUIRED` 다
- [ ] 담당자를 워크스페이스에서 제거해도 일감의 담당자 값은 남고 "떠난 멤버"로 보인다

### FR-ISS-007 날짜 (완료 기한 · 시작일 · 완료 예정일 · 완료일 · 종료일)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(다섯 날짜, 값이 둘 다 있을 때만 순서 검사 `INVALID_ISSUE_DATES`) · 자동 테스트. 남은 것: 한쪽만 있을 때 시험 · "기한 지남" 표시(화면). |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 일감에는 날짜 다섯 개가 있다. 계획(시작일 · 완료 예정일 · 완료 기한)과 결과(완료일 · 종료일)를 따로 둬서, 늦은 일감과 끝난 때를 알 수 있다.

**세부 요구사항**
1. 날짜는 다음 다섯 개이고 모두 시각 없는 날짜(`yyyy-MM-dd`)여야 한다. 모두 비어 있을 수 있다.

   | 필드 | 이름 | 뜻 |
   |---|---|---|
   | `due_date` | 완료 기한 | 늦어도 이날까지 끝내야 한다 |
   | `start_date` | 시작일 | 시작한(할) 날 |
   | `planned_end_date` | 완료 예정일 | 끝낼 것으로 보는 날 |
   | `completed_on` | 완료일 | 실제로 끝낸 날(`DONE` 으로 가면 자동, [FR-ISS-005](#fr-iss-005)) |
   | `closed_on` | 종료일 | 일감을 닫은 날(`CLOSED` · `CANCELLED` 로 가면 자동) |

2. 두 값이 모두 있을 때만 다음을 검사해야 한다: 시작일 ≤ 완료 예정일, 시작일 ≤ 완료 기한, 완료일 ≤ 종료일. 검사는 요청 값과 자동 채움을 모두 적용한 결과로 한다. 어기면 400 `INVALID_ISSUE_DATES` 이고 어긴 필드 이름을 담는다.
3. `issue.edit` 가 있으면 다섯 날짜를 모두 직접 고칠 수 있다(완료일 · 종료일 포함).
4. 열린 일감(`NEW` · 관리자 확인 넷 · `IN_PROGRESS` · `TESTING` · `ON_HOLD`)의 완료 기한이 오늘보다 앞이면 목록 · 보기에서 "기한 지남"으로 표시한다. 닫힌 일감(`DONE` · `CLOSED` · `CANCELLED`)에는 표시하지 않는다.
5. 상위 일감의 날짜를 하위 일감에서 계산하지 않는다(첫 출시).

**수용 기준**
- [x] 시작일이 완료 예정일 · 완료 기한보다 늦으면 400 `INVALID_ISSUE_DATES` 다 (IssueTest)
- [x] 완료일이 종료일보다 늦으면 400 이다(자동 채움으로 그렇게 되는 경우 포함) (IssueTest)
- [ ] 한쪽 값만 있으면 검사하지 않는다
- [x] `issue.edit` 로 완료일을 직접 고칠 수 있고 이력에 남는다 (IssueTest)
- [ ] 완료 기한이 지난 열린 일감에만 "기한 지남"이 보인다

## 3. 상위 · 하위와 연결

<a id="fr-iss-008"></a>
### FR-ISS-008 상위 · 하위 일감

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(같은 프로젝트 FK · 순환 `PARENT_CYCLE` · 10단계 `PARENT_DEPTH_EXCEEDED` · 없는 상위 `PARENT_NOT_FOUND`) · 자동 테스트. 남은 것: 동시 옮기기 순환 시험 · 상위 빼기 이력 시험. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 큰 일감을 작은 일감으로 나눈다(예: 요구사항 아래 기능 · 작업). moai-wiki 의 페이지 트리와 같은 규칙 — 같은 프로젝트 안, 순환 금지, 깊이 10 — 을 쓴다.

**세부 요구사항**
1. 일감은 같은 프로젝트의 일감 하나를 상위로 가질 수 있어야 한다. DB 는 `(project_id, parent_id)` → `(project_id, id)` 외래 키로 다른 프로젝트를 막는다. 상위가 없으면 최상위다.
2. 상위는 만들 때 또는 고칠 때(`issue.edit`) 번호로 정하고, `null` 로 빼서 최상위로 올린다.
3. 없거나 지운 상위 번호는 400 `PARENT_NOT_FOUND` 다.
4. 자기 자신이나 자기 하위를 상위로 정하면 400 `PARENT_CYCLE` 이다.
5. 깊이는 10 이하여야 한다(최상위가 1). 옮긴 뒤 그 일감 아래 가장 깊은 하위까지 10 을 넘으면 400 `PARENT_DEPTH_EXCEEDED` 다.
6. 두 사람이 서로를 상대 아래로 동시에 옮겨도 순환이 생기지 않아야 한다(프로젝트 단위로 잠그고 검사한다).
7. 하위 일감 목록은 보기([FR-ISS-002](#fr-iss-002))에 오고, 목록에서 상위로 거를 수 있다([FR-ISS-012](#fr-iss-012)).
8. 상위 바꾸기는 하위 일감의 이력에 전 · 후로 남는다.
9. 상위 일감의 상태 · 날짜를 하위에서 계산하지 않는다(첫 출시). 하위가 있는 일감은 지울 수 없다([FR-ISS-013](#fr-iss-013)).
10. 일감을 다른 프로젝트로 옮기면 하위 줄기가 함께 옮겨 가고, 옛 프로젝트에 남는 상위와의 연결은 끊는다([FR-ISS-024](#fr-iss-024)). 상위 번호도 워크스페이스 번호다.

**수용 기준**
- [x] 상위를 정하면 상위 일감의 보기에 하위로 나온다 (IssueTest)
- [x] 자기 자신 · 자기 하위를 상위로 정하면 400 `PARENT_CYCLE` 이다 (IssueTest)
- [x] 깊이 11 이 되는 옮기기는 400 `PARENT_DEPTH_EXCEEDED` 다 (IssueTest)
- [ ] 두 일감을 서로의 아래로 동시에 옮겨도 순환이 생기지 않는다
- [ ] 상위를 빼면 최상위가 되고 이력에 남는다

### FR-ISS-009 연결 일감

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 한 것: api(네 종류 · 한 쌍에 하나 · 양쪽 이력 · 감사 `issue.link.add` · `issue.link.remove`) · 2026-11-24 같은 워크스페이스의 다른 프로젝트 일감과도 연결 · 읽을 수 없는 쪽 숨김 · 다른 프로젝트 상대의 제목은 알림에 싣지 않음 · 자동 테스트. 남은 것: 다른 일감의 연결 id 404 시험 · 양쪽 이력 시험 · 화면 문구. |
| 관련 설계 | [일감 설계](../design/05-issue.md) |

**설명** — 상하위가 아닌 일감끼리의 관계(관련 · 차단 · 선행 · 중복)를 건다. moai-wiki 의 페이지 링크 자리다. 2026-11-24 부터 같은 워크스페이스의 다른 프로젝트 일감과도 건다(Redmine 의 관계처럼 — [ADR-030](../design/00-key-decisions.md#adr-030)).

**세부 요구사항**
1. 표 `issue_link`(id · source · target · 연결 종류 · 만든 사람 · 만든 때)에 다음 종류를 둬야 한다.

   | 종류 | source 에서 보면 | target 에서 보면 |
   |---|---|---|
   | `RELATES` | 관련 | 관련 |
   | `BLOCKS` | 차단함 | 차단됨 |
   | `PRECEDES` | 선행함 | 후행함 |
   | `DUPLICATES` | 중복함(이 일감이 저 일감의 중복) | 중복됨 |

2. `POST /workspaces/{workspace}/issues/{number}/links` `{target, type}` 는 `@IssueApi(issue.edit)` 여야 한다. 경로의 일감이 source 다.
3. 대상(`target`)은 같은 워크스페이스의 번호다 — 지우지 않았고 거는 사람이 지금 읽을 수 있는 일감이어야 한다(다른 프로젝트여도 된다). 아니면(없음 · 읽을 수 없음을 가리지 않고) 400 `LINK_TARGET_NOT_FOUND` 다. 대상의 프로젝트가 보관돼 있으면 409 `PROJECT_NOT_WRITABLE`, 자기 자신은 400 `INVALID_ISSUE_LINK` 다.
4. 같은 두 일감 사이에는 방향 · 종류와 상관없이 연결이 하나만 있어야 한다. 있으면 409 `ISSUE_LINK_EXISTS` 다.
5. `DELETE /workspaces/{workspace}/issues/{number}/links/{linkId}` 는 `@IssueApi(issue.edit)` 다. 그 연결이 경로의 일감에 걸린 것(어느 쪽이든)이 아니면 404 `ISSUE_LINK_NOT_FOUND` 다.
6. 연결은 양쪽 일감의 보기에 각자의 방향으로 보인다. 보는 사람이 상대 일감의 프로젝트를 읽을 수 없으면 그 연결은 보기에서 빠진다(있다는 것도 숨긴다 — 일감 주소의 "독자가 아니면 404" 와 같은 규칙). 이력 줄에는 상대 번호만 남는다.
7. 연결을 걸고 풀면 양쪽 일감의 이력에 남는다. 연결은 일감의 필드가 아니므로 `rowVersion` 을 요구하지 않고 바꾸지 않는다.
8. 첫 출시에는 연결이 일정 · 상태를 바꾸지 않는다(`BLOCKS` 가 닫기를 막지 않고, `PRECEDES` 가 날짜를 옮기지 않는다).
9. 걸기 · 풀기를 감사(`issue.link.add` · `issue.link.remove`)에 남긴다.
10. 연결을 알릴 때 상대가 다른 프로젝트 일감이면 상대 제목은 싣지 않고 번호만 싣는다 — 받는 사람이 그 프로젝트를 못 읽을 수 있다.

**수용 기준**

## 4. 이력과 댓글

| 항목 | 내용 |
|---|---|
| 우선순위 | M |

**설명** — 일감에 일어난 모든 변경과 댓글을 시간순으로 남긴다(moai-wiki 의 리비전 자리). 사람과 Agent 가 같은 일감을 다루므로 "누가 · 어느 길로" 바꿨는지가 늘 보여야 한다.

**세부 요구사항**
1. 표 `issue_journal` 은 id · 일감 · 주체 id · 주체 종류(`USER` · `SERVICE` — V2 그대로. MCP 로 한 일도 키 주인 `USER` 이고, MCP 는 `SERVICE` 를 쓰지 않는다) · 경로(`WEB` · `MCP`) · 만든 때 · 댓글(`notes`, Markdown, 없어도 됨) · 변경(`changes` jsonb `[{field, before, after}]`)을 가져야 한다.
2. 만들기 · 고치기 · 상위 바꾸기 · 연결 걸기 · 풀기 · 댓글마다 한 줄을 남겨야 한다. 한 요청은 한 줄이다. 댓글은 `notes` 만 있는 줄이다.
3. 남기는 필드는 유형 · 제목 · 설명 · 상태 · 관리자 · 담당자 · 상위 · 날짜 다섯 개 · 연결이다. 설명은 전 · 후 전문을 남기고 화면은 차이를 보여 준다.
4. MCP 로 한 일은 키 주인(`USER`) · 경로 `MCP` 이고 어느 키인지(키 id)를 남긴다. 사람 권한을 넘어 워크스페이스 이름으로 쓰는 주체(서비스 키)는 없다(2026-11-22 — [FR-MCP-001](04-mcp.md#fr-mcp-001)).
5. 이력은 업무와 같은 트랜잭션에 저장해야 한다. 이력 저장이 실패하면 변경도 되돌린다.
6. 이력 줄을 고치거나 지우는 API 는 없어야 한다. 댓글 고치기 · 지우기도 첫 출시에 없다.
7. 일감의 쓰기는 감사에도 남긴다: `issue.create` · `issue.update` · `issue.comment` · `issue.link.add` · `issue.link.remove` · `issue.delete`. MCP 로 한 쓰기는 엔드포인트 id · 키 id · 도구 이름을 함께 남긴다([FR-MCP-006](04-mcp.md#fr-mcp-006)).
8. 화면은 이력을 전체 · 댓글만 · 변경만으로 거르고, 경로가 MCP 인 줄에 표시를 단다.

5. 각 줄은 번호 · 유형 · 제목 · 상태 · 관리자 · 담당자 · 완료 기한 · 완료 예정일 · 상위 번호 · 하위 수 · 고친 때 · 기한 지남 여부를 준다.
6. 지운 일감은 나오지 않는다. 경로의 프로젝트 일감만 나온다(각 줄에 `project {key, name}`).
7. 모르는 필터 값(없는 상태 · 유형, 숫자가 아닌 상위)은 400 `INVALID_FILTER` 다.
8. 성능은 [NFR-PERF-001](05-non-functional.md#nfr-perf-001)(일감 10만 건 프로젝트에서 p95 800ms)을 지킨다.

**설명** — 사용자 결정(2026-11-22): "프로젝트의 아이템들은 리비전을 모두 관리해야 한다. 그리고 리비전별로 변화도 타임라인으로 보여 줘야 하고 변화한 것도 git 처럼 diff 처럼 보여 주고" · "당연히 누가 수정했는지도". 일감이 바뀔 때마다 그 시점의 일감 전체를 한 판으로 남기고, 판들을 타임라인으로 보이며, 두 판 사이의 변화를 git diff 처럼 보인다. moai-wiki 의 페이지 리비전과 같은 모양이다.

**세부 요구사항**
1. 변화 기록의 시각(만든 때 · 고친 때 · 판 · 이력 · 작업 시간을 적은 때)은 **밀리초까지** 남기고 보인다(2026-11-22 사용자 결정 "생성, 수정, 등등 변화에 대한 건 밀리세컨드까지"). 완료 기한 · 시작일 · 완료 예정일 · 완료일 · 종료일은 날짜까지만이다.
1-1. 일감을 만들면 1판이고, 필드(유형 · 제목 · 설명 · 상태 · 관리자 · 담당자 · 상위 일감 · 다섯 날짜 · 예상 공수)가 바뀔 때마다 새 판을 남겨야 한다. 판에는 그 시점의 일감 전체와 **누가(사람 이름 · id) · 어느 길로(웹 · MCP) · 언제** 바꿨는지가 있다.
2. 댓글 · 연결 · 작업 시간 기록은 판을 만들지 않는다(이력에는 남는다). 필드를 바꾼 이력 줄에는 그 판 번호가 붙는다.
3. 판은 덮어쓰지 않는다 — 고치거나 지우는 길이 없고, DB 가 막는다.
4. `GET …/issues/{n}/revisions?before=&limit=` — 새 판부터, 판마다 누가 · 어느 길로 · 언제 · 바뀐 필드 이름 · 지금 판 표시. 쪽 넘김(최대 50).
5. `GET …/issues/{n}/revisions/{no}` — 그 판의 일감 전체.
6. `GET …/issues/{n}/revisions/{no}/diff?from=` — 두 판의 차이. `from` 이 비면 바로 앞 판과, 1판은 "없음"과 견준다. 필드는 전 · 후, 설명은 줄 단위(git 처럼 넣은 줄 · 지운 줄 · 줄 번호, 넣은 · 지운 줄 수). 같은 판끼리는 400 `SAME_REVISION`, 없는 판은 404 `REVISION_NOT_FOUND`.
7. 화면: 일감의 "리비전 · 차이" 화면 — 판 타임라인(누가 · 언제 · MCP 표시 · 바뀐 필드), 판을 고르면 바로 앞 판과의 차이, 아무 두 판 견주기, 한 판 전체 보기. 차이는 지운 줄 빨강 · 넣은 줄 초록에 `−` · `+` 를 함께 적는다(색만으로 전하지 않는다). 고른 판은 주소에 남는다.
8. 판 보기는 `issue.read` 다(독자면 누구나).

10. 이미지 첨부(png · jpeg · gif — 서버가 첫 바이트로 알아낸 것)는 작은 미리보기 그림(긴 변 320px)을 원본 옆에 두고 첨부 목록이 쓴다. 미리보기 받기는 원본 받기와 같은 판정(독자가 아니면 404) · 머리글(inline · nosniff · sandbox CSP)이다. 파일 · 깨진 그림 · 너무 큰 그림은 미리보기 없이 파일 표시, WebP 는 원본을 쓴다.

**세부 요구사항**
1. 지금 쓰는 유형(새기능 · 버그 · 테스트 · 기술조사)마다 템플릿(Markdown, 30000자까지)이 하나 쓰인다. 고르는 순서는 프로젝트 덮어쓰기 → 워크스페이스 기본 → 처음 템플릿이다. 옛 유형에는 템플릿이 없다(`ISSUE_TYPE_RETIRED`).

5. MCP 일감 입구는 템플릿을 주고(`get_issue_template`), `create_issue` · `update_issue` 결과의 `checks` 에 빠진 항목(`TEMPLATE_SECTIONS_MISSING`)을 알린다(2026-11-25, 일감 #282 — 전에는 `templateCheck` 칸으로 출처와 함께 붙였다). 프로젝트 관리 입구는 같은 권한으로 템플릿을 보고 · 정하고 · 되돌린다.

**설명** — 사용자(2026-11-23): "이렇게 md 편집기를 만들고 이슈의 본문이나 덧글은 모두 md 로 작성할 수 있게 해 줘"(VS Code Markdown Editor 화면 — 위 도구 막대 · 왼쪽 목차 · 쓰면서 바로 그려짐). 저장 형식은 그대로 Markdown 이다.

**세부 요구사항**
1. 일감 설명(새 일감 · 고치기)과 댓글은 쓰면서 바로 그려지는 Markdown 편집기로 쓴다. 저장하는 값은 늘 Markdown 이다.
2. 위 고정 도구 막대: 목차 · 제목/문단 · 굵게 · 기울임 · 취소선 · 링크 | 글머리 · 번호 · 할 일 목록 · 표 | 인용 · 코드 블록 · 줄 안 코드 · 가로줄 | 되돌리기 · 다시 | 이미지 · 파일 넣기 · Markdown 원문. 도구 설명(단축키 함께)과 aria-label 이 있고, 좁은 화면에서는 막대 안에서만 가로로 밀린다.
3. 목차는 설명 편집기에서 편집 칸이 넓으면(900px 이상) 처음부터 열고, 제목을 누르면 그 자리로 간다. 댓글에는 목차가 없다.
4. "Markdown 원문"으로 원문을 그대로 고칠 수 있다(CodeMirror). 돌아오면 그 원문으로 편집기를 다시 만든다.
5. 손대지 않은 덩어리는 원문 그대로 저장한다 — 열자마자 저장하면 원문과 한 글자도 다르지 않다. 고친 덩어리만 편집기 모양이 된다(긴 목록 · 표의 한 칸을 고치면 그 덩어리 전체).
6. 첨부: 그림 · 파일을 붙여 넣거나 끌어 놓거나 단추로 고르면 그 일감에 올리고 그 자리에 `![이름](attachment:<id>)` 를 넣는다(올리는 동안 자리 표시 · 저장 단추 잠금, 새 일감은 만든 뒤부터). `attachment:` 그림은 편집 중에도 그 일감의 첨부로 보이고, 바깥 주소 그림은 받지 않는다.
7. 남이 쓴 글의 HTML 은 편집 중에도 실행하지 않는다(글자로 보인다). 편집 중에는 링크를 열지 않는다. 링크 넣기는 http · https · mailto · 이 화면 안의 경로 · 첨부 표시만 받는다.
8. 화면 보안 정책(CSP `script-src 'self'`)에서 바깥 스크립트 없이 돈다. 바깥 서비스(AI)를 부르는 편집기 기능은 끈다.
9. 다크 · 라이트를 따르고, 390px 에서도 쓸 수 있다.

**수용 기준**
- [x] 실제 일감 설명 · 댓글(moai-works · moai-wiki 39건)과 어려운 경우 16건을 편집기에 열자마자 꺼내 저장하면 원문과 한 글자도 다르지 않다(자동 시험) — 실제 앱에서도 #2 · #5 · #11 · #12 를 열고 원문 보기로 바꿔 저장된 글과 같음을 확인
- [x] 마지막 덩어리 하나를 고치면 그 덩어리만 바뀐다(자동 시험) — 이어진 목록은 그 목록 묶음이 편집기 모양이 된다(다시 읽으면 합쳐지지 않게)
- [x] 이웃한 목록 둘 가운데 하나만 고쳐 저장해도 다시 읽으면 목록이 둘이다 — `-`/`*` · `1.`/`1)` · 목록 뒤 들여 쓴 코드(자동 시험 · ego-browser 2026-11-23, 일감 #16)
- [x] 3만 자 글에서 쓰다 멈춘 뒤 일이 크게 준다 — 약 190–255ms → 26–70ms, 긴 작업 없음(ego-browser 2026-11-23, 일감 #16). 덩어리로 적은 글 = 통째로 적은 글(시험 자료 55건 · 고침 · 되돌림)
- [x] 붙여 넣기 · 단추로 그림을 올리면 그 자리에 표시가 들어가고 편집 중에도 그림이 보인다(ego-browser 2026-11-23)

- [x] CSP 위반 없이 편집기가 돈다 — 고치기 · 댓글 · 원문 보기 · 올리기(ego-browser, web-backend 11002)
- [x] 다크 · 390px 에서 쓸 수 있고 페이지가 가로로 밀리지 않는다(ego-browser 2026-11-23)

## 6. 워크스페이스 아래의 일감

사용자(2026-11-24, moai-works 일감 #29): "그리고 중요한 실수가 있었어 이슈 넘버가 프로젝트 별로 하는데 아니야 워크스페이스 별로 해야해" · "워크스페이스 단위로 유니크한 번호여야해" · "그렇다는건 이슈는 프로젝트 단위에 포함이 되지만 기본적으로 워크스페이스 아래 있는것이고 이슈는 프로젝트는 속성처럼 가지고 있어야해" · "전체 워크스페이스에서 이슈를 검색할 수도 있어야해" · "레드마인을 생각하면 돼". 일감은 워크스페이스 아래에 있고(Redmine 의 한 인스턴스 = 워크스페이스), 프로젝트는 일감의 속성이라 옮길 수 있다. 번호는 워크스페이스 안에서 하나다([FR-ISS-001](#fr-iss-001)). 권한 경계는 그대로 **그 일감의 지금 프로젝트**다. 결정은 [ADR-030](../design/00-key-decisions.md#adr-030), 설계는 [일감 설계](../design/05-issue.md).

### FR-ISS-024 일감 옮기기 (다른 프로젝트로)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-24: api(고치기의 `project` — 두 프로젝트의 권한 · 하위 줄기 함께 · 상위 끊기 · 유형 · 사람 확인 · 모듈 key 로 잇기 · 첨부 행의 프로젝트 따라감 · 이력 · 새 판(판에 프로젝트) · 감사 `issue.move` · 알림) · MCP(`update_issue` 의 `moveToProject`) · 화면(고치기의 프로젝트 고르기 · 옮길 때 확인 창) · 자동 테스트(WorkspaceIssueTest · McpIssueNumberTest · 화면 시험). 남은 것: 실제 서버 · ego-browser 로 옮기기 확인 |
| 관련 설계 | [일감 설계](../design/05-issue.md) · [ADR-030](../design/00-key-decisions.md#adr-030) |

**설명** — 일감을 다른 프로젝트로 옮긴다(Redmine 의 일감 Project 칸 · 옮기기). 번호 · 주소는 그대로이고 권한 경계만 옮길 프로젝트로 바뀐다.

**세부 요구사항**
1. `PATCH /workspaces/{workspace}/issues/{number}` 의 `project` 에 같은 워크스페이스의 다른 프로젝트 주소 이름(key)을 넣으면 옮긴다(`rowVersion` 필수, 다른 필드와 함께 바꿔도 된다). 같은 프로젝트를 넣으면 옮기지 않는다.
2. 권한 — 지금 프로젝트의 `issue.edit`(입구가 판정) **그리고** 옮길 프로젝트의 `issue.create`. 옮길 프로젝트가 없거나 읽을 수 없으면 둘을 가리지 않고 400 `TARGET_PROJECT_NOT_FOUND`(읽을 수 없는 프로젝트를 알려 주지 않는다), 보관한 프로젝트면 409 `PROJECT_NOT_WRITABLE`, 읽을 수 있지만 `issue.create` 가 없으면 403 `PERMISSION_REQUIRED` 다.
3. 하위 일감은 줄기째 함께 옮긴다(지운 하위 포함 — 상위 · 하위는 같은 프로젝트). 옛 프로젝트에 남는 상위와의 연결은 끊고(`parent` → 없음) 이력에 남긴다. 같은 요청에서 옮길 프로젝트의 일감을 `parent` 로 주면 그것이 새 상위다.
4. 유형은 옮길 프로젝트에서 쓸 수 있어야 한다(지금은 워크스페이스 공통 유형 가운데 쓰는 것). 아니면 400 `ISSUE_TYPE_NOT_ALLOWED` — 같은 요청에서 `type` 을 바꾸면 된다. 함께 옮길 하위 일감의 유형이 맞지 않으면 그 번호들을 알리고 거절한다(먼저 그 일감을 고친다).
5. 관리자 · 담당자는 옮길 프로젝트를 읽을 수 있는 멤버여야 한다(하위 일감 것도). 아니면 400 `USER_NOT_PROJECT_READER`.
6. 모듈은 프로젝트마다다 — 같은 key 의 쓰는 모듈이 옮길 프로젝트에 있으면 그것으로 잇고, 없으면 빼고 이력(`modules` 전 · 후)과 감사에 남긴다. 같은 요청에 `modules` 를 주면 옮길 프로젝트의 모듈로 그대로 정한다.
7. 첨부 · 댓글 · 작업 시간 · 연결 · 이력 · 리비전은 일감을 따라간다(일감 id 에 묶여 있다). 첨부 행의 프로젝트도 함께 바뀌고, 저장소의 객체 이름은 그대로라 받기가 깨지지 않는다.
8. 옮긴 일감마다 이력 한 줄(`project` {key, name} 전 · 후, 필요하면 `parent` · `modules`)과 새 리비전(리비전에 그때의 프로젝트)을 남긴다. 감사는 `issue.move` 하나(옛 · 새 프로젝트, 옮긴 번호들, 끊은 상위, 빠진 모듈, 경로). 관리자 · 담당자에게 다른 고치기와 같이 알린다.
9. 화면 — 고치기 양식에 프로젝트 고르기(지금 프로젝트와 `issue.create` 가 있는 프로젝트만). 바꾸면 저장 전에 확인 창(하위 함께 · 상위 끊김 · 모듈은 같은 key 로만 · 번호 그대로)을 띄운다. MCP — `update_issue` 의 `moveToProject`.

**수용 기준**
- [x] 지금 프로젝트의 `issue.edit` 가 없으면 403, 옮길 프로젝트를 읽을 수 없거나 없으면 400 `TARGET_PROJECT_NOT_FOUND`, 옮길 프로젝트의 `issue.create` 가 없으면 403 이다 (WorkspaceIssueTest)
- [x] 옮기면 번호가 그대로이고 하위 · 하위의 하위가 함께 옮겨 가며, 옛 상위와의 연결은 끊긴다 (WorkspaceIssueTest)
- [x] 옮길 곳에서 쓸 수 없는 유형이면(하위 것도) 400 `ISSUE_TYPE_NOT_ALLOWED` 이고, 같은 요청에서 유형을 바꾸면 옮긴다 (WorkspaceIssueTest)

- [x] 이력에 프로젝트 전 · 후, 새 리비전에 옮긴 프로젝트, 리비전 차이에 `project`, 감사에 `issue.move` 가 남는다 (WorkspaceIssueTest)

### FR-ISS-026 번호 다시 매기기 (V23)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-24: V23(Java 마이그레이션, 한 트랜잭션) · 옛 링크 풀기(`GET /workspaces/{ws}/projects/{key}/issue-refs/{number}`) · 화면의 옛 주소 돌리기 · 자동 테스트(WorkspaceIssueNumberMigrationTest · IssueRefRewriteTest · WorkspaceIssueTest). 코드 · 테스트 완료, 운영 DB 적용은 합친 뒤. 남은 것: 운영 DB 에 V23 을 적용하고 옛 → 새 번호 표 확인 |

**설명** — 프로젝트 안 번호로 쌓인 일감을, 처음부터 워크스페이스 번호였던 것처럼 다시 매긴다(사람이 정한 방식). 가리키던 것이 모두 같은 일감을 계속 가리켜야 한다.

**세부 요구사항**
1. 워크스페이스마다 만든 때(`created_at`) 순서로 1 부터 다시 매긴다. 같은 때면 옛 번호 순(그다음 프로젝트 · id). 지운 일감도 번호를 받는다. 마이그레이션이 돌 때의 데이터로 계산한다(그 사이 만든 일감도 들어간다).
2. 같은 일감을 가리키던 번호를 새 번호로 바꾼다: 리비전의 상위 번호(`issue_revision.parent_number`), 첨부 티켓(`attachment_ticket.issue_number`), MCP 접근 기록(`mcp_access_log.issue_number` — "어느 일감"을 찾는 식별자라서 — 와 `link_issues` 의 대상 번호 `target_ref`), 이력 줄의 상위 · 연결 번호(`issue_journal.changes`), 알림의 번호(`notification.params` 의 `number` · `childNumber` · `otherNumber`). 감사 기록의 글은 쓴 그대로 둔다.
3. 지금 일감 설명과 지우지 않은 댓글의 `#번호` 를 그 글이 달린 일감의 프로젝트 번호로 읽어 새 번호로 바꾼다 — 화면의 `#번호` 링크 규칙(ISSUE_REF)과 같고, 펜스 · 들여쓴 코드 블록 · 인라인 코드 · 링크(글 · 주소) · 꺾쇠 자동 링크 · 맨 주소 · 링크 정의 줄은 그대로 둔다. 그 프로젝트에 없던 번호도 그대로 둔다. 옛 리비전 · 옛 댓글 글(고치기 전 글)은 역사라 건드리지 않는다.
4. 일감의 `row_version` · `updated_at`, 댓글의 판 · 고친 때는 올리지 않고 알림도 보내지 않는다.
5. 일감마다 옛 → 새 번호를 `issue_number_change`(일감 · 워크스페이스 · 그때의 프로젝트와 주소 이름 · 옛 번호 · 새 번호 · 바꾼 `#번호` 수)에, 바꾸기 전 · 뒤 글을 `issue_number_text_change` 에 남긴다. 번호나 설명이 바뀐 살아 있는 일감마다 시스템 이력 한 줄(한 사람 `moai-works`, 경로 `SYSTEM` — "번호가 바뀌었습니다: 프로젝트 #옛 → #새")을 남기고, 설명이 바뀌었으면 새 리비전도 남긴다.
6. 끝나면 워크스페이스 순번 = 그 워크스페이스의 가장 큰 번호, `UNIQUE (workspace_id, number)`, 프로젝트의 옛 순번(`project.issue_seq`)은 지운다.

8. 첨부(2026-11-26, 일감 #312): MCP 로 올린 첨부에 에이전트 세션 이름을 남긴다 — `request_attachment_upload` 가 받은 선택 인자 `agentSession`(티켓에 묶인다), 없으면 올릴 때(PUT) 그 일감의 에이전트 세션, 둘 다 없으면 없음. 웹에서 올린 첨부는 늘 없음. 규칙 · 바뀌지 않음은 2 와 같고(지움 · 정리 표시 · 일감 옮기기는 그대로 된다), 그 첨부를 더한 이력 줄도 같은 이름이다. 일감의 에이전트 세션은 바꾸지 않고 에이전트 멤버로 등록하지도 않는다. 이미 있던 MCP 첨부는 그 일감의 지금 에이전트 세션으로 채운다. ### FR-ISS-030 첨부 보기 (내려받지 않고 팝업으로)

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 일부 — 2026-11-26(일감 #310): 화면(첨부 보기 팝업 — 첨부파일 탭의 보기 단추 · 작은 그림, 본문 · 댓글의 첨부 링크 · 그림에서 연다 · 확장자 → 형식 고르기 · 이미지 · PDF(pdf.js 6.5.438) · Markdown · 코드 · JSON · CSV/TSV · 글 · 동영상 · 소리 · 볼 수 없음 · 글은 앞 2 MB · 배율 25~400% · 전체 화면 · 이전/다음 · 키보드 · ko/en) · web-backend 화면 보안 정책 `media-src 'self' blob:` · 자동 테스트(화면 attachment-kinds 38건 · attachment-viewer-screens 18건, web-backend ContentSecurityPolicyTest 3건). 남은 것: ego-browser(390px · 데스크톱 · 다크 · 영어)와 web-backend(11002)에서 PDF · 동영상 재생 · CSP 위반 0 확인 |
| 관련 설계 | [일감 설계 — 첨부](../design/05-issue.md#is-attachments) · [SECURITY.md §9](../../SECURITY.md#9-화면web-frontend의-보안-규칙) |

**설명** — 일감 #310: 첨부파일 탭에서 이미지는 새 탭으로 열리고 그 밖의 파일은 내려받기만 됐다. 받기 주소는 이미지가 아니면 늘 내려받기(`application/octet-stream`) · sandbox 라 브라우저의 PDF 보기 · 동영상 재생을 그대로 쓸 수 없다. 화면이 바이트를 받아 그 자리의 팝업에서 보인다 — [FR-ISS-018](#fr-iss-018) 의 받기 규칙(판정 · 머리글)은 그대로다.

**세부 요구사항**
1. 첨부파일 탭의 줄마다 "보기" 단추가 있고 작은 그림을 눌러도 같은 팝업이 열린다(이미지도 새 탭이 아니라 팝업). 내려받기 · 표시 복사 · 지우기는 그대로다.
2. 형식은 파일 이름의 확장자를 먼저, 없으면 올릴 때 받은 형식으로 정한다 — 이미지(서버가 첫 바이트로 정한 png · jpeg · gif · webp) · PDF · Markdown(.md · .markdown) · 코드(확장자 → 언어, 색 · 줄 번호) · JSON(펴서 보이고 틀리면 원문) · CSV/TSV(따옴표 칸을 읽어 표) · 글(.txt · .log · `text/*` · 모르는 형식인데 앞부분이 NUL 없는 UTF-8) · 동영상(mp4 · webm) · 소리(mp3 · wav · ogg · m4a). SVG 는 보지 않는다(내려받기만). 그 밖(오피스 · 한글 · 압축 …)은 "이 형식은 미리 볼 수 없습니다"와 내려받기.
3. 글로 보는 형식은 앞 2 MB 만 받고 잘랐다고 알린다. 글은 UTF-8 로 읽는다. 파일 내용을 HTML 로 그리지 않는다 — Markdown 은 본문과 같은 보기(HTML 은 글자로), 코드 색은 React 요소로만 만든다.
4. PDF 는 바이트를 받아 pdf.js 로 쪽마다 그려 세로로 쌓고 "쪽 n / N" 을 보인다. 배율을 바꾸면 그 배율로 다시 그린다. worker · 글꼴 · CMap 은 같은 출처에서 받고 화면 보안 정책을 넓히지 않는다(eval · WebAssembly · blob: worker 없음).
5. 동영상 · 소리는 받은 바이트로 만든 blob: 주소로 재생하고, 닫으면 그 주소를 버린다. 화면 보안 정책에 `media-src 'self' blob:` 만 더한다.
6. 팝업: 파일 이름 · 크기 · n / 전체, 이전 · 다음(← / →, 입력 중이 아닐 때), 축소 · 확대 · 100%(배율 % 표시, 25~400% — 이미지 크기 · PDF 배율 · 글 · 코드 · Markdown · 표의 글자 크기), 이미지는 화면에 맞춤, Markdown · 표 · JSON 원문 보기, 글 · 코드 줄 바꿈, 전체 화면 켜고 끄기, 내려받기, 닫기(Esc). 키 + / - / 0. 휴대폰 폭에서는 전체 화면으로 연다. 다크 · 영어에서도 보인다.
7. 본문 · 댓글의 `[이름](attachment:<id>)` 링크를 누르면 같은 팝업이 열린다(그 일감의 첨부 목록 순서로 이전 · 다음). 가운데 누르기 · ⌘ 누르기는 링크 그대로이고, 목록에 없는 첨부(지웠음)는 내려받기다. 본문 속 첨부 그림을 눌러도 크게 본다.

**수용 기준**
- [x] 확장자 · 형식 → 보기 형식 표, SVG 는 보지 않음, 코드 언어가 모두 색을 입힐 수 있음, CSV 따옴표 칸, 글 판별, 배율 단계 (attachment-kinds.test 38건)
- [x] 열기(단추 · 작은 그림) · Esc · 닫기, 이전 · 다음(단추 · ← →), 배율(단추 · + - 0, 25~400%), 맞춤, 전체 화면, 영어 (attachment-viewer-screens.test)
- [x] 코드 색 · 줄 번호 · 줄 바꿈, CSV 표 · 원문, Markdown(HTML 은 그리지 않음) · 원문, JSON 펴기 · 틀린 JSON, 2 MB 자름, 볼 수 없는 형식 · 글이 아닌 파일, 받기 실패 · 다시 시도, 동영상 blob 주소 버리기, PDF 쪽 · 배율 다시 그리기 · 깨진 PDF (attachment-viewer-screens.test)
