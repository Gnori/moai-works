# 연동 요구사항 (FR-INT)

moai-works 가 바깥 시스템과 이어지는 길의 요구사항이다: 문서화한 **REST API**, 바깥 자동화 인증, **웹훅**, **Git 저장소 연동**, **CSV 가져오기**, **Redmine 이관**, 데이터 내보내기. AI Agent 연결(MCP)은 [MCP · AI Agent 요구사항](12-mcp.md)에 따로 있다. 설계는 [연동 설계](../design/09-integrations.md)에 있다.

| **합계 19** | | **1** | **15** | **3** |

| 공통 | 내용 |
|---|---|
| 같은 API | 화면이 쓰는 `/moai-works-api/v1/**` 가 곧 공개 API 다. 바깥용 API 를 따로 만들지 않는다 |
| 권한 | 모든 판정은 api 한 곳에서, 화면과 같은 규칙으로 한다. 바깥 자동화 · Git · 가져오기도 사람 또는 Agent 계정으로 판정한다 |
| 감사 · 이력 | 연동이 한 쓰기는 행위자와 경로(`via` — `REST` · `SCM` · `IMPORT`)를 이력 · 감사에 남긴다 |
| 비밀값 | 웹훅 서명 비밀 · Git 웹훅 비밀 · Redmine API 키는 암호화해 두고 화면 · 로그 · 감사에 다시 보이지 않는다 |
| 뒷일 | 웹훅 전달 · Git 이벤트 처리 · 가져오기는 api 안의 작업 큐(`job_queue`)에서 한다. 워커 모듈을 만들지 않는다 |
| 이벤트 이름 | 웹훅 이벤트는 [일감 설계](../design/05-issue-tracking.md)의 도메인 이벤트와 같은 이름(`대상.동작`)을 쓴다 |

<a id="fr-int-001"></a>
### FR-INT-001 REST API 문서 (OpenAPI)

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §2.8 OpenAPI](../design/09-integrations.md#in-openapi) |

**설명** — 화면이 쓰는 REST API 를 OpenAPI 문서로 내보내, 바깥 자동화가 같은 API 를 같은 규칙으로 쓰게 한다.

**세부 요구사항**
1. 코드에서 OpenAPI 3.1 문서를 만든다(손으로 쓰지 않는다).
2. 작업마다 접근 규칙(접근 어노테이션 · 필요한 권한 코드)과 나올 수 있는 오류 `code` 를 문서에 넣는다.
3. 로그인한 사람이 웹 화면의 "API 문서" 쪽에서 본다. 운영에서 문서 주소를 끌 수 있다.
4. 빌드가 문서를 만들고, 지난 판과 비교해 깨지는 변경을 찾는다.

**수용 기준**
- [ ] 모든 REST 핸들러가 문서에 있고 권한 코드가 적혀 있다
- [ ] 응답 필드를 지우는 변경이 빌드에서 "깨지는 변경"으로 잡힌다
- [ ] 문서 주소가 인증 없이 열리지 않는다

<a id="fr-int-002"></a>
### FR-INT-002 REST API 공통 규약

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §2 REST API 규약](../design/09-integrations.md#in-rest) · [§2.5 오류](../design/09-integrations.md#in-errors) · [§2.6 낙관적 잠금](../design/09-integrations.md#in-lock) |

**설명** — 화면 · 바깥 자동화 · MCP 어댑터가 같은 규칙의 API 를 쓴다. 지금 코드: 오류는 이미 RFC 9457 problem+json 에 `code` 를 담는다(`ApiExceptionHandler`), 낙관적 잠금 충돌은 409 `CONCURRENT_UPDATE` 다. 경로 · 페이지 · 정렬 규칙은 프로젝트 · 일감 API 와 함께 만든다.

**세부 요구사항**
1. 경로: `/moai-works-api/v1/workspaces/{workspace}/projects/{project}/…`, 일감은 `/workspaces/{workspace}/issues/{number}`. 경로 조각은 소문자 kebab-case 복수형이다.
2. 오류는 RFC 9457 problem+json 이고 늘 `code`(대문자 스네이크)가 있다. 입력 오류는 `errors[]`(필드 · 메시지)를 더한다.
3. 읽기 거부는 404, 쓰기 거부는 403 이다.
4. 목록은 정한 페이지 방식(쪽 번호 + 전체 수, 또는 커서)과 정렬 허용 목록을 따른다. 한 쪽은 최대 100개다.
5. 고치기는 `lockVersion`(일감) · `rowVersion`(그 밖)을 받아, 다르면 409 `CONCURRENT_UPDATE` 로 답한다.
6. 시각은 ISO 8601 UTC, 날짜는 `YYYY-MM-DD` 다. 클라이언트는 모르는 필드를 무시해야 하고, 필드를 더하기만 하는 변경은 같은 판에서 한다.
7. 깨지는 변경은 `/v2` 로 내고 `/v1` 을 6개월 함께 둔다.

**수용 기준**
- [ ] 모든 오류 응답이 problem+json 이고 `code` 가 있다
- [ ] 낡은 `lockVersion` 의 고치기가 409 `CONCURRENT_UPDATE` 다
- [ ] 쪽 크기 101 을 요청하면 400 `INVALID_REQUEST` 다
- [ ] 다른 워크스페이스 자원은 404 다

<a id="fr-int-003"></a>
### FR-INT-003 바깥 자동화 인증 — Keycloak 서비스 계정

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §3 바깥 자동화 인증](../design/09-integrations.md#in-auth) |

**설명** — CI · 사내 시스템이 사람 계정 없이 REST 를 부르게 한다. Keycloak 서비스 계정(client_credentials)을 워크스페이스의 **Agent 계정**에 이어, MCP 와 같은 주체 · 같은 권한 규칙을 쓴다. 지금 코드: 서비스 계정 토큰은 `@ServiceApi` 로 지정한 플랫폼 클라이언트만 받고, 워크스페이스 API(`@WorkspaceApi`)에서는 `USER_ONLY` 403 이다.

**세부 요구사항**
1. 시스템 관리자가 Keycloak 에 클라이언트(client_credentials)를 만들고, 워크스페이스의 Agent 계정에 잇는다.
2. 그 클라이언트의 토큰으로 부른 REST 는 그 Agent 계정으로 판정 · 기록한다(경로 `REST`).
3. 이어지지 않은 서비스 계정 토큰은 워크스페이스 API 에서 지금처럼 403 이다.
4. 클라이언트 비밀은 Keycloak 에만 있다.

**수용 기준**
- [ ] 이어진 서비스 계정으로 만든 일감의 작성자가 그 Agent 계정이다
- [ ] Agent 를 정지하면 서비스 계정 토큰도 다음 요청부터 거절된다
- [ ] 다른 워크스페이스 경로는 404 다
- [ ] 이력 · 감사에 경로 `REST` 와 클라이언트 id 가 남는다

<a id="fr-int-004"></a>
### FR-INT-004 개인 API 토큰

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §3.3 개인 API 토큰](../design/09-integrations.md#in-auth) |

**설명** — 사람이 자기 명의 스크립트를 위해 토큰을 받는다(Redmine 의 API 키와 같은 쓰임). 나중에 한다.

**세부 요구사항**
1. 본인이 발급하고, 원문은 한 번만 보이며, SHA-256 만 저장한다. 만료 · 폐기가 있고 워크스페이스 하나에 묶인다.
2. 판정은 그 사람과 같다. 범위(읽기만 등)를 고를 수 있다.
3. 멤버가 나가면 바로 무효다.

**수용 기준**
- [ ] 토큰 원문이 DB · 로그에 없다
- [ ] 폐기한 토큰은 다음 요청부터 401 이다
- [ ] 읽기 범위 토큰의 쓰기는 403 이다

<a id="fr-int-005"></a>
### FR-INT-005 웹훅 구독

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §4 웹훅](../design/09-integrations.md#in-webhook) · [§4.2 이벤트](../design/09-integrations.md#in-webhook-events) |

**설명** — 일이 일어나면 바깥 주소로 알림(HTTP POST)을 보낸다(채팅 봇 · CI · 사내 시스템).

**세부 요구사항**
1. `webhook.manage` 권한자가 이름 · 주소(https) · 고를 이벤트 · 대상 프로젝트(전체 / 고른 것) · 상태를 정한다.
2. 이벤트 이름은 `대상.동작`(예: `issue.created`) 꼴이고, 목록은 도메인 이벤트와 같다.
3. 사설 · 루프백 · 링크 로컬 · 클라우드 메타데이터 주소로는 보내지 않는다(SSRF 막기).
4. 웹훅은 만든 사람의 읽기 권한으로 거른다 — 그 사람이 볼 수 없는 일감 · 비공개 메모는 보내지 않는다.
5. 끄기 · 다시 켜기 · 지우기 · 시험 보내기(`ping`)가 있다.
6. 모든 변경은 감사에 남는다.

**수용 기준**
- [ ] 고르지 않은 이벤트 · 대상 밖 프로젝트의 이벤트는 오지 않는다
- [ ] `127.0.0.1` · `10.0.0.0/8` · `169.254.169.254` 주소는 저장이 거절된다
- [ ] 만든 사람이 볼 수 없는 비공개 일감의 이벤트가 오지 않는다
- [ ] `webhook.manage` 가 없으면 403 이고, 변경이 감사에 남는다

<a id="fr-int-006"></a>
### FR-INT-006 웹훅 전달과 HMAC 서명

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §4.3 봉투 · 서명](../design/09-integrations.md#in-webhook-sign) |

**설명** — 받는 쪽이 moai-works 가 보낸 것인지, 중간에 바뀌지 않았는지 확인할 수 있게 서명한다.

**세부 요구사항**
1. 본문은 JSON 봉투(이벤트 id · 종류 · 시각 · 워크스페이스 · 프로젝트 · 행위자 · 데이터)다.
2. 헤더: `X-Moai-Works-Signature: t=<유닉스 초>,v1=<HMAC-SHA256(비밀, t + "." + 본문)>` · `X-Moai-Works-Event` · `X-Moai-Works-Delivery`.
3. 비밀은 만들 때 서버가 정해 한 번만 보인다. 비밀을 바꾸는 동안(24시간)은 옛 비밀의 서명도 함께 보낸다.
4. 전달은 업무 트랜잭션 밖의 작업 큐에서 한다(업무 응답을 늦추지 않는다). 같은 이벤트는 웹훅마다 한 번만 쌓인다.

**수용 기준**
- [ ] 설계 문서의 방법으로 받는 쪽이 서명을 검증할 수 있다(예시 코드 시험)
- [ ] 비밀 원문이 화면 · 로그에 다시 보이지 않는다
- [ ] 받는 쪽이 느려도 일감 저장 응답 시간이 늘지 않는다

<a id="fr-int-007"></a>
### FR-INT-007 웹훅 재시도 · 실패 기록 · 자동 끄기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §4.4 전달 · 재시도](../design/09-integrations.md#in-webhook-retry) |

**설명** — 받는 쪽이 잠시 멈춰도 알림을 잃지 않고, 오래 멈추면 스스로 멈춘다.

**세부 요구사항**
1. 2xx 가 아니거나 10초 안에 답이 없으면 1분 · 5분 · 30분 · 2시간 · 6시간 · 12시간 뒤에 다시 보낸다(처음 포함 7번).
2. 410 Gone 은 바로 웹훅을 끈다.
3. 전달마다 시각 · 시도 횟수 · 응답 상태 · 응답 앞부분 · 걸린 시간 · 오류를 14일 둔다. 화면에서 보고 다시 보낼 수 있다.
4. 연속 50번 실패하거나 3일 동안 모두 실패하면 자동으로 끄고(`AUTO_DISABLED`) 만든 사람 · 관리자에게 알린다.
5. 순서는 보장하지 않는다 — 봉투에 시각과 `lockVersion` 을 넣어 받는 쪽이 낡은 것을 버리게 한다.

**수용 기준**
- [ ] 받는 쪽이 500 을 두 번 주고 200 을 주면 세 번째 시도에서 성공으로 남는다
- [ ] 연속 실패 기준을 넘으면 웹훅이 `AUTO_DISABLED` 가 되고 알림이 간다
- [ ] 다시 보내기가 같은 이벤트 id 로 간다

<a id="fr-int-008"></a>
### FR-INT-008 Git 저장소 연결

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §5 Git 연동](../design/09-integrations.md#in-git) |

**설명** — 프로젝트에 GitHub · GitLab · Gitea 저장소를 잇는다. 코드를 복제하지 않고 웹훅으로 커밋 · PR 정보만 받는다.

**세부 요구사항**
1. `repository.manage` 권한자가 프로젝트 설정에서 저장소(식별자 · 종류 · 웹 주소 · 기본 브랜치 · 고치기 키워드를 적용할 브랜치)를 더한다.
2. moai-works 가 웹훅 받는 주소와 비밀을 만들어 한 번 보여 주고, 저장소 쪽 설정 방법을 종류별로 안내한다.
3. 한 프로젝트에 저장소를 여러 개 둘 수 있다. 저장소 모듈이 켜져 있어야 한다.
4. 더하기 · 고치기 · 끄기 · 지우기 · 비밀 바꾸기는 감사에 남는다.

**수용 기준**
- [ ] 저장소를 더하면 받는 주소와 비밀이 한 번 보이고, 다시 볼 수 없다
- [ ] 저장소 모듈이 꺼진 프로젝트에서는 저장소 화면 · API 가 404 다
- [ ] `repository.manage` 가 없으면 403 이다

<a id="fr-int-009"></a>
### FR-INT-009 Git 웹훅 받기 · 서명 검증 · 커밋 저장

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §5.2 받기 · 서명](../design/09-integrations.md#in-git-receive) |

**설명** — 푸시 · PR 이벤트를 받아 서명을 확인하고 커밋을 저장한다. 같은 커밋을 두 번 반영하지 않는다.

**세부 요구사항**
1. GitHub `X-Hub-Signature-256` · Gitea `X-Gitea-Signature`(HMAC-SHA256)와 GitLab `X-Gitlab-Token` 을 상수 시간 비교로 검증한다. 틀리면 401 이고 저장하지 않는다.
2. 받은 이벤트는 먼저 저장하고 202 로 답한 뒤 작업 큐에서 처리한다.
3. 같은 전달 id 는 한 번만 처리하고, 커밋은 (저장소, sha) 로 한 번만 저장한다 — 같은 커밋이 다른 브랜치로 다시 와도 두 번 반영하지 않는다.
4. 커밋에는 sha · 작성자 이름 · 이메일 · 시각 · 메시지 · 브랜치 · 웹 주소를 둔다.
5. 저장소별 받기 속도 제한을 두고, 본문은 5MB 까지 받는다.

**수용 기준**
- [ ] 서명이 틀린 요청은 401 이고 아무것도 저장되지 않는다
- [ ] 같은 푸시를 두 번 보내도 커밋 저장 · 일감 반영이 한 번이다
- [ ] 일감 화면에 연결된 커밋이 보인다

<a id="fr-int-010"></a>
### FR-INT-010 커밋을 일감에 잇기 · 사람 대응

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §5.3 키워드](../design/09-integrations.md#in-git-keywords) · [§5.4 사람 대응](../design/09-integrations.md#in-git-users) |

**설명** — 커밋 메시지의 `refs #123` 으로 커밋을 일감에 잇는다(Redmine 과 같다). 커밋 작성자를 워크스페이스 멤버에 맞춘다.

**세부 요구사항**
1. 참조 키워드(기본 `refs` · `references` · `IssueID` · `see`)와 일감 번호 목록(`#123, #124 & #125`)을 찾는다. 키워드 목록은 워크스페이스 설정이다.
2. 일감은 저장소 프로젝트(와 하위 프로젝트) 안이어야 한다(저장소 설정으로 넓힐 수 있다).
3. 커밋 작성자 이메일을 워크스페이스 멤버(확인한 계정 이메일 · 본인이 더하고 확인한 커밋 이메일)에 맞춘다. 맞는 사람이 없으면 "대응 없음"으로 둔다.
4. 잇기는 일감 이력에 남기지 않고 일감의 "연결된 커밋"에 보인다(Redmine 과 같다). 글 속 `commit:abc123` 은 링크가 된다.

**수용 기준**
- [ ] `refs #123, #124` 커밋이 두 일감에 이어진다
- [ ] 설정이 꺼져 있으면 다른 프로젝트의 일감 번호는 잇지 않는다
- [ ] 이메일이 맞는 멤버가 커밋 작성자로 보인다
- [ ] `repository.read` 가 없는 사람에게는 연결된 커밋이 보이지 않는다

<a id="fr-int-011"></a>
### FR-INT-011 고치기 키워드로 상태 · 진척률 바꾸기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §5.3 키워드](../design/09-integrations.md#in-git-keywords) |

**설명** — `fixes #123` 커밋이 들어오면 일감의 상태와 진척률을 정한 값으로 바꾼다. 사람이 웹에서 바꿀 때와 같은 권한 · 워크플로 규칙을 지킨다.

**세부 요구사항**
1. 고치기 키워드(기본 `fixes` · `closes` · `resolves`)마다 트래커별로 바꿀 상태 · 진척률을 워크스페이스 설정으로 정한다.
2. 고치기 브랜치(기본: 기본 브랜치)로 들어온 커밋에만 적용한다.
3. 커밋 작성자가 멤버로 대응되고, 그 사람이 그 일감에서 그 전이를 할 권한과 워크플로가 있을 때만 바꾼다. 아니면 잇기만 하고 건너뛴 이유를 남긴다.
4. 이력의 행위자는 그 사람, 경로(`via`)는 `SCM`(커밋 sha)이고, 메모에 커밋 링크를 단다.
5. 같은 커밋 · 일감 쌍은 한 번만 적용한다.

**수용 기준**
- [ ] `fixes #123` 커밋이 상태를 바꾸고 이력에 "Git 커밋 abc1234 로"가 남는다
- [ ] 워크플로가 허용하지 않는 전이는 하지 않고 이유가 남는다
- [ ] 대응되는 멤버가 없으면 상태가 바뀌지 않는다
- [ ] 같은 커밋이 다시 와도 한 번만 바뀐다

<a id="fr-int-012"></a>
### FR-INT-012 커밋 메시지로 시간 기록

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §5.3 키워드](../design/09-integrations.md#in-git-keywords) |

**설명** — 커밋 메시지의 `#123 @2h` 로 일한 시간을 남긴다(Redmine 의 커밋 시간 기록).

**세부 요구사항**
1. `@2h` · `@1h30m` · `@90m` · `@1.5h` 를 시간으로 읽는다.
2. 대응된 멤버가 그 프로젝트에서 `time.log` 를 가질 때만 남긴다. 작업 분류는 저장소 설정의 기본값, 날짜는 커밋 날짜, 메모는 커밋 첫 줄이다.
3. 저장소 설정으로 끌 수 있다. 한 커밋 · 일감 쌍에 한 번만 남긴다.

**수용 기준**
- [ ] `refs #123 @2h` 커밋이 2시간 기록을 남긴다
- [ ] `time.log` 가 없는 사람의 커밋은 기록하지 않는다
- [ ] 같은 커밋이 다시 와도 기록이 하나다

- [ ] 같은 PR 이벤트가 다시 와도 한 행이다

<a id="fr-int-015"></a>
### FR-INT-015 CSV 일감 가져오기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §6 CSV 가져오기](../design/09-integrations.md#in-csv) |

**설명** — 다른 도구에서 뽑은 CSV 로 일감을 한꺼번에 만든다(Redmine 의 일감 가져오기).

**세부 요구사항**
1. 권한은 `issue.import` 와 `issue.create` 다. 파일은 10MB · 1만 줄까지다.
2. 인코딩(UTF-8 · CP949) · 구분자 · 날짜 꼴을 고르거나 자동으로 알아낸다.
3. 열 맞추기: CSV 열 → 일감 필드(사용자 정의 필드 포함). 머리글 이름(한국어 · 영어 · Redmine 내보내기)으로 자동으로 맞춘다.
4. 미리보기: 처음 20줄을 바뀐 값과 줄별 오류로 보인다.
5. 실행은 작업 큐에서 줄마다 하고, 끝나면 만든 수 · 실패 수와 오류 줄 CSV(오류 열 포함)를 내려받는다.
6. 만든 일감의 작성자는 가져온 사람, 경로는 `IMPORT` 다. 알림은 기본으로 보내지 않는다.
7. 같은 작업을 다시 돌려도 이미 만든 줄은 다시 만들지 않는다.

**수용 기준**
- [ ] 오류 줄이 있어도 나머지 줄은 만들어지고, 오류 줄 CSV 를 받는다
- [ ] 없는 상태 이름 · 담당할 수 없는 사람은 미리보기에서 줄 오류로 보인다
- [ ] 멈춘 작업을 이어 돌려도 일감이 겹치지 않는다
- [ ] `issue.import` 가 없으면 403 이고, 작업이 감사에 남는다

### FR-INT-016 Redmine 이관 — 연결과 대응 설정

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §7 Redmine 이관](../design/09-integrations.md#in-redmine) · [§7.2 대응 규칙](../design/09-integrations.md#in-redmine-map) |

**설명** — Redmine REST API 와 API 키로 Redmine 에 붙어, 옮길 프로젝트와 대응(트래커 · 상태 · 우선순위 · 작업 분류 · 사용자 정의 필드 · 사람 · 역할)을 정한다.

**세부 요구사항**
1. 워크스페이스 소유자 · 관리자(`config.manage` 와 `project.create`)가 Redmine 주소와 API 키(관리자 키 권장)를 넣고 연결을 시험한다.
2. API 키는 암호화해 작업 동안만 두고, 끝나거나 취소하면 지운다.
3. Redmine 의 프로젝트 트리 · 트래커 · 상태 · 우선순위 · 작업 분류 · 사용자 정의 필드 · 사용자 · 역할을 읽어 대응 화면을 만든다.
4. 대응: 있는 것에 잇기 또는 새로 만들기. 사람은 이메일로 멤버에 자동으로 잇고, 없는 사람은 "Redmine 사용자(이름)"로 남긴다. 역할은 Manager → 프로젝트 관리자 · Developer → 개발자 · Reporter → 보고자 · 그 밖 → 독자로 시작하고 고칠 수 있다.
5. 대응 설정은 저장해 다시 돌릴 때 쓴다.

**수용 기준**
- [ ] 틀린 키 · 주소는 연결 시험에서 이유와 함께 거절된다
- [ ] 작업이 끝나면 API 키가 DB 에서 지워진다
- [ ] 같은 이메일의 Redmine 사용자가 멤버로 자동 대응된다
- [ ] 권한이 없으면 403 이고, 작업이 감사에 남는다

### FR-INT-017 Redmine 이관 — 데이터 옮기기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §7.3 순서](../design/09-integrations.md#in-redmine-order) · [§7.5 첨부 · 본문](../design/09-integrations.md#in-redmine-content) |

**설명** — 대응 설정대로 Redmine 데이터를 옮긴다. 원래 시각 · 행위자를 지켜 이력이 끊기지 않게 한다.

**세부 요구사항**
1. 옮기는 것: 프로젝트(트리 · 모듈 · 멤버 · 역할) · 카테고리 · 버전(공유 범위) · 일감(모든 필드 · 사용자 정의 필드 · 상위 · 비공개) · 이력(필드 변경 · 메모 · 비공개 메모) · 관찰자 · 관계 · 시간 기록 · 위키(페이지 · 판 · 계층) · 첨부(일감 · 위키) · 뉴스.
2. 설계의 순서로 옮겨 참조가 끊기지 않게 한다.
3. 본문 서식(Textile · Markdown)을 Markdown(GFM)으로 바꾼다. 바꾸지 못한 부분은 그대로 두고 그 수를 보고한다.
4. 일감 · 이력 · 시간 기록의 원래 시각 · 행위자를 지킨다. 경로는 `IMPORT` 다.
5. 첨부는 Redmine 에서 받아 객체 저장소에 올린다(크기 상한은 첨부와 같다).
6. 옮기는 동안 알림 · 웹훅은 보내지 않는다.

**수용 기준**
- [ ] 시험용 Redmine 프로젝트의 일감 수 · 이력 수 · 시간 합 · 첨부 수가 옮긴 뒤 같다
- [ ] 이력의 시각 · 행위자가 Redmine 과 같다
- [ ] Textile 제목 · 목록 · 링크가 Markdown 으로 바뀐다
- [ ] 옮기는 동안 알림이 나가지 않는다

### FR-INT-018 Redmine 이관 — 번호 대응표 · 다시 돌려도 안전 · 결과

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [연동 설계 §7.4 번호 · 다시 돌리기](../design/09-integrations.md#in-redmine-rerun) |

**설명** — Redmine 의 일감 번호를 어떻게 옮길지 정하고, 이관을 여러 번 돌려도 겹치지 않게 한다.

**세부 요구사항**
1. 번호: 워크스페이스에 일감이 없고 사용자가 고르면 Redmine 번호를 그대로 쓴다. 아니면 새 번호를 주고 Redmine 번호 → 새 번호 대응표를 만든다.
2. 새 번호면 본문 · 메모의 `#123` · 위키 링크 · 첨부 참조를 새 번호 · 새 이름으로 바꾼다.
3. 옮긴 것마다 (Redmine 종류, id) → (moai-works 종류, id) 를 저장한다. 다시 돌리면 이미 옮긴 것은 건너뛰거나 Redmine 에서 바뀐 것만 고치고, 새 이력만 덧붙인다. 이관 뒤 moai-works 에서 고친 일감은 덮어쓰지 않고 보고한다.
4. 중간에 멈추면 이어서 한다(단계 · 위치를 저장한다).
5. 결과 보고: 종류별 만든 · 고친 · 건너뛴 · 실패 수, 실패 목록, 번호 대응표 CSV.

**수용 기준**
- [ ] 같은 이관을 두 번 돌려도 일감 · 이력 · 첨부가 겹치지 않는다
- [ ] 새 번호 모드에서 본문의 `#123` 이 새 번호로 바뀐다
- [ ] 이관 뒤 고친 일감이 다시 돌리기로 덮어써지지 않고 보고된다
- [ ] 번호 대응표 CSV 를 내려받을 수 있다
