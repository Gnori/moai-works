# 알림 · 메일 요구사항 (FR-NTF)

일감 · 위키 · 뉴스 · 문서 · 파일 · 포럼에서 일어난 일을 사람에게 알리는 기능 — 알림 종류, 받는 사람 규칙, 사용자 알림 설정, 화면 알림함, 메일 보내기, 메일로 일감 만들기 · 답장으로 메모 — 의 요구사항이다. Redmine 의 메일 알림 규칙(작성자 · 담당자 · 관찰자 · 멘션 · 프로젝트 전체, 사용자 설정 여섯 가지, 내가 한 변경은 안 받기)을 따른다. 설계는 [공동 작업 설계 §10](../design/08-collaboration.md#co-notify)에 있다.

| 공통 | 내용 |
|---|---|
| 권한 재판정 | 알림은 **받는 사람이 지금 그 대상을 읽을 수 있을 때만** 보낸다. 쓴 사람의 권한으로 정하지 않는다(비공개 일감 · 비공개 메모 · 필드 읽기 권한 포함) |
| 채널 | 화면 알림함(지금은 폴링, 나중 SSE) + 메일(지금은 `log` 모드, SMTP 는 나중) |
| 뒷일 | 받는 사람 계산 · 메일 보내기는 api 안 작업 큐가 한다. 업무 저장이 알림 때문에 느려지거나 실패하지 않는다 |
| Agent 계정 | Agent 계정은 알림을 받지 않는다. Agent 가 한 일은 "Agent X" 로 알린다 |
| 감사 | 알림 설정 · 워크스페이스 메일 설정 · 받은 메일 경로 바꾸기는 감사에 남는다. 받은 메일은 처리 결과를 기록한다 |
| 권한 검사 | 알림함 · 설정은 본인만. 워크스페이스 메일 설정은 `workspace.settings.manage`([워크스페이스 요구사항](01-workspace.md)) |

<a id="fr-ntf-001"></a>
### FR-NTF-001 알림 종류 · 워크스페이스 메일 설정

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.2](../design/08-collaboration.md#co-notify-kinds) |

**설명** — 어떤 일이 알림이 되는지 정하고, 워크스페이스마다 메일로 보낼 종류를 고른다(Redmine 의 "메일 알림" 설정과 같다).

**세부 요구사항**
1. 알림 종류는 일감 추가 · 일감 고침(하위: 메모 · 상태 · 담당 · 우선순위 · 대상 버전) · 멘션 · 위키 쪽 추가 · 위키 쪽 고침 · 뉴스 추가 · 뉴스 댓글 · 문서 추가 · 파일 추가 · 게시판 글이어야 한다.
2. `workspace.settings.manage` 를 가진 사람이 메일로 보낼 종류를 고를 수 있어야 한다. 기본은 일감 종류와 멘션이다.
3. "일감 고침"을 끄면 고른 하위 종류(메모 · 상태 …)만 메일로 보내야 한다.
4. 화면 알림은 종류 설정과 상관없이 만들어야 한다.
5. 꼬리말 · 텍스트만 보내기를 설정할 수 있어야 한다.
6. 시간 기록 · 버전 변경은 알림을 만들지 않아야 한다(Redmine 과 같다).

**수용 기준**
- [ ] "위키 쪽 고침" 메일을 끄면 메일은 안 가고 화면 알림은 생긴다
- [ ] "일감 고침"을 끄고 "상태"만 켜면 상태가 바뀐 변경만 메일이 간다
- [ ] `workspace.settings.manage` 없이 설정을 바꾸면 403 이고, 바꾸기는 감사에 남는다

<a id="fr-ntf-002"></a>
### FR-NTF-002 받는 사람 규칙

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.3](../design/08-collaboration.md#co-recipients) |

**설명** — 일감이면 작성자 · 담당자 · 바로 전 담당자 · 관찰자 · 멘션된 사람 · "모든 일"을 고른 프로젝트 멤버가 받는다. 위키 · 뉴스 · 문서 · 파일 · 포럼도 대상마다 받는 사람이 정해져 있다(Redmine 과 같다).

**세부 요구사항**
1. 일감 후보는 작성자 · 담당자 · 바로 전 담당자(담당이 바뀐 경우) · 관찰자 · 멘션된 사람 · 설정이 "모든 일"인 프로젝트 멤버 · "높은 우선순위는 늘 받기"를 켠 프로젝트 멤버(높음 이상)여야 한다.
2. 위키는 위키 · 쪽 관찰자 · 멘션 · 프로젝트 멤버, 뉴스는 프로젝트 멤버 · 멘션(댓글은 뉴스 관찰자), 문서 · 파일은 프로젝트 멤버, 포럼은 게시판 · 글 관찰자 · 새 글이면 프로젝트 멤버 · 멘션이어야 한다.
3. "프로젝트 멤버"는 그 프로젝트(또는 이어받은 상위)의 프로젝트 역할을 가진 사람이어야 한다. 공개 프로젝트를 읽기만 하는 워크스페이스 멤버는 "모든 일" 알림을 받지 않아야 한다.
4. 계정이나 멤버십이 활성이 아닌 사람은 빼야 한다.
5. 한 사람은 한 이벤트에 알림 하나만 받아야 하고, 이유는 가장 센 것(멘션 > 담당 > 작성 > 관찰 > 전 담당 > 높은 우선순위 > 멤버)이어야 한다.
6. 받는 사람 계산은 멱등이어야 한다(같은 이벤트를 두 번 처리해도 한 벌).

**수용 기준**
- [ ] 담당을 A → B 로 바꾸면 A 와 B 가 모두 받는다
- [ ] 작성자이면서 관찰자인 사람이 알림 하나만 받는다
- [ ] 공개 프로젝트를 읽기만 하는 멤버는 "모든 일" 설정이어도 그 프로젝트 새 일감 알림을 받지 않는다
- [ ] 펼치기 작업을 두 번 돌려도 알림 · 메일이 한 벌이다

<a id="fr-ntf-003"></a>
### FR-NTF-003 받는 사람 권한 재판정

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.3](../design/08-collaboration.md#co-recipients) |

**설명** — 알림과 메일은 내용을 담는다. 받는 사람이 그 대상을 볼 수 없으면 보내지 않고, 볼 수 없는 필드는 빼고 보낸다. 판정은 알림을 처리하는 순간의 권한으로 한다.

**세부 요구사항**
1. 받는 사람마다 프로젝트 독자 · 모듈 켜짐 · 읽기 코드를 다시 판정해야 한다.
2. 일감은 받는 사람의 보기 범위(비공개 일감은 작성자 · 담당자 · `issue.private.read`, "내 것만" 프로젝트는 자기 일감만)로, 비공개 메모는 `issue.note.private` 를 가진 사람에게만 보내야 한다. 관찰자라는 것만으로는 보이지 않는다([일감 요구사항](03-issue.md) · [프로젝트 요구사항](02-project.md)의 규칙).
3. 일감 변경은 받는 사람이 볼 수 있는 필드만 담고, 볼 수 있는 변경도 메모도 없으면 그 사람에게 보내지 않아야 한다.
4. 이벤트가 생긴 뒤 권한을 잃은 사람에게는 보내지 않아야 한다.
5. 같은 판정을 화면 알림 · 메일 두 채널에 써야 한다.

**수용 기준**
- [ ] 비공개 일감의 관찰자가 `issue.private.read` 를 잃으면 알림을 받지 않는다
- [ ] 비공개 메모가 달린 변경은 권한 없는 담당자에게 메모 없이 가거나(다른 변경이 있을 때) 가지 않는다
- [ ] 숨긴 사용자 정의 필드만 바뀐 변경은 그 필드를 못 보는 사람에게 가지 않는다
- [ ] 모듈이 꺼진 프로젝트의 위키 변경 알림이 생기지 않는다

<a id="fr-ntf-004"></a>
### FR-NTF-004 사용자 알림 설정

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.4](../design/08-collaboration.md#co-preference) |

**설명** — 사람마다 무엇을 받을지 고른다. Redmine 의 여섯 모드(모든 일 · 고른 프로젝트 · 내 일만 · 담당만 · 작성만 · 받지 않음)와 "내가 한 변경은 받지 않기"를 둔다. 워크스페이스마다 따로 정한다.

**세부 요구사항**
1. 모드는 `ALL` · `SELECTED` · `ONLY_MY_EVENTS`(기본) · `ONLY_ASSIGNED` · `ONLY_OWNER` · `NONE` 이어야 하고, 모드 × 이유 표가 설계와 같아야 한다.
2. `SELECTED` 는 고른 프로젝트의 모든 일과 나머지 프로젝트의 내 일을 받게 해야 한다.
3. 관찰과 멘션은 `NONE` 이 아니면 늘 받아야 한다. `NONE` 은 멘션까지 막아야 한다.
4. 옵션: 내가 한 변경은 받지 않기(기본 켬) · 높은 우선순위 일감은 늘 받기 · 메일 받기(끄면 화면만) · 일감을 만들거나 고칠 때 자동 관찰.
5. "내가 한 변경"은 내 개인 MCP 키로 한 변경을 포함하고, Agent 계정이 한 변경은 포함하지 않아야 한다.
6. 설정은 사람 × 워크스페이스마다 한 벌이어야 한다.

**수용 기준**
- [ ] 모드 × 이유 표의 모든 칸이 시험으로 확인된다
- [ ] 개인 MCP 키로 내가 고친 일감 알림을 내가 받지 않는다
- [ ] 내가 책임자인 Agent 계정이 고친 일감 알림은 내가 받는다
- [ ] 다른 사람의 설정을 바꾸려 하면 403 이다

<a id="fr-ntf-005"></a>
### FR-NTF-005 화면 알림함

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.5](../design/08-collaboration.md#co-inbox) |

**설명** — 메일과 별도로 화면 위쪽에 알림함을 둔다. 읽지 않은 수 배지, 알림 목록, 읽음 처리가 있다. 지금은 30초 폴링이다.

**세부 요구사항**
1. 알림마다 행위자(사람 · Agent · "사람 (MCP 로)") · 무엇을 했나 · 대상 · 받은 이유 · 시각을 보이고, 누르면 대상으로 가야 한다.
2. 같은 대상의 읽지 않은 알림은 한 줄로 묶어 보이고, 읽지 않은 수는 대상 수로 세야 한다.
3. 하나 읽음 · 모두 읽음, 대상 쪽을 열면 그 대상 알림 읽음이 되어야 한다.
4. 화면은 30초마다 읽지 않은 수를 묻고(ETag · 304), 탭이 안 보이면 멈춰야 한다.
5. 목록을 줄 때 프로젝트 독자 · 모듈을 다시 보고, 못 보게 된 항목은 제목을 숨겨야 한다.
6. 90일 지난 알림은 지워야 한다. 위쪽 바 배지는 내 모든 워크스페이스의 수를 보여야 한다.

**수용 기준**
- [ ] 일감 쪽을 열면 그 일감 알림이 읽음이 되고 배지 수가 준다
- [ ] 바뀐 것이 없을 때 읽지 않은 수 요청이 304 다
- [ ] 프로젝트에서 빠진 뒤 그 프로젝트 알림의 제목이 보이지 않는다
- [ ] 다른 사람의 알림 id 로 읽음 처리하면 404 다

<a id="fr-ntf-006"></a>
### FR-NTF-006 메일 보내기 — 아웃박스 · `log` 모드

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.6](../design/08-collaboration.md#co-mail-out) |

**설명** — 메일은 아웃박스에 쌓고 스케줄러가 보낸다. 지금은 SMTP 가 정해지지 않아 `log` 모드(로그에 남기기)로 보낸다. SMTP 는 같은 아웃박스 위에 모드만 더한다.

**세부 요구사항**
1. 받는 사람마다 한 통씩, 그 사람의 언어(ko/en) · 시간대 · 볼 수 있는 내용으로 렌더해 아웃박스에 넣어야 한다. BCC 로 모아 보내지 않아야 한다.
2. 스케줄러가 대기 메일을 집어 보내고, 여러 인스턴스가 같은 메일을 두 번 보내지 않아야 한다.
3. `moai-works.mail.mode=log` 에서는 받는 사람 · 제목 · 본문을 로그에 남기고 보냄으로 표시해야 한다.
4. 실패하면 1분 · 5분 · 30분 · 2시간 · 12시간 뒤 다시 하고, 다섯 번 실패하면 실패로 남겨야 한다.
5. 확인된 메일 주소가 없거나 계정이 정지된 사람은 건너뛰어야 한다.
6. 보낸 메일은 30일, 실패 · 건너뛴 메일은 90일 뒤 지워야 한다.
7. 첨부 파일은 메일에 붙이지 않고 링크만 넣어야 한다.

**수용 기준**
- [ ] `log` 모드에서 일감을 만들면 받는 사람 수만큼 로그 줄과 보낸 행이 생긴다
- [ ] api 인스턴스 둘이 함께 돌아도 메일이 한 번씩만 나간다
- [ ] 보내기를 실패시키면 다시 하기 간격이 설계와 같다
- [ ] 메일 본문 · 로그에 비밀값이 없다

### FR-NTF-007 메일 내용 · 스레드 헤더

| 항목 | 내용 |

| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.7](../design/08-collaboration.md#co-mail-thread) |

**설명** — 같은 일감의 메일은 메일 프로그램에서 한 스레드로 묶이고, 프로젝트별로 거르기 쉬워야 한다. Redmine 과 같은 제목 모양과 `Message-ID` · `In-Reply-To` · `References` · `List-Id` 를 쓴다.

**세부 요구사항**
1. 일감 메일 제목은 `[{프로젝트} - {트래커} #{번호}] ({상태}) {제목}` 이어야 한다.
2. 일감의 첫 메일 `Message-ID` 를 뿌리로, 그 뒤 메일은 `In-Reply-To` · `References` 에 뿌리를 넣어야 한다. 포럼 답글 · 뉴스 댓글도 같은 방식이다.
3. `List-Id` 는 프로젝트 · 워크스페이스마다 달라야 한다.
4. `X-Moai-Works-*` 헤더(워크스페이스 · 프로젝트 · 일감 번호 · 트래커 · 상태 · 우선순위 · 작성자 · 담당 · 받은 이유 · 행위자 종류 · 호스트)와 `Auto-Submitted: auto-generated` 를 넣어야 한다.
5. 본문은 텍스트 + HTML 이고, 행위자 줄("Agent 빌드봇이 고쳤다" · "김가 님이 MCP 로 고쳤다") · 바뀐 필드 · 메모 · 링크 · 받은 이유 · 알림 설정 링크를 담아야 한다.
6. Markdown 은 화면과 같은 허용 범위로 안전하게 HTML 로 바꿔야 한다.
7. 헤더에 메일 주소를 넣지 않아야 한다(표시 이름만).

**수용 기준**
- [ ] 한 일감의 만들기 · 고치기 · 메모 메일이 메일 프로그램에서 한 스레드로 보인다
- [ ] 메모 속 `<script>` 가 HTML 메일에 실행 가능한 꼴로 들어가지 않는다
- [ ] Agent 계정이 고친 메일의 `X-Moai-Works-Actor` 가 `AGENT` 다

<a id="fr-ntf-008"></a>
### FR-NTF-008 멘션

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.3](../design/08-collaboration.md#co-recipients) |

**설명** — 본문 · 메모 · 위키 · 뉴스 · 글 · 댓글에서 `@사용자` 로 사람을 부르면 그 사람이 알림을 받는다. 일감에서 부르면 관찰자로도 더한다.

**세부 요구사항**
1. 편집기에서 `@` 를 치면 그 대상을 볼 수 있는 사람 · Agent 를 골라 표준 멘션 꼴로 넣어야 한다. `@이메일` 도 받아 저장할 때 표준 꼴로 바꿔야 한다([일감 요구사항](03-issue.md)의 멘션 규칙).
2. 멘션된 사람이 그 대상을 읽을 수 있을 때만 알리고, 일감이면 관찰자로 더해야 한다. 위키 · 뉴스 · 글 · 댓글의 멘션은 알리기만 한다.
3. 읽을 수 없는 주체를 멘션하면 조용히 건너뛰고 글자로만 보여야 한다(존재를 알리지 않는다).
4. Agent 계정을 멘션하면 관찰자로 더하되 알림은 만들지 않아야 한다([FR-NTF-010](#fr-ntf-010)).

**수용 기준**
- [ ] 메모에 `@김가` 를 쓰면 김가가 이유 "멘션"으로 받고 관찰자가 된다
- [ ] 비공개 일감에서 권한 없는 사람을 멘션해도 그 사람에게 알림이 가지 않는다
- [ ] MCP `add_issue_note` 의 멘션도 같은 결과다

<a id="fr-ntf-009"></a>
### FR-NTF-009 묶어 보내기 — 일괄 변경 · Agent 상한

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.1](../design/08-collaboration.md#co-notify) · [§10.10](../design/08-collaboration.md#co-agent-notify) |

**설명** — 일괄 수정 50건이나 Agent 의 대량 변경이 메일 50통이 되지 않게 묶는다.

**세부 요구사항**
1. 같은 행위자 · 같은 묶음(일괄 수정 · 공유 범위 변경 정리 · 가져오기)의 변경은 사람마다 메일 한 통(바뀐 일감 목록)으로 묶어야 한다.
2. 화면 알림은 이벤트마다 남기되 화면이 묶어 보여야 한다.
3. Agent 계정마다 시간당 알림 상한(기본 200)을 두고, 넘으면 그 시간의 나머지를 받는 사람마다 요약 메일 한 통으로 보내야 한다.

**수용 기준**
- [ ] 일괄 수정으로 일감 50개 상태를 바꾸면 관찰자 한 사람이 메일 1통을 받는다
- [ ] Agent 가 한 시간에 300건을 바꾸면 201번째부터 요약 메일로 묶인다

<a id="fr-ntf-010"></a>
### FR-NTF-010 Agent 계정과 알림

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.10](../design/08-collaboration.md#co-agent-notify) |

**설명** — Agent 계정은 담당자 · 관찰자가 될 수 있지만 메일 · 알림함이 없다. Agent 가 한 일은 사람에게 "Agent X" 로 알린다.

**세부 요구사항**
1. Agent 계정이 담당 · 관찰 · 멘션되어도 메일 · 화면 알림을 만들지 않아야 한다.
2. Agent 계정이 행위자인 알림 · 메일에는 "Agent" 표시와 Agent 이름이 보여야 한다.
3. Agent 계정의 책임자에게 따로 사본을 보내지 않아야 한다.
4. Agent 는 MCP(`search_issues` 의 담당 = 나)로 자기 일을 찾을 수 있어야 한다([MCP 요구사항](12-mcp.md)).

**수용 기준**
- [ ] Agent 계정에 일감을 맡겨도 알림 · 메일 행이 생기지 않는다
- [ ] Agent 가 고친 일감 메일 본문에 "Agent {이름}" 이 있다

<a id="fr-ntf-011"></a>
### FR-NTF-011 메일로 일감 만들기

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.8](../design/08-collaboration.md#co-mail-in) · [§10.9](../design/08-collaboration.md#co-mail-keywords) |

**설명** — 정한 주소로 메일을 보내면 일감이 생긴다. 본문 키워드(`Status:` · `Priority:` …)로 필드를 정한다(Redmine 메일 받기).

**세부 요구사항**
1. 받는 주소마다 프로젝트 · 기본값 · 허용 키워드 · 모르는 사람 정책을 정하는 경로를 `workspace.settings.manage` 가 만들 수 있어야 한다.
2. 메일은 서비스 계정으로 인증한 HTTP 입구로 받아야 한다(IMAP 은 나중).
3. 제목 → 일감 제목, 본문 → 설명(HTML 은 Markdown 으로, 인용 · 서명은 잘라 냄), 첨부 → 첨부여야 한다.
4. 본문 맨 앞 · 맨 끝의 키워드 줄(영어 · 한국어)을 읽되, 허용 키워드만 받고 권한 · 워크플로 검사를 웹과 같이 해야 한다.
5. `Cc` 에 든 멤버는 관찰자로 더해야 한다(볼 수 있을 때).
6. 일감 서비스를 웹 · MCP 와 같은 판정으로 부르고 경로 `EMAIL` 을 남겨야 한다.

**수용 기준**
- [ ] `Priority: 높음` 이 든 메일이 우선순위 높음 일감이 된다
- [ ] 허용하지 않은 키워드 · 워크플로가 막는 `Status:` 는 무시되고 기록에 남는다
- [ ] 보낸 사람에게 `issue.create` 가 없으면 일감이 생기지 않는다

<a id="fr-ntf-012"></a>
### FR-NTF-012 답장으로 메모 더하기

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.8](../design/08-collaboration.md#co-mail-in) |

**설명** — 알림 메일에 답장하면 그 일감에 메모가 붙는다. 포럼 알림에 답장하면 답글이 된다.

**세부 요구사항**
1. `In-Reply-To` · `References` 의 우리 `Message-ID` 또는 제목의 `[… #123]` 로 대상 일감을 찾아야 한다.
2. 인용 부분을 잘라 내고 새로 쓴 부분만 메모로 넣어야 한다.
3. 답장 키워드(`Status:` 등)는 보낸 사람의 권한과 워크플로가 허용할 때만 적용해야 한다.
4. 보낸 사람이 그 일감을 읽을 수 없으면 없는 일감처럼 처리해야 한다.

**수용 기준**
- [ ] 알림 메일에 답장하면 그 일감에 메모가 붙고 이력에 "메일로"가 보인다
- [ ] 인용된 옛 메일 내용이 메모에 들어가지 않는다
- [ ] `issue.note` 가 없는 사람의 답장은 거절된다

<a id="fr-ntf-013"></a>
### FR-NTF-013 받은 메일 안전장치

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.8](../design/08-collaboration.md#co-mail-in) |

**설명** — 메일은 보낸 사람을 쉽게 속인다. 위조 · 자동 응답 고리 · 큰 메일 · 모르는 보낸 사람을 막는다.

**세부 요구사항**
1. 우리 호스트 헤더 · `Auto-Submitted` · `Precedence: bulk` · 부재중 응답 · 우리 보내는 주소에서 온 메일은 버려야 한다(고리 막기).
2. 같은 경로에서 같은 `Message-ID` 는 한 번만 처리해야 한다.
3. 보낸 사람은 확인된 메일 주소의 활성 멤버여야 하고, 믿는 MTA 의 DMARC(또는 DKIM · SPF) 결과가 pass 여야 한다(경로 설정, 기본 켬).
4. 모르는 보낸 사람은 `IGNORE`(기본) · `REJECT`(안내 한 통, 하루 1통) · `ACCEPT_AS`(정한 사람 · Agent 계정으로) 중 경로 설정대로 처리해야 한다. 메일로 계정을 만들지 않아야 한다.
5. 원문 크기 · 첨부 수 · 금지 확장자 상한을 두어야 한다.
6. 모든 받은 메일의 처리 결과(처리 · 무시 · 거절 · 실패 + 이유)를 기록하고, 원문은 30일 뒤 지워야 한다.

**수용 기준**
- [ ] 우리가 보낸 알림이 되돌아와도 일감이 생기지 않는다
- [ ] DMARC fail 메일은 멤버 주소여도 그 사람으로 처리되지 않는다
- [ ] 같은 메일을 두 번 받아도 일감이 하나다

<a id="fr-ntf-014"></a>
### FR-NTF-014 화면 알림 실시간 (SSE)

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.5](../design/08-collaboration.md#co-inbox) |

**설명** — 폴링 대신 서버가 새 알림을 바로 밀어 준다. BFF 가 api 의 SSE 를 그대로 흘려보낸다.

**세부 요구사항**
1. 알림 흐름 주소로 새 알림 신호를 받아야 한다. api 인스턴스가 여럿이어도 Redis 채널로 신호를 나눠야 한다.
2. 끊기면 `Last-Event-ID` 로 다시 잇고, 그래도 안 되면 폴링으로 돌아가야 한다.
3. 토큰은 브라우저에 두지 않고 BFF 세션으로 인증해야 한다.

**수용 기준**
- [ ] 다른 사람이 나를 멘션하면 2초 안에 배지가 바뀐다
- [ ] SSE 를 끊으면 30초 폴링으로 계속 바뀐다

<a id="fr-ntf-015"></a>
### FR-NTF-015 하루 요약 메일 · 받지 않기 링크

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [공동 작업 설계 §10.7](../design/08-collaboration.md#co-mail-thread) · [§18](../design/08-collaboration.md#co-decisions) |

**설명** — 메일을 바로 받지 않고 하루 한 번 모아 받고, 메일 안의 링크로 알림을 끈다.

**세부 요구사항**
1. 사용자 설정에 "바로 · 하루 한 번"을 두고, 하루 한 번이면 그날 메일을 한 통으로 모아 정한 시각에 보내야 한다.
2. `List-Unsubscribe`(one-click 포함) 헤더로 알림 설정 쪽 또는 끄기 동작을 연결해야 한다.

**수용 기준**
- [ ] 하루 한 번 설정인 사람은 그날 알림을 한 통으로 받는다
- [ ] one-click 받지 않기 요청 뒤 그 사람의 메일 받기가 꺼진다
