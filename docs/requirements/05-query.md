# 질의 · 목록 · 보드 요구사항 (FR-QRY)

일감을 거르고(필터 · 연산자), 목록으로 보고(열 · 정렬 · 묶기 · 합계 · 쪽), 저장하고(개인 · 공개 · 역할별), 내보내고(CSV · PDF · Atom), 칸반 보드로 다루는 요구사항이다. Redmine 의 질의를 기준으로 하고 칸반 보드를 더했다. **화면 목록 · 보드 · 내보내기 · MCP `search_issues` 는 모두 같은 질의 엔진**이다. 설계는 [일감 추적 설계 §12 · §13](../design/05-issue-tracking.md#is-query)에 있다.

## 1. 필터

<a id="fr-qry-001"></a>
### FR-QRY-001 필터 대상 필드

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.2](../design/05-issue-tracking.md#is-filters) |

**설명** — 일감을 프로젝트 · 트래커 · 상태 · 우선순위 · 작성자 · 담당 · 카테고리 · 대상 버전 · 날짜 · 시간 · 진척률 · 관계 · 상위/하위 · 관찰자 · 첨부 · 글로 거른다(Redmine 의 필터). Agent 가 만든 일감 · MCP 로 만든 일감을 거르는 필드를 더했다.

**세부 요구사항**
1. 필터 필드는 설계 §12.2 의 표와 같아야 한다(작성자 종류 `author_type` · 만든 경로 `created_via` 포함).
2. 필터끼리는 그리고, 한 필터의 값끼리는 또는이어야 한다.
3. 기본 필터는 "상태 = 열림"이어야 한다.
4. 필드마다 그 형식에 맞는 연산자만 받아야 하고, 맞지 않으면 400 이어야 한다.
5. 화면은 질의를 주소에 담아야 하고, 주소를 받은 사람이 열면 그 사람의 권한으로 돌아야 한다.

**수용 기준**
- [ ] "담당 = 나 ∧ 상태 = 열림"의 결과가 맞다
- [ ] 형식에 맞지 않는 연산자(예: 제목에 `in_next_days`)는 400 이다
- [ ] 주소를 다른 사람이 열면 그 사람이 볼 수 있는 일감만 나온다
- [ ] "만든 경로 = MCP" 와 "작성자 종류 = Agent" 로 거를 수 있다

<a id="fr-qry-002"></a>
### FR-QRY-002 필터 연산자와 값

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.4](../design/05-issue-tracking.md#is-operators) |

**설명** — Redmine 의 연산자(같다 · 아니다 · 포함 · 비어 있음 · 이상/이하/사이 · 오늘 · 이번 주 · N일 안/전 · 열림/닫힘 · 나)를 같은 뜻으로 둔다. API · MCP 는 영어 키(`eq` · `in_past_days` …)를 쓴다.

**세부 요구사항**
1. 연산자는 설계 §12.4 의 표와 같아야 한다: 같다 · 아니다 · 열림 · 닫힘 · 비어 있음 · 비어 있지 않음 · 포함 · 포함 안 함 · 시작 · 끝 · 이상 · 이하 · 사이 · 오늘 · 어제 · 내일 · 이번 주 · 지난주 · 지난 2주 · 다음 주 · 이번 달 · 지난달 · 다음 달 · 올해 · 지난 N일 안 · N일보다 전 · 꼭 N일 전 · 앞으로 N일 안 · N일보다 뒤 · 꼭 N일 뒤 · 관계 연산자.
2. 값 `me` 는 지금 주체(사람, 또는 서비스 키로 온 MCP 면 그 Agent 계정)여야 하고, `mine` 은 내가 역할을 가진 프로젝트여야 한다.
3. "아니다"는 빈 값을 포함해야 한다(Redmine 과 같다).
4. "포함"은 띄어 쓴 낱말이 모두 들어 있어야 한다.
5. "오늘" 같은 날짜는 보는 사람의 시간대(없으면 워크스페이스 시간대, 기본 Asia/Seoul)로, 주는 설정의 주 시작으로 계산해야 한다.

**수용 기준**
- [ ] 서울 시간 23:30 에 만든 일감이 "오늘" 필터에 든다(UTC 날짜와 달라도)
- [ ] 주 시작이 월요일일 때 "이번 주" 경계가 월 00:00 ~ 일 24:00 이다
- [ ] "담당 아니다 X" 에 담당이 빈 일감이 들어 있다
- [ ] 서비스 키 MCP 의 `me` 는 그 Agent 계정이다

<a id="fr-qry-003"></a>
### FR-QRY-003 권한 · 비공개 조건

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.3](../design/05-issue-tracking.md#is-query-acl) · [프로젝트 권한 §13.1](../design/04-project-permissions.md#pp-cache) |

**설명** — 질의는 어떤 필터를 넣든 그 사람이 볼 수 있는 일감만 낸다. 다른 일감을 보는 필터(관계 · 상위 · 하위)와 메모 · 소요 시간 필터에도 같은 조건을 건다.

**세부 요구사항**
1. 질의 SQL 은 권한 범위(읽을 수 있는 프로젝트 · 일감 모듈 · `issue.read` · MCP 엔드포인트 대상)와 비공개 보기 범위 조건을 늘 가져야 하고, 범위 없이 SQL 을 만들 수 없어야 한다.
2. 관계 · 상위 · 하위 필터의 상대 일감, 관찰자 대상에도 같은 조건을 걸어야 한다.
3. 필터 값으로 넣은 일감 번호 가운데 안 보이는 것은 없는 번호로 봐야 한다(결과로 존재가 드러나지 않는다).
4. 메모 필터는 볼 수 있는 메모만, 소요 시간 필터는 `time.read` 가 있는 프로젝트만 봐야 한다.
5. 모든 질의 길의 SQL 에 권한 조건이 있는지 자동 테스트로 확인해야 한다.

**수용 기준**
- [ ] 목록 · 보드 · 내보내기 · MCP · 간트 · 캘린더의 SQL 에 권한 조건이 있다(테스트)
- [ ] 관계 필터에 안 보이는 번호를 넣어도 결과로 그 일감의 존재를 짐작할 수 없다
- [ ] 보고자가 메모 "포함"으로 거르면 비공개 메모의 글은 맞지 않는다
- [ ] MCP 엔드포인트 대상 밖 프로젝트의 일감은 `search_issues` 결과에 없다

### FR-QRY-004 목록 열

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.5](../design/05-issue-tracking.md#is-query-list) |

**설명** — 일감 목록에 보일 열을 고르고 순서를 정한다(Redmine 의 "열" 옵션). 설명 · 마지막 메모는 줄 아래에 펼쳐 보인다.

**세부 요구사항**
1. 열은 설계 §12.5 의 표에서 고르고 순서를 정할 수 있어야 한다. 번호는 늘 맨 앞이다.
2. 기본 열은 워크스페이스 설정(트래커 · 상태 · 우선순위 · 제목 · 담당 · 고친 때)이어야 한다.
3. 설명 · 마지막 메모를 줄 아래에 펼쳐 볼 수 있어야 하고, 마지막 메모는 볼 수 있는 메모 가운데 마지막이어야 한다.
4. 못 보는 사용자 정의 필드는 열로 고를 수 없어야 한다.
5. 390px 에서는 고른 열을 카드형으로 보여야 한다.

**수용 기준**
- [ ] 처음 연 목록의 열이 설정의 기본 열과 같다
- [ ] 못 보는 사용자 정의 필드는 열 고르기에 없고, API 로 요청해도 나오지 않는다
- [ ] 보고자의 마지막 메모 열에 비공개 메모가 나오지 않는다
- [ ] 390px 에서 가로 넘김 없이 카드로 보인다

<a id="fr-qry-005"></a>
### FR-QRY-005 정렬

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.5](../design/05-issue-tracking.md#is-query-list) |

**설명** — 목록을 세 열까지 정렬한다(Redmine 과 같다). 우선순위 · 상태 · 트래커는 이름이 아니라 정한 순서로 정렬한다.

**세부 요구사항**
1. 정렬 열쇠는 세 개까지여야 하고, 값이 같으면 번호 내림차순으로 끝내야 한다.
2. 기본 정렬은 번호 내림차순이어야 한다.
3. 우선순위 · 상태 · 트래커는 정한 순서, 대상 버전은 기한 뒤 이름, 주체는 표시 이름, 사용자 정의 필드는 형식대로 정렬해야 한다.
4. 묶기를 쓰면 묶은 필드가 첫 정렬 열쇠가 되어야 한다.

**수용 기준**
- [ ] 우선순위 내림차순이면 "즉시"가 맨 위다
- [ ] 대상 버전 정렬이 버전 기한 순이다
- [ ] 같은 값이 많아도 쪽을 넘길 때 순서가 흔들리지 않는다(번호로 끝냄)

<a id="fr-qry-006"></a>
### FR-QRY-006 쪽 나누기

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.6](../design/05-issue-tracking.md#is-paging) |

**설명** — 화면은 쪽 번호로, REST · MCP 는 커서로 나눠 준다. Agent 가 큰 결과를 끝까지 읽어도 겹치거나 빠지지 않게 한다.

**세부 요구사항**
1. 화면은 쪽 크기 25 · 50 · 100 과 쪽 번호를 써야 하고, 전체 건수는 10,000 까지 세고 넘으면 "10,000+"로 보여야 한다.
2. REST 는 `limit` 100, MCP 는 50 까지여야 하고, 넘으면 상한으로 줄여야 한다.
3. REST · MCP 는 불투명 커서(마지막 행의 정렬 값 + 번호 + 질의 해시)를 써야 하고, 다른 질의에 커서를 쓰면 400 이어야 한다.
4. 10,000 행 뒤로는 쪽 번호로 갈 수 없어야 한다(필터를 좁히게 한다).

**수용 기준**
- [ ] 커서로 끝까지 읽으면 겹치거나 빠진 일감이 없다
- [ ] 다른 질의에 커서를 쓰면 400 이다
- [ ] MCP `limit` 100 을 보내면 50 개가 온다
- [ ] 결과가 10,000 을 넘으면 "10,000+"가 보인다

<a id="fr-qry-007"></a>
### FR-QRY-007 여러 프로젝트 · 하위 프로젝트 목록

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.1](../design/05-issue-tracking.md#is-query) · [§12.3 권한 조건](../design/05-issue-tracking.md#is-query-acl) |

**설명** — 한 프로젝트의 목록에 하위 프로젝트 일감을 넣고, 워크스페이스 전체의 "모든 일감"을 본다(Redmine 의 "모든 일감"과 "하위 프로젝트 일감 보기").

**세부 요구사항**
1. 워크스페이스 "모든 일감"은 읽을 수 있고 일감 모듈이 켜진 모든 프로젝트의 일감이어야 한다.
2. 프로젝트 목록은 설정(기본 켬)에 따라 하위 프로젝트 일감을 포함하고, 질의마다 바꿀 수 있어야 한다.
3. 프로젝트 필터에 `mine`(내가 역할을 가진 프로젝트)을 쓸 수 있어야 한다.
4. 여러 프로젝트를 보일 때 프로젝트 열을 쓸 수 있어야 한다.

**수용 기준**
- [ ] "모든 일감"에 `RESTRICTED` 비독자 프로젝트의 일감이 없다
- [ ] "모든 일감"에 일감 모듈이 꺼진 프로젝트의 일감이 없다
- [ ] "하위 포함"을 끄면 하위 프로젝트 일감이 빠진다
- [ ] `project = mine` 이 내가 역할을 가진 프로젝트만 낸다

<a id="fr-qry-008"></a>
### FR-QRY-008 화면 · REST · MCP 같은 엔진

| 항목 | 내용 |
|---|---|
| 우선순위 | M |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.1](../design/05-issue-tracking.md#is-query) · [§19 API](../design/05-issue-tracking.md#is-api) |

**설명** — 사람의 목록과 Agent 의 `search_issues` 가 다른 결과를 내면 사람과 Agent 가 같은 프로젝트를 관리할 수 없다. 그래서 질의 꼴(JSON)과 SQL 을 만드는 함수를 하나로 둔다.

**세부 요구사항**
1. 질의를 SQL 로 바꾸는 함수는 하나(`IssueQuerySql.build(scope, query)`)여야 한다.
2. MCP `search_issues` 의 입력은 질의 JSON 과 같은 꼴이어야 한다(필터 · 정렬 · 열 · 커서).
3. 보드 · 내보내기 · 간트 · 캘린더 · 로드맵 일감 목록 · 내 페이지 블록도 같은 엔진을 써야 한다([버전 요구사항](06-planning.md) · [활동 요구사항](10-activity-search.md)).
4. MCP 는 저장한 질의 id 로도 돌릴 수 있어야 한다(그 주체가 볼 수 있는 질의만).
5. 같은 주체 · 같은 질의면 REST 와 MCP 의 결과(번호 목록 · 순서)가 같아야 한다.

**수용 기준**
- [ ] 같은 질의를 사람 · Agent 각각 REST 와 MCP 로 돌려 번호 목록과 순서가 같다
- [ ] 저장한 공개 질의 id 로 MCP `search_issues` 를 돌릴 수 있고, 개인 질의 id 는 남이 쓰면 404 다
- [ ] 보드의 카드 집합이 같은 필터의 목록과 같다(열마다 상한 안에서)

5. 못 보는 필드는 없는 필드와 같은 오류여야 한다.

**수용 기준**
- [ ] 목록 형식 필드의 "같다" 필터가 GIN 색인을 탄다(실행 계획)
- [ ] 정수 형식 필드의 "사이" 필터가 맞다
- [ ] 사용자 정의 필드 열로 정렬된다
- [ ] 못 보는 필드로 거르면 없는 필드와 같은 400 이다

### FR-QRY-011 합계

## 4. 저장한 질의 · 내보내기

<a id="fr-qry-012"></a>
### FR-QRY-012 저장한 질의 (개인)

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.7](../design/05-issue-tracking.md#is-saved-query) |

**설명** — 자주 쓰는 필터 · 열 · 정렬 · 묶기를 이름 붙여 저장한다(Redmine 의 저장한 질의). 개인 질의는 나만 본다.

**세부 요구사항**
1. 질의는 이름 · 범위(프로젝트 하나 또는 모든 프로젝트) · 필터 · 열 · 정렬 · 묶기 · 합계 · 옵션 · 보기 종류(목록 · 보드)를 담아야 한다.
2. 개인 질의는 `issue.read` 가 있으면 저장할 수 있어야 하고, 만든 사람만 봐야 한다.
3. 사이드바에 내 질의 · 공개 질의를 보여야 한다.
4. 돌릴 때는 지금 권한으로 돌아야 하고, 지운 상태 · 못 보는 필드를 가리키는 조건은 빼고 알려야 한다.
5. 저장 · 고치기 · 지우기는 감사에 남아야 한다.

**수용 기준**
- [ ] 독자가 개인 질의를 저장하고, 다른 사람에게는 보이지 않는다
- [ ] 권한이 줄어든 뒤 저장한 질의를 돌리면 줄어든 결과가 나온다
- [ ] 지운 상태를 가리키는 조건은 빠지고 "조건 1개를 뺐다"가 보인다

<a id="fr-qry-013"></a>
### FR-QRY-013 공개 · 역할별 질의

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.7](../design/05-issue-tracking.md#is-saved-query) |

**설명** — 프로젝트 관리자는 팀이 함께 쓸 질의를 공개하거나 특정 역할에만 보인다(Redmine 의 공개 질의 · 역할별 질의).

**세부 요구사항**
1. 공개 범위는 `PRIVATE` · `ROLES`(고른 프로젝트 역할) · `PUBLIC`(그 프로젝트의 독자 모두, 모든 프로젝트 질의면 워크스페이스 멤버 모두)여야 한다.
2. 공개 · 역할별 질의는 그 프로젝트의 `query.save.public`, 모든 프로젝트 질의는 워크스페이스 층 `query.save.public` 이 있어야 저장 · 고치기 · 지우기를 해야 한다.
3. 역할별 질의는 실효 역할이 고른 역할에 드는 주체 · 만든 사람 · `project.manage` 만 봐야 한다.
4. 누가 돌려도 돌리는 사람의 권한으로 돌아야 한다.
5. 감사에 남아야 한다.

**수용 기준**
- [ ] 개발자가 공개 질의를 저장하면 403 이다
- [ ] "개발자" 역할 질의는 보고자의 질의 목록에 없고 개발자에게는 있다
- [ ] 공개 질의를 보고자가 돌리면 남의 비공개 일감이 없다
- [ ] 감사에 저장한 사람 · 공개 범위가 남는다

<a id="fr-qry-014"></a>
### FR-QRY-014 CSV 내보내기

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.8](../design/05-issue-tracking.md#is-export) |

**설명** — 질의 결과를 CSV 로 내려받는다(Redmine 과 같다). 큰 결과는 뒷일 작업으로 만들고, 스프레드시트 수식 주입을 막는다.

**세부 요구사항**
1. 지금 열 또는 모든 열을 고르고, 설명 · 마지막 메모를 넣을지 골라야 한다.
2. 인코딩은 UTF-8(BOM, 기본) 또는 CP949, 구분자는 `,` 또는 `;` 를 골라야 한다.
3. `=` `+` `-` `@` 탭 · 줄바꿈으로 시작하는 칸은 앞에 `'` 를 붙여야 한다.
4. 같은 권한 조건 · 같은 열 보이기 규칙을 써야 한다(비공개 메모 · 못 보는 필드는 나가지 않는다).
5. 행이 설정 한도(기본 5,000)를 넘으면 작업 큐로 만들고 끝나면 알려야 하며, 내려받기는 만든 사람만 api 를 거쳐야 한다(24시간).
6. 감사 `issue.exported`(형식 · 건수 · 질의)를 남겨야 한다.

**수용 기준**
- [ ] 제목이 `=HYPERLINK(…)` 인 일감이 `'` 로 시작해 저장된다
- [ ] CSV 에 비공개 메모 · 못 보는 사용자 정의 필드가 없다
- [ ] 6,000 행이면 작업으로 만들어지고 알림이 오며, 다른 사람이 내려받으면 404 다
- [ ] 감사에 건수와 질의가 남는다

## 5. 칸반 보드

### FR-QRY-015 칸반 보드

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §13](../design/05-issue-tracking.md#is-board) |

**설명** — 상태를 열로 놓고 일감을 카드로 보는 보드다. Redmine 에는 없는 추가 기능이고, 질의의 보기 종류 하나라서 같은 필터 · 같은 권한을 쓴다.

**세부 요구사항**
1. 보드는 프로젝트 모듈 `kanban` 이 켜져 있어야 하고, 질의의 보기 종류 `BOARD` 로 저장할 수 있어야 한다.
2. 열은 상태여야 하고, 기본은 범위 안 트래커들이 쓰는 상태를 상태 순서로 둔다. 숨길 상태 · 닫힌 상태 접기를 고를 수 있어야 한다.
3. 카드는 번호 · 제목 · 트래커 · 우선순위 · 담당(Agent 표시) · 기한(늦음 표시) · 진척률 · 하위 수 · 비공개 표시를 보여야 한다.
4. 열마다 100장까지 불러오고 "더 보기"로 이어야 한다.
5. 390px 에서는 열을 가로로 넘겨 한 열씩 보여야 한다.

**수용 기준**
- [ ] `kanban` 을 끄면 보드가 404 다
- [ ] 보드의 카드 집합이 같은 필터의 목록과 같고, 비공개 보기 범위도 같다
- [ ] Agent 가 담당인 카드에 "Agent" 표시가 있다
- [ ] 390px 에서 열이 가로로 넘어간다

<a id="fr-qry-016"></a>
### FR-QRY-016 보드 끌어 놓기와 워크플로

| 항목 | 내용 |
|---|---|
| 우선순위 | S |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §13](../design/05-issue-tracking.md#is-board) · [§8 워크플로](../design/05-issue-tracking.md#is-workflow) |

**설명** — 카드를 다른 열에 놓으면 상태가 바뀐다. 끌어 놓기도 일감 고치기와 똑같이 워크플로 · 필드 권한 · 잠금을 지킨다.

**세부 요구사항**
1. 카드마다 허용 상태를 함께 받아, 끌기 시작하면 갈 수 없는 열을 흐리게 하고 이유(워크플로 · 열린 하위 · 막힘)를 보여야 한다.
2. 놓기는 일감 고치기(`status` + `lock_version`)와 같은 요청이어야 한다.
3. 새 상태에서 필수인 필드가 비어 있으면 작은 창으로 채우게 해야 한다.
4. 충돌(409)이면 카드를 되돌리고 새 값으로 다시 그려야 한다.
5. 카드 메뉴의 "상태 바꾸기"로 키보드 · 화면 읽기 도구에서도 같은 일을 해야 한다.
6. 저널 · 이벤트는 일반 고치기와 같아야 한다.

**수용 기준**
- [ ] 허용되지 않은 열에 놓으면 403 이고 카드가 원래 열로 돌아간다
- [ ] 담당이 필수인 "해결" 열에 담당 없는 카드를 놓으면 채우기 창이 뜨고, 채우면 저장된다
- [ ] 다른 사람이 먼저 고친 카드를 놓으면 되돌아가고 새 값이 보인다
- [ ] 키보드만으로 카드의 상태를 바꿀 수 있다

3. CSV 와 같은 권한 · 열 규칙과 한도 · 작업 큐 · 감사를 써야 한다.

**수용 기준**
- [ ] 한글이 깨지지 않는다
- [ ] 일감 PDF 에 볼 수 있는 저널만 있고 비공개 메모가 없다
- [ ] 감사 `issue.exported` 가 남는다

<a id="fr-qry-020"></a>
### FR-QRY-020 Atom 피드

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §12.8](../design/05-issue-tracking.md#is-export) |

**설명** — 질의 결과를 피드 리더로 구독한다(Redmine 의 Atom). 피드 리더는 로그인 세션이 없으므로 개인 피드 토큰을 쓴다.

**세부 요구사항**
1. 사람마다 개인 피드 토큰을 만들고 끄고 다시 만들 수 있어야 하며, 원문은 한 번만 보이고 SHA-256 만 저장해야 한다.
2. 피드 경로는 새 접근 어노테이션 `@FeedApi` 로만 받아야 하고, 토큰이 정한 사람의 권한으로 같은 질의 엔진을 돌려야 한다.
3. 최근 고친 일감 50개를 내고, 비공개 메모는 넣지 않아야 한다.
4. 토큰 만들기 · 끄기는 감사에 남아야 한다.

**수용 기준**
- [ ] 토큰이 없거나 끈 토큰이면 401 이다
- [ ] 피드 결과가 토큰 주인이 목록에서 보는 결과와 같다
- [ ] DB 에 토큰 원문이 없다
- [ ] 피드 토큰으로 다른 API 를 부르면 401 이다

<a id="fr-qry-021"></a>
### FR-QRY-021 보드 WIP 한도 · 손으로 정한 순서

| 항목 | 내용 |
|---|---|
| 우선순위 | C |
| 진행 | 할 일 |
| 관련 설계 | [일감 설계 §13](../design/05-issue-tracking.md#is-board) |

**설명** — 열마다 진행 중 일감 수 한도를 두고, 열 안 카드 순서를 손으로 정한다.

**세부 요구사항**
1. 보드 설정에 열마다 WIP 한도를 둘 수 있어야 하고, 넘으면 열을 붉게 보이되 놓기를 막지 않아야 한다.
2. 열 안 카드 순서를 끌어서 정할 수 있어야 하고, 그 보드를 보는 모두에게 같은 순서여야 한다.
3. 순서 바꾸기는 일감 저널을 남기지 않아야 한다.

**수용 기준**
- [ ] WIP 한도를 넘으면 열이 붉어지고, 카드는 놓인다
- [ ] 순서를 바꾸면 다른 사람에게도 같은 순서로 보인다
- [ ] 순서 바꾸기 뒤 일감 저널이 늘지 않는다
