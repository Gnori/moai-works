# 핵심 설계 결정 (ADR)

설계 방향을 정하는 결정을 기록한다. 결정을 바꿀 때는 기존 기록을 지우지 않고 상태를 바꾸고(`대체` · `폐기` · `보류`), 필요하면 새 ADR 을 더한다.

**상태 표기:** `확정`(사람이 정했거나 이미 구현) · `대체`(다른 ADR 이 이 결정을 바꿨다) · `폐기`(하지 않기로 했다) · `보류`(첫 출시 범위 밖 — 나중 후보로 남긴다)

> **2026-11-22 재정리.** 사람이 "moai-works 는 moai-wiki 와 다를 게 없다 — 위키냐 프로젝트냐 차이만 있다" 고 정했다. 구조 · 인증 · 워크스페이스 · 역할과 권한 · MCP · 흐름 · 화면을 moai-wiki 와 같게 하고, 다른 것은 **위키 대신 프로젝트, 페이지 대신 일감**과 일감 모델(유형 · 관리자와 담당자 · 날짜 · 상하위 · 연결)뿐이다. 그에 맞춰 ADR 을 다시 정리했다.

## ADR-002 moai-wiki 와 같게 한다 — 위키냐 프로젝트냐 차이만

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-21 사람 지시: "moai-wiki 디렉토리 구조로 가자. src 아래로 모듈들 넣고 디펜던시도 같게, 인증도 같게, 역할 권한도, 워크스페이스도"). **2026-11-22 강화** — "다를 게 없다는 것", "위키냐? 프로젝트냐 차이만 있다는 거야", "구현도 비슷하게", "흐름도 같게", "MCP 체계도, 인증 체계도 같다", "웹도 moai-wiki 와 동일한 구조로" |
| 맥락 | moai-wiki 에는 계정 · 가입 · 워크스페이스 · 역할 · 멤버십 · 초대 · 감사 · MCP 키 · BFF 로그인 · React 뼈대가 동작하고 테스트가 있다. 위키 층(위키 · 위키 역할 · `@WikiApi`)도 설계와 코드가 있다. 2026-11-21 에 쓴 moai-works 설계는 Redmine 을 그대로 옮긴 무거운 모양(Agent 계정 · 트래커 · 워크플로 · 사용자 정의 필드 · 계획 · 협업 · 연동)이라 moai-wiki 와 크게 달라졌다 |
| 결정 | **같게 둔다:** 저장소 모양(`src/` 아래 api · web-backend · web-frontend · `infra/` · `tools/` · 규칙 문서 · `docs/` 구성), 의존성 판, 인증(Keycloak 렐름 · BFF 패스워드 그랜트 · 서버 세션 · api 의 JWT 직접 검증), 워크스페이스(개인/팀 · 퍼블릭/프라이빗 · 승인/자동 가입), 역할과 권한(Keycloak Organizations 정본 · DB 사본 판정 · 사용자 정의 역할 · 접근 어노테이션 · 권한 상승 방지), MCP(MCP 키 · 워크스페이스 엔드포인트 · 같은 서비스 · 매 호출 재판정), 흐름(가입 → 로그인 → 개인 워크스페이스 → 팀 워크스페이스 → 초대 · 가입 신청), 감사, 화면 뼈대, 문서 형식. **바꾼다:** 위키 → 프로젝트, 페이지 → 일감, 위키 역할 → 프로젝트 역할, 페이지 유형 → 일감 유형, 페이지 트리 → 상위 · 하위 일감, 페이지 소유자 → 일감 관리자(+ 담당자), 페이지 링크 → 연결 일감, 리비전 → 일감 이력, 피드백 → 댓글. **뺀다:** 내장 agent · collector · refiner · 자료실 · 보안등급 · 변경안 검토 |
| 결과 | 설계가 moai-wiki 의 위키 설계와 한 줄씩 맞대어진다([프로젝트 설계](04-project.md) · [일감 설계](05-issue.md) · [MCP 설계](06-mcp.md)). 토대를 고칠 때 두 저장소를 함께 볼 일이 생긴다([DEVELOPE.md](../../DEVELOPE.md) 의 형제 저장소 줄). 공통 라이브러리로 뺄지는 나중에 본다 |

## ADR-003 AI Agent 를 내장하지 않는다 — 바깥 Agent 가 MCP 로 붙는다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-21 사람 지시: "AI Agent 자체는 내장할 계획은 없고, AI Agent 가 프로젝트 관리할 수 있고 MCP 로 그걸 연결할 수 있게" · "moai-works-ai 는 제거") |
| 맥락 | 피봇 전 설계에는 Python AI 서비스(`moai-works-ai`)가 있었다. 요약 · 분류 같은 기능은 모델이 빠르게 바뀌고, 쓰는 사람마다 원하는 Agent 가 다르다. moai-wiki 의 내장 Wiki Agent · collector · refiner 에 해당하는 것을 두지 않는다 |
| 결정 | 시스템 안에 LLM · Agent 를 두지 않는다. api 가 **MCP 서버**가 되어 프로젝트 · 일감을 도구로 연다. Agent 는 사람의 MCP 키로 붙어 그 사람의 권한 안에서만 일한다([ADR-008](#adr-008) · [ADR-024](#adr-024)) |
| 결과 | `moai-works-ai` 를 지웠다. 모듈은 셋(api · web-backend · web-frontend). AI 기능은 "MCP 도구가 충분한가"로 바뀐다([FR-MCP-004](../requirements/04-mcp.md#fr-mcp-004) · [FR-MCP-005](../requirements/04-mcp.md#fr-mcp-005) · [MCP 설계](06-mcp.md)) |

<a id="adr-004"></a>
## ADR-004 판정은 api 한 곳, MCP 도구는 REST 와 같은 서비스를 부른다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (moai-wiki 와 같은 원칙) |
| 결정 | 권한 판정은 api 에만 있다. REST 핸들러는 접근 어노테이션 정확히 하나(없으면 기동 실패). MCP 도구는 서비스 메서드를 부르는 얇은 층이고, 범위는 요청 문맥(키 · 엔드포인트)에서만 오며 모델이 넘긴 프로젝트 · 일감도 주체의 권한으로 호출마다 다시 판정한다. 화면 · BFF 는 판정하지 않는다 |
| 결과 | 웹과 MCP 가 같은 결과를 낸다는 "동등성"을 테스트로 지킨다([테스트 전략](../plan/02-test-strategy.md)) |

<a id="adr-005"></a>
## ADR-005 권한 경계는 프로젝트, 프로젝트 역할은 고정 4개

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22, 고침 — 2026-11-21 의 제안 "관리자 · 개발자 · 보고자 · 독자"를 moai-wiki 의 위키 역할과 같은 모양으로 바꿨다) |
| 맥락 | moai-wiki 는 "위키 = 권한 경계"이고 위키 역할 넷(위키 관리자 ⊃ 큐레이터 ⊃ 편집자 ⊃ 독자)을 둔다. 사람이 "위키냐 프로젝트냐 차이만" 이라고 정했다 |
| 결정 | 프로젝트를 권한 경계로 삼는다(공개 범위 `WORKSPACE` · `RESTRICTED`, 독자가 아니면 404). 일감마다 읽기를 좁히지 않는다(비공개 일감 없음 — moai-wiki 가 페이지마다 읽기를 좁히지 않는 것과 같다). 프로젝트 역할은 `project-admin` ⊃ `project-curator` ⊃ `project-editor` ⊃ `project-reader` 넷으로 고정한다. 한 사람이 한 프로젝트에서 여러 역할을 가질 수 있고 권한은 합친다. 사용자 정의 프로젝트 역할은 두지 않는다 |
| 결과 | 판정 식이 moai-wiki 의 위키 층과 같다 — 독자 = 활성 멤버 ∧ (WORKSPACE ∨ 소유자 · 관리자 ∨ 프로젝트 역할), 권한 = 워크스페이스 역할 ∪ 프로젝트 역할([프로젝트 설계 §3](04-project.md#pj-read) · [FR-PRJ-006](../requirements/02-project.md#fr-prj-006) · [FR-PRJ-007](../requirements/02-project.md#fr-prj-007)) |

<a id="adr-008"></a>
## ADR-008 MCP 인증은 MCP 키 + 워크스페이스 엔드포인트

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22, 고침 — moai-wiki 설계 13 §11 · ADR-022 와 같은 모양으로 맞췄다). **고침 2026-11-22: 서비스 키 없음 — [ADR-024](#adr-024)** (그 전에는 개인 키 · 서비스 키 두 종류와 엔드포인트의 읽기 방식 `USER` · `SERVICE` 가 있었다) |
| 결정 | 워크스페이스마다 MCP 엔드포인트 `/mcp/{ws}/{ep}` 를 여러 개 둔다. 엔드포인트는 종류(`QUERY` 읽기 · `AGENT` 읽기 + 쓰기) · 대상 프로젝트(하나 이상) · 켠 도구 · 한도 · 상태를 가진다. MCP 키(Bearer, SHA-256 만 저장, 요청마다 캐시 없이 검사)는 사용자 계정 하나와 엔드포인트 하나에 묶이고, 키 범위 = 키 주인의 권한 ∩ 엔드포인트 범위다. 엔드포인트마다 MCP 서버 하나를 캐시한다. MCP 권한 부여 사양(OAuth 2.1)은 나중 |
| 결과 | 지금 코드의 고정 입구와 워크스페이스에 묶이지 않은 키 API 를 이 구조로 옮긴다([MCP 설계 §2](06-mcp.md#mc-gap) · [FR-MCP-001](../requirements/04-mcp.md#fr-mcp-001) · [FR-MCP-002](../requirements/04-mcp.md#fr-mcp-002) · [WBS 4단계](../wbs/05-stage-4-mcp.md)). 키는 2026-11-22 워크스페이스 · 주인 계정에 묶었다(V5) |
| 고침 2026-11-23 | **"키는 엔드포인트 하나에 묶인다"를 [ADR-028](#adr-028)이 바꿨다** — 키는 입구에 묶이지 않고, 입구는 기능(일감 · 프로젝트 관리)으로 나눈다. 엔드포인트를 만들 때 이 원칙을 따라 다시 정한다 |
| 대체 2026-11-23 | **워크스페이스마다 엔드포인트를 두는 계획은 [ADR-029](#adr-029)가 대체했다** — 사용자: "워크스페이스별로 mcp 엔드포인트 만드는 건 안 되지. 사용자가 접근 가능한 곳이면 다 되는 거지". 입구는 기능별 고정 둘(`/mcp/issue` · `/mcp/project`)로 두고, 키는 사용자의 것이라 워크스페이스에도 묶지 않는다. 어느 워크스페이스인지는 도구 호출의 `workspace` 인자와 키 주인의 권한으로 정한다 |

## ADR-017 워크스페이스 기본 역할은 넷 — 큐레이터 복원

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22) |
| 맥락 | moai-wiki 의 기본 역할은 소유자 · 관리자 · 큐레이터 · 멤버 넷이다. 큐레이터는 모든 위키에서 페이지를 만들고 고치지만 지우거나 위키를 관리하지는 못한다. 프로젝트 관리에서도 "모든 프로젝트의 일감을 다루는 사람"이 필요하다 |
| 결정 | 기본 역할은 `owner`(전부) · `admin`(소유자 전용 둘을 뺀 전부) · `curator`(workspace.read · member.read · issue.read · issue.create · issue.edit · issue.comment · issue.manager.assign · mcp.key.issue.personal) · `member`(workspace.read · member.read · issue.read · issue.comment · mcp.key.issue.personal) 넷이다. 멤버가 특정 프로젝트에서 일감을 만들려면 그 프로젝트의 프로젝트 역할(편집자 이상)을 받는다 |
| 결과 | 기본 역할 · 권한 코드는 [워크스페이스 설계 §4](03-workspace-identity.md#ws-catalog). 이미 있는 워크스페이스에도 큐레이터 역할(Keycloak 그룹 · 사본)이 생겨야 한다([§18.4](03-workspace-identity.md#ws-impl)). "큐레이터" 라는 이름을 그대로 둘지는 [정해야 할 것](../wbs/08-decisions.md)에 있다(제안: moai-wiki 와 같게 그대로) |

<a id="adr-020"></a>
## ADR-020 일감 상태는 고정 4개, 날짜는 자동으로 채운다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22) |
| 결정 | 상태는 `NEW`(신규) · `IN_PROGRESS`(진행) · `DONE`(완료) · `CLOSED`(종료) 넷으로 고정하고, 아무 상태로나 옮길 수 있다(워크플로 사용자 정의는 나중). `DONE` 으로 가면 완료일이 비어 있을 때 오늘을, `CLOSED` 로 가면 종료일이 비어 있을 때 오늘을 넣는다. `NEW` · `IN_PROGRESS` 로 되돌리면 완료일 · 종료일을 비운다. 편집 권한이 있으면 완료일 · 종료일도 직접 고친다. 날짜 검사는 시작일 ≤ 완료 예정일, 시작일 ≤ 완료 기한, 완료일 ≤ 종료일(값이 있을 때만) |
| 결과 | 상세는 [일감 설계 §5](05-issue.md#is-status). 상태 · 일감 유형을 프로젝트마다 바꾸게 할지는 [정해야 할 것](../wbs/08-decisions.md)에 있다(제안: 고정으로 시작) |

## ADR-021 MCP 는 web-backend 가 중계한다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22) — 사용자: "MCP 는 api 로 직접 서비스하지 말고 moai-works-web-backend 가 프록시로 해야 하니까 moai-works-web-backend 포트로 연결되어야" · "이건 moai-wiki 도 같다" |
| 결정 | 바깥 MCP 클라이언트는 web-backend 포트(로컬 11002)의 `/mcp/{ws}/{ep}` 로 붙는다. web-backend 는 `/mcp/**` 를 api 로 그대로 흘려보내기만 하고(세션 · CSRF 없음, MCP 키를 그대로 넘김, 스트림 버퍼링 없음, 실제 클라이언트 IP 를 붙임) 판정하지 않는다. 연결 안내는 web-backend 주소를 보인다. api 도 `/mcp/**` 를 그대로 서비스한다 — 직접 붙어도 되고 막지 않는다(2026-11-22 사용자: "MCP 는 api 에서도 서비스는 가능해. 안 되는 게 아니야"). 두 길 모두 키 검사 · 판정 · 접근 기록은 api 한 곳이다 |
| 결과 | [MCP 설계 — 중계](06-mcp.md#mc-relay) · [FR-MCP-009](../requirements/04-mcp.md#fr-mcp-009). moai-wiki 세션에 같은 결정을 알렸다 |

## ADR-022 MCP 접근은 읽기까지 모두 기록하고, 키는 지우지 않고 만료시킨다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22) — 사용자: "MCP 키 발급을 해 주면 감사 데이터 모두 기록해야 해. 클라이언트 정보 자세하게. 읽기, 수정, 삭제, 생성 모두" · "필터 기능도 잘 만들고, 워크스페이스의 권한이 있는 사용자는 그 이력을 볼 수 있어야" · "MCP 키 발급 이력도 워크스페이스 관리자가 확인 가능해야 하고 익스파이어도 시킬 수 있어야. 삭제는 아니고 키는 삭제 개념은 없어" |
| 결정 | MCP 키로 들어온 요청은 연결 · 도구 목록 · 도구 호출(읽기 · 생성 · 수정 · 삭제) · 인증 실패까지 한 줄씩 추가 전용 `mcp_access_log` 에 남긴다(클라이언트 이름 · 버전 · 프로토콜 · 세션 id · User-Agent · IP · trace_id 포함, 저장 실패면 요청도 실패). `audit.read` 가 있는 사람이 거르기 · 상세 · CSV 로 본다(키 주인은 자기 키만). 키는 지우지 않는다 — 키 주인이나 `mcp.key.manage` 가 있는 사람이 바로 만료시키고, 만료된 키도 발급 이력에 남는다. 워크스페이스 관리자는 발급 이력 전체를 본다 |
| 결과 | [MCP 설계 — 접근 기록](06-mcp.md#mc-access-log) · [FR-MCP-001](../requirements/04-mcp.md#fr-mcp-001) · [FR-MCP-006](../requirements/04-mcp.md#fr-mcp-006) · [FR-MCP-010](../requirements/04-mcp.md#fr-mcp-010). moai-wiki 세션에 같은 결정을 알렸다 |

<a id="adr-023"></a>
## ADR-023 시스템 관리자는 시스템만 관리한다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22) — 사용자: "moai-works 에도 시스템 어드민 계정도 있어야 해" · "시스템 어드민 계정은 워크스페이스 생성할 수 없어" · "시스템 어드민은 시스템만 관리할 수 있어야 해서 그 영역도 구분해야 해" · "팀 워크스페이스는 시스템 어드민이 사용 못 하게 막을 수도 있어" · "다만 삭제는 사용 중지 후에만 가능해" |
| 결정 | 시스템 관리자(렐름 역할 `system-admin`) 계정에는 개인 워크스페이스가 생기지 않고, 팀 워크스페이스를 만들 수 없으며(허용 수를 받아도), 가입 신청 · 초대 수락도 할 수 없다(403 `SYSTEM_ADMIN_NOT_ALLOWED`). 로그인하면 시스템 관리 화면으로 가고 워크스페이스 메뉴가 없다. 시스템 관리자는 팀 워크스페이스를 사용 중지 · 다시 사용하게 할 수 있고, 워크스페이스 삭제는 사용 중지한 워크스페이스에만 한다. 처음 시스템 관리자 계정은 렐름 설치 스크립트가 만든다(`sysadmin`) |
| 결과 | 2026-11-22 코드: 접근 판정(`AccessInterceptor` — `@UserApi` 기본 막기 · 워크스페이스 404) · 로그인 · 팀 만들기 · 가입 신청 · 초대 수락 · 화면 첫 경로. 사용 중지 · 삭제는 [FR-WSP-019](../requirements/01-workspace.md#fr-wsp-019) · [FR-WSP-020](../requirements/01-workspace.md#fr-wsp-020) 할 일(2026-11-23 만듦 — 팀 워크스페이스만, 멤버 REST 403 `WORKSPACE_SUSPENDED` · MCP 숨김, 지우기는 사용 중지한 뒤에만 — [워크스페이스 설계 §9.1](03-workspace-identity.md#ws-suspend)). moai-wiki 세션에 같은 결정을 알렸다(moai-wiki 는 시스템 관리자에게 이미 개인 워크스페이스가 만들어져 있어 정리가 필요하다) |

<a id="adr-024"></a>
## ADR-024 MCP 키는 사용자 계정의 권한 안에서만 일한다 — 서비스 키 · 서비스 읽기 방식을 없앤다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22) — 사용자: "MCP 키는 당연히 사용자 계정하고 연결되고" · "MCP 키는 사용자 계정과 연결되어 있으며 사용자 권한 범위만 접근 가능해야 한다". **일부 대체 (2026-11-23) → [ADR-029](#adr-029)**: 키는 워크스페이스에 묶이지 않는다(주인이 멤버이고 MCP 권한이 있는 워크스페이스 모두), 떠나도 만료시키지 않는다, 관리자는 남의 키를 만료시키지 않는다. 아래 글은 그대로 남긴다 |
| 맥락 | moai-wiki 에 맞춘 설계에는 MCP 키가 두 종류였다 — 키 주인으로 일하는 개인 키(`PERSONAL`)와, 워크스페이스 명의로 사람 권한과 상관없이 엔드포인트 범위를 쓰는 서비스 키(`SERVICE`). 서비스 키 때문에 엔드포인트에 읽기 방식(`USER` · `SERVICE`)과 `MCP_PERSON_REQUIRED` 를 두고, `SERVICE` 방식에서는 지정 멤버 프로젝트를 막고, 쓰기 주체 `SERVICE` · 비어 있는 만든 사람 열 · 서비스 키의 관리자 필수 규칙 · 발급 확인 화면이 따라왔다. 키 하나가 그 키를 가진 사람의 권한을 넘을 수 있었다 |
| 결정 | **모든 MCP 키는 사용자 계정 하나(주인 = 발급한 사람)에 묶이고, 그 계정이 접근할 수 있는 범위 안에서만 일한다.** 키 범위 = 주인의 권한 ∩ 엔드포인트 범위(대상 프로젝트 · 켠 도구 · 종류)이고, 호출마다 다시 판정한다(바뀌지 않은 규칙). 키 종류 구별(`PERSONAL` · `SERVICE`)을 없애 한 종류(사용자 키)만 두고, 엔드포인트의 읽기 방식도 없앤다. 워크스페이스 이름으로 일하거나 사람 권한을 넘는 키는 없다. MCP 로 한 쓰기는 늘 사람이 한 것이다 — 이력 · 감사 `actor_type = USER`(키 주인), 경로 `MCP`, 엔드포인트 id · 키 id. 자동화(CI · 보고)도 그 일을 맡은 사람의 키로 한다. 권한 코드 `mcp.key.issue.service` 는 쓰지 않는다 — 25개 표 · 지금 카탈로그에는 남기고, MCP 단계에서 moai-wiki 와 함께 카탈로그에서 뺀다. `mcp.key.issue.personal` 은 "자기 MCP 키 발급"으로 남는다 |
| 바뀌지 않는 것 | 키는 지우지 않고 만료시킨다(`POST …/mcp-keys/{id}/expire`, 만료시킨 사람 · 이유 — [ADR-022](#adr-022)). 원문은 `mai-wks-` + 43자. 주인이 정지되거나 워크스페이스를 떠나면 키를 바로 쓸 수 없고 만료된다(`MEMBER_LEFT`)(→ 2026-11-23 [ADR-029](#adr-029): 떠난 워크스페이스만 키에게 보이지 않고 키는 만료되지 않는다). 워크스페이스 관리자(`mcp.key.manage`)는 발급 이력 전체를 보고 어떤 키든 만료시킨다(→ ADR-029: 멤버들의 키를 보기만 하고, 막을 때는 역할에서 MCP 권한을 뺀다). `audit.read` 로 읽기까지의 모든 접근 기록을 본다. web-backend 가 중계하고 api 도 직접 서비스한다([ADR-021](#adr-021)). 시스템 관리자 계정은 키를 받을 수 없다([ADR-023](#adr-023)) |
| 결과 | [FR-MCP-001](../requirements/04-mcp.md#fr-mcp-001) · [FR-MCP-002](../requirements/04-mcp.md#fr-mcp-002) · [FR-MCP-003](../requirements/04-mcp.md#fr-mcp-003) · [FR-MCP-005](../requirements/04-mcp.md#fr-mcp-005) · [FR-ISS-006](../requirements/03-issue.md#fr-iss-006) · [FR-ISS-010](../requirements/03-issue.md#fr-iss-010) · [MCP 설계 §3 키](06-mcp.md#mc-keys) · [§7 판정](06-mcp.md#mc-authz) · [§7.1 서비스 키 없음](06-mcp.md#mc-reader-mode) · [데이터 모델 §6](02-data-model.md#dm-mcp) · [워크스페이스 설계 §11](03-workspace-identity.md#ws-mcp). 4단계 마이그레이션은 `mcp_api_key.key_type` 을 없애고 `owner_user_id` 를 필수로 하며, `issue.created_by` · `issue_link.created_by` 는 NOT NULL 그대로 둔다. 보안 결정이므로 moai-wiki 세션에 결정 원문과 적용 방법을 알린다 |

## ADR-027 MCP 일감 CRUD · 첨부 티켓 · 첨부 저장소 구조

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-22) — 사용자: "MCP 가장 먼저 필요한 건 자기가 볼 수 있는 프로젝트 목록, 아이템 검색, 아이템 관련 CRUD 등등" · "덧글, 첨부파일 포함" · "첨부파일은 REST API 로 구현해야 하지? MCP 로는 안 될 거야? 그래서 아마 임시 티켓을 받아 쓰고 쓰면 바로 익스파이어 되는 티켓 시스템" · "파일 저장소 구조 잘 설계 … 너무 한곳에 다 모아 두면 문제" |

| 결정 | MCP 도구로 일감 CRUD · 댓글 · 작업 시간 · 연결 · 첨부를 연다. 지우기는 `issue.delete` 권한 + 이유 필수 · 지움 표시만 · 감사에 경로와 이유. 첨부 파일은 MCP 에 싣지 않고 MCP 가 준 일회용 티켓(10분 · 한 번 · SHA-256 · 키 주인 · 일감 · 크기에 묶음, 쓸 때 다시 판정)으로 web-backend `/mcp/files/*` 에 REST 로 보낸다. 첨부 객체 이름은 `ws/<워크스페이스>/p/<프로젝트>/<연>/<월>/<첨부 id>`, 원래 이름은 DB 에만 |
| 바뀌지 않는 것 | 판정은 api 한 곳, 도구는 REST 와 같은 서비스 · 같은 권한 코드, 한 사람 = 키 주인 |

<a id="adr-029"></a>
## ADR-029 MCP 키는 사용자의 것이다 — 워크스페이스에 묶지 않는다

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-23) — 사용자: "워크스페이스별로 mcp 엔드포인트 만드는 건 안 되지. 사용자가 접근 가능한 곳이면 다 되는 거지" · "키는 워크스페이스별로 받는 게 아니라 사용자 기준으로 받는 거야" · "키는 로그인한 사용자 기준으로 받는 것이고 그 사용자가 소속된 워크스페이스, 소속된 프로젝트는 모두 접근 가능하고 권한에 따라 하는 거야". moai-works 일감 #5 |
| 맥락 | 키는 워크스페이스 하나에 묶여 있었다(V5 `mcp_api_key.workspace_id`). 여러 워크스페이스에서 일하는 사람은 워크스페이스마다 키를 받고 MCP 서버를 따로 등록해야 했고, 계획([ADR-008](#adr-008))은 워크스페이스마다 엔드포인트를 더 두는 쪽이었다. 관리자가 남의 키를 만료시키면 그 키가 닿는 곳이 그 워크스페이스 하나뿐이라 문제가 없었지만, 키가 사용자의 것이 되면 한 워크스페이스 관리자가 그 사람의 다른 워크스페이스 일까지 끊게 된다 |
| 결정 | **키 하나 = 주인 계정 하나.** V13 이 `mcp_api_key.workspace_id`(와 그 인덱스)를 지우고 보호 함수를 그 열 없이 다시 만든다(V11 이 `endpoint` 를 지운 방식). 지금 키는 그대로 쓴다. **키로 쓸 수 있는 워크스페이스** = 활성 워크스페이스 ∧ 주인이 활성 멤버 ∧ 주인의 지금 역할에 `mcp.key.issue.personal`(화면 이름 "MCP 키로 이 워크스페이스에서 일하기" — 코드 이름은 그대로). 그 밖의 워크스페이스는 키에게 보이지 않는다 — 워크스페이스 관리자는 역할에서 이 권한을 빼서 Agent 를 막는다. 입구는 그대로 `/mcp/issue` · `/mcp/project` 이고 워크스페이스별 엔드포인트는 만들지 않는다(키를 프로젝트 목록 · 읽기 전용으로 좁히는 것도 하지 않는다). **워크스페이스는 호출마다 정한다**(`McpScope` 한 곳): 프로젝트를 받는 모든 도구에 선택 인자 `workspace`(주소). 주면 쓸 수 있는 곳이어야 하고 아니면 404 `WORKSPACE_NOT_FOUND`(없음 · 비멤버 · 권한 없음을 구별하지 않는다). 비우면 쓸 수 있는 모든 워크스페이스에서 그 프로젝트 key(읽을 수 있는 것)를 찾아 하나면 그것, 없으면 `PROJECT_NOT_FOUND`, 여럿이면 400 `PROJECT_AMBIGUOUS`(문구에 워크스페이스 주소들). 새 도구 `list_workspaces`(두 입구 모두), `list_projects` 는 모든 쓸 수 있는 워크스페이스에 걸치고 줄마다 `workspace {slug, name}`. **발급은 개인 설정 › 내 MCP 키**(`POST /v1/me/mcp-keys`, `@UserApi`) — 워크스페이스를 고르지 않는다. 시스템 관리자 계정은 403, `mcp.key.issue.personal` 이 있는 워크스페이스가 하나도 없으면 403 `MCP_KEY_ISSUE_NOT_ALLOWED`. **만료시키기는 주인만**(`POST /v1/me/mcp-keys/{id}/expire`, 남의 키 404). 워크스페이스 관리자(`mcp.key.manage`)는 그 워크스페이스 멤버들의 키를 보기만 한다(`GET /v1/workspaces/{ws}/mcp-keys`). 키 발급 · 만료시키기 감사는 사용자 단위(`audit_log.workspace_id` 없음) |
| 브리프 밖에서 정한 것 | (a) 프로젝트 없이 워크스페이스에서 하는 일(워크스페이스 기본 템플릿 — `project` 를 비운 `list_issue_templates` · `set_issue_template` · `reset_issue_template`)은 `workspace` 를 비우면 쓸 수 있는 곳이 하나일 때만 그곳, 여럿이면 새 코드 400 `WORKSPACE_REQUIRED`(문구에 주소들). `PROJECT_AMBIGUOUS` 도 400. (b) `list_workspaces` 는 주소 · 이름 · 종류(`PERSONAL` · `TEAM`) · 역할 이름 목록(`roles`)을 준다. (c) `list_projects` 의 예전 맨 위 `workspace` 는 없앴다(줄마다 붙는다). (d) 워크스페이스를 떠나거나 내보내져도 키를 만료시키지 않는다 — 그 워크스페이스만 다음 호출부터 보이지 않는다(`MEMBER_LEFT` 는 옛 기록에만). (e) 관리 화면에서 발급한 IP · 프로그램은 주인에게만 보인다(사용자 단위 정보). (f) 첨부 티켓은 도구가 정한 프로젝트의 워크스페이스에 묶이고, 쓸 때 그 워크스페이스를 아직 키로 쓸 수 있어야 한다(아니면 404 `WORKSPACE_NOT_FOUND`). `MCP_WORKSPACE_INACTIVE` 는 없앴다 — 키 검사에서 보는 것은 주인 계정뿐이다(`MCP_PRINCIPAL_INACTIVE`). (g) 옛 `POST /v1/workspaces/{ws}/mcp-keys` · `…/{id}/expire` 는 돌려보내지 않고 없앴다(부르는 곳이 화면뿐이었다). 워크스페이스 키 목록은 `mcp.key.manage` 가 있어야 한다(예전에는 `workspace.read` 로 내 키를 줬다). (h) 사용자 단위 키 감사는 워크스페이스 감사 화면에 나오지 않는다 — 관리 화면의 "MCP 키 감사 기록" 단추를 없애고, 키마다 있던 감사 링크는 그 사람의 이 워크스페이스 감사 기록으로 바꿨다. 주인은 내 MCP 키(만료된 것까지)에서 자기 키 이력을 본다. (i) 알림 `mcp_key.expired`(남이 내 키를 만료시킴)는 더 생기지 않는다 — 옛 알림 · 설정 표시용으로 종류는 남긴다. `mcp_key.expiring` 은 워크스페이스 없는 알림이다 |
| 바뀌지 않는 것 | 판정은 api 한 곳, 도구는 REST 와 같은 서비스 · 같은 권한 코드, 모델이 넘긴 워크스페이스 · 프로젝트도 키 주인의 지금 권한으로 다시 판정한다. 한 사람 = 키 주인. 키는 지우지 않고 만료시킨다(원문은 한 번만, SHA-256 만 저장). 요청마다 캐시 없이 검사하고, 멤버십을 빼거나 역할을 바꾸면 다음 호출부터 반영된다. MCP 로 워크스페이스 안에서 한 일은 그 워크스페이스의 감사 · 이력에 경로 `MCP` 로 남는다. 시스템 관리자 계정은 키를 받을 수 없다([ADR-023](#adr-023)). web-backend 중계([ADR-021](#adr-021)) |
| 결과 | [ADR-024](#adr-024)의 "키 하나 = 워크스페이스 하나"와 [ADR-008](#adr-008)의 워크스페이스 엔드포인트 계획을 대체한다. <a id="adr-030"></a>
## ADR-030 일감은 워크스페이스 아래에 있다 — 번호는 워크스페이스에서 하나, 프로젝트는 속성

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-11-24) — 사용자: "그리고 중요한 실수가 있었어 이슈 넘버가 프로젝트 별로 하는데 아니야 워크스페이스 별로 해야해" · "워크스페이스 단위로 유니크한 번호여야해" · "그렇다는건 이슈는 프로젝트 단위에 포함이 되지만 기본적으로 워크스페이스 아래 있는것이고 이슈는 프로젝트는 속성처럼 가지고 있어야해" · "전체 워크스페이스에서 이슈를 검색할 수도 있어야해" · "레드마인을 생각하면 돼". 옛 번호를 다시 매기는 방법은 프로젝트 소유자가 정했다. moai-works 일감 #29. [ADR-019](#adr-019)를 대체한다 |
| 맥락 | [ADR-019](#adr-019)로 번호를 프로젝트 안 순번으로 했다. 한 워크스페이스에 `#12` 가 프로젝트마다 하나씩 있어 글 속 `#12` · MCP 호출 · 대화에서 어느 일감인지 늘 프로젝트를 함께 말해야 했고, 일감을 다른 프로젝트로 옮길 수도 없었다. Redmine 은 한 벌(인스턴스) 안에서 번호가 하나이고(`/issues/:id`), 프로젝트는 일감의 Project 칸이다 |
| 결정 | **Redmine 모델 — 워크스페이스 = Redmine 한 벌.** (1) **소속**: 일감은 워크스페이스에 속한다(`issue.workspace_id`, 프로젝트와 같은 워크스페이스여야 한다 — 복합 FK). 일감마다 프로젝트가 꼭 하나 있지만(`project_id` NOT NULL) 프로젝트는 일감의 속성이라 바꿀 수 있다(옮기기). (2) **권한 경계는 그대로 그 일감의 지금 프로젝트**다 — 독자가 아니면 404, 독자인데 권한이 없으면 403([ADR-005](#adr-005)). (3) **번호**: 워크스페이스 안에서 하나이고 다시 쓰지 않는다(지운 일감도 번호를 가진다). 만들 때 워크스페이스 행의 순번을 잠가 올리고(`UPDATE workspace SET issue_seq = issue_seq + 1 … RETURNING`), DB 가 `UNIQUE (workspace_id, number)` 로 막는다. `project.issue_seq` 는 지웠다. (4) **정식 주소**: 화면 `/w/:slug/issues/:number`, REST `/v1/workspaces/{ws}/issues/{number}`(새 접근 어노테이션 `@IssueApi` — 그 일감의 지금 프로젝트로 `@ProjectApi` 와 같은 판정). 옛 `/w/:slug/projects/:key/issues/:number`(· `/edit` · `/history` · 주소 값)는 번호 바꾼 기록으로 지금 번호를 찾아 돌린다. 프로젝트의 일감 목록 · 새 일감은 프로젝트 주소 그대로다. (5) **워크스페이스 일감 목록 · 찾기**(Redmine `/issues`): 사이드바 "일감" — 읽을 수 있는 프로젝트(열려 있고 issue.read) 모두의 합. 읽을 수 없는 프로젝트의 일감은 목록에도 전체 수에도 들어가지 않는다. 프로젝트 칸 · 프로젝트 거르기(여럿)와 프로젝트 목록의 거르기 전부, 찾기는 제목 · 설명 · `#번호`. (6) **옮기기**: 고치기의 `project` — 이 프로젝트의 issue.edit + 옮길 프로젝트의 issue.create(Redmine 의 옮기기와 같다). 하위 줄기를 통째로 함께 옮기고(상위 · 하위는 같은 프로젝트), 상위가 남으면 상위 연결을 끊는다. 유형은 옮길 곳에서 쓸 수 있어야 하고, 관리자 · 담당자는 옮길 곳의 독자여야 한다. 모듈은 같은 key 가 옮길 곳에 쓰는 모듈로 있으면 잇고 없으면 뺀다. 첨부 · 댓글 · 작업 시간 · 연결 · 이력은 일감을 따라간다. 이력 한 줄(field `project`) · 새 판(판에 프로젝트) · 감사 `issue.move` · 알림. (7) **연결**은 같은 워크스페이스의 다른 프로젝트 일감과도 된다 — 읽을 수 없는 쪽은 목록 · 보기에서 아예 빠진다(없는 것과 같다). (8) **글 속 `#123`** 은 그 워크스페이스의 123번 — 프로젝트가 달라도 정식 주소로 간다(읽을 수 없으면 보통의 "찾을 수 없음") |
| 옛 데이터 (V23) | 프로젝트 소유자가 정한 것: 워크스페이스마다 만든 때(같으면 옛 번호) 순서로 1 부터 다시 매긴다 — 처음부터 워크스페이스 번호였던 것처럼. 같은 일감을 가리키던 번호(판의 상위 번호 · 첨부 티켓 · MCP 접근 기록 · 이력 줄의 상위 · 연결 번호 · 알림의 번호)를 새 번호로 바꾸고, 감사 글은 쓴 그대로 둔다. 지금 설명 · 댓글의 `#n` 은 그 글이 달린 일감의 프로젝트 번호로 읽어 바꾼다(화면 ISSUE_REF 와 같은 규칙, 코드 · 링크 · 주소는 그대로). 옛 판 · 옛 댓글 글은 역사라 그대로. row_version · 고친 때는 올리지 않고 알림도 보내지 않는다. 옛 → 새는 `issue_number_change`, 바꾸기 전 글은 `issue_number_text_change` 에 남기고, 바뀐 일감마다 시스템 이력 한 줄(경로 `SYSTEM`, "번호가 바뀌었습니다")을 남긴다. 한 마이그레이션(한 트랜잭션)이고 돌 때의 데이터로 계산한다 |
| 브리프 밖에서 정한 것 | (a) MCP 에서 `project` · `workspace` 를 모두 비우면 키로 쓸 수 있는 워크스페이스 가운데 **그 번호를 준 적이 있는 곳**(지운 · 읽을 수 없는 일감 포함)을 찾는다 — 하나면 그곳, 여럿이면 400 `ISSUE_AMBIGUOUS`. 엉뚱한 워크스페이스의 같은 번호를 고르지 않게 하려는 것이다. (b) 준 `project` 와 일감의 프로젝트가 다르면 400 `ISSUE_PROJECT_MISMATCH` — 읽을 수 있는 일감일 때만이라 지금 프로젝트를 알린다. 읽을 수 없으면 `ISSUE_NOT_FOUND`. (c) 옮기기는 MCP `update_issue` 의 새 인자 `moveToProject`(`project` 는 일감을 가리키는 데 쓰므로 겹치지 않게). (d) 유형은 아직 워크스페이스 공통이라 "옮길 곳에서 쓸 수 있는 유형" = 쓰는 유형(active). 옛 유형(요구사항 · 작업)은 같은 요청에서 유형을 바꿔야 옮겨진다 — 하위 일감은 먼저 고친다. (e) 워크스페이스 목록에는 보관한 프로젝트를 넣지 않는다(프로젝트 목록과 같다). (f) 다른 프로젝트 일감과 이은 알림에는 상대 제목을 싣지 않는다(번호만). (g) 첨부의 저장소 객체 이름(`ws/…/p/<올릴 때의 프로젝트>/…`)은 옮겨도 그대로다 — 받기는 첨부 id · 일감으로 찾는다. 첨부 행의 `project_id` 만 따라간다(보호 트리거가 그 일감의 지금 프로젝트로만 허용). (h) 번호 다시 매기기의 바꾸기 전 글을 따로 남긴다(`issue_number_text_change`). (i) 작업 시간은 일감을 따라가므로 옮긴 일감의 옛 작업 시간도 공수 집계에서 새 프로젝트로 센다(Redmine 과 같다) |
| 바뀌지 않는 것 | 판정은 api 한 곳(화면 · BFF 는 판정하지 않는다), 권한 코드 · 역할, 프로젝트 목록 · 새 일감은 프로젝트 주소, MCP 도구는 REST 와 같은 서비스 · 같은 판정, `create_issue` 는 `project` 필수 |
| 결과 | 번호만으로 일감을 가리킨다(화면 · REST · MCP · 글). 워크스페이스 번호는 순번이라 번호 사이의 빈 곳으로 다른 프로젝트에 일감이 있다는 것은 알 수 있다(내용 · 프로젝트는 알 수 없다 — Redmine 과 같다). [ADR-002](#adr-002) 나중 후보의 "다른 프로젝트와의 연결 일감"을 했다.
