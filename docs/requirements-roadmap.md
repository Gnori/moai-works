# MOAI Works — 요구사항 마스터 플랜 (WBS)

> 작성 2026-06-03. **spec 작성 전 "플랜"** — 무엇을, 어떤 단위로, 어떤 순서로 명세화할지.
> 전체 기능은 [architecture.md](./architecture.md), 본 문서는 **요구사항 구조·순서**.

이 제품은 **멀티테넌트 SaaS + AI 업무 플랫폼**이라 범위가 매우 크다. 한 번에 큰 spec
("P0") 으로 가면 실패하므로, **작고 독립 출하 가능한 단위**로 잘게 나눈다.

---

## 1. 요구사항 계층 (4단계)

| 레벨 | 산출물 | 규모 | 예 |
|------|--------|------|-----|
| **L0 제품 마스터** | 본 문서 + 제품 비전 | — | MOAI Works 전체 |
| **L1 도메인 마스터** | 도메인별 마스터 spec (범위·에픽·의존성·인수기준 요약) | complex | "AI 메신저 마스터", "온보딩 마스터" |
| **L2 에픽** | 도메인 내 큰 묶음 (마스터 안의 절) | (마스터에 포함) | "메신저-실시간 전송", "온보딩-역할별 코스" |
| **L3 스토리 spec** | **실제 `/dev req` 단위** — 독립 구현·테스트·출하 | simple/standard | "채널 생성 API", "읽음 확인", "온보딩 체크리스트 CRUD" |

**원칙**
- `/dev req` 로 만드는 건 **L3(스토리)** — 대부분 **standard(~150줄)**, 작은 건 simple.
- 복잡한 도메인은 **먼저 L1 마스터**로 범위를 잡고 → L3 로 쪼갠다. (온보딩·메신저·지식·결재 등)
- **SaaS 토대가 모든 것의 선행조건** — 테넌트/인증/RBAC 없이 어떤 업무 모듈도 못 만든다.
- 각 L3 는 **수직 슬라이스**(API+최소 UI+테스트) 지향 — "출하 가능한 얇은 기능".

## 2. 도메인별 WBS (L1 → 에픽)

복잡도: 🔴 매우 복잡(엔터프라이즈 프로세스) · 🟡 보통 · 🟢 비교적 단순

| # | 도메인 (L1 마스터) | 복잡도 | 주요 에픽 (L2) | 예상 L3 spec 수 |
|---|-------------------|:---:|----------------|:---:|
| F0 | **SaaS 토대** | 🔴 | 테넌시 격리 · 테넌트 부트스트랩 · 인증/SSO · RBAC · 구독/Billing · quota · 감사로그 | ~10 |
| F1 | **조직/사용자** | 🟡 | 조직도(부서·직급·발령) · 사용자 CRUD · 권한 그룹 · 디렉터리 연동 | ~6 |
| F2 | **게시판** | 🟢 | 게시판 종류 · 글/댓글 · 첨부 · 권한·공지 | ~4 |
| F3 | **알림** | 🟡 | 알림 채널(웹/모바일/메일) · 구독·설정 · 실시간 푸시 | ~4 |
| F4 | **파일드라이브** | 🟡 | 저장(오브젝트) · 폴더·공간(부서/프로젝트/개인) · 권한 · 버전 · 검색 · **OOXML 파싱(Apache POI)→미리보기/OCR/지식화** | ~7 |
| F5 | **AI 메신저** | 🔴 | 채널 모델 · 실시간 전송(WS) · 멘션/답글/이모지 · 읽음 · 파일·공동검토 · 검색 + **AI: 요약·할일추출·Agent호출** | ~12 |
| F6 | **Mail-box** | 🟡 | 메일 연동(IMAP/Graph) · 조회 · 분류 · **AI: 요약·초안** | ~5 |
| F7 | **지식관리(RAG/Wiki)** | 🔴 | 인덱싱·임베딩 · 지능형 RAG · 출처기반 답변 · LLM Wiki · 권한 범위(전사/부서/개인) · 최신성 판별 | ~9 |
| F8 | **AI 문서작성** | 🔴 | **OnlyOffice 편집기**(OOXML 고충실 열기/편집/협업) · 템플릿 엔진 · 보고서/제안서/회의록/결재초안 · 지식기반 작성 · AI 생성(Document Builder/삽입) · Office·PDF 내보내기 | ~9 |
| F9 | **AI 온보딩** | 🔴 | (아래 §4 심층 분해) | ~10 |
| F10 | **전자결재** | 🔴 | **양식 엔진**(동적 폼) · 결재선(직렬/병렬/합의/전결/대결/위임) · 상신·승인·반려·회수·후결 · 문서함/원본보존 · 모바일 결재 · HR/회계 연동 | ~10 |
| F11 | **업무관리(Task)** | 🟡 | 업무/프로젝트 · 담당·기한 · 보드/간트 · 메신저 할일 연계 | ~6 |
| F12 | **인사·근태** | 🔴 | 근태(출퇴근·연차·휴가) · 인사정보 · 결재 연동 · 규정 엔진 | ~8 |
| F13 | **AI Agent 플랫폼** | 🔴 | Main/Sub 오케스트레이션 · 도메인 Agent · Tool 레지스트리 · 컨텍스트/권한 전파 · 관측성 | ~10 |
| F14 | **예약·자동화** | 🟡 | 스케줄러 · 조건 트리거 · 채널/메일 요약 잡 · 액션아이템 잡 | ~6 |
| F15 | **외부 연계** | 🔴 | 커넥터 프레임워크 · ERP/인사/회계 · MCP · 레거시 어댑터 | ~8 |
| H | **Home 대시보드** | 🟡 | 위젯(일정·알림·문서·미처리) · AI 업무 브리핑 | ~4 |

> 합계 대략 **130~140 L3 spec** 규모. (그래서 "세분화"가 필수.)

> **전자결재(F10) 보충** — 기업의 모든 승인 요청이 여기로 흐른다. **양식 + 결재선** 조합:
> 일반 기안서 · **휴가/연차 신청**(→ F12 인사·근태 잔여일 연동) · 지출결의 · 구매요청 ·
> 출장 신청 · 품의서 · 인사 발령 등 — **양식만 다르고 엔진은 공통**. 새 결재 유형 추가 = 양식
> 정의 1건. AI 문서작성(F8)이 결재 초안을 만들고, 승인 결과는 HR/회계/업무로 반영된다.

## 3. 시퀀싱 — Wave (의존성 순서)

```
Wave 0  F0 SaaS 토대        ─ 모든 것의 선행 (테넌시·인증·RBAC·감사)
Wave 1  F1 조직/사용자 · F2 게시판 · F3 알림 · H 대시보드(기본)
            └ 그룹웨어 "골격" 가동 (사람이 들어와 쓰기 시작)
Wave 2  F4 파일드라이브 · F11 업무관리 · F10 전자결재(코어) · F12 인사·근태(코어)
            └ 전통 그룹웨어 업무 성립
Wave 3  F5 AI 메신저(비-AI 부분 먼저) · F6 Mail-box 연동
            └ 협업·데이터 발생원 확보
Wave 4  F13 AI Agent 플랫폼(토대) · F7 지식관리(RAG)
            └ AI 계층 가동 (moai-agent 기반)
Wave 5  F5/F6 의 AI 기능 · F8 문서작성 · F9 온보딩 · F14 자동화
            └ "AI 업무 대행" 본격화
Wave 6  F15 외부연계(ERP·MCP·레거시) · 고도화
```

**규칙**: 각 도메인은 "비-AI 코어 먼저 → AI 기능 나중". AI 기능은 데이터(메시지·문서)와
F13 Agent 토대가 있어야 의미가 있다.

## 4. 예시 — "온보딩"은 단순하지 않다 (🔴 심층 분해)

기업 온보딩은 **콘텐츠·코스·진도·역할·승인·리포팅**이 얽힌 워크플로다. F9 를 L3 로 쪼개면:

| L3 spec | 규모 | 내용 |
|---------|------|------|
| 온보딩 콘텐츠 관리 | standard | 온보딩 항목(문서·영상·링크) CRUD, 버전, 게시 |
| 온보딩 코스/커리큘럼 | standard | 전사/부서/역할별 코스 구성, 항목 순서·필수여부 |
| 대상자 배정 규칙 | standard | 입사/발령 트리거 → 자동 코스 배정(조직·직무 기반) |
| 진도/체크리스트 추적 | standard | 사용자별 진행률, 항목 완료, 기한·리마인드 |
| 확인/승인 흐름 | standard | 멘토·관리자 확인, 서명/완료 승인 |
| 온보딩 리포팅 | standard | 부서·기간별 진행 현황 대시보드 |
| 온보딩 Agent | complex | 신규자 Q&A(지식 기반) · 문서 추천 · 교육이력 조회 · 다음 할일 안내 |
| (연동) 인사·문서·지식 | — | F1/F4/F7 의존 |

→ "온보딩" 하나가 **약 8개 L3 + 다도메인 의존**. 같은 깊이로 메신저·결재·지식·인사도 분해한다.

## 5. 규모·작성 순서 가이드

- **L1 마스터 먼저**: 큰 도메인(🔴)은 `/dev req <domain>-master --scale=complex` 로 범위·에픽·의존·인수기준 확정 → 그다음 L3.
- **L3 는 standard 기본**, 단순 CRUD·설정은 simple.
- **수직 슬라이스 + 테넌트 격리 테스트 필수** (SaaS: 모든 API에 "테넌트 경계" 테스트).
- 한 번에 1 Wave 내 3~5개 spec 정도만 활성화 (`active_development.md` 추적).
